## 1. 목적

R1 제품 기능을 쌓기 전에 브라우저 인증, Theme, Brand, 품질 도구와 동적 UI의
기본 계약을 확정한다. 이 문서는 구현과 검증 상태를 함께 관리하며, 아직 확정되지
않은 항목을 완료된 Foundation으로 표현하지 않는다.

## 3. ADR-001 Browser Session

### Context

기존 프론트엔드는 Access Token을 `localStorage`에 저장하고 모든 API 요청에
`Authorization` Header로 붙였다. XSS가 발생하면 JavaScript가 Token을 직접 읽을
수 있고, Logout과 서버 측 Session 폐기 계약도 없었다. 엔터프라이즈 DWP의 기본
Browser Session으로 사용할 수 없다.

### Decision

브라우저에는 서명된 Access Token을 `HttpOnly` Cookie로만 전달한다. Token의
`jti`를 서버의 `sys_auth_sessions` Registry에 등록하고, 모든 Browser 요청에서
서명·만료와 Session 활성 상태를 함께 검증한다.

- Cookie 기본 이름: `DWP_SESSION`
- `HttpOnly=true`
- Production `Secure=true`, Local Development만 `false`
- `SameSite=Lax`
- `Path=/`
- Cookie Max-Age와 Token 만료를 동일하게 설정
- Token Payload에는 `sub`, `tenant_id`, `roles`, `jti`, 발급·만료 시각 포함
- Logout 시 현재 `jti`를 폐기하고 Cookie를 즉시 만료
- 인증 실패 시 오래되거나 폐기된 Session Cookie도 만료
- Browser JavaScript와 API 응답에는 Access Token을 노출하지 않음

CLI, Service Integration과 향후 Agent Identity는 기존 `Authorization: Bearer`
경로를 사용할 수 있다. Browser Cookie와 Header가 함께 있으면 명시적인 Header를
우선하되, Browser 제품 코드에서는 Header Token을 만들지 않는다. Service Token의
발급자, Audience와 수명주기는 Agent·Service Identity ADR에서 별도로 분리한다.

### Session Registry

`sys_auth_sessions`에는 다음 최소 정보만 저장한다.

- Session ID와 JWT `jti`
- Tenant·User ID
- 만료·폐기 시각
- 발급 IP와 User Agent
- 생성·수정 Audit Column

원문 Token은 저장하지 않는다. 조회는 `jti` Unique Index를 사용한다. 장기적으로
사용자 Session 목록, 전체 기기 Logout, 관리자 강제 폐기와 만료 Session Purge를
추가한다.

### Login Flow

1. 프론트가 CSRF Token을 준비한다.
2. Local Login 또는 OIDC State 검증이 성공한다.
3. 백엔드가 `jti`와 Session Registry Row를 생성하고 서명 Token을 발급한다.
4. 응답은 Token이 없는 Session Metadata와 `Set-Cookie`만 반환한다.
5. 프론트는 `/api/auth/me`, `/api/auth/permissions`로 Session을 확인한다.
6. 새로고침과 새 Tab도 Cookie 기반 Session Check를 거쳐 인증 상태를 복원한다.

### Logout Flow

1. 프론트가 CSRF Header를 포함해 `/api/auth/logout`을 호출한다.
2. 백엔드가 현재 JWT의 `jti`를 폐기한다.
3. 백엔드가 `DWP_SESSION` Cookie를 Max-Age 0으로 만료한다.
4. 프론트가 사용자와 권한 Cache를 제거하고 로그인 화면으로 이동한다.

### Remaining Risk

- R1 외부 Pilot 전 Refresh Rotation, Idle Timeout, 사용자 Session 관리와
  Signing Key Rotation을 추가 검토한다.
- 기본 개발 Key를 Production에서 사용할 수 없도록 Deployment Gate를 둔다.
- Multi-region Registry Cache를 도입하면 폐기 전파 SLO와 Fail-closed 정책을
  별도로 정의한다.

## 4. ADR-002 CSRF와 API Request

Cookie는 Browser가 자동 전송하므로 상태 변경 요청에 CSRF 방어가 필요하다.
Spring Security의 Cookie CSRF Repository를 사용하고 다음 계약을 적용한다.

- `GET /api/auth/csrf`가 Token과 Header 이름을 반환하고 CSRF Cookie를 설정
- 프론트는 Token을 Memory에만 보관
- `POST`, `PUT`, `PATCH`, `DELETE`에 `X-XSRF-TOKEN` Header 전송
- 모든 API 요청은 `credentials: include`
- Login과 Logout도 CSRF 대상
- OIDC Callback은 `state`와 짧은 수명의 서버 저장소로 Login CSRF를 방어
- `GET`은 상태를 변경하지 않는 원칙 유지

CSRF Token은 인증 비밀정보가 아니지만 `localStorage`에 영구 보관하지 않는다.
Production은 Frontend와 Gateway를 Same-site로 배치하는 것을 기본으로 하고,
Cross-origin 배포 시 허용 Origin을 명시적으로 제한한다.

## 5. ADR-003 Theme와 Typography

### Decision

- `DwpThemeProvider`와 `AppearancePolicy`를 외형 정책의 단일 Source로 쓴다.
- 해석 순서는 `제품 기본값 -> Tenant 정책 -> 허용된 사용자 선호 -> OS 설정`이다.
- 사용자 선호는 `dwp.appearance.v1`에 Versioned Data로 저장한다.
- `system`·`light`·`dark`, High Contrast, Density와 Reduced Motion을 사용자에게
  제공하되 Tenant가 허용 범위를 제한할 수 있다.
- Font Family, Brand Accent와 Navigation Pattern은 제거하지 않는다. 제품 또는
  Tenant 관리자가 승인된 값만 선택하고 일반 사용자는 임의로 바꾸지 못한다.
- MUI Theme는 정책의 해석 결과만 받아 생성하며 CSS Variable Prefix는 `dwp`로
  고정한다.
- 초기 HTML과 Runtime은 `data-color-scheme`, `data-contrast`, `data-density`,
  `data-motion` 계약을 공유한다.

Typography는 한국어와 영문의 혼합 사용을 기본으로 한다. Product Font가 확정되기
전까지 다음 System Stack을 사용한다.

```text
"Noto Sans KR", "Apple SD Gothic Neo", "Malgun Gothic",
"Segoe UI", Arial, sans-serif
```

Self-hosted CJK Variable Font의 License, Subset과 성능을 측정한 뒤 첫 Pilot
Brand와 함께 확정한다. 업무 화면 Heading은 Viewport 폭에 따라 과도하게 커지지
않는 고정 Scale을 사용한다.

## 6. ADR-004 Brand 분리

Global Shell에 특정 고객 Logo, `AX Solution서비스`, `Pro`와 같은 Sample Tier를
하드코딩하지 않는다.

- Product 기본명은 `Digital Workplace`, 축약명은 `DWP`
- 기본 Workspace는 인증 Context 또는 Configuration에서 가져옴
- Tenant Logo, 이름과 Accent는 승인된 Brand Token으로만 주입
- Product Status Color와 Tenant Accent를 분리
- 개발 Fixture는 Production Default로 사용하지 않음

최종 Brand Identity가 선정되기 전에는 중립 Surface와 단색 Product Accent를
사용한다. 임시 Gradient Logo를 제품 Brand로 굳히지 않는다.

## 7. ADR-005 품질 도구와 Package Manager

목표 품질 체계는 다음과 같다.

1. Vitest Unit·Component Test
2. Storybook Autodocs, Interaction과 A11y
3. Playwright 핵심 Journey와 `@axe-core/playwright`
4. Playwright Screenshot Baseline
5. Keyboard, Screen Reader, 200% Zoom과 High Contrast 수동 Gate

현재 저장소는 Node 20, Yarn 4.17.1과 `nodeLinker: node-modules`를 사용한다.
Storybook Build, Unit, Lint, Typecheck, Production Build와 E2E를 같은 Lockfile에서
검증한다. App과 Component의 Desktop·Mobile Visual Baseline, Storybook Play와 Axe
자동 검사를 R0 Gate에 포함한다. Keyboard-only, Screen Reader와 200% Zoom은 수동
Gate로 별도 유지한다.

Nx Test Target 안의 `npx` 호출은 Network 탐색과 실행 불확실성을 만들 수 있으므로
Workspace에 설치된 Vitest Binary를 직접 사용한다.

## 8. ADR-006 Enterprise Component

MUI X Community Data Grid `9.11.0`을 MUI Core `7.3.11` 위의 R0 Reference Grid로
검증한다. Community Package는 MIT 범위만 사용하며 Pro·Premium Import와 License
Key 설정은 포함하지 않는다. Date·Time Picker는 R1 Locale·Timezone 요구가 확정된 뒤
별도 Package와 Adapter를 선택한다.

다음 요구가 실제 Pilot에서 확인될 때만 Pro·Premium License를 검토한다.

- 다중 Column Grouping·Aggregation·Pivot
- Excel 수준 Export와 대규모 Server-side Data 기능
- 고급 Tree Data와 Row Reordering
- SLA를 포함한 Vendor Support 필요

License 결정 전 임시 Grid를 자체 구현하지 않는다. Form State와 Schema Validation은
R1 Service Form의 실제 복잡도, Server Error Mapping과 Conditional Field를 기준으로
별도 ADR을 작성한다.

## 9. ADR-007 Home·AI Composition

Home, App과 AI 결과는 승인된 Component Registry와 JSON Schema로만 조합한다.

- Feature가 임의 Widget을 Global Home에 직접 삽입하지 않음
- Entitlement, Privacy Class, Owner와 Availability가 없는 App 등록 금지
- AI가 임의 HTML, Script 또는 JSX를 생성하지 않음
- 구조화된 Form, 승인과 중요 Transaction은 결정적 UI 유지
- 추천 Layout은 사용자가 확인하고 되돌릴 수 있음

상세 Product 계약은 `개인화 홈 및 앱 경험 기획.md`를 따른다.

## 10. ADR-008 외부 Template 제거와 DWP UI Foundation

### Context

초기 외부 Admin UI Template은 React·MUI 기반을 빠르게 구성하는 데 유효했다.
그러나 파생 Theme, Component, Asset과 Demo Information Architecture를 계속
확장하면 DWP가 필요한 Today, Cross-system Work, 구조화된 Agent Action과 고밀도
업무 화면이 제3자 제품 구조와 License 이력에 종속된다.

### Decision

- React, TypeScript, Vite, MUI와 Emotion은 유지한다.
- 다른 Admin Template으로 전면 교체하지 않는다.
- 외부 Template의 Palette, Typography, Shadow, Demo Information Architecture와
  Theme Playground를 DWP 제품 계약으로 사용하지 않는다.
- DTCG 호환 Token, Enterprise Component, DWP Floorplan과 AI 신뢰 Pattern을 DWP가
  직접 소유한다.
- Light·Dark·High Contrast와 Density는 접근성·생산성 기능으로 재정의한다.
- Font, Brand Accent와 Navigation Pattern 기능은 유지한다. 다만 일반 사용자
  설정이 아니라 제품·Tenant 관리 정책으로 운영한다.
- R0.5 Exit Gate 통과 전 R1 제품 기능을 구현하지 않는다.

현재 Source Tree에서는 식별된 파생 Source·Asset·Font·Icon과 Root Tooling을
삭제하거나 독립 구현으로 교체했다. DWP Source는 `UNLICENSED`로 표시하며 외부
Delivery 전 승인된 제품 License, Dependency SBOM과 Attribution을 별도 확정한다.
과거 Git Commit에는 제거 전 이력이 남을 수 있으므로 외부 전달 방식은 새 Clean
Repository 또는 승인된 History 정리 중 하나를 Release Owner가 선택한다.

상세 실행 범위와 Exit Gate는
`DWP UI Foundation 전략.md`를 따른다.
