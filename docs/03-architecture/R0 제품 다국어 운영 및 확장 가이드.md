# R0 제품 다국어 운영 및 확장 가이드

> 상태: Implemented Baseline v1.0
>
> 기준일: 2026-08-10
>
> 적용 저장소: `dwp-frontend`, `dwp-backend`
>
> 연계 문서: `R0 권한·메뉴·다국어 Admin Control Center ADR.md`

## 1. 목적과 완료 범위

DWP의 다국어는 화면마다 조건문으로 한국어·영어를 바꾸는 기능이 아니다. 언어 식별,
사용자 선호, 테넌트 기본값, 제품 번들, 서버 오류, 콘텐츠 Label과 Locale Formatting을
하나의 계약으로 관리한다.

현재 `ko`, `en` 제품 번들에 대해 다음 순서의 제품 표면을 다국어화했다.

1. Common Shell: Header, Navigation, Search, Notification, Account, 상태·오류 화면
2. Authentication: 로그인, SSO, Callback, 인증 상태와 오류
3. Personal Home: App Launchpad, 개인화 편집, 공지, Daily Brief와 Home Widget
4. Work Surface: Work, Ask, Activity, Apps와 AI 신뢰 Pattern
5. Account·Admin: 개인 설정, Session, Branding, Home, 공지, Access, Directory,
   Reference Data, Registry와 Audit

표시 문자열, 접근성 Label, Toast, Dialog와 Empty/Error 상태도 같은 번들 계약을
따른다. 지원 언어 변경은 계정에 저장되며 로그인 전에는 기기 선호로 저장된다.

## 2. Locale 결정 계약

Locale은 BCP 47 표준 Tag를 Canonical Form으로 저장한다. 예시는 `ko`, `en-US`,
`zh-Hant-HK`다. DB 컬럼은 향후 Script·Region Subtag를 수용할 수 있도록 35자를
사용한다.

Runtime 우선순위는 다음과 같다.

```text
Authenticated user preferred_locale
-> Tenant default_locale
-> Product default locale en
-> Translation key
```

- 로그인 전: Local Storage `dwp.locale` -> Browser language -> `en`
- 로그인 후: `/auth/me`의 `preferredLocale`과 `tenantDefaultLocale`로 재조정
- API 요청: 선택한 Canonical Locale을 `Accept-Language`로 전송
- 서버 요청: 가장 우선순위가 높은 유효 BCP 47 Language Range를 보존
- 제품 미지원 Region Tag: 같은 Base Language를 우선 사용하고 없으면 `en`
- Locale과 Timezone은 별도 선호다. 언어를 바꿔도 업무 시각의 Timezone은 바꾸지 않는다.

## 3. Source of Truth

| 데이터 종류                 | 원본                                      | 이유                                                      |
| --------------------------- | ----------------------------------------- | --------------------------------------------------------- |
| 제품 UI 문구                | Versioned Source Bundle                   | 배포·Rollback·정적 분석과 번역 Coverage를 함께 보장       |
| 공통 API 오류               | Stable Error Code + Server Message Bundle | Client가 문구가 아닌 Code로 분기하고 Locale별 메시지 제공 |
| Tenant 메뉴명·서비스명·공지 | DB의 BCP 47별 콘텐츠                      | 고객별 용어와 운영 콘텐츠를 배포 없이 관리                |
| 기준정보 Label              | Reference Item Locale Label               | Stable Code와 표시 Label을 분리                           |
| 사용자 언어                 | Auth `preferred_locale`                   | 기기 간 일관성과 Account Self-service 제공                |
| Tenant 기본 언어            | Tenant `default_locale`                   | 신규 사용자와 미설정 사용자의 기본값                      |

제품 문구 전체를 DB에 저장하지 않는다. `adm_message_overrides`는 승인된 Tenant 콘텐츠
Namespace를 위한 기반이며, 제품 System 문구를 임의로 덮는 범용 편집기로 사용하지
않는다. Runtime Override 관리 화면은 Draft·승인·배포·Rollback·감사가 완성된 뒤에만
활성화한다.

## 4. Frontend 구현 규칙

### 4.1 Namespace

| Namespace | 소유 표면                                                     |
| --------- | ------------------------------------------------------------- |
| `common`  | 공통 명령, 상태, 단위, 오류와 언어 선택                       |
| `shell`   | Brand, Header, Navigation, Search, Notification과 Status Page |
| `auth`    | 로그인, SSO와 Callback                                        |
| `home`    | Personal Home, App Launchpad, Widget와 공지                   |
| `work`    | Work, Ask, Activity, Apps와 AI Pattern                        |
| `account` | Profile, Appearance, Language와 Session                       |
| `admin`   | Tenant Admin Control Center 전체                              |

- Feature는 자신이 소유한 Namespace를 사용하고 공통 명령만 `common`을 참조한다.
- Key는 문장 자체가 아니라 의미와 소유 위치로 명명한다.
- `defaultValue`는 Reference Data의 제품 기본 언어 안전망에만 사용한다.
- 화면에서 문장을 조립하지 않고 Interpolation과 i18next Plural Rule을 사용한다.
- `aria-label`, Tooltip, Placeholder, Toast와 Dialog 문구도 반드시 번역 Key를 사용한다.

### 4.2 날짜·숫자·목록

`@dwp-frontend/shared-i18n`의 `formatDate`, `formatNumber`, `formatRelativeTime`,
`formatList`를 사용한다. Feature에서 `new Intl.*`를 직접 만들거나 `월`, `개`, `분`을
문자열로 붙이지 않는다. 통화, Timezone과 Calendar 요구는 Formatter Option으로
명시한다.

### 4.3 언어 변경

로그인 `LanguageMenu`와 Account Language 설정은 같은 `usePreferredLanguage` 계약을
사용한다. 로그인 사용자는 서버 저장이 성공한 뒤 UI Locale을 바꾸며, 비로그인 사용자는
로컬 선호를 사용한다. 일반 사용자에게 지원되지 않는 Locale을 입력받지 않는다.

## 5. Backend 구현 규칙

- API 응답의 식별자는 Locale과 무관한 Stable Code여야 한다.
- Client는 번역된 `message` 문자열을 조건 분기에 사용하지 않는다.
- 공통 오류는 `error.<error-code>` Message Bundle에서 해석한다.
- 내부 Exception, Parser 상세와 Secret은 사용자 메시지로 반환하지 않는다.
- `Accept-Language`가 없거나 잘못되면 제품 기본 언어 `en`을 사용한다.
- 업무 콘텐츠 API는 요청 Locale을 받되, 명시값이 없으면 Request Locale을 사용한다.
- Tenant 콘텐츠 조회도 User -> Tenant -> Product 순서로 Fallback한다.
- Validation 메시지는 표준 Message Key를 사용하고 Field별 민감값을 포함하지 않는다.

## 6. 새 언어 추가 절차

새 제품 언어는 다음 Gate를 모두 통과한 경우에만 지원 상태로 전환한다.

1. Product Owner가 Target Locale, 법적 문구, 번역 Owner와 지원 수준을 승인한다.
2. `productLocales`에 Canonical BCP 47 Code, Native Name과 English Name을 등록한다.
3. `libs/shared-i18n/src/locales/<locale>/` 아래 7개 Namespace를 모두 추가한다.
4. Backend 공통 오류 Message Bundle을 같은 Locale로 추가한다.
5. Tenant 기본 Locale, Reference Label과 운영 콘텐츠의 Fallback 데이터를 준비한다.
6. 번역 Key·Interpolation·Plural·날짜·숫자 자동 검사를 통과한다.
7. 320·390·1280·1440 Viewport에서 긴 문자열, 줄바꿈, 잘림과 Overlay를 검증한다.
8. Keyboard, Screen Reader, 200% Zoom, Light·Dark·High Contrast를 검증한다.
9. Native Reviewer가 용어집, 존칭, 법적 문구와 오류 행동을 승인한다.
10. RTL 언어는 `document.dir`, Icon 방향, Navigation과 Data Grid를 별도 승인한다.

Locale 폴더와 `productLocales` 레지스트리가 다르거나 Namespace·Key·Interpolation이
어긋나면 `yarn i18n:check`가 실패한다.

## 7. 검증 명령과 Release Gate

```bash
# dwp-frontend
corepack yarn i18n:check
corepack yarn test
corepack yarn typecheck
corepack yarn build

# dwp-backend
./gradlew :dwp-core:test :dwp-auth-server:compileJava :dwp-platform-server:compileJava
```

자동 Gate는 다음을 확인한다.

- 제품 Locale Registry와 Locale Directory 일치
- 모든 Locale의 Namespace·Key·Interpolation Placeholder 동등성
- 제품 Source의 직접 JSX 문구, 표시 속성, Feedback 문구와 직접 `Intl` 생성 금지
- BCP 47 Canonicalization과 User·Tenant Fallback
- Backend 언어 해석과 공통 Error Code 번들 Coverage

자동 검사는 번역 품질과 Layout 품질을 완전히 보장하지 않는다. Release Candidate마다
Native Review와 언어별 Visual·Accessibility Matrix를 수행한다.

## 8. 후속 운영 과제

- Translation Memory, 용어집, Reviewer와 Source Revision을 포함한 TMS Workflow
- Tenant Localization Admin의 Draft·승인·배포·Rollback·Audit
- 실제 사용자 Timezone·통화·단위 선호와 지역별 보존 정책
- CJK 제품 Font의 품질·성능·License 승인
- 세 번째 제품 언어 도입 시 번들 분할 성능과 RTL 필요성 재검토

위 항목은 현재 제품 화면의 한국어·영어 동작을 임시 구현으로 만드는 미완료 사항이
아니다. 언어 수와 운영 조직이 늘어날 때 필요한 Delivery·Governance 확장 Gate다.
