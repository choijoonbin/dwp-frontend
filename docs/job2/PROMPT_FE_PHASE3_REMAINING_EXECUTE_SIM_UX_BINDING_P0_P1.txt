# [Cursor Prompt] FE — Phase3 잔여(P0/P1) Execute(sim) UX/바인딩 확정 + 스트림 UI 보강

배경
- Phase3 E2E에서 Analysis Run/SSE/Analysis/Proposals/Decision은 통과.
- 그러나 Execute(sim)가 “어떤 actionType/어떤 proposal을 실행하는지” UX가 불명확하거나 미연결인 상태.
- 목표는 “사용자가 proposal을 선택 → execute(sim) → 결과를 같은 카드에서 확인” 가능한 최소 UX를 완성하는 것.
- FE는 audit_event_log에 직접 쓰지 않으며, BE가 기록.

운영 정책(중요)
- 스트림 연결은 옵션B(운영 기본): FE는 Aura 직접 URL을 쓰지 않고 BE 프록시 streamUrl만 사용.
- analysis-runs 응답이 200/202 모두 가능하면 둘 다 처리(추후 202로 고정 가능).

---

## 1) 구현 범위 (In / Out)
### In (P0)
1. Action Proposals 탭에서 proposal 리스트를 “실행 단위”로 표현
2. 각 proposal 카드에:
   - 실행(시뮬) 버튼
   - 실행 결과 영역(성공/실패 + simulation 결과 요약)
   - 실행 중 로딩/중복 클릭 방지(디바운스)
3. execute(sim) 요청을 proposal과 1:1로 연결:
   - 선택된 proposalId(권장) 또는 actionType+payload를 BE로 전송
4. 실행 결과(actionId/simulation)를 해당 proposal 카드 상태로 매핑하여 표시

### In (P1)
5. 스트림 탭 UI: raw SSE 라인 출력 대신 step 기반 타임라인/진행률 UI
   - started/step/completed/failed 표시
   - step label/percent/detail 표시
   - failed(stage 포함) 안내 + 재시도 CTA

### Out
- 실제 ERP 실행(실제 결제차단 전기 등)은 Phase4 이후
- 복잡한 권한/워크플로(승인 라우팅) 고도화는 Phase4 이후

## 2) FE 화면/컴포넌트 설계(권장)
### 2.1 Action Proposals 탭(필수 P0)
- ProposalCard 구성:
  - 상단: actionType 뱃지 + requiresApproval 뱃지 + 상태(status)
  - 본문: rationale(요약) + checklist(있으면 리스트)
  - 하단: [실행(시뮬)] 버튼 + 결과 패널
- 결과 패널:
  - actionId 표시(있으면)
  - simulation 결과를 key/value 또는 테이블로 요약 표시(너무 길면 “상세 보기” 토글)
  - 실패 시 에러 메시지(문자열 또는 {message,stage} 처리)

### 2.2 중복 클릭/중복 실행 방지(P0)
- 동일 proposal 카드에서 execute(sim) 요청 중에는 버튼 disabled
- 실행 완료 후에는 재실행을 허용하되 “최근 실행 시간” 표시(옵션)
- runId가 바뀌면(새 분석) 기존 결과는 카드별로 초기화

## 3) FE ↔ BE API 계약 (반드시 반영)
### 3.1 GET action-proposals (이미 존재)
- 요청: /api/synapse/cases/{caseId}/action-proposals?runId=...
- 응답 필드 중 FE가 반드시 사용:
  - proposalId(or id)
  - actionType
  - rationale
  - payload (object)
  - requiresApproval (boolean)
  - checklist (array, optional)
  - status
  - fingerprint
  - updatedAt (정렬/표시용)
- 정렬: updatedAt desc 또는 sortOrder 기준(협의)

### 3.2 POST actions/execute (P0 핵심)
- FE는 “proposal 기반 실행”을 위해 다음 중 하나를 선택해 구현:
  - 권장안(A): proposalId 기반
    - request: { caseId, runId, proposalId, gatewayRequestId?, simulate:true }
  - 대안안(B): actionType + payload 기반(레거시)
    - request: { caseId, runId, actionType, payload, gatewayRequestId?, simulate:true }
- 응답:
  - { actionId, simulation: { ... }, status, message? }
- FE 바인딩 규칙:
  - 응답을 “요청을 보낸 proposal 카드”에 연결해 표시

※ BE가 아직 proposalId를 안 받는다면, 우선 actionType+payload로 구현하되
   다음 라운드에 proposalId로 전환 가능하도록 구조를 만들어둘 것.

## 4) 코드 작업 지시(파일 경로 포함)
- Case Detail > Action Proposals 탭 컴포넌트:
  - proposal 리스트 렌더링/상태 관리
  - execute(sim) mutation 추가(react-query 권장)
- API client:
  - execute(sim) POST 함수 추가/수정
- 상태/캐시 키:
  - proposals queryKey에 caseId+runId 포함
  - execute 결과는 local state(카드별 map)로 관리 권장
- 에러 처리:
  - error가 string 또는 {message, stage} 모두 대응

## 5) 테스트 시나리오(DoD)
### P0 DoD
1) 케이스 상세 → 분석 시작 → proposals 생성 확인(0건이면 “0건 이유” 표시)
2) proposals 탭에서 proposal 1개 → 실행(시뮬) 클릭
3) 네트워크에서 execute 요청 payload가 “선택된 proposal”과 일치 확인
4) 응답 actionId/simulation이 같은 카드에 표시
5) 실행 중 중복 클릭 방지
6) 새 분석(runId 변경) 후 proposals가 새로고침되고 run 간 결과가 섞이지 않음

증적
- DevTools 캡처 3장: proposals 응답, execute 요청/응답, UI 결과 표시

### P1 DoD(스트림 UI)
- started/step/completed/failed가 타임라인으로 표시되고 step label/percent가 노출
- failed 시 stage 기반 메시지 + 재시도 CTA
