# 로컬 권한별 로그인 검증 계정

## 목적과 범위

이 문서는 DWP 로컬 개발환경에서 일반 구성원, 회사 관리자, 프로바이더
관리자의 화면과 권한 경계를 점검하기 위한 계정을 정의한다. 세 계정은 번들된
`default` 샘플 테넌트에서만 사용하는 역할 격리형 검증 데이터이며 운영 계정이
아니다.

- 로그인 URL: `http://localhost:4200/sign-in`
- 테넌트: `default` / SKAX / 내부 ID `1`
- 공통 로컬 비밀번호: `admin1234!`
- 적용 조건: Backend의 Auth V29, Provider V20 이상 마이그레이션 적용

## 계정 정보

| 검증 관점         | 이메일                     | 역할               | 로그인 후 확인할 시작점          |
| ----------------- | -------------------------- | ------------------ | -------------------------------- |
| 일반 구성원       | `minseo.kim@sk.com`        | `WORKSPACE_MEMBER` | 개인 홈 `/`                      |
| 회사 관리자       | `hyunwoo.park@sk.com`      | `TENANT_ADMIN`     | 개인 홈 `/`, 관리 센터 `/admin`  |
| 프로바이더 관리자 | `provider.admin@dwp.local` | `PROVIDER_ADMIN`   | 프로바이더 제어 영역 `/provider` |

세 계정은 모두 같은 로그인 화면과 테넌트 컨텍스트를 사용한다. 별도의 브라우저
저장소 변경이나 테넌트 전환은 필요하지 않다.

## 역할별 기대 화면

### 일반 구성원

- 사이드바가 없는 개인 홈과 개인 계정 메뉴를 사용할 수 있다.
- 현재 할당 앱은 `구성원 디렉터리`이며 실제 People 시드의 김민서 프로필과
  조직 연결을 함께 점검할 수 있다.
- 관리 센터와 프로바이더 제어 영역은 노출되지 않아야 하며 직접 URL 접근 시
  접근 거부 화면으로 이동해야 한다.
- `업무`, `DWP에게 묻기`, `활동` 등 아직 역할에 할당되지 않은 앱은 홈 런치패드에
  표시되지 않는 것이 정상이다.

### 회사 관리자

- People의 박현우(`SK0003`, Digital Platform 부문장) 구성원과 연결된 HRIS 계정이다.
  회사 관리자 권한은 별도 가상 사용자가 아니라 이 구성원 ID에 역할로 등재된다.
- 일반 홈과 함께 `관리 센터` 진입 항목이 표시되어야 한다.
- 홈에는 업무, DWP에게 묻기, 활동, 메일과 일정, 협업, 임직원 서비스,
  구성원 디렉터리, 지식, 비즈니스 ERP, 레거시 업무, 관리 앱이 할당된다.
- 관리 센터에서 다음 메뉴 그룹을 확인한다.

| 그룹            | 기대 메뉴                                                          |
| --------------- | ------------------------------------------------------------------ |
| 사용자 경험     | 브랜딩, 홈 경험, 공지사항                                          |
| ID 및 접근 권한 | 접근 제어, 역할 및 권한, ID 프로비저닝                             |
| 플랫폼 설정     | 기준정보, 시스템 코드 계약, 앱 레지스트리, 내비게이션              |
| 거버넌스        | API 모니터링, 감사 관제, 증적 탐색기, 조사 워크벤치, 증적 거버넌스 |

- `TENANT_ADMIN`은 회사 설정 관리자이며 HR 원천 데이터 운영자는 아니다.
  `Workforce Management`와 HR 데이터 변경 기능은 `HR_ADMIN` 또는
  `PEOPLE_ADMIN`에만 부여하는 것이 정상이다.
- 프로바이더 제어 영역은 노출되지 않아야 하며 `/provider` 직접 접근도 거부되어야
  한다.

### 프로바이더 관리자

- 사용자 메뉴에서 `프로바이더 제어 영역`으로 진입하거나 `/provider`를 직접 연다.
- 운영 그룹에서 운영 지휘, 고객 및 테넌트, 변경 통제, 서비스 운영을 확인한다.
- 통제 그룹에서 권한 있는 지원, 구독 및 권한, 거버넌스 및 감사를 확인한다.
- 전체 고객 테넌트를 다루는 역할이므로 일반 앱은 기본 할당하지 않는다.
- 활성 지원 세션 없이 회사 관리 센터에 진입할 수 없어야 한다. 고객 지원 세션을
  명시적으로 연었을 때만 승인된 범위 안에서 해당 테넌트 기능을 위임받는다.

## 점검 순서

1. 기존 계정에서 로그아웃한 뒤 로그인 화면을 새로 고침한다.
2. 위 표의 계정과 공통 비밀번호로 로그인한다.
3. 헤더의 이름, 직책, 테넌트와 사용자 메뉴의 진입 항목을 확인한다.
4. 홈 앱과 사이드바 메뉴가 역할별 기대 목록과 일치하는지 확인한다.
5. 허용된 직접 URL과 금지된 직접 URL을 각각 열어 서버 권한까지 확인한다.
6. 다음 계정을 점검하기 전에 반드시 로그아웃한다. 다른 브라우저 프로필이나
   시크릿 창을 사용하면 세 역할을 동시에 비교할 수 있다.

## 검증 기준선

2026-08-11 로컬 Gateway 기준으로 다음을 확인했다.

| 계정              | 로그인 | Tenant Control Center | Provider Control Plane |
| ----------------- | ------ | --------------------- | ---------------------- |
| 일반 구성원       | 성공   | HTTP 403              | HTTP 403               |
| 회사 관리자       | 성공   | HTTP 200              | HTTP 403               |
| 프로바이더 관리자 | 성공   | HTTP 403              | HTTP 200               |

역할 응답은 각각 `WORKSPACE_MEMBER`, `TENANT_ADMIN`, `PROVIDER_ADMIN` 한 개만
포함한다. 비밀번호, 세션 쿠키, CSRF 토큰 또는 액세스 토큰을 이 기준선 외의 로그나
산출물에 복제하지 않는다.

## 보안 주의사항

- 이 계정과 공통 비밀번호는 로컬 샘플 데이터 전용이다.
- 배포 환경에서는 V29/V20의 로컬 검증용 자격 증명을 비활성화하거나 배포 Seed에서 제외하고,
  고객 IdP 또는 승인된 계정 활성화 절차로 대체한다.
- 실제 운영 비밀번호나 토큰은 Git 문서, 이슈, 화면 캡처에 기록하지 않는다.
- 역할을 추가해 화면을 임시로 여는 대신 필요한 리소스 권한과 역할 경계를 수정한
  뒤 다시 세 계정으로 회귀 검증한다.
