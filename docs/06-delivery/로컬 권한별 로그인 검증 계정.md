# 로컬 권한별 로그인 검증 계정

## 목적과 기준선

이 문서는 DWP 로컬 환경에서 역할별 메뉴, 직접 URL, API 권한과 직무 분리를 비교하기
위한 검증 계정 목록이다. 모두 SKAX `default` 샘플 테넌트 전용이며 운영 자격 증명이
아니다.

- 로그인 URL: `http://localhost:4200/sign-in`
- 테넌트: `default` / SKAX / 내부 ID `1`
- 공통 로컬 비밀번호: `admin1234!`
- 적용 기준: Auth V53, People V39, Platform V71, Provider V32, Approval V4 이상
- 권한 설계: [R1 권한 계층 및 앱 접근 거버넌스 ADR](../03-architecture/R1%20권한%20계층%20및%20앱%20접근%20거버넌스%20ADR.md)

권한은 하나의 상속 계층이 아니다. 테넌트 관리, ID 관리, HR 운영, 감사, 앱별 책임,
프로바이더 운영을 독립된 권한면으로 비교해야 한다. 화면에서 메뉴가 보이지 않는 것뿐
아니라 직접 URL과 API도 같은 결과를 내야 한다.

### 앱 접근 직무 분리 시나리오

1. 요청자는 Apps에서 접근 목적과 필요 기간을 제출한다.
2. `taehoon.kang@sk.com`은 요청을 승인하거나 반려한다. 자신의 요청은 결정할 수 없다.
3. 승인 후 `subin.oh@sk.com`이 실제 권한을 이행한다. 요청자 본인 또는 같은 요청의
   승인자는 이행할 수 없다.
4. Auth의 런타임 Entitlement가 `ACTIVE`가 되면 다음 API 요청부터 권한이 반영된다.
5. Access Manager가 회수하면 재로그인 없이 다음 요청부터 권한이 사라진다.
6. 이행 실패는 `FAILED`로 남고 Access Manager만 같은 요청을 재시도한다.

현재 로컬의 `메일과 일정` 앱은 실제 생산성 Provider가 연결되기 전
`CONFIGURATION_REQUIRED` 상태다. 외부 Connector가 없는 상태를 성공으로 가장하지
않기 때문에 새 사용자 요청 생성은 차단된다. 이 계정들로 관리 센터 메뉴·직접 URL·API
경계는 검증할 수 있으며, 실제 요청→승인→이행 E2E는 Provider Sandbox 연결 후 실행한다.
DWP 내부 Auth Entitlement 부여·회수 수명주기 자체는 구현되어 있다.

## 3. 프로바이더 운영 계정

프로바이더 계정은 일반 회사 관리자가 아니다. 고객 테넌트 기능은 활성화된 승인형 지원
세션에서만 접근하며, 일상 운영은 아래 전문 역할을 사용한다.

| 이메일                                | 역할                          | 주 검증 책임                     |
| ------------------------------------- | ----------------------------- | -------------------------------- |
| `provider.provisioner@dwp.local`      | `PROVIDER_TENANT_PROVISIONER` | 테넌트 개통·활성화               |
| `provider.entitlement@dwp.local`      | `PROVIDER_ENTITLEMENT_ADMIN`  | 계약·구독 Entitlement 변경       |
| `provider.approver@dwp.local`         | `PROVIDER_CHANGE_APPROVER`    | 고위험 운영 변경 독립 승인       |
| `provider.operator@dwp.local`         | `PROVIDER_OPERATOR`           | 서비스 운영·장애·유지보수 실행   |
| `provider.support@dwp.local`          | `PROVIDER_SUPPORT`            | 승인·기간·Scope가 있는 지원 세션 |
| `provider.auditor@dwp.local`          | `PROVIDER_AUDITOR`            | 읽기·감사·사후 검토              |
| `provider.release.approver@dwp.local` | `PROVIDER_RELEASE_APPROVER`   | 기능 배포 독립 승인              |
| `provider.data.approver@dwp.local`    | `PROVIDER_DATA_APPROVER`      | 데이터 정책 독립 승인            |
| `provider.admin@dwp.local`            | `PROVIDER_ADMIN`              | 전체 경계 회귀·비상 복구 검증용  |

### 기대 경계

- 모든 프로바이더 전문 계정은 `/provider`에서 자신의 Permission이 있는 메뉴만 본다.
- Tenant Provisioner는 구독 변경 권한을, Entitlement Admin은 테넌트 개통 권한을,
  Change Approver는 작업 실행 권한을 가져서는 안 된다.
- Release/Data Approver는 각각 기능 배포 또는 데이터 정책 승인 범위만 가진다.
- Provider Auditor는 변경 버튼이 없는 읽기·감사 경험이어야 한다.
- `PROVIDER_ADMIN`은 로컬 통합 검증과 비상 복구용이다. 실제 운영자의 일상 계정으로
  배포하지 않는다.
- 활성 지원 세션이 없으면 프로바이더 역할로 `/admin`에 들어갈 수 없다.

## 4. 화면 점검 순서

1. 기존 계정에서 로그아웃한 뒤 로그인 화면을 새로 고침한다.
2. 위 계정과 공통 비밀번호, `default` 테넌트로 로그인한다.
3. 헤더 이름·직책·권한 표시와 계정 메뉴의 Control Plane 진입 항목을 확인한다.
4. 허용 메뉴와 버튼을 확인하고 금지된 메뉴가 숨겨졌는지 확인한다.
5. 숨겨진 메뉴의 직접 URL을 입력해 Route Guard와 서버 API가 모두 거부하는지 확인한다.
6. `/api/auth/me`에서 `roles`, `resourceRoles`, `permissions`가 계정 표와 일치하는지
   확인한다.
7. 다음 계정 전에 반드시 로그아웃한다. 동시에 비교할 때는 브라우저 프로필이나 시크릿
   창을 분리한다.

404가 반환되어야 한다. 이 차이로 권한 경계와 데이터 존재 여부를 함께 검증한다.

- `subin.oh@sk.com`: `APP_ACCESS_MANAGER` 5개 범위와 요청 Queue 200.

## 6. 보안 주의사항

- 이 계정과 비밀번호는 로컬 Seed 전용이다.
- 배포 환경에서는 로컬 자격 증명을 비활성화하거나 Seed에서 제외하고 고객 IdP와 승인된
  계정 활성화 절차로 대체한다.
- 운영 비밀번호, 세션 쿠키, CSRF Token, Access Token을 문서·로그·화면 캡처에 남기지
  않는다.
- 화면을 임시로 열기 위해 역할을 추가하지 않는다. 필요한 역할·리소스·Permission·유효
  기간을 모델에 반영하고 세 계층의 서버 권한을 다시 검증한다.
- 역할 조합을 변경한 뒤에는 기존 세션 무효화, 감사 이벤트, Effective Permission과 메뉴
  갱신을 함께 확인한다.
