# DWP 신원 체계 재사용 독립 감사

상태: READONLY_AUDIT_COMPLETE / COMMON_P0_OPEN / G3_CLOSED. 결론은 기존 DWP 신원·권한 체계를 재사용하면서 필요한 owner DTO/SPI·source/lifecycle를 고도화하는 것입니다. 모듈별 전체 코딩 준비 완료 승인은 아닙니다.

## 결론

정상 직원 self identity에는 새 `ppl_principal_worker_links` 독립 authoritative 원장이 필요하다고 판단할 근거가 없습니다. Auth가 이미 사용자↔person 관계를 소유하고 People가 person↔worker↔고용관계↔assignment를 소유합니다. 직접 principal-worker 전용 table이 없다는 사실과 기존 신원 연결이 없다는 사실은 다릅니다. “기존 연결이 없다”를 이유로 두 번째 신원 원장을 만들면 재연결·퇴사·rehire·revocation의 진실이 분리됩니다.

그러나 현재 연결이 완성형 HRIS의 multiemployment/purpose-bound self authorization DTO·production adapter까지 구현됐다는 의미도 아닙니다. 현재 BIGINT actor와 public principal UUID의 projection, 정확한 Auth person binding, native 전체 고용 context, freshness/revoke/version/CAS, 실제 owner provider·transport가 공통 준비 P0입니다.

“현행 DWP에 신원 연결이 없다”라는 이전 진단은 CORRECTED/SUPERSEDED입니다. root도 현행 Auth/Gateway source를 직접 재확인한 뒤 통합계획을 Auth principal→person / HRM person→worker·고용 owner 분리 재사용으로 정정했습니다. 아래 IDR-P0-001은 최초 pinned proposal의 방향 문제를 기록한 것이며 그 아키텍처 방향은 정정되었습니다. 5 P0/6 P1은 snapshot 감사 분류이지 현재 열린 ticket 수가 아닙니다. 실제 새 common contract/provider/transport 및 현행 legacy 안전성·다중 고용·효력·replay/lifecycle 보완은 별도 OPEN이며 방향 정정만으로 구현/Gate를 닫지 않습니다.

## 확정 개선 사항

- IDR-P0-001 [P0] 정상 self identity의 신규 독립 링크 원장은 기존 DWP 신원 관계를 중복한다: HRM identityMappingDelta는 'G2 does not define principal→worker link'를 근거로 새 authoritative HRM PrincipalWorkerEmploymentLink를 ADD한다. 직접 principal-worker 전용 table이 없는 것은 맞지만 기존 Auth는 tenant-scoped user↔person UUID를 저장하며 People가 native person↔worker↔relationship↔assignment 관계를 소유한다. 따라서 현재 조회/DTO의 부족과 신원 관계 부재는 다르다. → Auth 소유 principal↔person 관계를 재사용하고 People owner는 이를 tenant-local native employment graph에 연결하여 purpose-bound self context를 파생한다. 링크/receipt store를 유지하더라도 derived admission/snapshot/history임을 명시하고 독립 신원 authority·shadow RBAC로 사용하지 않는다.

- IDR-P0-002 [P0] 새 Auth principal receipt는 principal↔person ownership을 증명하지 않는다: Auth.PrincipalVerificationReceipt.v2 authorityChain fields는 principalPublicId/status/verifiedAt/expiry/version/digest를 포함하지만 personPublicId 또는 Auth-owned person binding revision이 없다. ACTIVE principal 증명은 그 principal이 요청한 person의 소유자인지 증명하지 못한다. 기존 IdentitySubjectLookupService.Subject에는 publicId/personPublicId/status/identityPlane가 함께 있다. → 기존 Auth subject owner API를 기반으로 exact principal public UUID↔person public UUID↔tenant/plane/status와 principalVersion/accessRevision/personBindingRevision을 owner가 refetch·검증하는 versioned DTO/SPI를 제공한다. self는 current verified session principal과 동일해야 하며 다른 사용자를 링크하는 관리자 작업은 Auth 소유 relink 결정/SoD 증거가 필요하다. receipt freshness/revoke epoch는 명시 계약으로 닫아야 한다.

- IDR-P0-003 [P0] 기존 내부 user ID와 principal/person/worker UUID의 DTO 경계를 연결해야 한다: 현재 Auth /me userId, Gateway verified user header, People Actor.userId는 BIGINT이다. Auth.Principal PUBLIC_UUID는 com_users.public_id이다. HrWorkerRepository.WorkerIdentity의 UUID는 person.public_id이며 worker_id는 내부 BIGINT이다. 실제 worker/relationship/assignment PUBLIC_UUID는 V41에 각각 존재한다. → Auth owner가 현재 userId↔publicId↔personPublicId를 projection한다. People owner SQL은 실제 worker.public_id/relationship.public_id/assignment.public_id와 native tenant FKs를 projection한다. EmploymentContext를 기존 relationship/assignment 조합에 어떻게 대응하는지 정확히 정의하고 새 opaque 'employment' ID를 무근거 생성하지 않는다. body actor UUID/email/name/correlation 및 UUID equality fallback 금지.

- IDR-P0-004 [P0] 대표 assignment 조회를 전체 self 고용 authorization으로 재사용할 수 없다: People의 기존 person는 여러 worker를 가질 수 있고 worker는 여러 legal-employer relationship/assignment를 가질 수 있다. HrWorkerRepository는 lateral primary/effective sort LIMIT1 및 outer LIMIT1을 쓰며 assignment는 LEFT JOIN이다. HcmPopulationRepository도 현재 assignment 하나를 LIMIT1로 선택한다. 현재 query는 특정 asOf/self-context/relationship selector를 받지 않는다. → Auth person으로부터 해당 person에 속한 owner-native workers/relationships/assignments를 모두 조회하고 purpose/clock/zone/effective-state에 따라 eligible contexts를 발행한다. 0개는 fail-closed, 1개만 정책상 default, 여러 개는 명시 context selection을 요구한다. 선택 ID는 principal에 bound하고 foreign context/expired slice를 owner에서 거부한다. 프로필 조회와 급여/근태 업무 자격은 별도 목적 정책이다.

- IDR-P0-005 [P0] 기존 sync의 stale/replay/relink 처리에는 추가 owner 안전장치가 필요하다: Auth sync는 eventId receipt만 중복 판별한다. sourceVersion은 기록하지만 최신 version/CAS ordering 검증은 없다. byPerson이 없으면 HRIS externalId로 기존 사용자를 찾아 person_public_id를 다시 설정할 수 있다. person/external이 각각 서로 다른 사용자로 resolve되면 충돌을 거부하는 방어는 존재한다. → existing canonical binding을 재사용하되 canonical source identity key/owner version과 monotonic lifecycle epoch, payload digest receipts, CAS/replay/conflict를 추가한다. 다른 person으로 relink는 자동 fallback이 아니라 Auth-owned maker/checker/identity ownership 검증 및 이전 session/context/cursor revoke를 요구한다. retry publisher의 at-least-once delivery를 business latest-order 보장으로 오인하지 않는다.

- IDR-P1-006 [P1] worker 상태를 DWP 계정 전체 상태로 고정 매핑하는 legacy 패턴은 개선해야 한다: 기존 Auth sync는 LEAVE→SUSPENDED, PENDING→INVITED, TERMINATED→INACTIVE로 고정 매핑한다. SUSPENDED/INACTIVE는 세션을 revoke하고 INACTIVE는 직접 role/group membership을 제거한다. Import는 worker 하나의 상태를 person lifecycle에도 적용한다. → Auth 계정 access 상태, People person lifecycle, worker/relationship/assignment 상태를 독립 소유하고 canonical 전체 context를 기준으로 configurable joiner/mover/leaver/leave/reentry 정책을 평가한다. 보안 revoke는 current owner admission 조건을 만족해야 하며 active 관계가 남으면 자동 전사 계정 삭제/권한 제거하지 않는다.

- IDR-P1-007 [P1] HRM-local identity edges를 모두 cross-boundary opaque reference로 표현하면 native integrity를 잃는다: 제안된 ppl_principal_worker_links의 localForeignKeys는 비어 있고 person/worker/employment/HRM receipt까지 모두 opaque cross-boundary reference이다. uniqueKeys는 surrogate/public ID뿐이며 temporal overlap은 문장으로만 선언한다. 실제 native People graph는 tenant-local composite FKs와 effective constraints를 이미 갖고 있다. → Auth principal만 진짜 Auth-owner opaque edge로 유지한다. People 내부 canonical 관계는 기존 internal BIGINT tenant-composite FK/owner SQL graph를 재사용한다. derived context/snapshot store가 필요하면 actual native IDs+versions과 constraint/source를 명시하고 tuple temporal overlap을 executable planned SQL/fixtures로 제공한다. 현재 새 테이블의 구현 완료를 주장하지 않는다.

- IDR-P1-008 [P1] People trusted service-token/header chain과 새 signed owner proof는 동일한 검증 수준이 아니다: Gateway는 외부 user/tenant/person/authority/service-token/identity headers를 제거하고 Auth /me 결과 및 서버 service token을 mint한다. People는 constant-time service token을 검증한 뒤 header의 user/tenant 양수와 person UUID를 parsing하여 Actor로 저장한다. 일반 People 요청은 그 시점에 Auth user↔person pairing을 refetch하거나 per-request signed assertion을 검증하지 않는다. 내부 eligibility 경로에는 gateway service identity까지 요구한다. → 기존 Gateway sanitization/token 보호를 유지하고 신규 common adapter는 허용된 internal caller audience/purpose/route와 Auth-owned pairing/current status/revision을 검증해야 한다. signed owner proof 또는 bounded authenticated owner SPI transport의 정확 producer/verifier/freshness/revoke 계약을 정의한다. 관리자 supplied links는 candidate refs일 뿐 인증 identity가 아니며 self-provision/rebind를 허용하지 않는다.

- IDR-P1-009 [P1] 새 scope/cursor authority revision은 person·relationship·정확 context의 변경까지 bind해야 한다: 기존 HCM ActorWorkforce.revision은 workerVersion/assignmentVersion/organizationVersion이며 relationship/person version 및 exact context public IDs가 없다. actor selection CURRENT_ASSIGNMENT는 ACTIVE/LEAVE worker와 ACTIVE/SUSPENDED/PENDING assignment를 사용하며 HrWorkerRepository의 ACTIVE person predicate와 동일하지 않다. mutation 용 share-lock query와 owner scope recomputation은 이미 존재한다. → Auth pairing revision/revoke epoch+person/worker/relationship/assignment ID/version/effective window/purpose/captured clock을 bound한다. actor 및 target local state는 command transaction 안에서 refetch/lock/CAS하고 scope 재계산 결과를 receipt/outbox에 묶는다. status mapping/clock/zone이 다른 목적은 명시적으로 번역하여 일부 current query를 full authorization으로 사용하지 않는다.

- IDR-P1-010 [P1] Workforce v1 contract guard는 재사용 가능하지만 self identity production adapter는 아직 없다: WorkforceSnapshotProvider/RequestVerifier는 owner SPI이고 guarded port가 verified request→provider→page/cursor를 검증한다. 그러나 main source 검색에는 actual provider/verifier implementation 또는 composition call이 없다. verified request는 caller HRIS-PER와 bootstrap purpose/projection만 허용하고 projection은 worker/assignment 중심이며 principal/person/employment context binding이 없다. → 기존 immutable DTO/page/cursor/owner-composition pattern을 재사용하고 versioned AUTH_PERSON_BOUND_SELF_EMPLOYMENT 또는 caller/purpose-specific projection/SPI와 actual Auth adapter+People native query를 별도로 구현한다. 기존 v1을 약화하지 않고 consumer는 public guarded port만 사용한다. provider/transport/source/freshness 미완료는 G3 common P0로 유지한다.

- IDR-P1-011 [P1] 기존 unit/MockMvc 증거는 실제 신원 전수 migration·고용 sequence 검증이 아니다: 선택한 13개 기존 source class의 local XML은 118 tests, zero failure/error/skip이다. 이번 READONLY 감사에서 재실행하지 않았으며 전부 Testcontainers 없이 mock/lambda/exchange stub/contract fixture 또는 MockMvc이다.
