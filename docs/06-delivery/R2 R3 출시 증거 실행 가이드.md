# R2 R3 출시 증거 실행 가이드

- 상태: 실행 Harness 완료, 운영·고객 증거 대기
- 기준일: 2026-08-13
- 원장: `release-evidence/release-readiness.json`
- Provider-Tenant 수용 원장: `release-evidence/provider-tenant-acceptance.json`
- 내부 검사: `corepack yarn release:evidence:check`
- 검사기 자체 회귀: `corepack yarn release:evidence:test`
- 출시 차단 검사: `corepack yarn release:gate`

## 1. 상태 원칙

내부 자동 테스트는 출시 준비의 필요조건이지만 실제 고객 규모, 보조기술 사용자, 운영
Topology와 책임자의 승인을 대신하지 않는다. 원장은 `COMPLETE`, `PENDING_INTERNAL`,
`BLOCKED_EXTERNAL`, `FEATURE_DISABLED`만 허용한다.

- `COMPLETE`: 실행 가능한 자동 검사와 존재하는 완료 증거가 있고 Blocker가 없다.
- `PENDING_INTERNAL`: 저장소 안에서 추가할 자동화·결함 수정이 남았으며 `INTERNAL_*` Blocker와
  현재의 fail-closed 증거가 있다.
- `BLOCKED_EXTERNAL`: WORM·SIEM·KMS·고객 OOB·실환경·인적 승인처럼 저장소가 닫을 수 없는
  `EXTERNAL_*` Blocker와 fail-closed 증거가 있다.
- `FEATURE_DISABLED`: 출시 필수 기능이 아니며 자동 검사로 비활성·거부 상태를 증명한다.

문서나 파일이 존재한다는 이유만으로 `COMPLETE`를 선언하지 않는다. 내부 자동화가 없으면
반드시 `PENDING_INTERNAL` 또는 `BLOCKED_EXTERNAL`이고, 외부 기능은 승인 전 실행하지 않는다.

`release:evidence:check`는 ID 누락, 중복, 빈 Owner·Blocker, 존재하지 않는 증거와 거짓
완료를 CI에서 차단한다. Provider-Tenant 원장은 `PT-A01`~`PT-A30`을 정확히 30개로
강제한다. `release:gate`는 `R2`, `R3`, `A`, `PT`의 필수 항목이 모두 `COMPLETE`가
아니면 종료 코드 2로 실패한다.

Queue Full, Disk Full, Backend 장기 중단과 인증 Context 손실을 각각 시험한다.

## 4. 증거 등록 절차

1. 민감 로그 원문 대신 승인된 증거 저장소의 HTTPS Link와 비민감 요약을 남긴다.
2. Evidence에는 실행 Commit, 환경, Dataset 규모, 시간, 도구 Version과 결과를 포함한다.
3. 결함이 있으면 Gate를 `COMPLETE`로 바꾸지 않고 재시험 Link를 추가한다.
4. Owner와 승인자가 결과를 확인한 뒤 해당 원장 항목만 `COMPLETE`로 변경한다.
5. `corepack yarn release:evidence:check`와 `corepack yarn release:gate`를 실행한다.
6. Release Artifact의 SHA-256·서명·SBOM과 배포 대상 Commit을 함께 보존한다.

같은 저장소의 증거는 저장소 루트 기준 상대 경로만 사용하며 절대 경로, URL, `../` 탈출을
허용하지 않는다. `dwp-backend` 같은 외부 저장소 증거는 문자열 경로로 위장하지 않고
`repository`, `path`, `revisionSource`, `checkoutSource`를 명시한다. Release mode에서
`revisionSource`는 소문자 40자리 Commit SHA로 해석돼야 하고, `checkoutSource`의 공식 Git
Checkout HEAD와 정확히 일치하며 해당 경로가 실제로 존재해야 한다.

GitHub의 `Release readiness` 수동 워크플로는 검증할 `dwp-backend`의 소문자 40자리
Commit SHA를 `backend-commit`으로 요구한다. 브랜치나 이동 가능한 Tag는 공식 계약 입력으로
허용하지 않는다. 비공개 백엔드 저장소를 읽을 때는 Frontend 저장소 Secret
`DWP_BACKEND_READ_TOKEN`에 Contents read-only Token을 등록한다. 워크플로는 해당 Commit의
`contracts/`를 별도 경로로 Checkout하고 Frontend Snapshot이 모든 공식 Backend 계약과
바이트 단위로 일치할 때만 출시 승인 검사를 계속한다.

NIST SSDF의 Release Integrity 원칙에 따라 Source 검증과 실제 Release Artifact 무결성
정보를 연결한다. 로컬 테스트 Screenshot이나 임의 서명 문구를 운영 승인으로 사용하지 않는다.

## 5. 현재 판정

- R0·R1 내부 구현: 완료
- R2 출시 검증: 외부 규모·사용자·보조기술 증거 대기
- R3 운영 Hardening: 운영 Topology·보안 인프라·Adapter 및 Provider IdP 보증 증거 대기
- D-01~D-18: 미승인 기능은 fail-closed 또는 비활성
- A-01~A-07: 실제 책임자 승인, 고객 승인 SoR, 2테넌트 Pilot 훈련 증거 대기
- PT-A01~PT-A30: 28건 완료, 외부 인프라 1건 차단, Break-glass 1건 안전 비활성

따라서 현재 저장소는 내부 개발 기준선을 검증할 수 있지만 Production Release는
`release:gate`가 의도적으로 차단한다.
