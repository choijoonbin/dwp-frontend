# PROMPT_FE_CaseDetail_StatusAndActionButtons_WireUp_P0.txt
대상: dwp-frontend (SynapseX Case Detail 화면)
목표: 케이스 상세 우측 상단 “중간/트리아지” 상태 버튼 및 우측 패널 액션 버튼들이 **클릭해도 아무 동작이 없는 상태**를 P0로 해결한다.
근거(현상): 케이스 상세 페이지에서 액션 버튼 5개(onClick 없음) + 상태 변경 UI도 이벤트 미연결. 반면,
`useUpdateCaseStatusMutation` / `updateCaseStatus`는 이미 존재하며 엔드포인트는 `POST /api/synapse/cases/{caseId}/status`,
지원 status는 `TRIAGED | IN_PROGRESS | RESOLVED | DISMISSED`. fileciteturn37file0

## 0) 작업 원칙
- FE는 audit_event_log에 직접 쓰지 않음. 상태 변경 API 호출 시 **BE가 audit 적재**해야 한다.
- 기존 컴포넌트/레이아웃은 최대한 유지(기능 연결만).
- 테넌트/인증 헤더는 axiosInstance 경유로 자동 주입되는 현재 규칙 유지.

---

## 1) 작업 범위(In/Out)
### In (P0)
1) 케이스 상세 화면에서 상태 변경 UI를 실제 API 호출과 연결
2) 우측 “액션 승인/거절/정보 요청/결제 차단 설정/역분개 전기” 버튼 중
   - 최소 1개는 “상태 변경”에 매핑하여 동작 확인 가능하게 만들기(권장: 트리아지/진행중/해결/무시)
   - 나머지는 **현재 백엔드 액션 실행 API가 없다면** disabled + tooltip(“준비중”) 처리
3) 성공/실패 토스트, 로딩(disabled), optimistic UI(선택) 적용
4) 테스트/검증 시나리오 + Network 증빙 캡처 가이드 제공

### Out (P0에서 제외)
- 실제 “결제 차단/역분개/정보요청” 등의 도메인 액션 실행 API 신규 개발
- Aura SSE/Agent Stream 고도화
- 액션 승인(HITL) 워크플로 전체 구현

## 2) 구현 지침(프론트)
### 2-1. 케이스 상세 컴포넌트 찾기
- Case Detail 페이지(예: `/synapse/cases/:id`)에서
  - 상단 상태 칩/버튼(“중간”, “트리아지”) 렌더링 위치
  - 우측 액션 패널 버튼 렌더링 위치(현재 onClick 없음)
를 찾는다.

### 2-2. 상태 변경 Mutation 연결
- 이미 존재하는 훅 사용:
  - `useUpdateCaseStatusMutation()` (use-synapse-operations-query.ts Lines 243-274 근처)
- 상태 변경 호출 형태:
  - `mutate({ caseId: String(caseId), status: 'TRIAGED' | 'IN_PROGRESS' | 'RESOLVED' | 'DISMISSED' })`

### 2-3. UI 매핑(권장 기본값)
- 상단의 상태 버튼 2개가 “현재 상태 표시” 뿐이라면, 다음 중 하나로 바꾼다.
  A) 클릭 시 드롭다운(Select)로 4개 상태 선택 후 mutate 호출
  B) 현재처럼 2개 버튼만 유지하되:
     - “트리아지” 클릭 → status='TRIAGED'
     - “중간” 클릭 → status='IN_PROGRESS'
  ※ 케이스의 원본 status가 'OPEN'인 경우, 화면 표시용 매핑 필요:
     - OPEN → (표시) “대기/신규” 같은 라벨이 맞지만, P0에서는 기존 라벨 유지 가능.
     - 단, 변경 호출은 지원 enum(4개) 중으로만.

### 2-4. 액션 패널 버튼 처리(P0)
- 최소 동작 보장(테스트 가능) 위해 아래처럼 매핑:
  - “액션 승인” 버튼 → status='RESOLVED'
  - “거절” 버튼 → status='DISMISSED'
  - “정보 요청” 버튼 → status='TRIAGED' (또는 유지)
  - “결제 차단 설정”, “역분개 전기”는 백엔드 액션 API가 없다면:
    - disabled 처리 + Tooltip: “Phase B에서 지원 예정”
- “조치 실행 센터로 이동” 링크는 유지.

### 2-5. 로딩/오류/토스트
- mutate 진행 중:
  - 관련 버튼 disabled
  - 버튼에 spinner 또는 “처리중” 표시(가능하면)
- 성공 시:
  - 화면의 상태 칩/라벨이 즉시 변경
  - 토스트: “상태가 변경되었습니다.”
  - 케이스 상세 query invalidate/refetch (TanStack Query 사용 시 queryKey 확인 후 invalidate)
- 실패 시:
  - 토스트: “상태 변경 실패”
  - 원래 상태로 롤백(optimistic를 썼다면)

## 3) 테스트/검증(DoD)
### 3-1. 기능 DoD
- 케이스 상세에서 상태 변경이 실제로 동작:
  1) “트리아지” 또는 드롭다운에서 TRIAGED 선택 → 200 OK
  2) “중간” 또는 IN_PROGRESS 선택 → 200 OK
  3) “액션 승인” 클릭 → RESOLVED 200 OK
  4) “거절” 클릭 → DISMISSED 200 OK
- 변경 직후 UI에 상태가 반영되고, 새로고침 후에도 유지됨(백엔드 저장 확인)

### 3-2. Network 증빙(필수)
- DevTools Network 캡처:
  - `POST /api/synapse/cases/{caseId}/status` 요청/응답(200)
  - Request payload(status)와 Response를 보이게 캡처

### 3-3. Audit 검증(연동 확인)
- FE는 직접 쓰지 않지만, QA가 BE에서 audit 적재 여부 확인:
  - resource_type=CASE, resource_id={caseId} 기준으로
  - event_type이 CASE_STATUS_CHANGE(또는 유사) 1건 생성되는지 확인
  - ※ event_type은 BE 구현에 따르되, 최소 “상태 변경에 대한 audit 1건”이 목표
