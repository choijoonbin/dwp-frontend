[FRONTEND PROMPT] SynapseX 다국어(i18n) 적용 — ko/en 2개 언어, Shell↔Remote 공통, 최신 트렌드 방식
(대상: DWP Frontend / Nx MFE(Shell+Remotes) / React)

## 결론/결정안(3줄)
- i18n은 **i18next + react-i18next**로 구현하고, Shell(Host)이 **단일 i18n 인스턴스**를 제공하여 Remote들이 공유한다.
- 언어는 **ko / en 2개**만 지원하며, 기본은 ko. `localStorage(lang)` + `<html lang>` + `Accept-Language`로 전파한다.
- 번역 리소스는 `libs/shared-i18n`에 공통 모듈을 만들고, 각 앱/도메인은 `locales/{lang}/{namespace}.json`로 분리 + lazy-load 한다.

---

## 0) 범위(In/Out)
### In
- 우측 상단 “언어 버튼(ko/en)” 구현 + 상태 영속화(localStorage)
- 메뉴/라우트/공통 컴포넌트/토스트/에러메시지의 텍스트를 `t()`로 치환
- Shell↔Remote 언어 동기화(한 번 변경하면 전체 앱 즉시 반영)
- API 호출 시 `Accept-Language` 헤더 자동 주입(axios instance)
- 코드/케이스 타입 라벨 등은 “코드관리 API” 또는 “i18n 리소스” 중 하나로 표준화(아래 결정)

### Out(1차에서 제외)
- RTL 언어, plural ICU 복잡 규칙(필요하면 i18next-icu 추가)
- 다국어 번역 관리 UI(어드민에서 번역 편집) — Backend 범위로 분리
- 서버 사이드 렌더링(Next SSR) 고려(현재 프로젝트 구조 기준)

## 1) 구현 원칙(우리 프로젝트 기준)
- **MFE 공통 언어 상태는 Shell이 source of truth**
- Remote는 `shared-i18n` 훅을 통해 lang 변경 이벤트를 구독
- 파일 기반 번역을 우선(운영 리스크↓) + 필요 시 Backend 번역테이블로 확장 가능
- “코드값→라벨”은 다음 중 택1로 통일:
  A) **코드관리 API 기반**(권장: 이미 코드관리 메뉴가 존재) → label_ko/label_en 제공
  B) i18n JSON에 CASE_TYPE 라벨을 둠(빠르지만 코드 관리와 이중화 위험)

권장 결정: **A) 코드관리 API + 다국어 컬럼** (BE 프롬프트에서 설계)

## 2) 작업 대상 파일/폴더(생성/수정 경로 명시)
### 2.1 신규 라이브러리 생성
- `libs/shared-i18n/`
  - `src/lib/i18n.ts`  (i18next init + language persistence)
  - `src/lib/useLanguage.ts` (get/set + subscribe)
  - `src/lib/I18nProvider.tsx` (react-i18next provider)
  - `src/lib/index.ts`

### 2.2 번역 리소스 폴더
- `libs/shared-i18n/src/locales/ko/common.json`
- `libs/shared-i18n/src/locales/en/common.json`
- 도메인별 namespace 예:
  - `.../ko/synapse.json`, `.../en/synapse.json`
  - `.../ko/admin.json`, `.../en/admin.json`

### 2.3 Shell(Host) 적용
- Shell app entry(root)에서 `<I18nProvider>`로 전체 감싸기
- Topbar(User avatar 옆 언어 버튼)에서 `setLanguage('ko'|'en')`

### 2.4 Remote 적용
- Remote들은 별도 init 금지
- `useTranslation()`는 동일 i18n 인스턴스를 사용하도록 shared-i18n export 사용

### 2.5 Axios 헤더 주입
- `axiosInstance` 요청 인터셉터에서:
  - `headers['Accept-Language']= currentLang`
- 이미 tenant/user/trace 헤더가 있다면 동일 레이어에 추가

## 3) 코드 구현 상세(필수 요건)
### 3.1 i18n 초기화
- 초기 lang 결정 우선순위:
  1) localStorage('lang')
  2) browser navigator.language가 ko면 'ko' else 'en'
  3) default 'ko'
- `<html lang>` 속성 반영

### 3.2 lazy-load(초기 번들 최소화)
- i18next backend(HTTP) 대신 **dynamic import**로 namespace 로딩
- 예: `resourcesToBackend((lang, ns) => import(\`./locales/${lang}/${ns}.json\`))`
- 초기 ns는 `common`만 로드

### 3.3 UI: 언어 토글 버튼
- 버튼 라벨: “한국어 / English” 또는 “KO / EN”
- 현재 선택 언어 표시(체크)
- 변경 시 toast(선택) “Language switched to …”

### 3.4 메뉴/권한 라벨/배지 텍스트
- Sidebar 메뉴명은 서버에서 내려오는 name을 그대로 쓰는 구조라면:
  - 서버 메뉴 name을 다국어로 내려주거나(권장: BE)
  - 또는 menu key(id)를 i18n key로 매핑(차선)
- 케이스 타입/상태 라벨은 “코드관리 API”에서 언어별 라벨 사용

### 3.5 에러메시지 국제화
- 공통 에러 코드(예: E403/E500) → i18n key 매핑
- 백엔드 message를 그대로 번역하지 말고, errorCode 기반으로 FE에서 번역

## 4) Definition of Done(완료 조건)
- 우측 상단 버튼으로 ko/en 전환 시, Shell과 모든 Remote UI 텍스트가 즉시 변경됨
- 새로고침해도 언어가 유지됨(localStorage)
- API 호출에 Accept-Language가 포함됨(네트워크 탭으로 확인)
- 메뉴/케이스 타입/상태 라벨이 선택 언어로 표시됨(코드관리 연계 기준)
- fallback 전략:
  - 번역 키 누락 시 key 그대로 노출 + console warning(개발모드)
