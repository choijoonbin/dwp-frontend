# DWP Space 글로벌 벤치마크 및 제품 방향

- 조사일: 2026-08-18
- 대상: Microsoft Teams·Entra, Slack Enterprise, Notion, Confluence, SAP Build Work Zone
- 목적: DWP Tenant 안에서 구성원이 목적 중심 협업 공간을 만들고 운영하는 범용 제품 모델 정의

## 1. 결론

DWP의 `Space`는 회사 전체 Digital Workplace나 단순 채팅방의 다른 이름이 아니다. 조직,
프로젝트, TF, 운영, 커뮤니티, 사고 대응처럼 **공통 목적을 가진 사람·콘텐츠·업무 앱·AI를
정책 아래 묶는 컨텍스트**다.

가장 중요한 운영 원칙은 다음과 같다.

1. 모든 Space 생성과 모든 콘텐츠를 중앙 관리자가 건별 승인하지 않는다.
2. 승인된 Template·내부 전용·일반 등급 Space는 자동 승인 또는 Line Manager 승인으로
   셀프서비스를 유지한다.
3. 외부 사용자, 높은 기밀등급, 신규 Connector, 고위험 AI Grounding처럼 위험이 커지는
   경우에만 데이터 소유자·보안·준법·앱 담당자를 동적으로 결재 경로에 추가한다.
4. 생성 후 운영은 Space Owner와 Moderator에게 위임하고 중앙 관리자는 정책, Template,
   예외, 수명주기, 감사와 전체 상태를 관리한다.
5. 일상 대화·댓글은 즉시 게시하되 공식 공지·지식·외부 공개 콘텐츠는 유형별 게시 승인을
   적용한다.

즉 DWP Space의 경쟁력은 협업 기능의 개수보다 **정책 기반 셀프서비스, 교차 앱 컨텍스트,
원본 ACL을 보존하는 AI, 수명주기 자동화**를 하나의 제품 경험으로 연결하는 데 있다.

## 3. DWP 제품 경계

```text
Provider
  └─ Tenant (회사·보안·데이터 격리 경계)
      └─ Digital Workplace (회사의 DWP 제품 경험)
          ├─ My Work (개인 집계 Context, 실제 Space가 아님)
          ├─ Spaces (목적별 협업·업무 Context)
          │   ├─ Members / Roles / Policy
          │   ├─ Content / Knowledge / Activity
          │   ├─ Apps / Connectors / Resources
          │   └─ Agent Context
          └─ Apps (Space 종속 또는 Tenant 전역 실행)
```

- Tenant는 계약, Identity, 암호화, 보존, 데이터 지역과 감사의 경계다.
- Digital Workplace는 회사가 도입한 DWP 전체다.
- My Work는 사용자가 여러 Space와 App에서 받은 업무를 모아보는 가상 Context다.
- Space는 명시적 Owner·Membership·정책·수명주기를 가진 업무 객체다.
- App은 Tenant 전역으로 실행될 수도 있고, Space의 Context를 받아 실행될 수도 있다.

## 4. 승인 모델

### Space 생성

| 위험 조건                                             | 기본 처리        | 필수 검토자 예시                  |
| ----------------------------------------------------- | ---------------- | --------------------------------- |
| 승인 Template + 내부 전용 + 일반 등급 + 사전 승인 App | 자동 승인        | 없음, 사후 표본 감사              |
| 프로젝트·TF + 기간 지정 + 내부 구성원                 | Manager 승인     | Line Manager 또는 Sponsor         |
| 조직 전체 공개·공식 지식                              | 다단계 승인      | Space Governance + Communications |
| 외부 사용자·공유                                      | 다단계 승인      | Space Governance + Security       |
| 민감 데이터·규제 데이터                               | 다단계 승인      | Data Owner + Compliance           |
| 신규 App·Connector 또는 고위험 OAuth Scope            | 별도 App 승인    | App Owner + Security              |
| AI Grounding에 민감 원본 연결                         | 별도 데이터 승인 | Data Owner + AI Governance        |

### 콘텐츠 게시

| 콘텐츠·행위                | 기본 정책                                    |
| -------------------------- | -------------------------------------------- |
| 일반 게시물·댓글·회의 메모 | 즉시 게시 + 신고·Moderation                  |
| 공식 공지·정책·표준 지식   | Reviewer 승인 후 게시                        |
| 내부 파일 업로드           | Malware·DLP·분류 자동 검사, 정책 위반만 보류 |
| 외부 공개·Tenant 전체 배포 | Communications·Compliance 승인               |
| 사전 승인 App 추가         | Space Owner가 즉시 추가                      |
| 신규 Connector·Scope 변경  | App Governance 승인                          |

중앙 승인자가 모든 콘텐츠를 확인하는 방식은 처리량이 늘수록 병목과 형식적 승인을 만든다.
정책 엔진이 낮은 위험을 자동 처리하고 사람은 예외와 고위험 항목에 집중해야 한다.

## 5. 차별화 방향

1. **Cross-app Space Graph**: 전자결재, HR, Calendar, News, Service Request, 외부 SaaS의
   객체를 복제하지 않고 Space에 안전하게 연결한다.
2. **Policy Explainability**: 사용자가 제출 전에 예상 승인 경로와 이유를 확인한다.
3. **Governed Agent Context**: Agent가 현재 Space, 사용자 Membership, 연결 원본 ACL의
   교집합 안에서만 검색·행동하고 근거와 실행 이력을 남긴다.
4. **Lifecycle by Evidence**: 단순 생성일이 아니라 활동, Owner 유무, Member 변화,
   연결 자원 상태를 근거로 갱신·보관을 추천한다.
5. **Portable Template Contract**: 업종 Pack은 Core Space를 Fork하지 않고 Versioned
   Template, Policy, App Binding으로 확장한다.

## 6. 피해야 할 설계

- Tenant와 Space를 모두 Workspace로 표시하여 사용자가 보안 경계를 오해하게 만드는 것
- 조직·부문·본부·팀 같은 계층을 Space Type이나 DB Column으로 고정하는 것
- Space마다 별도 Role 체계를 새로 만들고 공통 IAG와 분리하는 것
- Space 생성용 결재 엔진을 전자결재와 별도로 구현하는 것
- 외부 문서·메일·채팅 원문을 권한 검증 없이 DWP DB와 Vector Store에 복제하는 것
- AI가 Space Context를 바꾼 뒤 이전 Context의 Conversation과 Retrieval 결과를 유지하는 것
- 중앙 관리자가 일상 게시물까지 모두 승인하도록 강제하는 것

## 8. 구현 전 최종 재검증

2026-08-18 구현 기준선 확정 전에 최신 공식 운영 문서를 다시 대조했다.

- [Google Chat Space 설정](https://support.google.com/chat/answer/13340792?hl=en)은
  Owner·Manager·Member Capability를 분리하고 Private·Discoverable·Open, 가입 요청 허용을
  각각 제어한다. DWP의 `visibility`와 Owner Access Queue 분리는 이 경계를 따른다.
- [Confluence Space 권한](https://support.atlassian.com/confluence-cloud/docs/assign-space-permissions/)은
  사용자·그룹·Guest 권한과 중앙 관리자의 권한 복구를 제공한다. 여러 Group의 권한이 합산되는
  운영 위험을 고려해 DWP는 멤버십 출처, 접근 주체, 유효기간과 최종 Owner 보호를 함께 표시한다.
- [Confluence Space 접근 요청](https://support.atlassian.com/confluence-cloud/docs/manage-space-access-requests/)은
  제한된 Space에서 요청하고 Space 관리자가 역할을 부여하는 흐름을 제공한다. DWP는 이를
  Owner Review Queue와 Tenant IAG Grant Source로 연결한다.
- [Microsoft 365 Group 만료 정책](https://learn.microsoft.com/en-us/entra/identity/users/groups-quickstart-expiration)은
  셀프서비스 생성 후 활동 기반 자동 갱신, Owner 알림, 미갱신 삭제와 복원을 결합한다.
  [Teams Archive](https://learn.microsoft.com/en-us/microsoftteams/archive-or-delete-a-team)는
  삭제 전 Archive와 Retention을 권장한다. DWP의 Lifecycle Review·Archive·Deletion Pending
  분리는 이 운영 모델을 확장한다.
- [Slack 역할](https://slack.com/help/articles/201314026-Permissions-by-role-in-Slack)은
  조직 역할과 Channel 관리 역할을 분리한다. DWP도 Tenant 운영 책임과 Space 내부 역할을
  합치지 않고 Scope별 SoD를 유지한다.

결론은 중앙 승인형 포털도, 자유 생성형 채팅 채널도 아니다. **Template 기반 셀프서비스 +
위험 기반 승인 + 명시적 Owner + 활동 기반 수명주기 + 원본 ACL을 보존하는 App·AI 연결**이
DWP에 가장 확장성 있는 제품 모델이다.
