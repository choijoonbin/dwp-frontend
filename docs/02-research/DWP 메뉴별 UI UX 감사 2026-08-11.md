# DWP 메뉴별 UI/UX 및 제품 완성도 감사

- 기준일: 2026-08-11
- 점검 범위: 사용자에게 노출되는 45개 메뉴, 로그인·권한·오류·로딩 등 전역 흐름
- 검증 환경: Chromium 데스크톱·모바일, 390/768/1280/1920 반응형, 200% 텍스트 확대,
  프론트엔드·Storybook·백엔드·Agent 자동 테스트, Docker DB/Redis와 실제 Gateway 세션
- 목적: SAP나 Salesforce의 시각 스타일을 답습하지 않고, 글로벌 제품의 검증된 기능을 더 현대적이고 정제된 DWP 경험으로 구현하기 위한 기준 수립

> 이 문서의 3.2장, 4장과 9장은 최초 감사 기준선이다. 구현 후 보수 재평가와 실제 진행 상태는
> 11장 이후가 우선하며, 완료 증거가 없는 항목은 구현 코드가 존재하더라도 완료로 보지 않는다.

## 1. 결론

DWP는 기반이 허술한 제품이 아니다. 공통 Shell, 권한 기반 메뉴, 디자인 토큰, 다국어,
감사·조직·Provider 운영 도메인과 실제 API가 이미 상당 부분 연결되어 있다. 특히 Work,
기준정보, API 모니터링, 감사 개요·이벤트, Provider 코드 계약·데이터 거버넌스는 제품의
강점으로 발전시킬 수 있는 구조를 갖췄다.

그러나 현재 완성도는 메뉴마다 편차가 크다. 일부 화면은 실제 업무를 수행할 수 있는
운영 제품인 반면, 홈·Ask·공지·프로비저닝·내비게이션·Provider 지원은 넓은 빈 공간,
단순 표, 참조 데이터 또는 미흡한 빈 상태 때문에 초안처럼 보인다. 조직도는 기능 범위는
넓지만 첫 진입 시 전체 조직이 지나치게 작게 보이는 기본 프레이밍 때문에 핵심 가치가
가려진다. 감사 조사에는 실제 조회 오류도 확인됐다.

따라서 전면 재디자인보다 다음 세 가지를 우선한다.

1. 실제 업무가 중단되는 오류와 전역 장애 전파를 먼저 제거한다.
2. 모든 운영 화면에 검색·필터·저장된 보기·상세 Inspector·명확한 상태 계약을 적용한다.
3. 메뉴별 카드 장식을 늘리는 대신 작업의 우선순위, 변화, 위험, 다음 행동을 더 잘 보이게 한다.

데이터 상태는 다음처럼 구분한다.

- `Live`: 백엔드 API와 실제 저장·조회 흐름이 연결됨
- `Hybrid`: 일부 API와 참조 데이터가 함께 사용됨
- `Reference`: 화면 시연용 정적 데이터가 주 동력임

## 3. 제품 전체 진단

### 3.1 잘된 기반

- 공통 Shell과 제품 영역별 Sidebar가 일관되고, Lucide 기반 아이콘과 접근 권한에 따라 메뉴가 걸러진다.
- 운영 화면은 과도한 마케팅형 카드보다 표, 필터, 상세 패널을 중심으로 구성되어 업무 제품에 적합하다.
- 디자인 토큰, Appearance 정책, 공통 Action·Form·Dialog·Grid·날짜 계약과 도입 검사기가 존재한다.
- 조직, 인력, 감사, Provider 운영을 별도 제어 영역으로 분리한 정보 구조는 확장성이 좋다.
- 한국어·영어, 밀도, 고대비, 모션 감소, 개인 설정 등 엔터프라이즈 제품의 기반 기능이 준비되어 있다.

### 3.2 제품 수준을 낮추는 공통 문제

1. **기능 완성도 편차**: 실제 API 화면과 정적 시연 화면이 같은 메뉴 깊이에서 섞여 사용자가 신뢰 수준을 구분하기 어렵다.
2. **빈 공간의 질**: 데이터가 적을 때 안내와 다음 행동 대신 넓은 빈 표 또는 빈 캔버스가 남는다.
3. **운영 탐색 계약 부족**: 메뉴마다 필터, 저장된 보기, 열 설정, 상세 미리보기, URL 상태 보존 방식이 다르다.
4. **전역 장애 전파**: 개인 설정이나 Provider 프로필 같은 보조 API 실패가 전체 화면을 로딩 또는 오류 화면으로 바꿀 수 있다.
5. **언어 혼용**: 한국어 UI 안에 영문 공지·감사 이벤트·서비스명이 그대로 나타나 제품 마감도가 낮아 보인다.
6. **단조로운 시각 체계**: 옅은 청색·회색과 얇은 구분선이 거의 모든 화면을 지배해 중요도와 도메인 차이가 약하다.
7. **공통 컴포넌트 전환 미완료**: 정책과 공통 API는 좋지만 다수 기존 화면이 여전히 MUI Button, Dialog, TextField를 직접 사용한다.
8. **폭이 넓은 표의 대응 부족**: 1280px에서 배치·감사 이벤트 등 일부 Grid의 마지막 열이 가려지고 가로 스크롤 의존도가 높다.
9. **교차 메뉴 연결 부족**: 사람, 조직, 권한, 감사, 운영 장애가 각각 강하지만 한 객체에서 관련 업무로 이동하는 경로가 약하다.
10. **모바일 실증 부족**: 코드에 반응형 규칙은 있으나 이번 감사에서는 실기기 크기의 전 메뉴 회귀 검증을 완료하지 못했다.

## 7. 목표 UI/UX 원칙

1. **업무 우선**: 페이지 제목보다 사용자가 지금 처리해야 할 변화·위험·결정을 먼저 보인다.
2. **점진적 상세화**: 목록은 비교에 집중하고 Detail Inspector와 Drawer에서 맥락과 명령을 제공한다.
3. **한 화면, 한 주 행동**: 색이 채워진 Primary Action은 한 작업 구간에 하나만 둔다.
4. **밀도는 역할별로**: 일반 사용자는 단순하게, 운영자는 정보량을 유지하되 그룹·정렬·고정 열로 읽기 쉽게 한다.
5. **색은 의미에 사용**: Brand Blue 외에 성공·주의·위험·AI·변화의 Semantic Color를 제한적으로 사용한다.
6. **상태는 데이터의 일부**: Loading, Empty, Partial, Stale, Error, Permission, Offline을 화면 설계에 처음부터 포함한다.
7. **모션은 인과관계를 설명**: Drawer, Logout, 조직 Focus, Row Update에 짧은 Transition을 사용하고 모션 감소 설정을 존중한다.
8. **탐색 상태를 잃지 않음**: 필터·정렬·선택·확대 위치를 URL 또는 Saved View로 복구한다.
9. **변경 전 영향을 보여줌**: 역할, 조직, 레지스트리, 기준정보, Provider 작업은 실행 전 Diff와 영향 범위를 제공한다.
10. **서비스는 부분적으로 실패할 수 있음**: 보조 API 실패가 Shell과 핵심 업무를 막지 않도록 화면 단위로 격리한다.

현재 `EnterpriseDataGrid`를 새로 만드는 것이 아니라, 위 패턴과 결합해 서버 페이징,
저장된 보기, 열 Preset, 선택, Export Job, Inspector를 메뉴마다 같은 방식으로 사용한다.

## 10. 완료 기준

메뉴가 존재하거나 API가 호출된다는 이유만으로 완료 처리하지 않는다. 다음 조건을 모두 만족해야 한다.

- 핵심 사용자가 대표 업무를 처음부터 끝까지 수행할 수 있다.
- Loading, Empty, Partial, Error, Permission, Success 상태가 모두 설계되고 테스트된다.
- 390px부터 1920px까지 내용 겹침과 접근 불가능한 명령이 없다.
- 키보드, Focus, Screen Reader, 200% Zoom, 고대비, 모션 감소를 통과한다.
- 서버 권한과 UI 권한이 동일한 정책을 강제하고 모든 변경이 감사된다.
- 필터·정렬·선택·상세 위치가 이동 후에도 예측 가능하게 복구된다.
- 한국어·영어와 긴 실제 데이터에서 잘림·혼용·기술 코드 노출이 통제된다.
- 화면별 임의 컴포넌트 대신 승인된 공통 제품 패턴을 사용한다.
- 정상 흐름뿐 아니라 API 지연·부분 장애·재시도에서도 Shell과 핵심 업무가 유지된다.

이 감사의 다음 단계는 P0를 별도 결함으로 고정한 뒤, P1 화면을 Journey 단위로 하나씩
재설계·구현하고 각 완료 기준을 E2E 및 Visual Regression Gate에 연결하는 것이다.

### 11.1 판정 원칙

- `A`는 10장의 완료 기준을 모두 충족하고 대표 사용자 여정, 부분 장애, 접근성, 반응형 증거가 있을 때만 부여한다.

### 15.2 아직 충족하지 않은 출시 증거

- NVDA·JAWS·VoiceOver를 사용한 실제 Screen Reader 수동 점검과 Keyboard-only 사용성 기록
- D-01 기업 SSO, D-02 운영 Model·평가, D-03 외부 지식 Connector, D-04·D-05 조직 설계 확장,
  D-08 Calendar·결재, D-11 고객 HRIS 인터페이스에 대한 고객·보안·데이터 소유자 결정
- D-06의 Team 공유·소유권 이관, D-07의 서비스별 Outbox/Replay 계약, D-09의 안전한 반출 정책,
  D-10의 CI Browser/OS 매트릭스, D-12의 비동기 Export 저장소·Worker, D-13의 실행기·통지 계약,
  D-14의 미디어 저장·보존, D-15의 공지 승인·채널·확인 정책
- 실제 고객 규모의 조직도·Grid 성능, 장애 주입, 장시간 Soak, 복구·Rollback 시험

따라서 현재 판정은 **Wave 1·Wave 2 내부 구현 가능 범위 완료, P1~P3 제품 기반과
D-02·D-03·D-06·D-07·D-10의 현재 실행 가능 범위 완료, 외부 결정 항목 보류**다.
위 조건이 충족되기 전에는 `완벽`, `경쟁사보다 우수`, `전 메뉴 완료` 표현을 사용하지 않는다.
