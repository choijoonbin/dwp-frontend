# DWP 메신저 글로벌 벤치마크 및 제품 방향

- 기준일: 2026-08-19
- 상태: 설계 검토안
- 대상 기능: `DWP-R1-MSG-001`

## 1. 조사 범위와 해석 기준

여기서 `글로벌 Top 5`는 단순 설치 수 순위가 아니라 엔터프라이즈 협업, 관리, 보안,
회의 연속성, 생태계 대표성을 기준으로 선정한 비교군이다.

1. Slack
2. Microsoft Teams
3. Google Chat
4. Zoom Team Chat
5. Cisco Webex App

Discord는 엔터프라이즈 관리 제품 비교군에서는 제외하되, 초대형 메시지 저장 구조를 검증하는
기술 사례로 사용한다. 화면을 복제하지 않고 각 제품의 강점과 약점을 DWP의 Tenant, Space,
People, Calendar, Approval, Mail, Notification 경계에 맞게 다시 설계한다.

## 2. 현재 DWP 진단

| 항목        | 현재 상태                                               | 설계 판단                                                   |
| ----------- | ------------------------------------------------------- | ----------------------------------------------------------- |
| 앱 런처     | `ref-app-collaboration`, `APP.COLLABORATION` 자리표시자 | 실제 제품 `messaging`, `APP.MESSAGING`으로 승격 필요        |
| 사용자 검색 | People Directory API와 `personPublicId` 보유            | 사람 원장을 복제하지 않고 검색·상태만 참조                  |
| Space       | 목적, 소유자, 멤버십, 정책, 앱 연결의 독립 원장         | Space 대화 멤버십의 권위 원장으로 사용                      |
| 알림        | PostgreSQL 원장, Kafka, SSE 기반 별도 설계              | 오프라인 멘션·DM 전달만 위임하고 채팅 원장으로 사용 금지    |
| 이벤트      | CloudEvents 정렬·Inbox·Outbox 계약 보유                 | Space/People 동기화와 검색·알림 파생에 재사용               |
| 로컬 인프라 | PostgreSQL 18, Redis 7.4, Kafka 4.3.1                   | 메시징 기본 기반은 충분하나 검색·파일·실시간 계층 추가 필요 |

기존 Space ADR은 자체 Slack/Teams 엔진을 비목표로 두었다. 이번 요구는 그 경계를 변경하는
제품 결정이다. Space에 채팅 코드를 흡수하는 대신 별도 Messaging Bounded Context를 만들고,
Space는 멤버십과 정책만 제공하도록 ADR을 확장해야 한다.

## 3. 제품별 분석

| 제품           | 가장 강한 부분                                                | 그대로 수용하지 않을 부분                   | DWP 적용                                         |
| -------------- | ------------------------------------------------------------- | ------------------------------------------- | ------------------------------------------------ |
| Slack          | 채널, Activity, Threads, Later, 사용자 정의 섹션, 앱·Workflow | 채널 난립과 읽지 않음 숫자 중심의 피로      | Space 기반 분류와 `주의 필요` 업무 신호로 재구성 |
| Teams          | Team/Channel 역할, 표준·비공개·공유 채널, 앱·파일·관리 정책   | 제품·팀·채널 계층의 무거움과 높은 화면 밀도 | Space 권한을 상속하되 대화 탐색은 한 단계로 유지 |
| Google Chat    | 단순한 DM/Space 구분, Thread, Task, Announcement, App         | 고급 Triage와 대규모 대화 관리가 약함       | 명료한 대화 유형과 DWP 업무 카드 결합            |
| Zoom Team Chat | 회의 전·중·후 동일 대화의 연속성                              | 회의 중심 정보 구조와 제한된 업무 원장 연계 | Calendar Event에 연결된 지속 대화로 적용         |
| Webex          | 안전한 Space, 예약 전송, Thread·인용·전달·Flag, 섹션과 필터   | DWP Space와 용어 충돌, 기능 발견성 저하     | 제품 용어는 `대화`, 연결 원장은 `Space`로 분리   |

### 3.1 반드시 수용할 공통 기능

- 1:1 DM, 그룹 DM, Space 연결 채널, 공지형 채널
- Thread, Reaction, Mention, 인용, 링크, 예약 전송, 임시 저장
- Activity, 나중에 보기, 읽지 않음, 검색, 파일, 사용자 정의 섹션
- 키보드 우선 탐색과 `Cmd/Ctrl+K` 명령 팔레트
- 조직도에서 사람을 찾아 결정적 1:1 대화를 재사용하는 흐름
- Space 구성원·역할 변경의 자동 반영과 이력 노출 정책
- 회의 전·중·후 같은 대화를 유지하는 Calendar 연결
- Retention, Legal Hold, eDiscovery, 감사, 외부 사용자 정책
- Bot/App, Webhook, 업무 카드와 세분화된 Scope

### 3.2 경쟁 제품의 약점을 보완할 DWP 차별점

1. **Context Continuity**: 대화가 Space, 일정, 결재, 업무, 서비스 요청의 맥락을 잃지 않는다.
2. **Governed Action Capsule**: 메시지를 업무·일정·결재 요청으로 전환하되 대상 앱에서 권한과
   입력을 다시 확인한다.
3. **Decision Trail**: 메시지나 Thread를 `결정`으로 승격해 소유자, 결론, 기한, 근거 링크를
   Space에 남긴다.
4. **Access Pulse**: 공유된 업무 카드마다 원본 접근 가능 여부를 서버에서 확인한다. 권한이
   없으면 내용 대신 접근 요청 경로를 제공한다.
5. **Explainable Membership**: 사용자가 왜 대화에 포함됐는지 `직접`, `Space`, `조직 그룹`,
   `초대` 출처와 적용 시점을 표시한다.
6. **Quiet Priority**: 단순 안 읽은 개수보다 멘션, 답변 요청, 마감, 내 담당, 보안 경고를
   설명 가능한 규칙으로 우선한다.
7. **Policy-safe AI**: 향후 요약·회신·일정·휴가 제안은 원문 인용, 현재 ACL, 보존 정책,
   사람 승인을 모두 통과해야 한다.

## 4. 메시지 저장에 대한 사실 검증

`채팅 내용은 DB에 보관하지 않는 것이 최신 방식`이라는 전제는 맞지 않는다.

- Slack은 메시지를 데이터베이스에 영속화한 뒤 실시간 WebSocket 계층으로 전달한다.
- Microsoft Teams와 Google Chat은 사용자 화면의 메시지와 별개로 보존·eDiscovery 정책을
  적용할 영속 데이터 계층을 운영한다.
- Discord는 수조 개 메시지를 Cassandra에서 ScyllaDB로 이전했다. 이는 DB를 없앤 사례가
  아니라 규모에 맞는 메시지 저장소로 교체한 사례다.
- Kafka는 전달과 재처리, Redis는 Presence·Typing·연결 라우팅에 적합하며 메시지 원장이 아니다.

DWP R1은 PostgreSQL 18의 Partitioned Message Store를 사용한다. 현재 규모를 확인하지 않은
채 ScyllaDB를 먼저 도입하면 운영 복잡성만 증가한다. `MessageStorePort`와 부하 Gate를 두고,
실측 한계가 확인된 경우에만 ScyllaDB 계열 저장소로 이전한다.

## 5. 최종 제품 방향

### 5.1 명칭과 경계

- 제품·런처 명칭: `메신저` / `Messenger`
- Route: `/messages`
- App Resource: `APP.MESSAGING`
- Backend Bounded Context: `messaging`
- Space와 구분되는 사용자 용어: `대화`, `채널`, `DM`

`협업`은 너무 넓고 Space, Mail 내부 협업, Approval 협업과 의미가 겹친다. 구현 시 기존
`APP.COLLABORATION`을 호환 기간 후 폐기한다.

### 5.2 R1 범위

- 내부 사용자 1:1·그룹 DM
- Space 연결 채널과 공지 채널
- Thread, Reaction, Mention, 읽음, Presence, Typing
- 메시지 수정·삭제, 예약, 임시 저장, 나중에 보기
- 안전한 파일 첨부, 서버 검색, Activity와 메신저 홈
- People Directory와 Space 멤버십 연동
- Calendar 회의 대화, Notification 오프라인 전달
- Tenant 관리자 정책, 운영, 보존, 감사 화면

### 5.3 R1에서 의도적으로 제외할 범위

- 자체 음성·영상 미디어 엔진: Calendar/Rooms와 외부 회의 공급자에 연결한다.
- 외부 Tenant 공유 채널: 데이터 소유권·보존 충돌 모델을 검증한 뒤 R3에 도입한다.
- 기본 종단간 암호화: 검색·DLP·Legal Hold와 충돌하므로 KMS 기반 전송·저장 암호화를
  기본으로 하고 제한형 Confidential Mode를 별도 검토한다.
- AI 자동 발송·자동 초대·자동 삭제: 제안과 사람이 승인한 실행을 분리한다.
- 관리자 전체 본문 열람: 운영자는 메타데이터만 보고 Compliance Case만 통제된 본문 접근을
  허용한다.
