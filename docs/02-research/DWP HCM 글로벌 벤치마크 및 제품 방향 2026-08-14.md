## 2. 공통 성공 패턴

1. **하나의 역할 인지 시작점**: 제품 카탈로그보다 사용자의 다음 행동을 먼저 보여준다.
2. **Employee Self-service**: 본인 정보·근태·휴가·문서·Benefits·성장을 직접 확인한다.
3. **Manager Workspace**: 조직 전체 HR 화면이 아니라 직속 팀 예외·승인·위험에 집중한다.
4. **Target Population**: 역할만으로 전체 구성원 데이터가 열리지 않는다.
5. **Domain Delegation**: 근태·휴가·급여·Benefits·Talent 운영을 독립 위임한다.
6. **Effective Dating**: 사람·발령·조직 관계의 과거·현재·미래를 구분한다.
7. **Workflow and Evidence**: 제출·결정·변경을 Version과 감사 증거로 보존한다.
8. **System of Record 연계**: Payroll·Benefits·LMS·ATS를 무리하게 복제하지 않는다.
9. **개인화 가능, 권한은 불변**: Widget 순서와 크기는 바꿀 수 있지만 데이터 권한은 못 바꾼다.
10. **Mobile Task Completion**: Desktop Dashboard 축소가 아니라 단일 행동 완료 흐름을 제공한다.

### 제품 내부 개발만으로 닫지 않는 출시 Gate

1. 국가·지역·고용형태별 휴일, 근무 일정, 휴가 적립·이월·소진·승인 후 취소 정책
2. Payroll 계산, 세금, 회계, KMS, 명세 문서 저장소와 실제 다운로드 권한
3. 보험·연금 사업자의 가입·변경·해지 Transaction과 법정 증빙
4. ATS·채용 승인·Offer·Background Check, LMS Content·수료 Write-back
5. 성과 Review Cycle, 1:1, Feedback, 360, Calibration, Compensation, Succession
6. 고객별 HR Agent Group, SLA Calendar, Knowledge Source, 개인정보 보존·삭제·SIEM 정책

이 항목은 화면과 임시 Table만 추가해서 완료로 표시하지 않는다. System of Record, 법무,
보안, 데이터 소유권 결정과 Contract Test가 확보된 순서대로 별도 Aggregate를 승인한다.

## 6. UX 결론

- 사용자에게 아름답게 보이는 것만으로는 충분하지 않다. 5초 안에 상태를 판단하고 1~3회
  상호작용으로 핵심 업무를 완료해야 한다.
- Soft Neutral Surface와 제한된 의미 색상을 사용하되 한 색조 Dashboard로 만들지 않는다.
- KPI Card 수를 늘리지 않고 Action Queue, 기간, 비교 기준, Drill-down이 있는 신호만 시각화한다.
- 개인 HR Home은 젊은 사용자에게 친숙한 간결함과 Motion을 제공하되, 인사·급여·건강
  정보의 신뢰·접근성·감사 가능성을 희생하지 않는다.
- 경쟁사의 Visual을 복제하지 않고 DWP Design Token, Lucide Icon, 공통 Form·Dialog·State
  Component로 일관된 제품 언어를 유지한다.

### 6.1 개인 홈과 HCM 홈의 경계

개인 홈은 승인·일정·공지·앱처럼 제품을 가로지르는 **오늘의 업무 요약**을 소유한다. HCM
홈은 그 정보를 반복하지 않고 사용자가 인사 맥락에서 바로 판단해야 하는 **나의 HR 상태와
다음 행동**을 소유한다.

| HCM 홈 우선 정보 | 판단 질문                                          | 표현 원칙                           |
| ---------------- | -------------------------------------------------- | ----------------------------------- |
| 이번 주 근무     | 기록이 기준 시간에 도달했는가                      | 실제 기록/기준과 진행률             |
| 휴가             | 지금 사용할 수 있는 잔여와 대기 건은 무엇인가      | 잔여·사용·대기 분리                 |
| 급여             | 다음 급여일과 준비 상태는 어떠한가                 | D-day와 검증 항목, 금액 노출 최소화 |
| 복리후생         | 현재 적용 혜택과 등록 가능한 기간이 있는가         | 적용 건수와 열린 Window             |
| 성장             | 목표·필수 학습 중 다음에 할 일은 무엇인가          | 실제 Goal·Learning 상태             |
| 팀 관리          | 직속 팀의 승인·예외 중 내가 판단할 항목은 무엇인가 | Manager에게만 누적 노출             |

[SAP SuccessFactors의 Home Page UX](https://help.sap.com/doc/38d877e5b3404eddbd23d67f6622e7ce/2511/en-US/SF_PLT_User_Experience_en-US.pdf)는
시스템이 제시하는 Task와 사용자가 찾는 Action을 구분하고 Quick Action을 짧은 완료 경로로
정의한다. [Oracle Journeys](https://www.oracle.com/human-capital-management/employee-experience/oracle-me/journeys/)는
역할·위치·수명주기 맥락의 안내를, [Microsoft Viva Connections](https://learn.microsoft.com/en-us/viva/connections/create-dashboard)는
역할별 Card Targeting과 사용자 Reorder·Hide를 제공한다. DWP는 이 공통점을 다음과 같이
적용한다.

1. 첫 화면은 장식용 KPI가 아니라 실제 HCM Aggregate의 근무·휴가·급여·혜택·성장 신호로
   구성한다.
2. 일반 구성원 신호에 Manager·HR 운영 신호를 권한에 따라 누적하되, Target Population은
   Backend에서 다시 검증한다.
3. Quick Action은 근태 입력·휴가 신청·급여 명세·HR 도움처럼 앱 안에서 완료 가능한 동선만
   제공한다.
4. Widget 순서·크기·노출은 개인화하되, 신호의 원천과 데이터 권한은 바꾸지 못한다.
5. Mobile에서는 Dashboard 축소판을 만들지 않고 Snapshot → Action → Insight → Guidance의
   단일 세로 흐름으로 재배치한다.

### 6.2 시각·상호작용 결정

- Neutral Canvas 위에 HCM의 Teal을 신뢰·완료 신호로, Cobalt·Violet·Coral·Saffron을 서로
  다른 업무 범주에만 제한적으로 사용한다. 이는
  [Fluent 2 Color](https://fluent2.microsoft.design/color)의 중립색 기반 계층 원칙을 따른다.
- 숫자만 놓인 동일 KPI Card를 반복하지 않는다. Progress Ring, Segment, 상태 문장처럼
  질문에 맞는 Micro-visualization을 사용하고 모든 시각화에 같은 의미의 Text를 병기한다.
- Hover·등장 Motion은 관계와 실행 가능성을 알려주는 짧은 Feedback으로 제한한다.
  [Apple Motion](https://developer.apple.com/design/human-interface-guidelines/motion) 원칙에 따라
  `prefers-reduced-motion`에서는 이동·전환을 제거한다.
- Glass·과도한 Blur·큰 Marketing Hero 대신 선명한 Typography, 안정적인 Grid, 실제 상태와
  정교한 Feedback으로 고급스러움을 만든다.

## 7. 출시 판단

현재 구현은 내부 Reference와 권한·데이터·Workflow 아키텍처를 검증하는 수준으로 적합하다.
고객 출시 완료를 주장하려면 고객 HRIS, 국가 정책, Payroll·Benefits·Document Connector,
KMS, 운영 규모, 보조기술 수용 시험이 모두 통과해야 한다.

실행하고 제외 사유를 Release Evidence에 남긴다.

### 비판적 판정

- DWP HCM은 일반 구성원, People Manager, HR Domain Operator, Workforce Designer의 탐색과
  Backend 권한을 분리했다. 메뉴 은닉만으로 권한을 구현하지 않는다.
- Profile·Assignment·Organization은 유효일 기반이고, Time·Absence·Benefits·Pay·Talent는
  서로 다른 수명주기를 유지한다. 편의를 이유로 하나의 범용 HR Table에 합치지 않는다.
- HR 문의·증명·정보 변경은 기존 Service Catalog·Request·Timeline을 재사용한다. 같은 의미의
  `hr_cases` 같은 중복 Aggregate를 만들지 않는다.
- HR Home의 Widget 구성은 개인화할 수 있지만 Entitlement, Target Population, 원천 데이터
  범위를 확장하지 못한다.
- Payroll 계산, 보험 가입, 채용, 학습 콘텐츠, 성과 보정처럼 실제 System of Record 계약이
  없는 기능은 Demo 수치·임시 Table·빈 메뉴로 완료 처리하지 않는다.

| HR Document·전자서명                   | HR Service 요청                         | KMS, Template, 전자서명, 보존·삭제 및 다운로드 권한 계약      |
| Performance·Calibration·Compensation   | Goal·Learning 개인 기준선               | Cycle·Reviewer·보정·보상·이의 제기 정책과 독립 감사 Aggregate |
| Recruiting·Offer·Background Check      | 노출하지 않음                           | ATS System of Record와 Candidate 개인정보·동의·보존 계약      |
| Workforce Scheduling·Clock             | Time Entry·Exception 기준선             | 교대·휴게·Clock Device·법정 규칙·소급 및 대결 정책            |
| Payroll·Benefits Transaction           | 보안 조회·문의·요청 기준선              | 국가 계산 Engine 또는 Provider API, Reconciliation, 실패 보상 |
| Employee Relations·HR Agent Operations | 공통 Service Operations에서 제한적 처리 | Agent Group, SLA Calendar, 민감도, Legal Hold, SIEM·보존 정책 |

따라서 위 후보는 누락을 감추는 항목이 아니라 외부 의사결정이 필요한 명시적 Product Gate다.
Gate가 열리기 전에는 기존 서비스 흐름으로 안전하게 연결하고, 열린 뒤에만 소유권이 분명한
Aggregate와 역할별 메뉴를 추가한다.
