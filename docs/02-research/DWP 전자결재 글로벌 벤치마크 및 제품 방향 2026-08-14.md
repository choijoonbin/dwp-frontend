# DWP 전자결재 글로벌 벤치마크 및 제품 방향

- 상태: Product Discovery Baseline
- 기준일: 2026-08-14
- 범위: 내부 전자결재, 업무 승인, 외부 전자서명 연결, 사용자·관리자 경험
- 후속 문서: `../03-architecture/R1 Enterprise Approval Decision Hub ADR.md`

## 1. 조사 정의

전자결재에는 공인된 단일 글로벌 순위가 없다. 따라서 이 문서의 `Top 10`은 매출 순위를
뜻하지 않는다. 대규모 기업 도입 범위, 업무 프로세스 깊이, 승인 UX, 문서 서명, 감사
증적과 DWP 적합성을 기준으로 선정한 **대표 벤치마크 집합**이다.

| 구분              | 제품                                                                       |
| ----------------- | -------------------------------------------------------------------------- |
| 업무 플랫폼형     | Microsoft Power Automate·Teams Approvals, ServiceNow, SAP, Oracle, Workday |
| 업무 레코드형     | Salesforce, Atlassian Jira Service Management                              |
| 문서·서명형       | Docusign, Adobe Acrobat Sign                                               |
| 프로세스 자동화형 | Nintex                                                                     |

비교는 공개 데모의 외형이 아니라 각 공급사의 공식 제품·관리 문서에 확인되는 동작을
기준으로 했다.

## 2. 결론

DWP가 만들어야 할 것은 그룹웨어식 문서함의 복제품이 아니라 **Enterprise Approval &
Decision Hub**다.

1. 모든 업무 앱의 승인 대기 건을 한곳에서 찾고 판단할 수 있어야 한다.
2. 승인 대상의 원본 데이터는 HRIS·ERP·서비스 요청 등 소유 도메인에 남긴다.
3. DWP는 결재선, 판단 시점의 스냅샷, 결정, 의견, 증적과 후속 반영 상태를 소유한다.
4. 법적 효력이 필요한 외부 서명은 Docusign·Adobe Sign 같은 전문 서비스와 연결한다.
5. AI는 요약·차이·위험·누락 증거를 설명하지만 승인·반려 권한을 대신 행사하지 않는다.
6. 운영 화면은 화려한 대시보드보다 빠르게 비교하고 결정할 수 있는 밀도 높은
   워크벤치가 되어야 한다.

## 4. 공통 프로세스 패턴

### 4.1 시작

- 사용자가 승인 양식을 선택해 기안한다.
- HRIS·ERP·서비스 요청·Agent가 업무 문맥 안에서 승인 요청을 생성한다.
- 기존 외부 결재 시스템의 Task를 Adapter가 DWP 통합 결재함에 투영한다.

### 4.2 제출 전 검증

- 필수 입력, 첨부, 분류 등급과 원본 레코드 버전을 검증한다.
- 자기 승인, 이해상충, 중복 요청과 결재선 순환을 차단한다.
- 금액·조직·직책·지역·데이터 등급에 따라 결재선을 미리 계산해 보여준다.
- 제출 시 양식·규칙·원본 스냅샷의 버전과 해시를 고정한다.

### 4.3 결재 실행

- 순차, 병렬, 혼합 단계를 지원한다.
- `ANY`, `ALL`, `COUNT`, `PERCENT` 정족수를 지원한다.
- 결재, 합의, 검토, 서명, 참조, 확인과 자동화 Step을 구분한다.
- 승인·반려 외에 보완 요청, 정보 요청, 위임, 재지정, 회수와 취소가 존재한다.

### 4.4 후속 반영

- 최종 승인 후 원업무 시스템에 멱등 명령을 전달한다.
- `승인됨`과 `업무 반영 완료`를 다른 상태로 관리한다.
- 원업무 반영 실패는 재시도·보상·운영자 복구 대상으로 남긴다.

### 4.5 증적과 보존

- 누가, 어떤 자격으로, 누구를 대신해, 어떤 버전을 보고 결정했는지 보존한다.
- 의견·첨부·IP·기기·인증 수준·Correlation ID와 결과를 시간순으로 연결한다.
- 결정과 Timeline은 수정·삭제하지 않고 정정 이벤트를 추가한다.
- 법적 서명 결과는 공급사 Envelope ID, 완료 인증서와 문서 Hash를 연결한다.

## 5. UX 비교에서 얻은 설계 원칙

### 5.1 통합 결재함은 Dashboard가 아니라 Decision Workbench다

상단에 큰 Hero나 장식형 KPI Card를 두지 않는다. 사용자는 `무엇을`, `왜 내가`,
`언제까지`, `어떤 위험으로` 판단해야 하는지 빠르게 알아야 한다.

- Desktop: 제품 탐색 + 380~440px Queue + 유동형 Detail의 3단 구조
- Tablet: Queue와 Detail을 전환하되 선택 상태와 Filter 유지
- Mobile: Queue에서 Detail로 진입하고 하단 고정 Action Bar 제공
- 목록 행: 고정 높이, 제목·요청자·업무 앱·현재 단계·SLA·위험을 일정한 순서로 표시
- 상세: 판단 요약 → 핵심 사실·변경 Diff → 문서·첨부 → 결재선 → 의견·증적 순서

### 5.2 행동은 위험도에 따라 다르게 제공한다

- 저위험·동질 항목만 정책이 허용한 범위에서 일괄 승인한다.
- 고위험 항목은 Detail을 열고 필요한 근거를 확인해야 Action이 활성화된다.
- 반려·경로 변경·대리 결정에는 사유를 필수로 받고 확인 Dialog를 사용한다.
- 서버 확정 전 목록에서 완료로 보이는 낙관적 처리를 하지 않는다.

### 5.3 고급스러움은 장식보다 판단의 명료함에서 만든다

- 밝은 중립 Surface, 짙은 Ink, 제한된 Tenant Accent와 의미 기반 상태색을 사용한다.
- 실제 문서 Preview, 구조화된 Diff, 가독성 높은 Timeline을 주 시각 자산으로 사용한다.
- Glass 효과는 Shell의 작은 Overlay에만 제한하고 업무 본문에는 사용하지 않는다.
- 모션은 160~220ms의 상태 전환으로 제한하고 `prefers-reduced-motion`을 존중한다.
- AI 영역에는 `AI 요약`, 근거 수, 최신 시각과 출처를 명확히 표시한다.

## 6. DWP 차별화 방향

| 차별화                   | 내용                                                                             |
| ------------------------ | -------------------------------------------------------------------------------- |
| Cross-app Decision Graph | HRIS·직원 서비스·구매·권한·Agent 실행을 하나의 결재함과 증적 Graph로 연결        |
| Explainable Routing      | 왜 내가 결재자인지, 어떤 조직·직책·정책 버전이 적용됐는지 설명                   |
| Decision Brief           | 원문을 대체하지 않는 출처 기반 요약, 변경점과 누락 증거 표시                     |
| Fulfillment Visibility   | 승인 이후 실제 업무 반영, 실패, 재시도와 보상까지 동일 Timeline에서 확인         |
| Governed Agent Entry     | Agent가 초안·경로 Preview를 준비하되 사람의 명시적 확인으로만 제출·결정          |
| Korea-ready Global Model | 전결·대결·합의·공람을 설정 가능한 역할·정책으로 표현하고 한국식 고정 계층은 배제 |

## 7. 로컬 업무 관행의 글로벌 모델링

| 국내 용어 | DWP 모델                                   | 통제                                            |
| --------- | ------------------------------------------ | ----------------------------------------------- |
| 결재      | `APPROVER` Task                            | 명시적 결정과 인증 수준 저장                    |
| 합의·협조 | `CONSENTER` 또는 `REVIEWER` Step           | Blocking 여부와 정족수 설정                     |
| 전결      | 정책이 지정한 권한자에서 완료              | 적용 규칙과 생략된 단계가 Timeline에 노출       |
| 대결      | `DELEGATE`가 원 권한자를 대신해 결정       | 실제 행위자와 위임자를 모두 저장                |
| 후결      | 긴급 선실행 후 사후 승인하는 예외 Workflow | 별도 권한·기한·경보·사후 검토 필수, 기본 비활성 |
| 참조·공람 | `FYI` 또는 `ACKNOWLEDGEMENT`               | 읽음과 확인을 분리                              |
| 시행·접수 | 원업무 Fulfillment와 수신 확인             | 승인 완료와 구분                                |

## 8. 채택하지 않는 방향

- 전자결재를 HRIS·ERP 하위 메뉴 한곳에 종속시키지 않는다.
- 승인 완료 전에 원업무 DB를 직접 변경하지 않는다.
- 게시된 Workflow·Form Version을 덮어쓰지 않는다.
- 단순 Role 보유만으로 Task 결정 권한을 주지 않는다. 활성 Task 후보·범위·SoD를 함께 검증한다.
- 자동 승인, 자기 승인, Agent 대리 승인을 기본값으로 두지 않는다.
- 감사 목적이라는 이유로 Tenant 관리자에게 기밀 문서 본문 전체 열람권을 주지 않는다.
