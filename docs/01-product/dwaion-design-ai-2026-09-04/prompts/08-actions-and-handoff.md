# U08 · 업무 행동 카탈로그와 계획 검토

DWP 내부 DWAI·ON 화면의 디자인과 상호작용 명세를 작성하라. 기존 글로벌 헤더·사이드바·캐릭터·토큰을 유지한다. 공통 계약 00-common-design-contract.md를 함께 적용한다. 제품 코드는 아직 만들지 않는다.
현재 기능과 확장은 프레임 주석에서 구분한다. 가짜 Live/정확도/분석 진행률, 장식 오로라·글로우, 카드 안 카드, 큰 환영 히어로를 만들지 않는다. 한국어 기본이며 아래 예시는 모두 디자인용 가상 데이터다.

## 목적과 현재

사용자: AI 답변을 실제 업무로 이어갈 구성원. 질문: “무엇이 누구에게 전달되며 어디서 확정하나?” 주 행동: 계획 검토 후 담당 앱으로 이동. Archetype: catalog → review workflow.
경로 /dwaion/actions 및 대화 action shelf. 지원 계약은 일정 생성/메일 초안/서비스 요청/결재 요청이다.

## 세 화면

A. 카탈로그: 가능한 행동, 필요한 권한, 영향과 담당 앱. 현재 허용된 행동만. 개인 테넌트 문맥에 Provider 관리 명령을 섞지 않는다.
B. 검토: 선택 행동, 단계, 실제 입력, 대상, 출처, 누락 필드, 위험과 최종 확정 위치.
C. 인계: 전달 중/검토 앱 열림/문맥 만료/대상 접근 실패. 돌아가서 입력을 다시 확인할 수 있다.

## 중요 내용

- 현재 미리보기는 입력 일부를 길이/개수로 요약한다. 실제 수신자·전체 초안·날짜를 비교하고 수정하는 상세 UI는 필요한 보완이다.
- 현재 초안은 질문/답변을 옮기는 범위다. 참석자·날짜를 정확히 AI 추출했다고 주장하지 않는다. 모르는 값은 비워두고 확인을 요구한다.
- 서버 preview는 REVIEW, mutationAllowed=false. DWAI 내부에서 일정/발송/결재를 확정한 화면으로 만들지 않는다.
- 원본 앱은 초안 자동 저장을 할 수 있다. 초안 저장, 전송/제출, 승인, 업무 완료를 각각 구분한다.
- 인계 상태를 “완료” 토스트 하나로 끝내지 않는다. 수신 확인 및 원본 결과 receipt는 현재 공통 보장 계약이 없으므로 신규 API 필요로 표시한다.
- 제안에서 온 검토와 대화에서 온 검토는 출발 근거가 다르다. 현재 origin은 action-shelf만 지원하므로 제안 origin을 조용히 위조하지 않는다.

## 예시와 상태

메일 초안: 수신자 미지정, 제목 “내일 회의 준비”, 본문 확인, 원본 메일 앱에서 수정/발송. 일정: 시작/종료/시간대 확인.
계획 충돌, 현재 권한 변경, 이중 클릭, 만료, 대상 앱 다운, 초안 저장 성공·제출 실패를 그린다.
“실행 취소”는 보상 API가 있을 때만. 없으면 실제 가능한 수정/철회 경로를 제시한다.

## 반환물

1440px 정상과 390px 모바일, 위 위험 상태 최소 2개를 제공하라. 1280/320px·200% 확대, dark/고대비/reduced motion, 키보드·focus·긴 한/영 문자열 대응을 주석으로 제시한다. 주요 터치 44px, 고정 입력/도우미의 겹침 방지. 클릭→다음 상태→실패 복구를 번호로 연결하고 기존 UI/신규 UI/신규 API/운영 조건부를 구분하라. 정상 그림 한 장으로 끝내지 않는다.
