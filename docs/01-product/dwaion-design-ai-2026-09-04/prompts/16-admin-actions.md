# A04 · 업무 행동과 실행 권한

DWP DWAI·ON의 권한 있는 관리자 화면을 설계하라. 공통 00-common-design-contract.md와 확정한 사용자 홈 디자인 체계를 유지하되 관리 작업에 맞는 정보 밀도를 사용한다. 사용자 메뉴와 별도 관리 표면이며, 관리 권한이 개인 대화 원문 열람 권한을 뜻하지 않는다.
앱 코드는 아직 만들지 않는다. 데이터·명령이 있는 현행 기능과 신규 계약을 주석으로 구분한다. 장식 글로우/오로라, 카드 안 카드, 허구의 Live·정확도·가용률은 금지한다. 예시 값은 가상 데이터다.

## 목적과 현재

사용자: 행동 정책 운영자. 질문: “어떤 행동을 누가 어떤 방식으로 검토해야 하나?” 주 행동: 정책 변경 검토. Archetype: policy matrix + inspector.
경로 /dwaion/admin/actions. 행동 키/이름, 필요한 권한, 위험도, 활성화, USER_HANDOFF/APPROVAL_HANDOFF/BLOCKED를 제공한다. 사용자 확인은 필수다.

## 설계

1. 행은 행동, 담당 앱, 영향/위험도, 필요 권한, 처리 방식, 상태, 정책 버전.
2. 상세에서 읽기/초안/외부 영향의 차이, 사용자에게 보이는 확인 단계, 원본 앱 최종 권위를 명확히.
3. 변경 전후 비교, 사유, 저장 확인, 최신 버전 충돌 복구. UPDATE/MANAGE 권한 분리.
4. APPROVAL_HANDOFF는 업무의 인계 방식이다. 이 정책 설정 변경 자체가 누군가에게 승인받았다는 의미가 아니다.
5. Provider 관리 명령과 tenant 업무 행동은 plane/권한이 다르다. 개인 업무 카탈로그와 같은 목록으로 섞지 않는다.
6. 사용자·상황별 정책 시험과 결과 receipt 연결은 신규 계약 프레임. 정책 시험은 실제 원본 업무 변경 없이 이루어져야 한다.
7. 활성화만으로 실행 가능을 보장하지 않는다. 사용자 권한·운영 Gate·원본 앱 상태가 추가 조건이다.

## 위험 상태

권한 부족, 정책 차단, 대상 앱 미준비, revision 충돌, 저장 실패, 확인할 영향 정보 없음.
“이 권한만 주면 자동 승인/발송 가능” 같은 우회 설명을 금지한다.
