# 현행 분석 · 화면 구성 · 아키텍처 방향

## 1. 결론

DWAI·ON은 DWP의 AI 브랜드이자 권한 안에서 업무를 이해하고 다음 행동으로 연결하는 앱이다. 현재는 **근거 기반 대화 + 검토형 제안함 + 도메인 앱 인계**를 제공하는 단계다. 범용 자율 실행, 지속형 Agent, 실시간 음성 대화가 모두 완성된 제품은 아니다.

고도화의 핵심은 메뉴를 늘리는 것이 아니라 다음 여정을 끊김 없이 만드는 것이다.

`업무 신호 → 질문 또는 제안 → 근거 확인 → 계획 검토 → 원본 앱 확정 → 결과 확인`

이 문서의 평가는 소스 및 계약 검토다. 새 실사용 조사, 침투 테스트, 운영 모델 품질 평가 또는 글로벌 순위 인증이 아니다. UI 시안만으로 글로벌 1위 수준이라고 판정하지 않는다.

대화 상세는 `/dwaion/conversations/:conversationId`로 이어진다. 별도 최상위 메뉴가 아니다. `/ask`는 호환 진입 경로이며 새로운 디자인의 주 URL로 사용하지 않는다.

사용자 작업 표면은 SELF 범위, 관리 표면은 RESOURCE_SET 및 별도 capability 기준이다. 관리자라는 이유로 다른 사람의 대화 원문을 읽는 화면을 설계하지 않는다. 관리 화면은 사용자 메뉴 옆에 무조건 모두 노출하는 구조가 아니다.

## 3. 현행 사실과 과장하면 안 되는 부분

- 홈의 우선 업무는 공통 업무 큐 정렬을 소비한다. 현재 AI가 매 순간 다시 순위를 학습했다는 증거가 아니다.
- 대화 수는 현재 조회 목록 범위다. 프론트 목록은 API 기본 최근 30개를 사용하며 전체 검색·전체 집계를 제공하지 않는다.
- 일반 대화의 선택 소스는 업무 항목/메일/일정이다. 결재 전문 Agent는 별도 결재 소스를 사용한다. 일반 composer에 존재하지 않는 전사·ERP·전체 사내 지식 소스를 임의 추가하지 않는다.
- 현재 사용자 Agent 키는 `DWP_ASSISTANT`, `DWP_APPROVAL_EXPERT`를 중심으로 연결된다. 목록 수나 모델 버전을 시안의 고정 값으로 복제하지 않는다.
- 현재 행동 계약은 일정 생성, 메일 초안, 서비스 요청, 결재 요청 네 종류다. `REDIRECT`/`APPROVAL_HANDOFF`이며 미리보기 응답은 `mutationAllowed=false`이다.
- 제안 수락은 수명주기 결정이다. 메일 발송·결재 승인·일정 초대 완료가 아니다.
- 제안 분석은 사용자가 허용한 상태에서 `지금 분석`을 실행하는 흐름이다. 상시 감시/완전 자동 분석으로 표현하지 않는다.
- 마이크는 짧은 녹음의 STT 후 검토, 읽어주기는 요청형 TTS다. 웨이크워드·백그라운드 청취·끼어들기 가능한 양방향 통화는 별도 개발이다.
- 모델 답변과 근거 기반 대체 응답을 구분한다. 대체 응답도 근거 확인에 유용하지만 LLM 정상 운영 증거는 아니다.
- 실행 이력의 COMPLETED와 원본 앱의 업무 완료는 다르다. end-to-end receipt가 없는 경우 `대상 앱에서 확인`을 사용한다.

관련 구현: `dwaion-home*.tsx`, `dwaion-home-model.ts`, `dwaion-workspace*.tsx`, `dwaion-archive-model.ts`, `libs/shared-utils/src/api/agent-conversation-api.ts`, `libs/shared-utils/src/dwaion-contract.ts`. 모두 frontend 저장소 상대 경로이며 새 파일을 만들 때는 같은 기능 경계를 유지한다.

## 5. 필요한 화면과 메뉴 정책

### 지금 보완할 문맥 화면

1. 답변·근거 작업면: 인용 확인, 후속 질문, 대체 응답과 실패 구분.
2. 제안 검토: 제안 이유·근거·수명·다음 행동·수락/미루기/해제.
3. 행동 미리보기: 입력·대상·위험·단계와 원본 앱 최종 확정.
4. 실행 상세: 발생 시각, 처리 결과, 정책 판정, 원본 결과 확인 여부.
5. 음성 상태와 도우미 확장: 녹음/검토/읽기/종료, 패널과 전체 앱 연속성.

이는 기존 메뉴의 하위 화면이다. 별도 AI 앱을 추가하거나 동일 목적 메뉴를 중복 생성하지 않는다.

## 6. 아키텍처와 UI 계약

`DWP shell → DWAI feature → generated Agent API → Gateway 위임 신원 → Agent 정책/실행 → 원본 앱 PEP → 원본 결과`

위 흐름은 질문·제안·행동 실행 경로다. 에이전트 레지스트리는 별도의 Platform registry API, 업무 큐는 공통 업무 API를 소비한다. 모든 DWAI 데이터가 Agent 서비스 한 곳에 저장된다는 의미가 아니다.

- 프론트: home/studio/archive/proposal/action/run/governance별 모듈. 재사용 상태·폼·대화상자는 design-system. 동일 화면을 전역 도우미에 복제하지 않고 필요한 질문/답변 컴포넌트를 공유한다.
- API: 실제 질문 경로는 `/api/agent/v1/ask`, 대화는 `/api/agent/v1/conversations`, 제안은 `/api/agent/v1/proposals`, 행동은 `/api/agent/v1/actions`. 페이지 가드가 허용돼도 각 요청과 원본 소스 권한은 다시 확인한다.
- 신원: tenant/user/session/plane 및 유효 권한 결속을 유지한다. Provider 운영 문맥에서 일반 tenant용 AI를 임의 렌더링하지 않는다.
- 전달: 질문은 one-time opaque launch를 사용한다. URL/history에 질문 원문을 넣는 디자인·공유 기능을 만들지 않는다.
- 상태: 질문, 제안 결정, 계획 검토, 원본 명령은 다른 상태 기계다. 이를 하나의 녹색 `완료`로 합치지 않는다.
- 결과: 재시도/중복 클릭/응답 유실 때 동일 명령을 중복 실행하지 않도록 idempotency와 revision을 서버 정본으로 사용한다.
- 개인정보: 제안과 실행 로그에 원본 업무 본문을 복제하지 않는다. 원문 확인은 권한 있는 원본 앱 또는 검증된 근거 상세에서 한다.
- 새 기능: API/정책/관측 계약 없는 버튼은 현행 프레임에서 숨긴다. 디자인 탐색 프레임에만 신규로 표시한다.

## 7. 보수적 완성도 판단

| 영역                     | 판정                          | 남은 핵심                                 |
| ------------------------ | ----------------------------- | ----------------------------------------- |
| 홈·질문·보관함 시안 반영 | 기반 있음                     | 최신성/범위/부분 실패의 지속 검수         |
| 근거 기반 답변           | 기반 있음, 운영 조건부        | 실제 모델 품질/연결 및 근거-문장 UX       |
| 제안→실행 여정           | 부분 완성                     | 수락/인계/확정 결과의 연결과 표현         |
| 음성                     | 검토형 입력/출력 단계         | 실시간 양방향 모드는 별도                 |
| 개인 루틴                | 검증 전용 기반 완성           | scheduler·예산·알림·제안 전달 운영 worker |
| 개인 AI 제어             | 저장·보존 경계 완성           | answer runtime 적용·물리 삭제 executor    |
| 개인 결과물              | 편집·버전·개인 게시 기반 완성 | source verifier·조직 DLP·공유·파일 export |
| 팀 결과물/Agent Studio   | 확장 설계 필요                | 공동 편집·공유·평가·게시·롤백             |

완료된 UI 작업과 제품 전체 완성을 혼동하지 않는다. 이 패키지의 목표는 다음 디자인과 구현의 누락을 줄이는 것이며 모든 운영 기능 완료 선언이 아니다.
