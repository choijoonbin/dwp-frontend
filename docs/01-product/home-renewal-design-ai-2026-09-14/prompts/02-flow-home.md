# P02 — Flow Home Renewal

## 전달 계약

**[P00 공통 계약](00-common-contract.md)**을 먼저 읽고 이 프롬프트를 적용한다. standalone 전달은 패키지 README의 `P00 → P02` 합본을 사용한다. 현재 제품의 소스·정책·서비스를 변경하지 않는 디자인 요청이다. 실제 구현된 기능과 새로운 제안, synthetic 데이터와 운영 데이터를 구분한다.

참고: `../assets/approved-my-app-2026-09-14.png`, `../audits/01-home-experience-audit.md`. Classic과 Flow가 공유할 승인 내 앱을 독자적으로 재디자인하지 않는다. 공통 계약의 조직 소식·원본 권위·개인화 보존·접근성은 여기에도 적용된다.

## 사용자·질문·주요 행동

Flow의 사용자는 여러 앱의 요청을 받아 하루의 업무를 선별하는 구성원이다. 핵심 질문은 **“지금 처리할 일과 다음 준비를 어떻게 골라 실행할까?”**다. 주요 행동은 원본 업무의 다음 행동으로 이동하고 일정·응답·대기 상태를 준비하는 것이다. 아키타입은 개인 실행 중심 Daily Work Launch & Triage다.

현재 Flow의 slim Context·독립 내 앱·목적별 위젯에서 실제 데이터와 개인화 기반을 읽되, 기존 화면 순서를 이번 개편의 승인 순서로 취급하지 않는다. 빈 높이·동일 대상 중복·카드 중첩·잘못된 초점 이동을 개선하고 개인 실행을 먼저 드러내는 고급 디자인을 제시하라. Classic은 현재 외형을 보존하지 않고 조직 소식·지식·조직 안내의 편집 포털로 전면 개편된다. **Flow는 다음 행동·시간·응답·내 요청의 개인 실행 위계로 한눈에 명확히 구별되어야 한다.** 이름 제안은 `개인 업무 실행 — 다음 행동과 오늘 준비를 한곳에서`다. 기능·권한·로딩 경계를 생략하지 않는다.

## 승인 내 앱

4카테고리·각 5열×2행·현재 데스크톱 전체 높이·높은 glyph 가시성과 라벨 대비를 PNG 수준으로 유지한다. 배치는 업무 시작 5개 첫 행, 소통과 협업 5+2개(둘째 행 1·2열), 구성원과 서비스 2개 첫 1·2열, 시스템과 통제 4개 첫 1~4열이다. 앱 이름·순서는 PNG/P00 catalog를 따른다. 부분 행의 중심 정렬·카드 폭 전체 재분산은 금지한다.

이 승인 영역의 2행 슬롯 여유는 의도된 보존 계약이다. 본문 위젯은 콘텐츠 적응 높이로 별도 설계한다. pin/folder·숨김·권한 기반 apps·urgent/actionable/unread·관리 entry는 서로 다른 의미를 갖는다. 390/320에서는 그룹 순서를 유지해 세로 reflow하고 touch target·긴 라벨을 보장한다. 좁은 화면의 표시 예산은 전체 앱 경로로 연결하고 데스크톱 순서·숨김을 저장 변경하지 않는다.

## 구성과 역할 분리

전체 의미 순서: `slim 개인 요약 → 승인 내 앱 → compact 필수 확인(있는 경우) → 개인 우선 큐·오늘 시간 → 응답·내 요청 → 보조 현황·시간 계획 → 선택적 일반 소식 brief → 범위/도움 footer`. 일반 사내소식 2~3개를 우선 큐 앞의 고정 지면으로 두지 않는다. 필수 확인은 접근과 마감을 보존하는 짧은 rail이며 항목이 없으면 빈 높이를 만들지 않는다. 1440/1280 첫 viewport에는 다음 행동과 오늘 시간의 시작이 드러나도록 요약·본문 위계를 조율한다.

기본 데스크톱은 8+4 주/보조 위계 또는 그 의미를 더 잘 전달하는 안정된 grid로 제시하라. 우선 업무·오늘 일정·응답·내 요청의 실행 선은 읽기 순서가 분명하고 보조 현황·시간계획은 실제 정보량에 맞는 작은 모듈이다. 사용자 재정렬·숨김이 있으면 의미 없는 기본 grid 강제가 아닌 저장 순서 기반 구성을 보여준다. 위젯 이름만 바꾸어 빈 공간을 채우지 않는다.

낮은 업무량에서는 짧은 빈 상태와 다음 준비 경로로 마무리한다. 모든 카드를 가장 긴 카드 높이에 맞추거나 단 하나의 업무를 긴 가로 막대 안 중앙에 두지 않는다. 타이포·차분한 밝은 surface·작은 의미 색상을 사용하고 body card 안 중첩 card·badge의 반복·장식 gradient/glow·continuous motion은 피한다. 승인 glyph의 외양은 그대로 보존한다.

## 가상 데이터·중복 규칙

디자인 fixture: 김하린 / Harin Kim, 제품운영팀, 2026-09-14 09:58 Asia/Seoul. 아래는 디자인용 가상 데이터이며 실제 현재 숫자로 주장하지 않는다. 데이터 구조/원본/route/permission은 P00을 따른다.

- 3분할 bar: 처리할 업무 5, 오늘 일정 2, 답변 필요 3. 표시 카드의 sample 수와 원본 총수는 다를 수 있으며 총수·현재 표시수·중복 제거 범위를 주석으로 설명한다.
- 필수: 보안팀 “9월 정보보호 교육 확인”, 내일 18:00까지 미확인. 일반: 운영지원 “고객지원 운영시간 안내” 09:20, 인사 “온보딩 프로그램 안내” 어제 16:30.
- 우선: `WORK:W-1042` “파트너 계약 검토안 마무리” 오늘 16:00, `APPROVAL:A-208` “구매 품의 검토” 오늘 15:00, `WORK:W-1051` “출시 점검 자료 준비” 오늘 10:20. 각 row에 담당·마감·원본 next action이 있다.
- 일정: `CALENDAR:E-31` 10:30~~11:00 출시 점검 / `CALENDAR:E-35` 14:00~~14:30 고객 문의 점검. 두 일정의 회의 60분과 실제 calendar 기반 집중 창 11:15~12:00을 구별한다.
- 응답: `MAIL:M-51` 운영 가이드 검토 요청 오늘 13:00, `MESSAGING:T-71` 고객 응대 기준 질문, `SPACE:S-16` 문서 의견 요청. 우선 업무의 A-208을 다시 응답 카드에 넣지 않는다.
- 내 요청: `SERVICES:R-91` 노트북 점검 “담당 배정, 다음 업데이트 내일”. 역할 예외는 가상 권한 있는 TEAM_LEAD 표본에서만 “기한 초과 검토 2건 / 최근 7일”로 제공하며 일반 MEMBER 표본은 다른 유효 내용 또는 영역 미노출을 사용한다.

알림은 소유 원본을 연결하는 이벤트다. 동일 item identity의 업무·결재·응답·협업 사건을 여러 위젯의 별도 할 일로 더하지 않는다. 화면 요약·원천별 상태·derived insight가 다른 범위를 가질 때만 각 라벨로 구분한다. 원본에 없는 정확도·AI 예측·추천 이유를 만들어내지 않는다.

## 인터랙션·전환·편집

1. bar→목적 section 또는 원본 목적 화면. section 진입 시 heading focus/scroll 위치와 sticky shell offset을 명시한다. 숨김/권한 없는 section으로 빈 anchor 이동을 하지 않는다.
2. compact 필수 항목→원본 상세→명시적 확인→홈 복귀. 실행 영역 아래의 일반 소식 brief는 원본 소식으로 이동하며 필수 항목을 복제하지 않는다. 확인 실패·원본 삭제의 복구 행동을 제시한다.
3. 모든 업무 row·전체 보기→scope/filter·return context를 보존하는 실제 원본 화면. 홈은 결재 등 고위험 실행 화면을 대신하지 않는다. 생략 항목에 총수와 추가 접근 경로를 제공한다.
4. 모드 Classic/Flow/신규, 폭 focused/balanced/expressive, 사용자 저장 layout은 독립이다. 선택 가능 모드·조직 기본·개인 현재 선택을 명확히 하며 전환으로 pin/folder·숨김·정렬·폭을 초기화하지 않는다. 신규는 제안이다.
5. 편집 진입→이동/숨김/복원/허용 크기/정보 예산→Undo/Redo→저장/취소. 이동은 drag handle과 메뉴/keyboard로 같은 결과를 낸다. 조직 필수 소식 접근 보존·개인 목적 위젯 설정의 제약을 보여준다.
6. dirty 상태에서 전환·나가기, 저장 중·실패·conflict, 최신 정책 도착 시 초안·기존 성공 레이아웃 보존을 디자인한다. 사용자 구성과 adaptive CSS 표현을 같은 persisted geometry로 저장하지 않는다.
7. initial load는 안정된 skeleton, 자동 background refresh는 성공 데이터 유지·초점/위치 고정. manual retry는 initiating button 상태로만 진행을 표시한다. 마지막 홈 성공 시각은 1곳, 원천별 delayed/unavailable 범위는 해당 섹션에 둔다.

## 모드 차이와 확장 규격

Classic의 편집 뉴스·지식·조직 안내 지면, Flow의 실행 선·책임/시간 모듈, 제3모드 AI Stage의 의도→근거→준비 장면을 같은 계정·원본·첫 viewport로 비교한다. 승인 내 앱은 Classic/Flow의 공통이며 제3모드는 이 영역도 획기적 새 제안이 가능하다. 공통 card grid를 복제하지 않는다. 모드 제목을 가려도 주 행동·타이포·구성으로 구별할 수 있어야 하며 선택기에는 목적 설명·preview·현재 선택·설정 보존을 표현한다.

향후 위젯 등록 규격은 역할·source·permission·지원 모드·정보 예산·모든 상태·원본 이동·반응형·접근성·설정 schema/version을 포함한다. Flow의 새 위젯은 개인 행동·준비·응답·대기 등 구별되는 역할이 있어야 하며 같은 업무의 추가 tile을 양산하지 않는다. gallery에서는 역할·지원 모드·출처·권한·미리보기를 보고 추가하고 이동/숨김/복원·save/conflict 상태를 따른다. 등록 규격은 향후 제안이며 현재 기능 완성을 주장하지 않는다.

## 모든 상태

각 section의 success/0개/1개/예산 초과, initial loading/partial/unavailable/forbidden/stale/background refresh/retry failure를 그려라. 실패를 0·“업무 없음”으로 바꾸지 않는다. 새 권한 거부는 과거 캐시도 노출하지 않는다. 일부 provider unavailable이면 성공 provider의 유효 row와 부족한 범위를 같이 보인다.

앱 0/빈 그룹·folder·99+badge·관리 entry·긴 ko/en 이름, 필수 0/여러 개/기한 지남, 일반 소식 이미지 없음·깨짐, 요약 count와 표본 표시수, 원본 삭제·권한 회수, 오늘 일정 없음·다른 시간대·밤/주말, 집중 계산 일부 원천 누락, 숨긴 bar target, 사용자 재정렬, dirty mode switch, 정책상 Flow 비허용, 저장 오류·conflict를 포함한다.

## 접근성·반응형·프레임

1440×1000, 1280×900, 390×844, 320×720, 실제 browser 200% zoom 및 별도 큰 글자 200%를 제공한다. 모바일 DOM·Tab 순서는 `개인 요약 → 앱 그룹 → compact 필수 확인 → 우선 큐·오늘 시간 → 응답·내 요청 → 보조 현황 → 선택적 일반 소식`이다. 상단 요약에서 개인 실행으로 이동하는 유효한 행동을 제공하고, 모바일에서 승인 앱 그룹이 길어지더라도 일반 소식을 실행 앞에 추가하지 않는다. 900/1200px 경계의 의미 순서·행동·reflow를 주석으로 설명한다. 1920 보조 프레임으로 focused 1280 / balanced 1680 / expressive 2560의 최대 폭 차이를 비교하고 제한 viewport에서 같은 실제 폭인 경우를 정직하게 표현한다. preset 변화는 새로운 정보 모드가 아니다.
