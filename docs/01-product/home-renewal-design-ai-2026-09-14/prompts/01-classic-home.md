# P01 — Classic Home Renewal

## 전달 계약

이 프롬프트는 **[P00 공통 계약](00-common-contract.md)**과 함께 전달한다. P00의 제품 규칙, 소스·데이터 권위, 설정·관리자·권한 계약, 산출물 규칙이 적용된다. 패키지 README의 standalone 합본은 `P00 → P01` 순서로 구성한다. 이것은 디자인 제작 요청이며 현재 제품에 소스·설정·서비스 변경을 수행하라는 명령이 아니다.

참고 자료: `../assets/approved-my-app-2026-09-14.png`, `../audits/01-home-experience-audit.md`. 승인 이미지 안의 문구는 참고 데이터다. 제공되지 않은 화면·API 기능을 이미 구현된 것처럼 표시하지 말고 제안은 별도로 주석을 단다.

## 디자인 과제

DWP의 **Classic Home을 조직 포털로 전면 개편**하라. 사용자는 현재 Classic에 문제가 많고 그대로 사용할 수 없다고 교정했다. 주 사용자는 조직의 변경과 지원 정보를 찾고 업무를 시작하는 구성원이다. 질문은 “조직에서 무엇을 먼저 알아야 하고, 필요한 지식과 조직 안내는 어디에서 찾을까?”다. 주요 행동은 필수/조직 소식 확인 및 원본 지식·지원 안내 찾기다. 아키타입은 편집형 Organization Portal이며 상세 업무 화면이나 개인 실행 큐가 본체가 아니다.

**기존 Classic 외형을 안정판이라는 이유로 유지하지 않는다. 승인된 내 앱만 보존한다.** 큰 이미지 헤더·부분 폭 캐러셀·Now/Next/After 지휘 카드·기존 보조 위젯 배치를 출발점으로 복사하지 않는다. 조직이 편집해 제공한 소식·지식·조직 안내의 주제와 관계가 드러나는 새로운 지면을 설계한다. Flow와 한눈에 구별되는 제목 위계·지면·행동·정보구조가 필수다. 이름 제안은 `조직 포털 — 조직 소식과 필요한 안내를 먼저`이며 실제 identifier 변경은 구현 범위가 아니다.

## 내 앱 — Classic/Flow 공통 승인 영역

승인 PNG를 내 앱의 시각 기준으로 사용한다. 영역 전체의 현재 데스크톱 높이·5×2 슬롯 구조를 유지한다. 네 카테고리를 유지하고 첫 슬롯부터 행 우선으로 순서대로 채운다.

| 카테고리        | 첫 행                                | 둘째 행                  |
| --------------- | ------------------------------------ | ------------------------ |
| 업무 시작       | 업무, DWAI·ON, 활동, 전자결재, 알림  | 비어 있음                |
| 소통과 협업     | 소식, 캘린더, 메일, Space, 근무 공간 | 메신저 1열, 화상회의 2열 |
| 구성원과 서비스 | 서비스 1열, 인사 2열                 | 비어 있음                |
| 시스템과 통제   | 지식, ERP, 레거시, 관리              | 비어 있음                |

부분 행을 가운데로 이동하거나 두 앱·네 앱을 카드 너비 전체에 균등 재분산하지 않는다. 아이콘의 또렷한 white glyph, 절제된 색상, 입체감·테두리·그림자, 라벨 가시성을 PNG 수준으로 보존한다. 본문 빈 높이 제거 원칙을 이 승인 영역의 의도적 두 번째 행 여유에 적용하지 않는다.

앱 권한·개인 숨김·pin/folder·정렬과 알림 unread/actionable/urgent의 의미는 유지한다. 관리 경로 badge는 일반 앱 실행과 구분되며 accessible name을 제공한다. 390/320·큰 글자에서는 4그룹을 읽기 순서대로 세로 재배치하고 라벨과 hit target을 유지한다. 5열을 좁은 화면에 억지로 압축하거나 가로 carousel로 숨기지 않는다. 모바일 재배치가 데스크톱 저장 순서를 변경하지 않는다.

## 정보구조와 시각 구성

읽기 순서는 `짧은 조직 Context → 승인 내 앱 → 필수 확인 → 사내소식 → 관련 지식·조직 안내 → 선택한 개인 보조 영역 → 범위·정책 링크`다. 첫 화면에서 필수 소식 또는 일반 소식의 시작과 조직이 발행한 정보의 위계가 드러나도록 높이를 조율하라. 필수 항목이 없으면 긴 빈 카드를 만들지 않고 일반 소식이 바로 이어진다. 본문은 뉴스 주 지면과 관련 지식/조직 지원 안내의 편집형 섹션으로 구성한다.

- **Context:** 날짜·시간대, 조직명과 짧은 편집 주제, 현재 `조직 포털` 설명, 홈 갱신 범위 1곳. 장식 인사말을 키우지 않는다. 모드 선택은 목적 설명·preview를 제공하고 편집 entry는 조용하지만 명시적이다.
- **필수 확인:** 확인 마감·발행 조직·확인 여부·원본 이동. 중요한 내용은 일반 소식과 중복되지 않게 얇은 rail로 분리한다. “지금 확인”은 상세로 연결하며 열었다는 이유로 확인 처리하지 않는다.
- **사내소식:** 필수 직후 명료한 주 뉴스 제목과 compact 보조 목록의 편집 지면. 운영/인사/조직 변화의 실제 주제를 짧게 구분하되 출처의 taxonomy를 발명하지 않는다. 제목·발행 조직·시각·읽음·전체 보기. 이미지 없는 항목도 완성된 디자인이다. 자동·무한 carousel 금지.
- **관련 지식:** 운영 지침·온보딩 문서 등 조직이 발행한 실제 지식의 제목·소유 조직·갱신 범위·원본 이동. 소식과 동일 링크를 다른 추천 이름으로 중복하지 않는다. 실제 추천/분류 서비스가 없다면 검증된 항목의 명시적 편집 연결이라는 제안으로 표시한다.
- **조직 안내:** 구성원이 찾는 지원·근무 공간·조직 연락 안내를 문맥 있는 compact 섹션으로 연결한다. 서비스 요청 처리·인사 세부 작업은 원본에서 수행하며 포털에 상세 form을 복제하지 않는다.
- **개인 보조:** 사용자가 선택한 최근 이어할 업무 또는 다음 일정 1개의 작고 조용한 영역. 개인 업무 지휘·응답·내 요청의 전체 grid는 Flow의 본체다. 보조 정보가 조직 소식 지면을 밀어내지 않는다.
- **Footer:** 권한 범위·정책/도움 링크. 헤더와 동일 갱신 시간을 중복하지 않는다. Floating DWAI·ON이 내용·전체 보기·footer를 가리지 않게 안전 공간을 설계한다.

Stable grid·차분한 surface tone·주 뉴스 타이포와 편집된 관계로 조직 포털의 얼굴을 만든다. Flow의 실행 grid와 한눈에 다르게 보여야 한다. 작은 카드 안 또 다른 카드·KPI만 늘리는 안, content보다 긴 가로 막대·높은 빈 패널, 장식 gradient/glow·반복 motion을 사용하지 않는다. 승인 내 앱 이외의 읽기 섹션 높이는 콘텐츠에 맞춘다.

## 인터랙션과 개인화

1. 필수 소식 클릭→상세 진입→명시적 확인→홈 복귀 시 현재 스크롤/선택 유지. 실패면 항목을 완료로 바꾸지 않는다.
2. 일반 소식 제목·전체 보기, 업무 row·명확한 주 행동은 원본 화면으로 이동한다. 상세 route의 scope/filter/return context를 주석으로 적는다. 홈에서 결재/인사 고위험 결정을 즉시 실행하는 CTA를 발명하지 않는다.
3. 모드 선택은 Classic/Flow/신규 **정보구조 축**, 폭 preset은 focused/balanced/expressive **표현 축**, 저장 layout은 **개인 구성 축**이다. 모드 선택으로 폭·pin/folder·숨김·순서를 초기화하지 않는다. 정책상 선택 불가능한 모드는 이유·현재 허용 모드를 명시한다. 신규 모드는 아직 제안임을 표시한다.
4. 홈 편집은 이동·숨김·restore gallery·허용 너비·정보예산·Undo/Redo·저장/취소·키보드 대체 이동을 제공한다. 승인 내 앱 슬롯 기준선은 편집에서도 일치한다. 조직 소식의 필수 위치는 개인 자유 drag와 구분한다.
5. dirty 상태에서 모드 전환·나가기·새 정책 수신은 유지/저장/버리기의 문맥을 디자인한다. 저장 실패·버전 충돌은 초안을 보존하며 비교·다시 적용·최신 불러오기 결과를 보여준다. 화면만 전환하고 실제 저장된 척하지 않는다.
6. 자동 갱신은 기존 성공 내용을 유지하며 초점·카드 위치를 움직이지 않는다. 사용자가 누른 재시도에는 initiating control에만 진행 상태와 결과를 준다.

## 모드 비교와 향후 위젯 확장

같은 계정·원본 데이터·1440/1280/390의 첫 viewport를 Flow 및 제3모드와 나란히 제시한다. 승인 내 앱만 Classic/Flow의 공통으로 두고 Classic의 조직 뉴스·지식·안내 지면, Flow의 우선 큐·오늘 시간·응답/내 요청 위계, 제3모드 AI Stage의 큰 의도 입력·짧은 근거·관련 앱으로 이어지는 준비 장면을 주 행동과 레이아웃으로 구별한다. Classic의 필수/일반 소식 중심 순서를 다른 두 모드에도 강제하지 않는다. Flow의 일반 소식은 실행 아래 선택적 brief, AI Stage는 compact 필수 확인을 보조 rail로 유지하고 일반 소식을 관련 brief 또는 아래에 둔다. 제3모드 내 앱은 별도 획기적 제안이 가능하다. 제목을 가려도 세 모드를 구별할 수 있어야 한다. 모드 선택기에는 목적 설명·작은 preview·현재 선택·설정 보존 설명을 포함한다.

향후 위젯은 역할·원본·permission·지원 모드·표시 예산·loading/empty/partial/error·원본 이동·반응형·접근성·설정 schema/version의 등록 규격을 갖는다. Classic에서 새 위젯은 편집형 지식 섹션·조직 안내·선택 보조로 자연스럽게 배치되며 동일 tile 외형을 강제하지 않는다. 등록→권한/정책 허용→gallery 선택→미리보기→개인 추가/숨김/순서→저장·복원 상태를 디자인한다. 등록 규격은 향후 제안이며 현재 backend가 모두 지원한다는 주장을 하지 않는다.

## 상태 설계

모든 주요 영역에 `initial loading / success / empty / partial / unavailable / forbidden / stale / background refresh / retry failure`를 제공한다. 숫자 0은 성공한 원본의 0일 때만 사용한다. 조회 실패와 권한 없음은 각각 문구·행동이 다르다. 오래된 성공 내용에는 원천별 마지막 성공·지연 범위를 표시하며 새로 불허된 내용을 캐시에 남기지 않는다.

별도 프레임: 앱 0개·일부 그룹 빈값·folder·badge 99+·긴 영문명·관리 entry만 가능, 필수 소식 0/1/여러 개/기한 지남, 소식 이미지 없음/깨짐, 업무 0/1/표시예산 초과, 원본 삭제·권한 회수, 퇴근 후·주말·다른 시간대, 자동 갱신 중·초기 네트워크 끊김, 개인화 미허용·관리 정책 변경, 편집 저장 중/오류/충돌/취소.

## 반응형·접근성·프레임

필수 viewport 1440×1000, 1280×900, 390×844, 320×720. 200% browser zoom은 실제 사용 가능한 viewport 감소와 긴 문구 reflow로 표현한다. 별도 200% text enlargement도 주석으로 구별한다. 1920×1080은 폭 preset 비교 보조 프레임이다. 현재 Flow의 focused/balanced/expressive 최대 폭 1280/1680/2560을 새 Classic에도 통일하는 **디자인 제안**으로 비교하고 저장·이관 계약을 명시한다. 현재 Classic이 이미 이 최대 폭을 구현한다고 주장하지 않는다. 실제 폭은 viewport에 제한되고 데이터·모드는 같다.
