W/A/E/I/G 화면군이 크면 프롬프트 안의 ID별 소그룹으로 나눠 전달한다. 한 화면군 내부 누락을 홈 이미지 한 장으로 대체하지 않는다. 신규 교차 앱 데이터 의미는 H1부터 확인하고 X 단계에서 세부 확장 프레임을 완성한다. 제3 모드 채택 여부와 새 기능 구현 범위는 반환 결과·사용자 결정에 기록한다.

## 요청마다 붙일 내용

공통 계약과 화면군 프롬프트, 승인 내 앱 PNG, 필요한 현재 분석, 앞 단계 채택 디자인, 해당 화면의 source·menu 계약을 전달한다. 외부 디자인 AI는 로컬 경로를 읽을 수 없으므로 문서 내용을 업로드하거나 복사한다. 상대 경로로 다른 문서를 읽으라는 지시만 보내지 않는다. `ready-to-send` 파일은 공통 계약과 화면군 본문을 합친 복사용 문서다. 홈에는 추가로 현재 분석 문서를 함께 전달한다.

위 분류·API·기술 ID는 디자인 프레임 밖 주석에 둔다. 정상 예시는 가상 데이터로 채우고 source 실패·권한 부족·미연결은 별도 상태로 반환한다.

## 검토 Gate

**D0 근거:** 이 패키지는 현재 소스 감사다. 관련 파일과 설정은 구현 직전에 다시 확인한다. 다른 앱의 동시 변경을 되돌리거나 과거 테스트를 새 PASS로 사용하지 않는다.

**D1 홈 구별:** 내 앱을 제외한 첫 viewport에서 Classic의 조직 콘텐츠 중심과 Flow의 개인 실행 중심이 구분되는가? 대표 사용자에게 각각 무엇을 먼저 클릭할지 설명받을 수 있는가? Classic은 전면 재설계됐는가? 앱 그룹·이름·배지·두 줄 순서가 승인 기준을 따르는가? 의미와 주 행동이 같고 배경만 다른 시안은 수정한다.

**D2 확장·편의:** 처음 보는 위젯을 검색→미리보기→추가→설정→배치→저장할 수 있는가? 키보드·터치 대안, 중복/미연결 안내, 크기별 정보량, 지원 종료·버전 변경·이관·복원, 필수 조직 구역과 개인 구역, 느린 source의 부분 로딩이 설계됐는가? 기존 보기 데이터가 모드 변경으로 손실되지 않는가?

**D2A AI Stage:** AI가 단순 링크나 채팅 장식이 아니라 의도·근거·준비·실행 연결의 중심인가? Classic/Flow와 첫 화면·대표 흐름이 확연히 다른가? 문맥 장면 전환·직접 조작·빠른 피드백과 reduced-motion·포커스 안정 대안이 같은 효용을 제공하는가? 현재 reference-only REVIEW 계획과 새 owner 행동이 구분되는가? 근거 없음·취소·partial·권한 철회·step 실패/결과 불명에도 복구와 이어하기가 명확한가?

**D3 모든 메뉴·상태:** [메뉴 인벤토리](contracts/account-admin-menu-inventory.md)의 계정 8개·관리 24개와 legacy audit route를 프레임/상세/탭 ID에 대응한다. 실제 도메인 관리자 redirect는 기존 원본으로 연결한다. 홈 설정 전체 목록과 신규 위젯 계약도 대응한다. 관련 S01~S15 상태·긴 문자열·모바일·확대·초점·권한·409·결과 불명 누락을 확인한다.

P12 X01~~X18 및 P13 N01~~N11도 같은 대응표에 포함한다. 신규 메뉴/앱은 기존 구현처럼 기록하지 않고 채택·기능 owner·실제 API 필요·운영 조건을 명시한다. 앱별 메뉴 추가가 필요한 경우 생략하지 않고 현재 route·확장 탭·새 route를 구분한다.

**D4 원본 무결성:** 다운로드 파일별 SHA-256, 크기, frame/revision 매핑을 manifest로 보존한다. 빈 파일·깨진 이미지·중복 프레임·모바일 반폭 export·원본 접근 실패를 확인한다. 캡처만 있는 프레임은 캡처 기준임을 명시하고 편집 원본이 있다고 주장하지 않는다.

**D5 시스템 반영:** 확정된 디자인과 실제 owner 계약을 기준으로 작은 화면군 단위 구현한다. 새 위젯 API·schema·migration·등록/철회·permission이 필요하면 해당 기능과 함께 설계·구현한다. 실제 데이터·설정·권한·명령은 네이티브 owner를 사용하고 mock 디자인용 데이터를 운영에 심지 않는다. 전역 mode 활성 조건과 tenant effective mode를 구분한다.

**D6 검증:** 변경에 필요한 type/build/기존 회귀와 실제 UI 확인을 수행한다. 1440/1280/390/320·200%·light/dark·ko/en·키보드, 위젯 중앙 wheel/touch 문서 스크롤, 모드 차별성과 배치 보존, 개인화 저장/복원/409, 권한 회수·identity 전환·partial/stale·deeplink를 확인한다. 신규 명령은 중복 제출·실패·결과 불명·owner 복구를 실제 계약으로 검사한다. 실행하지 않은 항목은 PENDING이다.

## 구조 수정과 구현 마감

디자인으로 되돌릴 항목은 모드 목적·메뉴/정보 구조·주 흐름·위험 변경·모바일 구조·데이터 의미의 모순이다. 토큰 매핑·간격·레이블·실제 바인딩·ARIA·세부 상태는 채택 원본 의도와 시스템 계약을 맞춰 구현한다. 구조 결함을 반복 제한 때문에 방치하지 않는다. 다른 프로젝트의 “주 시안 1회+수정 1회” 상한은 이번 사용자 요청에 적용하지 않는다.

## 100% 반영의 의미와 추적표

목표는 반환·채택한 디자인의 모든 지정 프레임과 상태·행동을 시스템에 반영하는 것이다. 단일 데스크톱 스크린샷의 픽셀 유사성만으로 완료하지 않는다. 각 행에 다음을 기록한다.

| Design ID/revision | 원본 파일/hash    | 실제 route/surface | 데이터/명령 owner | 구현 파일    | 상태/크기       | 검증 근거   | 차이·사유·결정     |
| ------------------ | ----------------- | ------------------ | ----------------- | ------------ | --------------- | ----------- | ------------------ |
| 반환 후 작성       | 원본 확보 후 작성 | 실제 등록 경로     | CURRENT/확장 계약 | 구현 후 작성 | S01~S15 중 적용 | 재실행 결과 | 미정은 숨기지 않음 |

원본·계약·모바일·상태가 미정이면 해당 항목은 완료로 표시하지 않는다. 접근성·권한·반응형에 필요한 native 조정은 원본 의도를 보존하며 차이를 추적한다. 현재 단계는 의뢰 준비이고 디자인 구현은 아직 시작하지 않았다.
