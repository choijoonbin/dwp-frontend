## 1. 결정 요약

DWP의 로그인 첫 화면은 앱 아이콘만 나열하는 포털도, Today Widget만 나열하는
Dashboard도 아니다. 사용자가 권한을 부여받은 업무 공간을 즉시 인식하고 실행한 뒤,
같은 화면에서 오늘 처리할 업무와 AI Brief를 확인하는 **개인화 Work Entry**로 만든다.

첫 화면의 정보 계층은 다음 순서로 고정한다.

1. **Assigned Apps**: 역할·권한별 Native·Legacy·SaaS 앱의 목적별 그룹과 빠른 실행
2. **Today**: 마감 업무, 승인, 요청, 일정, 중요 커뮤니케이션과 AI Daily Brief
3. **Apps Catalog**: `/apps`에서 검색, 상태·소유자 확인과 전체 앱 관리

WEHAGO 참고 화면의 권한 기반 앱 제공, 목적별 그룹과 일관된 Global Shell은 유효한
출발점이다. DWP는 이를 복제하지 않고 앱 실행과 시스템 간 Action Hub를 한 Home에
연결한다. 앱 그룹은 관리자가 정의한 의미 체계를 유지하고 사용자는 그 안에서 순서와
폴더를 개인화한다. 개인화는 자유로운 화면 꾸미기가 아니라 권한, 역할, 명시적 선호와
설명 가능한 추천을 조합한다.

## 2. 참고 화면에서 얻은 시사점

사용자가 제공한 WEHAGO 로그인 후 개인 화면과 거래처관리 화면을 기준으로 다음을
분석했다.

### 2.1 유지할 강점

- 사용 권한이 부여된 앱을 로그인 직후 확인하고 바로 실행할 수 있다.
- ERP, 소통, 나의 앱처럼 앱을 목적별로 묶어 인지 부담을 낮춘다.
- 일정, 게시판, 뉴스와 Timeline을 개인 업무 시작 화면에 배치한다.
- 포털에서 업무 앱으로 이동해도 Global App Rail과 Header가 유지된다.
- 업무 앱 내부는 Module Navigation과 List·Detail 중심의 높은 정보 밀도를 쓴다.

### 2.2 그대로 채택하지 않을 한계

- 앱 선택이 출발점이면 System Silo와 화면 전환 비용이 그대로 남는다.
- 동일한 시각 비중의 Widget이 많아지면 지금 가장 중요한 업무가 묻힌다.
- 뉴스, 배너와 빈 Widget이 첫 화면의 핵심 면적을 차지할 수 있다.
- 사용자가 직접 배치한 정적 Portal은 역할·마감·업무 맥락 변화에 늦게 반응한다.
- 앱 안에서 발생한 승인, 요청과 후속 조치를 다시 Home에서 통합하기 어렵다.
- AI가 추천한 이유, 사용한 근거와 실행 전 검토 절차가 화면 계약으로 보이지 않는다.

따라서 앱 Launcher를 로그인 후 첫 상호작용 계층으로 올리되 전체 Home을 정적 아이콘
보드로 만들지 않는다. Launcher 다음에 Today를 붙여 앱을 알고 들어가는 업무와 여러
앱에 흩어진 Action을 한곳에서 처리하는 업무를 모두 지원한다.

### 3.1 시장 방향에 대한 판단

최근 경쟁축은 `개인화 포털`에서 `개인화된 업무·행동 계층`으로 이동했다. 앱과
Widget은 여전히 필요하지만 차별점은 다음에 있다.

- 사용자가 지금 처리할 항목을 시스템 경계 없이 모으는 능력
- 역할, 마감, 영향도와 선호를 함께 반영하는 설명 가능한 우선순위
- 검색·요약에서 Form, 승인과 실제 실행으로 이어지는 연속성
- 원본 시스템 권한, 최신성, 근거와 감사 이력을 보존하는 능력
- 관리자 통제와 사용자 자율성을 충돌 없이 조합하는 Personalization Policy

DWP가 일반 그룹웨어 Suite를 다시 만들거나 자유 배치형 Widget Marketplace를
핵심 제품으로 삼으면 글로벌 제품과의 기능 수 경쟁에 빠진다. DWP의 경쟁력은
기존 Suite와 Legacy를 교체하지 않고, 그 위에 일관된 업무·AI·통제 경험을 만드는
데 있다.

## 4. 목표 Information Architecture

### 4.1 Shell 경계

로그인 직후 `/`는 Sidebar가 없는 **Personal Home Shell**을 사용한다. 상단 Header에는
Tenant Logo와 DWP Product Mark의 공동 Lockup, Workspace, Global Search, Language,
Notification과 사용자 이름·직책·Avatar를 제공한다. 앱을 실행한 `/work`, `/ask`,
`/activity`, `/apps`, `/admin` 등의 업무 Route에서만
Sidebar가 있는 **Business App Shell**을 사용한다. Product Mark와 Account Menu의 `Home`은
항상 `/`로 돌아가며 이때 Sidebar도 함께 제거된다.

두 Shell이 공유하는 Header 계약은 다음과 같다.

| 영역         | 필수 요소                                                   | 원칙                                               |
| ------------ | ----------------------------------------------------------- | -------------------------------------------------- |
| Workspace    | 현재 Tenant·Workspace, 역할 또는 대리 사용 상태             | Sample 고객명을 하드코딩하지 않는다.               |
| Global Ask   | 통합 검색, 질문, 명령과 최근 Context                        | Desktop에서는 Header의 핵심 Control로 둔다.        |
| Quick Create | 업무·요청 생성 등 권한 기반 Command                         | 단일 `+` Command와 검색 가능한 Menu를 사용한다.    |
| Notification | 중요 알림, 멘션, 승인과 System 상태                         | 숫자 Badge보다 우선순위와 읽음 상태를 명확히 한다. |
| Account      | Profile, Preferences, Theme, Accessibility, Session, Logout | 낮은 빈도 설정과 Mobile Language를 통합한다.       |

Desktop Business Navigation은
`Work`, `Ask`, `Activity`, `Apps`에서 시작해 R1 이후 `Inbox`, `People`, `Services`,
`Knowledge`, `Agents`를 목적 중심으로 확장한다. `Admin`은 앱 Entitlement와 Route
Guard를 모두 통과한 사용자에게만 Home Launcher와 Account Menu에서 보인다. `Today`는
Home의 정보 계층이며 별도 Sidebar 메뉴로 중복하지 않는다.

### 4.2 Home

Home의 순서는 앱 실행과 하루 시작의 두 사용 패턴을 함께 지원한다.

1. **Assigned Apps**: Entitlement로 필터링된 목적별 앱 그룹과 사용자 폴더·순서
2. **Important Announcements**: 대상·기간이 적용된 필수 조직 공지와 Action
3. **Daily Brief**: 오늘의 핵심 상황, 추천 순서, 근거와 갱신 시각
4. **My Work**: 마감 업무, 승인, 요청과 사람 확인이 필요한 Agent 결과
5. **Schedule**: 오늘 일정, 준비 자료, 충돌과 후속 Action
6. **Recommended Actions**: 사용 가능한 서비스, 다음 단계와 최근 반복 업무
7. **Optional Widgets**: 사용자가 선택한 보조 정보

앱 그룹은 Tenant 관리자가 App Registry에서 정의한다. 사용자는 그룹 간 의미를
바꾸지 않고 그룹 안에서 앱·폴더 순서를 조정하고 폴더 이름을 변경할 수 있다. 앱을
다른 앱의 중앙 Drop Target에 놓으면 폴더가 생성되며 `Customize` 메뉴로도 동일한
작업을 수행할 수 있어 Drag 동작에 의존하지 않는다.

빈 Section은 큰 Empty Card로 공간을 유지하지 않는다. 필수 설정이나 오류가
아니면 접거나 숨기고, 처음 사용할 때만 짧은 Empty State와 다음 행동을 제공한다.

### 4.3 Apps

Apps는 WEHAGO식 권한 기반 Launcher의 장점을 확장한다.

- `Pinned`, `Recent`, `Assigned`, `All` View
- 업무 목적과 소유 부서 기반 Category 및 검색
- 사용 권한, 점검 상태, 외부 이동 여부와 지원 Contact 표시
- 즐겨찾기, 순서 조정과 숨김
- 권한 요청이 허용된 앱은 요청 Flow로 연결
- 관리자가 고정한 필수 앱과 사용자가 고정한 앱을 구분
- Mobile에서는 앱 Group을 가로 스크롤로 숨기지 않고 검색 가능한 List·Grid 제공

앱 실행 유형은 다음 세 가지로 제한한다.

| 유형          | 사용 조건                                | 이동 계약                                                      |
| ------------- | ---------------------------------------- | -------------------------------------------------------------- |
| Native        | DWP가 직접 소유한 업무 경험              | Route 이동, Global Shell·Return Context 유지                   |
| Embedded      | 보안·접근성·반응형 검증을 통과한 승인 앱 | Sandbox, Origin·Permission 정책, 실패 시 원본 링크             |
| SSO Deep Link | 외부 SaaS 또는 Legacy 앱                 | 새 창 여부 사전 표시, SSO, 목적 화면 Deep Link, 복귀 상태 유지 |

임의 iframe과 화면 Scraping은 기본 통합 방식으로 사용하지 않는다. API가 없는
Legacy의 RPA는 승인된 최소 범위와 감사가 있을 때만 별도 Action으로 제공한다.

## 5. Personalization Policy

### 5.1 적용 우선순위

개인화 결과는 다음 순서로 결정한다. 위 단계는 아래 단계가 덮어쓸 수 없다.

1. Security, Entitlement, Legal Hold와 필수 정책
2. Tenant, 조직, 역할, 지역, 언어와 Device 정책
3. 사용자의 Pin, Hide, Reorder, 관심 Topic과 알림 선호
4. 마감, 일정, 업무 영향도와 현재 Context
5. 최근·빈번 사용, 완료·무시·해제 행동
6. AI 추천과 탐색적 제안

AI 추천은 항상 다음 Control을 제공한다.

- `왜 표시되었나요` 설명
- 숨김, 추천 해제 또는 같은 유형 줄이기
- 개인화 기록과 선호 초기화
- 관리자가 강제한 항목과 추천 항목의 시각적 구분
- 민감정보 사용 범위와 개인화 데이터 보존기간 확인

### 5.2 추천과 우선순위 원칙

초기 R1은 검증 가능한 규칙 기반 우선순위를 기본으로 한다.

```text
priority = deadline + businessImpact + approvalBlocking + explicitPin
           + assignedRole + recency - dismissed - completed
```

ML 또는 LLM이 순위를 보조하더라도 권한을 확대하거나 필수 항목을 숨길 수 없다.
개인 성과 평가, 감정 추론, 비공개 건강정보와 과도한 행동 감시는 개인화 입력으로
사용하지 않는다. 추천 품질은 클릭률보다 업무 완료, 숨김·거부, 잘못된 추천과
절감시간으로 평가한다.

## 6. Widget 및 App Registry 계약

Home을 Feature별 JSX 조각의 집합으로 만들지 않는다. App과 Widget은 Registry와
Versioned Manifest를 통해 등록한다.

| 필드                         | 내용                                     |
| ---------------------------- | ---------------------------------------- |
| `id`, `version`              | 변경 불가능한 식별자와 계약 버전         |
| `titleKey`, `descriptionKey` | 번역 Key와 짧은 업무 목적                |
| `owner`, `supportContact`    | 업무·기술 소유자와 지원 경로             |
| `category`, `tags`           | 검색과 분류 Metadata                     |
| `entitlements`               | 필요한 Role, Permission, Feature Flag    |
| `launchType`, `target`       | Native, Embedded, SSO Deep Link와 목적지 |
| `sizes`, `responsive`        | 승인된 Widget 크기와 Mobile 대체 View    |
| `dataContract`               | API, Cache, Freshness, Empty·Error 상태  |
| `privacyClass`, `retention`  | 표시 데이터 등급과 보존 정책             |
| `analytics`                  | 노출, 실행, 완료와 실패 Event            |
| `availability`               | 정상, 점검, 제한, 폐기 상태              |

AI가 Home 구성을 제안할 때도 Registry에 등록된 Component와 허용 Layout
Schema만 조합한다. 임의 HTML·JSX 생성과 미검증 외부 Widget 삽입은 금지한다.

### 6.1 R1 Reference 경계

- APP Permission이 아직 Seed되지 않은 개발 DB에서는 Admin Role을 제외한 Reference App을
  호환 모드로 제공한다.
- APP Permission이 한 건이라도 있으면 Home, Sidebar, Catalog와 Route Guard가 정확한
  Resource Grant를 동일하게 적용한다.
- 순서, 폴더와 Widget 선호는 `usr_home_preferences`의
  `(tenant_id, user_id, surface_key)`별 Versioned JSONB에 저장한다. `workspace-home`,
  `hris-home`처럼 앱별 설정과 Version을 분리하며 실행 코드나 업무 데이터는 저장하지 않는다.
  서버는 Payload 크기, 구조, 등록 Widget, 허용 크기, Folder 수와 필수 Widget을 검증하고
  Frontend는 현재 App Registry·Entitlement로 App ID와 역할별 Widget을 다시 조정한다.
- 공통 Personal Home Composer는 순서, 표시, 승인된 `compact·medium·large·full` 의미 크기와
  `balanced·expressive·focused` 표현 모드를 제공한다. Mobile에서는 의미 크기와 관계없이
  단일 열로 재배치하고, Reduce Motion 선호에서는 비필수 Transition을 제거한다.
- Local Storage는 서버 연결 전 호환·복구용 App Layout Fallback으로만 사용하며 업무 데이터,
  메일, AI Prompt는 저장하지 않는다.
- Tenant별 Home 배경, 문구, 위치와 가독성 Overlay는 Platform Admin 데이터로 관리한다.
  파일 본문은 저장소 Port에 두고 DB에는 Key, MIME, 크기, 해시, 해상도, 버전과 감사정보만
  저장한다. 개발 환경은 Tenant 경로로 격리한 Local Storage를 쓰고 운영은 같은 Port의 S3
  구현으로 전환한다.
- Tenant 회사명·Logo는 별도 Branding Aggregate로 관리하고 DWP Product와 공동 표시한다.
- 공지는 Draft·Published·Archived Lifecycle, 역할 대상과 게시기간을 적용한다. 공지는 관리형
  Widget이며 사용자가 숨길 수 없다.

## 7. AI 경험 계약

R1의 AI는 Home에서 다음 범위만 담당한다.

- 일정, 메일, 업무와 공지의 Daily Brief
- Action Item 후보와 관련 원본 링크
- 마감·영향도·선호에 근거한 우선순위 제안
- 사용 가능한 Service와 App 추천
- 사용자가 선택한 항목의 요약과 초안

모든 AI 결과에는 생성 시각, 사용한 Source 범위, 누락·실패한 Connector와 원본
Link를 제공한다. AI가 만든 업무 후보는 사용자가 확인하기 전 Work나 외부
시스템에 생성하지 않는다. R3의 Agent Action은 Plan Preview, Risk Tier, 승인,
Execution Timeline과 취소 계약을 통과한 뒤 Home에 노출한다.

## 8. Responsive Experience

### Desktop

- 1280px 이상에서는 Assigned Apps 전체와 Today 시작점을 첫 Viewport에서 함께 보인다.
- 비교와 반복 처리를 위해 Compact·Standard Density를 지원한다.
- Detail은 우측 Context Panel로 열되 Main Work를 가리지 않는다.
- Apps는 안정적인 Tile 크기와 List 전환을 제공한다.

### Mobile

- Header와 Drawer에서 `Work`, `Ask`, `Activity`, `Apps`를 핵심 목적지로 둔다.
- Assigned Apps는 의미 그룹별 가로 Snap 영역으로 제공하되 다음 Group의 일부를 보여
  탐색 가능성을 알리고, `All apps` 검색 경로를 항상 함께 제공한다.
- 첫 화면은 Brief 전체보다 처리할 상위 항목과 승인·알림을 우선한다.
- 긴 Widget Dashboard를 축소하지 않고 Section별 List와 전체 화면 Detail로 바꾼다.
- 320px 폭, Safe Area, 200% Zoom과 긴 한국어·영문 Workspace명을 검증한다.

## 9. R1 MVP 범위

### 포함

- 통합 Home의 권한 기반 Assigned Apps와 별도 Apps Catalog
- 그룹 내 Reorder, 폴더 생성·이름 변경·해제와 사용자별 Personalization Reset
- 사용자 Home Editor의 Widget 표시·순서·제한 크기·표현 모드, 관리형 공지와 Tenant
  Co-branding
- 규칙 기반 Daily Brief와 My Work 우선순위
- 일정, 승인·요청, 중요 공지의 최소 Connector Fixture
- Pin, Hide, Reorder와 Personalization Reset
- 추천 이유, 데이터 갱신 시각과 원본 링크
- Native·SSO Deep Link 실행과 복귀 Context
- Desktop·Mobile, Light·Dark, 한국어·영문과 WCAG 2.2 AA 기준

### 제외

- 자유 크기 조절이 가능한 범용 Portal Builder
- 광고, 일반 뉴스와 업무 무관 콘텐츠 Feed
- DWP가 직접 만드는 메일 서버, 범용 Messenger와 화상회의 엔진
- 사용자 확인 없는 AI 자동 실행
- 등록되지 않은 Generative UI와 외부 Widget
- 개인 성과를 추론하거나 감시하는 Personalization

## 10. 수용 기준과 KPI

| 영역            | R1 수용 기준                                                    |
| --------------- | --------------------------------------------------------------- |
| Relevance       | 사용자의 권한 밖 앱·업무 노출 0건, 필수 업무 누락 0건           |
| Time to Work    | 로그인 후 우선 업무 확인까지 중앙값 30초 이내                   |
| Navigation      | Pilot 핵심 Journey의 시스템·화면 전환 수 30% 이상 감소          |
| Completion      | Today에서 시작한 대상 업무 완료율과 완료시간 Baseline 대비 개선 |
| Trust           | Daily Brief Source Coverage 95% 이상, 갱신 실패 명시 100%       |
| Personalization | 추천 숨김·거부 사유를 수집하고 같은 오류 유형 반복률을 추적     |
| Accessibility   | 핵심 Journey 자동 Axe 중대 위반 0건과 Keyboard 수동 Gate 통과   |
| Performance     | 실제 Pilot 데이터에서 Home LCP 목표와 API P95 예산 충족         |

클릭률과 Widget 추가 수는 보조 지표로만 사용한다. North Star는 Home 소비가 아니라
권한과 정책을 준수해 완료된 업무 결과다.

## 11. Design Partner 검증 질문

1. 직원이 업무 시작 시 가장 먼저 확인하는 시스템과 정보는 무엇인가?
2. 놓쳤을 때 가장 큰 비용이 발생하는 승인, 요청, 일정과 공지는 무엇인가?
3. 개인이 숨기거나 재정렬할 수 없는 규제·운영 항목은 무엇인가?
4. 앱 권한은 어떤 원장에서 결정되고 변경 전파에 얼마나 걸리는가?
5. 외부 앱 이동 후 사용자가 원래 업무로 돌아오는 경로가 있는가?
6. Daily Brief에 사용할 수 없는 민감정보와 지역별 보존 제한은 무엇인가?
7. 추천이 잘못됐다고 판단하는 구체적 사례와 허용 가능한 자동화 수준은 무엇인가?
8. Desktop Power User와 Mobile Approver의 사용 빈도와 업무 차이는 무엇인가?

이 질문의 답과 Pilot Telemetry를 기준으로 Section 순서, 우선순위 규칙과 첫
Connector를 확정한다. 디자인 취향만으로 Home Layout을 고정하지 않는다.
