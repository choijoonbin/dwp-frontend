# DWP-R1-CORE-005 수용 테스트 및 출시 Gate

## Gate 상태

| Gate                 | 조건                                                | 현재                           |
| -------------------- | --------------------------------------------------- | ------------------------------ |

| G1 Definition        | 범위, 용어, KPI, 권한, 외부 결정                    | 최종 후보, 승인 Gate 명시      |

설계 문서가 완성되었다고 기능 완료로 표시하지 않는다. G4 증거가 없으면 `released` 또는
`operational` 상태를 사용할 수 없다.

## 기능 수용 기준

### User Inbox

- [ ] 새 Domain Event가 한 번의 User Notification으로 Materialize된다.
- [ ] 같은 Event 재전달은 중복 Row·Badge·외부 Delivery를 만들지 않는다.
- [ ] 같은 `thread_key` 변화는 Count·Preview를 갱신하고 목록을 오염시키지 않는다.
- [ ] Read, Unread, Saved, Done, Snoozed 상태 조합이 서로 손실되지 않는다.
- [ ] Bulk 100건의 부분 성공·재시도·Undo가 명확하다.
- [ ] Deleted·Revoked Target을 열 때 안전한 410 상태와 설명을 제공한다.
- [ ] 정확한 수신 이유와 Effective Policy Source를 표시한다.
- [ ] Search·Filter·Saved View가 Tenant·User Scope를 벗어나지 않는다.
- [ ] Badge Counter Drift를 Reconciliation Job이 탐지·복구한다.
- [ ] Redis·SSE를 모두 재시작해도 `change_version` Sync가 누락된 상태 변경을 복구한다.
- [ ] 보존 Watermark 이전 Cursor는 전체 재동기화를 요구하고 일부 Delta를 정상으로 오인하지 않는다.

### Preference

- [ ] Global → App → Type → Channel Override가 예상 순서로 합성된다.
- [ ] Tenant 관리 정책으로 비활성화한 Channel을 사용자가 켤 수 없다.
- [ ] Mandatory Type은 잠금·Owner·사유를 표시한다.
- [ ] Quiet Hours, Timezone, DST 경계, 휴일과 Urgent 우회가 검증된다.
- [ ] 설정 자동 저장의 409 충돌·실패 Rollback·재시도가 동작한다.
- [ ] 권한을 잃은 App Type은 Delivery되지 않고 설정은 안전하게 비활성 보존된다.

### Admin·Provider

- [ ] Draft → Review → Publish 역할 분리가 Backend에서 강제된다.
- [ ] Published Contract·Template·Policy를 Update·Delete할 수 없다.
- [ ] Policy Simulation과 실제 Runtime 결과가 Contract Test로 일치한다.
- [ ] Provider Secret·Push Token·본문이 운영 목록과 Log에 노출되지 않는다.
- [ ] Replay는 Preview, 사유, 승인, 제한 Batch, Reconciliation과 Audit을 가진다.
- [ ] Tenant Admin은 다른 Tenant Metadata·Queue·Content를 조회할 수 없다.
- [ ] Provider Operator는 Support Session 없이 사용자 본문을 조회할 수 없다.

### 필수 Load Scenario

- Normal Mix 60분 Soak
- 월요일 로그인·업무 시작 Spike
- 100k Audience Batch Fan-out
- SSE 10k부터 목표 동시 연결까지 단계적 Ramp
- Provider 429·500과 Retry Storm
- One Hot Tenant가 다른 Tenant SLO에 미치는 영향
- Critical·Interactive·Bulk QoS Lane별 독립 Saturation과 예약 Headroom
- 180일 Data Volume에서 Feed·Unread·Filter Query
- Partition Maintenance·Backup 중 Online Traffic
- Kafka Consumer Rebalance와 Rolling Deployment
- Regional Cell 장애, Warm Standby Restore와 Residency 검증

### 합격 Target

- Event → Inbox p95 2초, p99 5초
- Event → 열린 Browser p95 3초
- Inbox Query p95 200ms, Error 0.1% 미만
- Summary p95 100ms
- Duplicate Visible Notification 0.1% 미만, Lost Notification 0건
- DB Connection·CPU·IO, Kafka Lag, Redis Memory가 승인 Headroom 안에 있음
- Critical Lane은 Peak Pilot에서 50% 이상 Headroom, Bulk Saturation 중에도 Critical SLO 유지
- Hot Tenant 시험에서 정상 Tenant p95가 승인 Baseline 대비 20% 이상 악화되지 않음

Target은 Pilot Capacity 승인 후 환경별 수치로 고정한다.

## 출시 차단 조건

- Production Kafka가 Single Broker·RF1
- 첫 Producer가 Transactional Outbox·Schema Contract·DLQ Owner 없이 연결
- 범용 자유 형식 발송 API 존재
- User·Tenant IDOR 또는 민감 Preview 노출 1건 이상
- 중복·유실·Replay·Provider 장애 Drill 미수행
- Retention·Mandatory·Urgent·Support Visibility 미승인
- SSE 단절 시 Catch-up 불가
- Durable `change_version` 없이 Memory·Redis Hint를 Catch-up 원장으로 사용
- Badge가 Static·Polling Count이거나 DB `COUNT(*)`로만 계산
- Admin·Provider Scope가 같은 Role·Tenant Header Switch로 처리
- Figma·Responsive·Accessibility 증거 없이 UI 완료 표시
- Runtime DB Role에 Owner·Superuser·`BYPASSRLS` 권한 존재
- Critical·Interactive·Bulk가 동일 Worker Capacity를 무제한 공유
- Production Ingress에서 SSE Buffering·Heartbeat·Drain 검증 누락
- 승인 Residency와 다른 Region으로 Tenant Payload가 복제·전달
- 조직·Role 알림을 승인된 People Target Population Snapshot Contract 없이 활성화
- Email Route를 SPF·DKIM·DMARC·Bounce·Complaint Callback 검증 없이 활성화
