## 문제와 근거

### 현재 Baseline

- Header Badge `2`와 두 건의 알림이 Source에 정적으로 선언되어 있다.
- 사용자별 읽음·완료·저장·Snooze, 실시간 수신, 개인 설정과 감사 증적이 없다.
- 앱들이 알림을 발행하는 공통 Contract, Type Catalog, 중복 억제, Rate Limit이 없다.
- 향후 앱별로 알림을 직접 구현하면 채널 중복, Tenant 격리 누락, 장애 시 유실과 운영 화면 분산이
  발생한다.

### 용어

| 용어                | 정의                                  | 금지 혼용      |
| ------------------- | ------------------------------------- | -------------- |
| Domain Event        | 이미 발생한 불변 업무 사실            | 사용자 문구    |
| Notification Intent | Event와 정책을 평가한 알림 후보       | 최종 전달 성공 |

| Delivery            | In-app, Email, Push 등 Channel 시도   | 알림 자체      |
| Reminder            | 예약 시각에 다시 주의를 요청하는 유형 | 모든 알림      |

| Announcement        | Communications가 소유하는 게시 콘텐츠 | 알림 원장      |

한국어 UI에서는 `알림`을 사용한다. `알람`은 시각 기반 경보나 Reminder에만 사용한다.

## 범위

### In scope

- Header Notification Glance와 실시간 Badge
- 전체 알림 센터, Filter, Saved View와 Bulk Triage
- 읽음·안 읽음, 저장, 완료, Snooze, 구독 해제와 정확한 Deep Link
- Global·App·Type·Channel별 개인 설정, Quiet Hours, Digest
- Tenant Type Catalog, Policy, Template, Suppression, Provider와 운영 Console
- Provider Fleet Health, Quota, Incident Kill Switch와 제한된 지원 진단
- Kafka Domain Event 소비, Transactional Projection, Retry·DLQ·Replay
- In-app, Email, Web Push Adapter Baseline; Mobile·Teams·Slack은 Adapter Gate
- Provider Callback·결과 불명 Reconciliation, Bounce·Complaint·Endpoint Suppression
- 한국어·영어 Template와 사용자 Timezone

### Non-goal

- 메일 Inbox, Chat Message, 업무 Task 원장을 알림 Table로 복제하지 않는다.
- 자유 형식 Marketing Campaign 도구를 만들지 않는다.
- Notification 수신 사실로 원업무 접근 권한을 부여하지 않는다.
- AI가 우선순위, 수신자, 필수 정책 또는 발송을 독자 결정하지 않는다.
- 첫 Release에서 SMS·Voice, Cross-tenant Campaign, 무제한 Broadcast를 제공하지 않는다.

### 제품 경계

- 알림 센터는 독립 Route와 Launcher Entry를 가지며 Header Bell에서 빠르게 진입한다.
- Universal `Inbox`가 구현되면 알림 센터는 Inbox의 Provider가 될 수 있지만, 영속 원장과 권한은
  Notification Platform이 유지한다.
- Communications는 게시·대상·필수 확인을 소유한다. Notification은 해당 게시물의 전달과
  수신자 상태만 소유한다.
- Approval, HCM, Mail, Space 등 원업무 상태는 각 앱이 계속 소유한다.

## 핵심 Journey

### 1. Actionable 알림

1. 결재 Service가 `approval.requested` Domain Event를 Outbox로 Commit한다.
2. Notification Platform이 Contract·정책·수신자·중복·Quiet Hours를 평가한다.
3. 사용자 Inbox에 Materialize하고 열린 Browser에는 SSE Hint를 보낸다.
4. Header Badge가 조용히 갱신되고 필요 시 한 번의 Toast를 표시한다.
5. 사용자는 Inline Action 또는 정확한 결재 Deep Link를 연다.
6. 원업무가 권한과 최신 상태를 다시 확인한다.
7. 처리 완료 Event가 기존 Notification Thread를 `DONE`으로 갱신한다.

### 2. 복귀 후 Catch-up

1. 사용자가 로그인하면 Summary와 Cursor를 조회한다.
2. 알림 센터는 `Action required`, `Mentions`, `For you` 순서로 보여준다.
3. 사용자는 Source, 이유, 시각과 해야 할 행동을 Scan한다.
4. 여러 항목을 선택해 Done·Save·Snooze 처리한다.
5. `왜 이 알림을 받았나요?`에서 적용된 정책과 변경 가능한 설정을 확인한다.

### 3. 사용자 설정

1. 계정 설정의 `알림`에서 Global Delivery Profile과 Quiet Hours를 정한다.
2. 사용 권한이 있는 App과 실제 활성 Type만 노출한다.
3. App 기본값을 상속하거나 Type·Channel별 예외를 자동 저장한다.
4. 관리형 필수 항목은 잠금·Owner·사유를 표시한다.
5. 다음 Notification부터 합성된 Effective Policy를 적용한다.

### 4. 운영 장애

1. Provider 실패율·Kafka Lag·Oldest Job Age가 SLO를 넘는다.
2. Tenant Operator 또는 Provider Operator가 Scope에 맞는 Incident를 본다.
3. Retry Storm을 막고 Channel Circuit Breaker 또는 Kill Switch를 적용한다.
4. 실패 원인을 수정하고 제한된 Batch로 Replay한다.
5. 전후 상태, Operator, 사유와 결과를 감사한다.

## 알림 Type 최소 Contract

모든 Type은 다음을 등록해야 한다.

- 고유 `type_key`, Owner App·Team, Source Domain Event와 Schema Range
- 사용자에게 중요한 이유와 기본 `priority`, `urgency`, `reason_code`
- 수신자 해석 방식과 Target Population
- `thread_key`, Dedupe Window, Max Frequency와 종료·Tombstone Event
- 허용 Channel, Mandatory 가능 여부, Quiet Hours 우회 가능 여부
- Localized Template 변수 Schema와 Data Classification
- Deep Link Pattern, 허용 Inline Action과 권한 재검사 API
- Retention, DLQ·Replay Owner와 운영 Runbook

Contract가 없는 Event는 알림을 만들지 않고 Quarantine한다.

## 정책과 위험

- 개인정보·기밀등급: Metadata 기본. HR·보안 Type은 민감정보를 제목·Preview에서 제거한다.
- 보존·삭제: `D-NTF-01` 승인 전 Production 출시 불가.
- 법무·규제: 필수 통지와 단순 편의 알림을 구분하고 User Disable 가능성을 명시한다.
- 접근성: 깜박임 금지, Keyboard Triage, `aria-live`, Reduce Motion과 200% Zoom을 지원한다.
- 소음: 사용자별 Burst, Type Dedupe, Thread Grouping, Digest와 Channel Arbitration을 적용한다.
- 비용: 외부 Channel별 Quota·단가·Retry Cost를 Tenant·Provider 지표로 분리한다.
