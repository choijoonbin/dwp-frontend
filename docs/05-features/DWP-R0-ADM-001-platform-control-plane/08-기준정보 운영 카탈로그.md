# 기준정보 운영 카탈로그

## 1. 메뉴 목적

`기준정보`는 테넌트가 소유하고 업무 화면·연계 API·AI Agent가 함께 사용하는 안정적인
업무 어휘를 운영하는 메뉴다. 제품 릴리스가 읽기 전용으로 관리하는 `제품 계약 레지스트리`,
HRIS가 원장으로 관리하는 인사·조직 코드와는 소유권을 분리한다.

Tenant 관리자는 이 메뉴에서 다음 작업을 수행한다.

- 업무 코드 세트와 값 생성·수정
- `DRAFT`, `ACTIVE`, `RETIRED` 수명주기 통제
- 상위 코드 기반의 유연한 계층 구성
- 시작·종료 시각을 이용한 예약 적용과 만료
- 로케일별 표시명과 설명 관리
- Runtime 배포 리비전과 현재 사용 가능한 값 확인
- 세트와 하위 값의 변경 활동 추적

## 2. 화면 정보 구조

| 영역          | 운영 질문                                   | 표시 정보                                                |
| ------------- | ------------------------------------------- | -------------------------------------------------------- |
| 카탈로그 요약 | 테넌트 기준정보 규모와 배포 상태는 정상인가 | 세트, 값, 배포 중, 초안 수                               |
| 세트 목록     | 어떤 업무 어휘를 관리할 것인가              | 상태, 값 수, 리비전                                      |
| 세트 헤더     | 이 세트가 Runtime에 제공되는가              | 설명, 수명주기, 배포 상태, 리비전                        |
| 운영 상태     | 데이터 품질과 적용 조건은 준비되었는가      | 현재 사용 가능, 초안, 기간 지정, 번역 완성도, 최상위 값  |
| 기준값        | 실제 업무 코드는 무엇인가                   | 표시명·안정 코드, 상태, 적용 기간, 언어, 계층, 최근 변경 |
| 변경 활동     | 누가 어떤 변경을 했는가                     | 작업, 대상, 수행자, 결과, 시각                           |

Runtime API는 활성 세트에서 활성 상태이고 현재 유효기간에 포함되는 값만 반환한다. 초안과
종료 값은 운영 화면의 이력에는 남지만 일반 사용자 Runtime 응답에서는 제외한다.

## 3. 초기 SKAX 카탈로그

V22 Migration은 기능을 바로 검증할 수 있도록 다음 Tenant-owned 샘플을 제공한다.

| 세트               | 검증 목적                           |
| ------------------ | ----------------------------------- |
| `WORK_PRIORITY`    | 안정 코드, 정렬, 한국어·영어 표시명 |
| `SERVICE_REGION`   | 국내·글로벌 권역과 하위 거점의 계층 |
| `WORK_CATEGORY`    | 업무 요청 분류의 공통 사용          |
| `DELIVERY_CHANNEL` | 활성·초안·종료와 예약·만료 정책     |

샘플은 시스템 불변 Enum이 아니다. Tenant 관리자가 실제 업무 계약에 맞게 수정하고 활성화하는
운영 출발점이다. Migration이 만든 활동은 사용자 변경으로 위장하지 않고 `SERVICE` 수행자의
`reference-set.seeded` 이벤트로 기록한다.

## 4. 데이터와 API 계약

- `adm_reference_sets`: Tenant 세트, 상태, Runtime 리비전, 낙관적 잠금 버전
- `adm_reference_items`: 안정 코드, 상태, 정렬, 계층 FK, 유효기간
- `adm_reference_item_labels`: 로케일별 표시명과 설명
- `sys_platform_audit_events`: 세트 Aggregate의 변경 활동
- `/v1/admin/reference-sets/**`: Tenant 관리자용 Command·Query API
- `/v1/admin/reference-sets/{setKey}/audit-events`: 세트와 하위 값의 활동 API
- `/v1/reference-data/{setKey}`: Runtime용 축소 Read API

모든 조회와 변경은 `tenant_id`를 강제하며 세트 키와 값 코드는 활성화 이후 의미를 재사용하지
않는다. 삭제 대신 종료를 사용해 과거 업무 기록의 해석 가능성을 보존한다.

## 5. 글로벌 벤치마크와 적용 결정

- Oracle Reference Data Sets는 공통 세트와 Business Unit별 세트 공유를 구분하며, 공유 세트
  변경이 할당된 모든 조직에 영향을 줄 수 있음을 강조한다. DWP도 Tenant 소유 경계를 우선
  적용하고, 다중 조직 공유·영향도는 소비처 계약이 생기는 R1에 추가한다.
  [Oracle Reference Data Sets](https://docs.oracle.com/en/cloud/saas/applications-common/25d/faesc/reference-data-sets-and-sharing-methods.html)
- SAP Master Data Governance는 변경 요청, Staging, 승인, 활성화, 배포를 분리한다. DWP R0는
  직접 변경과 Append-only Audit을 제공하고, 규제 또는 고위험 세트에만 4-eyes 승인 모델을
  적용하는 것을 R1 Gate로 둔다.
  [SAP Master Data Governance](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/6d52de87aa0d4fb6a90924720a5b0549/56a57357f2b1aa6be10000000a4450e5.html)
- ServiceNow Data Certification은 정확성·완전성·신뢰성을 정기 또는 온디맨드로 검증하고
  Dashboard에서 상태와 진행률을 Drill-down한다. DWP는 현재 번역·유효성·상태 건강도를
  실시간 표시하고, Owner·인증 주기가 확정되면 인증 Task를 추가한다.
  [ServiceNow Data Certification](https://www.servicenow.com/docs/r/servicenow-platform/configuration-management-database-cmdb/c_DataCertification.html?contentId=IWxYb9XCqR3ybmtkJA0RTQ)
- Microsoft Purview는 명확한 소유권, 권한, 품질 통제를 Master Data 운영의 전제로 둔다.
  DWP는 역할 기반 Tenant 관리자 권한과 변경 활동을 현재 통제로 사용한다.
  [Microsoft Purview master data management](https://learn.microsoft.com/en-us/purview/data-governance-master-data-management-profisee)

## 6. 후속 통제 Gate

다음 기능은 화면만 먼저 만들지 않는다. 실제 데이터 계약이 준비된 순서로 구현한다.

1. 세트 Owner·Data Steward 및 정기 인증 주기
2. 앱·API·Agent 소비처 Registry와 변경 영향도(Where-used)
3. 고위험 세트의 변경 요청, Staging, 검증, 4-eyes 승인
4. 대량 Import·Export의 사전 검증, 오류 보고서, 원자적 반영
5. 공통 세트와 조직별 Override의 우선순위 및 충돌 정책

각 Gate는 권한, 감사 이벤트, 복구 절차, 수용 테스트가 함께 정의될 때 완료로 본다.
