# 04 데이터 설계

## Database

Database는 `dwp_platform`이며 인증 원장과 Agent Vector 저장소에서 분리한다.

| Table                       | 책임                | 주요 제약                                   |
| --------------------------- | ------------------- | ------------------------------------------- |
| `adm_reference_sets`        | Tenant 기준정보 Set | `(tenant_id, set_key)` Unique, Version      |
| `adm_reference_items`       | Set의 Code          | `(tenant_id, set_id, code)` Unique          |
| `adm_reference_item_labels` | Locale Label        | `(tenant_id, item_id, locale)` Unique       |
| `sys_platform_audit_events` | 관리 변경 Audit     | UUID, Tenant, Actor, Before·After JSON      |
| `sys_code_sets`             | 제품 코드 계약      | Owner, 계약 종류, 공개 정책, Schema 버전    |
| `sys_code_values`           | Release 기준 코드값 | `(code_set_key, code)` Unique, 다국어 Label |
| `sys_code_bindings`         | 실제 소비·강제 증적 | DB·API·UI·동작의 Source와 Enforcement       |

모든 관리 Table은 `tenant_id`를 가진다. FK는 동일 Aggregate 연결에 사용하고 모든
Repository 조회에도 Tenant 조건을 포함한다.

`adm_reference_*`는 Tenant 관리자가 생성·활성화·폐기하는 업무 어휘다. 반면
`sys_code_*`는 상태 머신, 보안 효과, Protocol처럼 실행 의미가 있는 제품 계약의 읽기 전용
Registry다. Registry는 다른 Service의 원장을 복제하지 않으며 `owner_service`와
`source_reference`로 권위 원천을 가리킨다. People의 발령 사유·조직 역할처럼 Tenant별
확장이 가능하면서 Domain FK가 필요한 값은 People DB의 Tenant Catalog가 소유한다.

코드 계약은 다음 세 축을 분리한다.

| 축        | 값                                                                                     | 의미                                |
| --------- | -------------------------------------------------------------------------------------- | ----------------------------------- |
| 설정 수준 | `SYSTEM`, `EXTENSIBLE`, `USER`                                                         | 변경 권한과 호환성 경계             |
| 계약 종류 | `REFERENCE`, `STATE_MACHINE`, `SECURITY`, `PROTOCOL`, `OBSERVABILITY`, `REGISTRY_META` | 값이 수행하는 제품 의미             |
| 강제 방식 | `CHECK`, `FOREIGN_KEY`, `CATALOG_LOOKUP`, `TYPED_CONTRACT`                             | 선언이 실제 Runtime에 적용되는 증적 |

`scripts/audit-code-contracts.sh`는 각 Service DB의 enum `CHECK` 값과 Registry를 직접
대조하고 FK Catalog의 고아 참조를 검사한다. DB `CHECK`가 없는 API 기간·필터와 개인 설정
JSON·홈 위젯은 별도 Contract Manifest로 정확한 값을 검증한다. 문서나 화면에 등록된 것만으로
완료로 보지 않으며, 모든 Binding의 강제 방식이 확인되어야 `REGISTERED` 상태가 된다.
Java Main Source의 Enum Inventory도 전수 추출해 명시적 Registry Mapping과 대조하므로 새 Enum은
소유권과 계약 Set을 정하지 않은 채 CI를 통과할 수 없다. 코드값·Binding·계약 Metadata 변경은
`schema_version`을 단조 증가시켜 Runtime Cache가 변경을 식별할 수 있게 한다.
GitHub Actions는 별도 `contracts` 실행 Profile로 네 개의 데이터 소유 Service를 빈 PostgreSQL에
기동해 Flyway 전체 이력과 이 감사를 Pull Request마다 반복한다. 실패 시 Service Log를 제한된
보존기간의 Artifact로 남긴다.

일반 사용자 Runtime API는 명시적으로 `runtime_visibility=RUNTIME`인 활성 Code Set만 조회한다.
`CATALOG_LOOKUP` Binding은 실제 소비 증적이며 공개 여부를 암묵적으로 결정하지 않는다. 응답도
`codeSetKey`, `schemaVersion`, 표시용 활성값으로 축소하며 Owner, 원천 Table·Class, 강제 Binding
증적과 전체 Inventory는 `/v1/admin/code-catalog/**`에서 관리자 역할에만 제공한다.
Runtime Service Token은 관리자 경로에 사용할 수 없고 `ADMIN_ONLY` Set은 Runtime API에서
존재 여부를 드러내지 않고 404로 응답한다.

## Lifecycle와 정합성

- Set과 Item: `DRAFT`, `ACTIVE`, `RETIRED`
- Set 활성화 조건: 폐기되지 않은 Item 1개 이상, 각 Item의 Label 1개 이상
- Runtime: Active Set의 Active Item 중 유효기간 내 항목만 반환
- Set `content_revision`은 Runtime Cache 무효화 Key로 사용한다.
- `version`은 동시 변경을 감지한다.

## 코드 카탈로그 운영 원칙

- `SYSTEM`: Release Migration으로만 변경하며 Tenant UI에서 편집하지 않는다.
- `EXTENSIBLE`: 사전 정의 코드 의미는 유지하고 Owner Service의 전용 API로 Tenant 값을
  추가한다.
- `USER`: Tenant가 소유하는 기준정보 Lifecycle과 승인 정책을 따른다.
- 표시명은 바꿀 수 있지만 안정 코드와 이미 실행된 상태 이력은 재사용하거나 의미를
  변경하지 않는다.
- 서비스 간 직접 DB 조회는 금지하며 API·Event 또는 중앙 읽기 모델을 사용한다.
- 인증 기본 역할은 Auth의 `sys_builtin_role_catalog`, 조직 시나리오 승인 역할은 People의
  `ppl_approval_role_catalog`가 소유한다. 조직 내 역할인 `ppl_organization_role_catalog`와
  접근 승인 역할을 혼합하지 않는다.

## 보존·삭제

- Retired 객체는 일반 Delete 대신 보존한다.
- Audit은 일반 API로 삭제하지 않는다.
- 실제 보존기간, Legal Hold와 Export 정책은 Security·Privacy 승인 후 Migration으로
  확정한다.
