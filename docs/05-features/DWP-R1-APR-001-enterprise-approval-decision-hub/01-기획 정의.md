## 문제와 근거

- 대상 사용자: 일반 구성원, 요청자, 결재자, 위임자, 업무 운영자, Workflow 설계자,
  Tenant 감사자
- 현재 Trigger: HR·IT·구매·권한·조직 변경과 Agent 실행마다 서로 다른 승인 화면과
  상태를 찾아야 한다.
- 문제: 결재 근거와 경로가 분산되고, 승인 이후 실제 업무 반영 실패가 보이지 않으며,
  위임·재지정·보완의 의미가 도메인마다 달라진다.
- 근거: Microsoft, ServiceNow, SAP, Oracle, Workday 등은 통합 Task와 역할 기반
  Workflow를 제공하고, Docusign·Adobe는 서명 증거를 별도 전문 영역으로 관리한다.
- Baseline: Pilot에서 업무별 대기시간, 결재선 오류율, 정보 보완 횟수, 원업무 반영
  실패율과 감사 증거 수집시간을 실측한다.

## 범위

### 현재 구현된 R1 기준선

- 독립 결재 앱 Shell과 개인 통합 결재함
- 기안, 임시 저장, 제출, 회수, 보완, 정보 요청, 승인과 반려
- 순서가 고정된 다단계 결재와 역할 후보 기반 `ANY` 정족수
- Role 기반 Routing, 자기 결재 차단과 설계·게시 직무 분리
- 기간·Workflow 범위형 위임
- 동적 양식·Workflow·Policy Version과 게시 통제
- SLA 현황, 운영 Queue와 통합 전달 상태
- 원업무 Fulfillment Outbox·Inbox와 불변 Timeline
- 한국어·영어, 시간대·통화·숫자·날짜 Locale
- Home·Work·Activity·Notification Projection

### Production 확장 Gate

- 사용자·그룹·직책·Manager Chain 후보 Snapshot과 설명 가능한 Routing
- `ALL`, `COUNT`, `PERCENT` 정족수와 후보별 독립 Task·Decision
- Claim·Release, 운영자 재지정, 에스컬레이션과 Durable Timer
- 첨부 Object Storage·Malware Scan·KMS·WORM, 실제 원업무 Adapter
- 외부 전자서명 Provider와 지역별 법적·보존 정책

### Reference Form

1. 일반 품의
2. 구매·비용 승인
3. 시스템·권한 변경 승인
4. 계약 검토·외부 서명 요청

Reference Form은 제품의 고정 문서 유형이 아니라 Version형 예시다. 고객은 승인된 Form
Studio에서 필드와 Workflow Binding을 확장한다.

### R2

- Docusign·Adobe Sign Sandbox와 외부 수신자 인증
- 계약 원문·완료 인증서·직인·서명 Hash
- Mobile Push와 정책형 Action Card
- Process Mining, 병목·SLA 예측과 고급 분석

### Non-goal

- 범용 ERP·HRIS의 원업무 기능 재개발
- 계약서 작성·CLM 전체 기능
- 법무 검토 없이 자체 공인 전자서명 구현
- 자연어만으로 결재 정책을 즉시 배포
- 민감 업무의 무인 자동 승인

### Horizontal Core와 Industry Pack 경계

Workflow, Task, Decision, Routing과 Evidence는 Horizontal Core다. 통신 투자 심의,
반도체 설비 변경 등은 Industry Pack이 소유한 Form·Rule·Source Adapter로 추가한다.

## Journey

### J1. 사람이 기안

1. Home 또는 결재 앱에서 양식을 선택한다.
2. 임시 저장하며 필드·첨부·원업무 참조를 입력한다.
3. 결재선 Preview와 정책 경고를 확인한다.
4. 제출 후 불변 Revision과 Instance가 생성된다.
5. 결재자는 근거와 변경점을 확인하고 결정한다.
6. 원업무 반영 결과가 Timeline에 표시된다.

### J2. 업무 앱에서 시작

1. HRIS·Employee Services·Access 앱이 승인 Request를 멱등 생성한다.
2. Approval 서비스는 업무 Snapshot과 Callback 계약을 고정한다.
3. 사용자는 통합 결재함 또는 원업무 화면에서 같은 Task를 처리한다.
4. 최종 결정 Event를 원업무가 소비하고 결과를 회신한다.

### J3. 정보·보완 요청

1. 결재자가 정보 요청 또는 보완 요청을 선택하고 질문과 대상을 지정한다.
2. 정보 요청은 같은 Revision에서 답변 후 심사를 재개한다.
3. 보완 요청은 새 Draft Revision을 만들며 이전 Revision을 보존한다.
4. 재제출 시 결재선과 Source Version을 다시 검증한다.

### J4. 부재 위임

1. 사용자가 시작·종료, 업무 범주와 대리자를 지정한다.
2. 시스템은 자기 승인·SoD·권한 범위를 사전 검사한다.
3. 활성 Task에는 원 권한자와 실제 행위자가 함께 표시된다.
4. 위임 종료 후 새 Task는 원 권한자에게 Routing된다.

### J5. 장애 복구

1. 승인 후 원업무 반영이 실패한다.
2. 사용자는 `반영 실패`와 영향·다음 조치를 확인한다.
3. Operator는 결정 내용을 바꾸지 않고 재시도 또는 보상한다.
4. 모든 시도와 결과가 같은 Correlation Timeline에 남는다.

## 정책과 위험

- 개인정보·기밀등급: Form·첨부별 `PUBLIC`, `INTERNAL`, `CONFIDENTIAL`, `RESTRICTED`
- 보존·삭제: Tenant·문서 유형별 정책, 결정·Timeline은 Legal Hold 우선
- 법무·규제: 전자서명 효력, 직인, 원본성과 지역별 보존은 별도 법무 Gate
- 파일: 허용 확장자·크기, Malware Scan, Content-Disposition, Object Key 비노출
- AI: 원문을 재학습에 사용하지 않으며 결정·권한·결재선을 임의 생성하지 않는다.
- 실패 기본값: 민감 Task 만료 시 자동 승인하지 않고 에스컬레이션 또는 중단한다.

## 결정

- 제품명: 화면은 `결재`, 기술 bounded context는 `Approval Decision Hub`
- 앱 위치: 개인 Home `업무 시작`, 업무 Shell과 분리된 독립 Product Shell
- 관리 위치: 관리 센터 `업무 자동화 > 결재 관리`
- Source of Record: 원업무는 업무 도메인, 결정 원장은 Approval 서비스
- 전자서명: 내부 구현이 아니라 Provider Adapter
- 열린 질문: Engine, Signature Provider, Object Store·KMS, 고객별 후결 정책, Pilot 범위
