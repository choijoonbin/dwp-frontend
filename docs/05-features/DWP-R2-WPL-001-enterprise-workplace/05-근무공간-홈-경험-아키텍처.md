# 근무공간 홈 경험 아키텍처

## 1. 목표

근무공간 홈은 운영 KPI를 나열하는 관리자 대시보드가 아니다. 구성원이 오늘 어디에서 무엇을
해야 하는지 빠르게 판단하고, 체크인·일정 확인·공간 예약으로 바로 이동하는 개인 업무 시작점이다.
따라서 정보 우선순위는 `다음 행동 > 오늘 흐름 > 현재 이용 가능 공간 > 주간 리듬 > 확인 항목`으로
고정한다. 사업장 수와 예약 건수 같은 운영 지표는 관리자 화면에서 다룬다.

## 3. 현재 구현 계약

### 3.1 읽기 합성

현재 Increment는 브라우저에서 다음 Gateway API의 읽기 결과를 합성한다.

- Workplace Explore: 선택 층 자원, 점유, 정책, 사업장 시간대
- Workplace Bookings: 개인 좌석·사물함·주차·공용 장비 예약
- Calendar Room Bookings: 회의실 예약
- Calendar Home: Calendar `VIEW` 권한이 있을 때만 오늘 일정, 주간 부하, 확인 항목

각 Query Key는 시간 버킷을 포함하지 않는다. 60초 간격 백그라운드 재검증 중에도 마지막 정상 결과를
유지하고 최초 로딩과 재검증을 분리한다. 소스별 상태는 `LOADING`, `READY`, `STALE`, `DENIED`,
`UNAVAILABLE`, `SKIPPED`로 구분한다. 일시적 5xx에서는 마지막 검증 결과를 stale로 표시하지만
쓰기 행동은 비활성화한다. 401/403/404, `SCOPE_CONTEXT_EXPIRED`,
`AUTHORITY_RESOLUTION_UNAVAILABLE` 같은 권위적 거부에서는 보존 데이터를 즉시 폐기한다. 보존
snapshot은 tenant·사용자·scope에 결속한다. 모든 필요 소스가 최초 판정을 끝내기 전에는 live 또는
empty 상태로 단정하지 않는다.

Explore Query는 응답과 해당 요청의 `from/to/timeZone`을 하나의 snapshot으로 저장한다. 매분 시간이
바뀌더라도 이전 점유 결과를 새 60분 범위에 재해석하지 않으며, 새 요청이 검증되기 전에는 이전 범위와
읽기 결과를 함께 유지한다. 응답이 도착할 때 범위·점유·typed discovery target을 원자적으로 교체한다.
화면 판단 시계는 mount 시점 기준 60초 타이머가 아니라 다음 가용 범위 시작, 체크인 창, 예약과 회의의
시작·종료 중 가장 가까운 의미 경계에 맞춰 깨어난다. 경계를 넘으면 이전 결과는 참고 표시할 수 있지만
예약 수치와 쓰기 행동, 만료된 시각을 담은 typed link는 즉시 닫고 새 검증 응답 뒤에만 다시 연다.

### 3.2 범위와 가용성

다음 60분 가용성은 전체 테넌트나 모든 사업장을 뜻하지 않는다. Explore 응답의 `selectedFloor`만
대상으로 하며 화면에 사업장·층을 함께 표시한다. UI는 물리적 상태(`비어 있음`, `사용 중`, `내 예약`,
`고정 배정`, `현장 사용`)와 현재 예약 절차 적격성을 별도 칩과 접근성 이름으로 표시한다. 예약 적격
수치·정렬·상세 버튼은 하나의 eligibility evaluator를 사용한다. `UNAVAILABLE`, 타인 고정 배정,
아직 시작되지 않은 `DROP_IN`, Calendar에 매핑되지 않은 회의실, 현재 점유 자원, 읽기 전용 계정은
예약 절차 가능 수에서 제외한다. 승인 필요 자원은 예약 불가로 오인하지 않고 후속 승인 절차가 있는
예약으로 취급한다. 회의실은 Calendar/Rooms 정책과 `APP.ROOMS CREATE`, 그 밖의 근무공간은
Workplace 정책과 `APP.WORKPLACE CREATE`를 각각 평가한다. 선택 사업장의 시간대와 조회 시작·종료
범위가 소유 도메인의 예약 창, 운영시간, 최소·최대 이용시간에 맞고 최신 Explore 및 회의실 정책
응답이 검증된 경우에만 예약 명령을 활성화한다. 캐시된 회의실 정책의 백그라운드 갱신이 실패해도
마지막 정책은 참고 표시만 하고 회의실 수치·정렬·예약 명령은 복구 전까지 닫는다. 서버가 권한,
자원별 effective policy, 사용자 충돌과 활성 예약 한도를 다시 검증하므로 화면 표기는 `예약 1차 확인
통과`이며 예약 가능성의 최종 권위가 아니다.

회의실 쓰기는 Rooms 화면과 일반 Calendar 화면 모두 Calendar 명령 경계로 수렴한다. Calendar는
resource lock을 획득한 뒤 canonical room time zone, 미래 시각, `MEETING` 유형, non-all-day,
운영시간, 최소·최대 길이, 사전 예약 가능 기간, 유한 recurrence 및 예약 전후 buffer를 create/update
모두에서 강제한다. buffer 충돌 검사는 수정 중인 event만 제외하며, UI도 같은 buffer를 사전 표시하되
서버 판정을 대체하지 않는다. 따라서 `/rooms/bookings` 또는 일반 Calendar API 중 어느 경로를
호출해도 `FOCUS/TASK` 유형이나 과거·운영시간 밖·buffer 인접 예약으로 정책을 우회할 수 없다.

### 3.3 명령 권위와 권한

- 체크인은 Workplace booking update 권한이 있을 때만 직접 노출한다.
- 체크인 명령은 `bookingId`와 `version`을 기존 Workplace command endpoint로 전송한다.
- Calendar 일정은 typed deep link로 이동하지만 Calendar 쓰기를 Workplace에서 수행하지 않는다.
- Workplace 예약과 회의 항목은 각각 `booking`, `event` query를 소비해 목록의 정확한 항목으로 포커스한다.
- 홈의 공간 찾기 링크는 검증한 `site/floor/date/time/duration/type`을 typed query로 보존해 첫 Explore
  요청이 홈의 60분 가용성 범위와 일치하도록 한다.
- 검증 범위의 시작 시각이 지나면 이전 `date/time/duration`은 탐색 링크에서 제거한다. 새 범위를 받기
  전에는 과거 범위의 예약 행동을 복원하지 않는다.
- Calendar `VIEW` 권한이 없으면 Calendar Home 요청 자체를 보내지 않는다.
- Projection 또는 클라이언트 계산 결과로 권한, 충돌, 정책 판정을 대체하지 않는다.
- 예약 재시도는 같은 사용자 의도에 대해 같은 idempotency key를 유지하고, 입력이 바뀌었을 때만 새 의도로 교체한다.

### 3.4 상태와 접근성

- 사업장 미설정 또는 접근 권한 없음과 단순 예약 없음은 서로 다른 상태로 표현한다.
- 일정 또는 확인 항목의 필수 소스가 부분 실패하면 정상 empty/healthy 문구를 확정하지 않는다.
- 회의실 필요 항목은 `FULL` 상세, 비 redacted, non-all-day, 미거절, 편집 가능 일정이면서 위치·자원·
  온라인 회의 URL이 모두 없고 아직 시작하지 않은 경우에만 생성한다. FREE_BUSY, 읽기 전용, 거절,
  종일, 온라인·진행 중 회의를 실행 가능한 대면 일정으로 오분류하지 않는다. 장기적으로는 Calendar가 소유한
  `needsPhysicalSpace` 계약으로 대체한다.
- 320/390/768/1440 CSS px와 200% 텍스트 확대에서 수평 페이지 overflow가 없어야 한다.
- 일정과 확인 항목은 전체 행이 키보드로 접근 가능한 링크다.
- 가용성 meter와 주간 부하 시각화는 텍스트 대체 이름을 제공한다.
- Axe serious/critical 위반은 0건이어야 한다.

### 3.5 개인정보와 캐시 경계

- Calendar가 소유한 공간 점유에서는 현재 사용자 본인의 예약만 예약자 이름을 반환한다. 공개 일정도
  다른 사용자의 organizer 이름을 Workplace에 복제하지 않는다.
- 고정 좌석 배정자는 본인에게만 이름이 표시된다. tenant 설정만으로 타인의 이름과 정확한 좌석을
  공개하지 않는다.
- Floor background는 권한 재검증 없이 장기 재사용하지 않도록 `private, no-cache,
must-revalidate`로 제공한다. 장기 캐시는 revisioned asset과 authority revalidation 계약이 생긴 뒤에만
  허용한다.
- Team Presence와 동료 위치는 개인 opt-in 계약이 마련되기 전까지 출시하지 않는다.

## 4. 출시 보류 계약

현재 홈을 엔터프라이즈 통합 Projection 또는 실시간 Team Presence로 표기하지 않는다. 다음 조건이
완료되어야 다음 Increment를 출시할 수 있다.

1. Workplace·Calendar·Service Center lifecycle outbox와 멱등 consumer
2. tenant/user/capability revision으로 분리된 Home read model
3. source별 `asOf`, `watermark`, `lastSuccessAt`, `staleAt`, 실패 reason code
4. private/confidential Calendar 필드의 redaction·retention 계약
5. WorkPlan과 실제 Presence 분리, tenant 정책과 개인 opt-in의 이중 개인정보 gate
6. canonical `siteId/floorId/resourceId`, `bookingAuthority`, policy/capability revision
7. Service Center 시설 요청의 canonical 공간 참조와 권한 계약
8. Occupancy SSE, DLQ·replay·lag 관측과 운영 cardinality·query count 부하 증거

목표 endpoint는 Gateway 뒤의 읽기 전용
`GET /api/platform/v1/workplace/experience/home?v=1&date=...&siteId=...&timeZone=...`이다.
응답은 `projectionRevision`, `generatedAt`, `staleAt`, `scope`, `sources`, `nextActions`, `timeline`,
`availability`, `recommendations`, 선택적 `presence`, `notices`를 포함한다. 쓰기 명령은 이 endpoint로
보내지 않고 Client Command Router가 각 소유 도메인으로 전달한다.

## 5. 수용 증거

- Rooms 단위 테스트: 10 files, 63/63 통과. 전체 frontend Vitest 255 files, 1459/1459 통과
- Rooms E2E: 독립 서버 Chromium·mobile 92/92 통과. 다음 행동, 동일 idempotency key 재시도,
  stale write 차단, 동일 query key의 403/409/503 권한 회수, cross-timezone 지연 응답, typed deep
  link, 사업장 미설정·읽기 전용 경로, 물리적 공석·예약 적격성 분리, 캐시된 회의실 정책의
  Home/Explore success→503→recovery 차단·복구, owner별 mixed APP 권한, owner policy 시간 범위,
  Home→Explore 60분 typed handoff, 지연된 분 경계의 range+occupancy 원자 교체와 만료 행동 즉시 차단,
  회의 시작 경계에서 room-needed 즉시 제거, 실행 가능한 미래 대면 일정만의 room-needed 분류,
  partial positive-empty 차단을 포함
- 실제 Chromium과 Playwright: 320/390/768/1440, 390px 200% 텍스트 확대, 수평 overflow 0,
  주요 제목의 실제 약 2배 확대와 긴 공간명·설비·위치 정보 줄바꿈 확인
- 접근성: 홈 `main` 영역 Axe serious/critical 0
- Backend Platform 전체 779/779과 1,133 production files source-size gate 통과. Calendar organizer·
  고정좌석 배정자 redaction, floor background 재검증 cache contract, 회의실 future/type/time-zone/
  운영시간/duration/advance/recurrence/buffer 권위 검증을 포함
- Frontend production build와 architecture/API boundary/i18n/source-size/bundle budget gate 통과
