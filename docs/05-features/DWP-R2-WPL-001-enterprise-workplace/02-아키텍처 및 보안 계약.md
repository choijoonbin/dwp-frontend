# DWP-R2-WPL-001 아키텍처 및 보안 계약

## 1. 애플리케이션 경계

- 프론트는 독립 배포 가능한 Rooms/Workplace 제품 앱이며 sibling product 구현을 직접 import하지 않는다.
- 모든 런타임 호출은 Gateway `/api/**` 클라이언트를 사용한다.
- 회의실 이벤트와 참석자는 Calendar, 비회의 공간과 배치도는 Workplace가 소유한다.
- 외부 Calendar, 출입, 센서 공급자는 Adapter와 Outbox/Event 계약으로 연결하며 핵심 예약 모델을
  공급자 DTO에 종속시키지 않는다.

## 2. 명령 안전성

- 예약과 Release Window 생성은 필수 `Idempotency-Key`와 요청 Fingerprint를 저장한다.
- 같은 키와 같은 요청은 최초 결과를 반환하고 같은 키의 다른 요청은 충돌로 거부한다.
- 브라우저는 동일한 사용자 입력을 재시도할 때 같은 키를 재사용하고 입력이 바뀔 때만 새 키를 만든다.
- 미래 `RESERVED` 예약 변경은 같은 `ResourceType`만 허용하며 서버가 정책, 접근, 가용성과 Version을
  원자적으로 다시 검사한다.
- 모든 변경은 낙관적 Version과 감사 사유를 가지며 서버 판정이 UI 상태보다 우선한다.

## 3. 인가와 개인정보

- 앱 RBAC는 `APP.WORKPLACE`, `APP.ROOMS`, `ADMIN.WORKPLACE`, `ADMIN.ROOMS` Capability를 사용한다.
- 공간 범위 ABAC는 Gateway가 검증한 사용자, Tenant, Group Ref와 Resource Role만 입력으로 사용한다.
- 대상 Site를 역추적할 수 없는 관리자 명령과 범위 밖 조회는 fail-closed로 거부한다.
- 목적, 이름과 Person ID는 보존기간 후 익명화하고 Legal Hold는 승인된 기간만 예외로 유지한다.
- 감사 원장과 Audit Outbox는 사용자 데이터 변경과 분리된 append-only 증거를 유지한다.

## 4. 배치도 미디어 수명주기

배치도 Asset은 `STAGED > REFERENCED > PENDING_DELETE > DELETING > DELETED` 상태를 사용한다.
정리 Worker는 DB 행을 잠그고 참조 수가 0인 경우에만 `DELETING`으로 전이한 후 외부 저장소에서
삭제한다. 동시에 새 Revision이 같은 Asset을 참조하려 하면 DB Trigger가 전이를 직렬화한다.
이미 다시 참조된 Asset은 삭제를 건너뛰고 Cleanup 작업만 완료한다. Lease가 만료되면
`PENDING_DELETE`로 복구해 멱등 삭제를 재시도한다.

업로드는 크기, Magic Byte, 포맷과 원본 픽셀 수를 검증한다. 원본 해상도 메타데이터는 유지하되
디코드 검증은 source subsampling으로 최대 픽셀 버퍼를 제한해 압축 이미지 메모리 급증을 막는다.

## 5. 장애 계약

- 최초 조회가 실패하면 로컬 오류 상태와 다시 시도를 제공한다.
- 이전 정상 응답이 있으면 데이터를 숨기지 않고 stale 경고를 표시한다.
- 예약 정책이 없으면 임의 기본 정책으로 명령을 허용하지 않는다. 검색은 계속 제공하되 예약 선택과
  제출을 비활성화한다.
- 회의실 정책과 Workplace 정책은 각 권위 API에서 읽으며 한쪽 장애가 다른 자원 종류의 조회까지
  불필요하게 차단하지 않는다.
