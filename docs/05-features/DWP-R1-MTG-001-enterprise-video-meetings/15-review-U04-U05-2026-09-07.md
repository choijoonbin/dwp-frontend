## 실제 동작과 보안 경계

- `useMeetingPrejoinSession`은 기존 `useMeetingDevicePreview`/`MeetingDeviceSession`을 재사용한다. 동일 state의 장치 ID와 observed active 상태를 stage, 입력 meter, entry recap, 실제 `onSubmit`으로 보낸다. 기본값이 켜짐이어도 permission 요청 중/실패한 장치는 켜짐으로 보고하지 않는다.
- 저장된 microphone/camera/speaker IDs 및 noiseSuppression을 로컬 capture에 전달한다. 장치 선택 변경은 켜져 있는 해당 local capture만 재시작하며, 꺼진 장치 선택으로 권한을 몰래 요청하지 않는다.
- 입장 시 local preview를 먼저 중지한 후 실제 룸이 publication track을 얻는다. 기존 RoomExperience의 계정별 device storage/reconciliation/LiveKit 옵션 전달 계약은 변경하지 않았다.
- 콘텐츠 동의 미확인·철회, 사용자 이름 공백, 장치 요청 중, 중복 제출은 native form 경로까지 차단한다. 키보드 사용자가 먼저 이동했으면 지연된 초기 heading focus가 포커스를 탈취하지 않는다.
- 자료의 `meetingId/materialId/materialVersion/expiresAt` 및 HTTPS URL을 확인한다. 티켓 만료 시 다시 검증하도록 전환하고, 만료 직후 클릭도 재검사한다. 원문·자격증명·파일 contents는 이 UI에 보관하거나 업로드하지 않는다. 등록은 기존 opaque reference API이고, 열람은 기존 access-ticket API다.
- U05 의제 query는 tenant/user/identity-plane/meeting 범위 키, `gcTime:0`, access-sensitive 메타데이터를 사용한다. 에러 또는 다른 meeting 응답에서 이전 의제를 계속 노출하지 않는다. 준비 의제 실패는 방의 독립적인 입장 권한을 임의로 승격하지 않는다.
- U04 기존 계정 변경/403/늦은 RSVP 응답 폐기, invitation/agenda/material optimistic version 및 개인 준비 상태 격리 경계를 보존했다.

## 후속 API/아키텍처 설계 — 미구현을 완료로 표기하지 않음

이 하위 작업은 frontend 전용이며 다음 backend/API를 추가하지 않았다.

1. **사전 브리핑**: meeting/version/agendaVersion + approved material references + 명시적 분석 동의에 결속된 run API가 필요하다. 응답은 요약·provenance·관측 시각·실제 계산한 confidence만 제공한다. 저장 시 tenant/meeting/run, 암호화 본문, retentionUntil, audit event, 삭제 worker readiness를 결속해야 한다. 기존 사후 intelligence 결과를 사전 분석으로 잘못 재사용하지 않는다.
2. **회의 전 대화 및 안건별 질문/자료**: meeting-bound conversation ID와 현재 참석자 ACL, 메시지 보존/삭제, 참여 철회 이벤트 처리가 필요하다. 안건별 질문/메모 및 자료 관계에는 agenda item/version을 결속하는 참조 모델이 필요하다. 기존 회의 중 chat endpoint를 입장 전 권한으로 우회 호출하지 않는다.
3. **자료 선택 UI**: 현재 governed reference 등록/열람 API는 연결되어 있으나, 원본의 업로드/picker UX에는 DWP Files/SharePoint/Confluence의 사용자 권한이 적용된 picker/broker가 필요하다. source 선택→opaque reference→회의 등록→열람시 재검증으로 연결하며 원문·provider token을 Meeting frontend에 저장하지 않는다.
4. **배경 처리**: 실제 capture track에 적용하는 provider/browser processor capability, 장애/해제/기기변경 lifecycle 및 room handoff가 필요하다. CSS blur로 전체 영상을 흐리게 만들고 배경 분리라고 표시하지 않는다.

### 후속 독립 감사 보정: U05 제목 위계 및 실제 로컬 배경 흐림

위 동결 이후 루트의 추가 승인으로 다음 범위를 재개했다. 앞선 '배경 처리 미연결' 판정은 당시 의존성·코드 상태이며, 이후 별도 processor 담당이 추가한 로컬 처리기를 연결했다. 오피스 배경과 승인 문서 picker는 아직 별도 경계다.

- **제목 위계의 실제 차이**: 원본 desktop은 회의명 H1 + 상태/일정/주최자 compact metadata 다음에 stage가 시작한다. 기존의 '카메라와 마이크 점검' H1 + 별도 큰 회의 요약 카드는 기능 제약과 무관한 디자인 차이였다. 회의명을 유일한 H1·초기 포커스로 올리고 desktop 외곽/패딩을 없앴다. mobile 원본에는 회의 정보 카드가 있으므로 xs 카드 형태는 보존했다. 작은 장치 설명, context region, 동의 및 입장 form semantics는 유지했다.
- **로컬 장치 선택 계약**: `MeetingDevicePreferences.backgroundBlur?: boolean`은 기존 브라우저 저장값과의 입력 호환만 허용한다. 기본값/파싱/resolve/저장은 `=== true`로 정규화하고 기본 false다. tenant·user·identity plane scope 키는 유지한다. 서버 preference API와 DB schema에 미디어 설정이나 장치 ID를 추가하지 않았다.
- **실제 preview 처리**: `useMeetingDevicePreview`에서 raw capture를 얻되 blur가 선택되면 processor의 첫 합성 frame 완료를 기다린 뒤 결과 track만 새 MediaStream으로 연결한다. 재시작 시 DOM `srcObject`부터 즉시 비우며, 초기 실패·runtime 실패·계정/권한 revoke·기기 교체·늦은 완료에서 원본 track과 파생 자원을 닫는다. CSS blur나 원본 fallback은 없다.
- **UI·handoff**: U05의 원본 입력/배경 흐림 선택은 `selectBackgroundBlur` → `MeetingPreJoin.onBackgroundBlurChange`를 호출한다. 카메라가 꺼져 있으면 저장만 하고 권한을 자동 요청하지 않는다. 실제 입장 publication 연결은 루트의 RoomExperience/LiveVideoMeetingRoom 담당이며, 같은 browser-scoped 값과 processor를 사용한다. - `MeetingPreparationMaterialProvider`는 access-ticket 발행만 제공한다. governed HTTP adapter의 `/internal/v1/meeting-preparation-material/access-ticket`는 outbound 계약이며 대응 원본 storage owner handler는 이 저장소에서 확인되지 않았다. 기본 provider는 disabled다. 원본 ACL·문서 버전·hash를 검증하는 source selector + broker 구현/설정이 필요하다.
- 내부 DWP storage owner로 구성하면 외부 유료 서비스가 본질적으로 필수인 것은 아니다. SharePoint/Confluence 연결을 선택하면 조직 연결·권한 동의·credential 및 원본 API 계약이 추가로 필요하다. 파일 선택 input만 추가하거나 임의 URL/reference를 만든 것을 승인 자료 연결로 판정하지 않는다.
