## Product behavior and authority

- **Primary user:** an admitted organizer or cohost in a live meeting.
- **Operational question:** which participant is currently connected, and can the host end that participant's connection?
- **Primary action:** select a participant, review the named target and session impact, then confirm **Disconnect / 연결 종료**. Cancel is initially focused. The experience remains inside the existing immersive meeting workspace and its participant panel.
- **Authority:** the current backend meeting and participant records determine access. The actor needs `APP.MEETINGS:UPDATE` or `MANAGE`, an admitted host role, and a current active room incarnation. The organizer cannot be disconnected. A cohost cannot disconnect another host. Self-disconnect uses the existing leave workflow. Provider-support and support-session identities are rejected.
- **Scope:** the operation ends the target's current provider connection and prevents the application from issuing another admission/token for that participant in this room incarnation. This is not an account ban.
- **Lifecycle:** the target sees the connection-terminated departure screen without an immediate rejoin action. An old room's SDK callbacks, delayed token issuance, host start/end, and account changes cannot replace or clear a newer room credential.

The new public endpoint is `POST /api/meetings/v1/meetings/{meetingId}/participants/{participantId}/disconnect`, with `Idempotency-Key` and `{ expectedVersion }`. The response binds meeting, participant, command ID, `PENDING | DISCONNECTED`, and `blockedForCurrentSession: true`. A pending provider operation is not shown as completed. The client resolves the exact governed ACTION route `route.meetings.work.participant-disconnect.action`; secure rollout states attach the fresh decision revision and context scope while preserving the version-bound idempotency key. A 401/403/404/409 response invalidates the meeting projection. A newer participant version resets the stale intent, while a same-version response exposes an explicit bounded refresh before retry.

## Server consistency and provider behavior

Migration `V39__govern_meeting_participant_disconnect.sql` adds a durable command and current-incarnation token fence. The request transaction locks the meeting, validates current authority and optimistic version, writes the fence, transitions the participant to denied, and records an event and audit entry. Audit failure rolls back the operation. Idempotency is bound to tenant, actor, participant, room incarnation, and the expected version; a conflicting reuse returns a conflict.

The provider call runs outside the database transaction. A short lease and fenced completion coordinate concurrent workers; failures remain pending and use the configured retry delay. Automatic claims stop at the shared `maximumAttempts` ceiling while the current-incarnation access fence remains in force for operator reconciliation. Recovery only retries existing commands. The LiveKit adapter validates the stored room metadata and constructs the canonical participant identity before `RemoveParticipant`. An already absent room or participant is an idempotent completion. No recording content or customer media is read by this workflow.

The room incarnation fence is also checked by public join and token issuance, independently of attendance state. The new table's meeting foreign key uses cascade cleanup so existing governed meeting retention is not blocked by the additional command record.

**Self-hosted LiveKit limitation:** removing a participant does not revoke an already issued token. The application fence prevents new application-issued tokens, but a holder may connect directly to the self-hosted SFU with an unexpired cached JWT. The local synthetic probe explicitly exercises this limitation. Production admission revocation remains a separate deployment requirement; do not describe this feature as a permanent ban or complete JWT revocation. See [LiveKit tokens and grants](https://docs.livekit.io/frontends/reference/tokens-grants/) and [participant management](https://docs.livekit.io/intro/basics/rooms-participants-tracks/participants/).
