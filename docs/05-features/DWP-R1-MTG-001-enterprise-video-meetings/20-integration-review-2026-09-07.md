## 원인과 수정 방향

1. 원본의 메뉴별 정보 구조를 일반 카드/표 조합으로 단순화했다. 회의 홈의 즉시 행동, 기록함의 탐색, AI 결과의 근거·후속 행동, 개인실의 설정·상태가 서로 다른 구조인데 충분히 구분되지 않았다. 각 메뉴의 원본 PNG/HTML을 직접 읽고 전용 구성과 반응형 우선순위를 복원했다.
2. 회귀 테스트가 이전 구현 캡처를 기준으로 통과하면서 원본과의 차이를 증명하지 못했다. 원본과 구현 이미지를 별도로 보존하고, 변경된 구현의 회귀 기준만 검토 후 갱신한다. 승인 원본 ZIP/PNG/HTML 해시나 허용 오차를 수정해 통과시키지 않는다.
3. 디자인에 있는 콘텐츠를 담을 실제 계약과 화면 표시가 분리되어 있었다. 일부 메뉴는 이름만 복원해도 동작하지 않는 상태였다. 이번에는 즐겨찾기를 개인별 DB/API까지 연결하고, 이미 존재하는 준비 안건·응답 집계·템플릿 개정·정확한 AI 후보 ID를 UI에서 실제 소비하도록 수정했다.
4. 모의 API가 실서비스 응답의 제약을 충분히 반영하지 못했다. 현재 사용자에게 보이는 참가자 일부와 전체 집계를 같은 값으로 가정했던 준비 API 검증 오류, organizer 응답 시각 null 계약, 전체 참가 인원 누락을 실제 사용자 화면과 응답 계약으로 보정했다.
5. 장치 설정의 배경 선택에는 실제 전송 처리기가 없었다. 미리보기 CSS가 아니라 첫 처리 프레임 준비 후에만 영상을 공개하는 로컬 처리기와 LiveKit 캡처 계약을 연결했다. 독립 배포의 BASE_URL·CSP·WASM MIME까지 검증했다.

## 즐겨찾기 저장 설계

Meeting 소유 V37은 `vm_meeting_record_bookmarks`를 만든다. 기본 키는 `(tenant_id,user_id,meeting_id)`이고 `favorite`, `version`, `updated_at`만 저장한다. 제목·참가자명·원문·미디어 URL·접근 티켓은 저장하지 않는다. Meeting tenant/ID 복합 FK와 부모 삭제 cascade, 즐겨찾기 partial index를 둔다.

- GET `/v1/history/bookmarks`: 현재 페이지의 1–100개 서로 다른 회의 ID만 읽으며 각 회의의 현재 접근 권한과 ENDED/CANCELLED 상태를 확인한다. 하나라도 허용되지 않으면 부분 결과 없이 거부한다. 미저장 상태는 false/0/null이며 GET은 쓰지 않는다.
- PUT `/v1/meetings/{id}/bookmark`: 현재 actor의 VIEW 권한, 명시적 boolean·expectedVersion, stable Idempotency-Key를 요구한다. SUPPORT 및 위조 actor 헤더는 차단한다. 권한을 재확인한 뒤 버전 CAS·감사·명령 영수증을 한 트랜잭션으로 저장한다.
- GET `/v1/history?favoriteOnly=true`: 개인 즐겨찾기 조건과 기존 회의 접근 조건을 목록·총수 모두에 적용한다. repeatable-read로 페이지와 총수를 같은 DB snapshot에 묶는다.
- 프론트엔드는 낙관적으로 별을 켜지 않는다. 현재 페이지의 개인 상태 확인 이후만 명령을 보내고 서버 페이지/상태를 다시 읽는다. 신원·페이지 변경 시 AbortSignal과 응답 세대 경계로 이전 응답을 버린다. 권한 회수 오류는 이전 기록 표시를 철회한다.

정확한 테이블/SQL/PG·실제 SecurityFilter 회귀 메서드: backend `docs/workspace/meeting-record-bookmarks-2026-09-07.md`.
