## 왜 이전 구현이 부족했는가

이전 closeout에는 시안의 영구 6개 하위 메뉴를 채택하지 않고 `/work/queue` 하나에 상세·계획·AI를 모으겠다는 결정이 명시되어 있었다. 사용자가 승인한 디자인보다 앞선 단일 진입점 설계를 우선한 판단이 잘못이었다. 원천 앱이 상태를 소유한다는 원칙도 앱 내부의 허용된 상세 조작까지 축소하는 이유로 적용되었다.

검증 역시 큐의 렌더링, 원천 이동, 일부 반응형 동작에 집중했고 **18개 원본 각각의 정보 구조·화면 상태·대표 사용자 여정**을 완료 조건으로 삼지 않았다. 자동 테스트 통과를 디자인 반영 완료와 혼동했다. 따라서 당시의 “화면·기능 구현 완료” 표현은 전체 승인 시안의 완성을 뜻하는 근거로 사용할 수 없다.

이번에는 원천의 최종 권한·상태 소유권을 유지한다. Work 소유 업무는 내부에서 실행하고, 독립 제품인 Approvals·Services 업무는 Work 요약에서 소유 앱으로 문서 handoff한다. 화면별 기능 검증과 시각 대조를 분리하며 시안의 예시 데이터는 운영 사실로 이식하지 않는다.

## 제품 역할과 6개 메뉴

주 사용자는 여러 앱에 처리 책임이 흩어진 임직원이다. 핵심 질문은 “내가 지금 어떤 업무를 판단하고 실행해야 하는가?”이며, 주 행동은 대상 검토 후 해당 원천이 허용한 명령 실행이다. 기본 형태는 목록–상세이고, 오늘 계획은 실행 순서를 정하는 작업 화면, 작성·일정 연결은 집중형 양식이다.

| 메뉴         | 독립 경로                 | 사용자 행동                                        |
| ------------ | ------------------------- | -------------------------------------------------- |
| 통합업무함   | `/work/queue`             | 확인된 원천 업무 전체를 검색·비교하고 상세를 연다. |
| 내 조치 대기 | `/work/action-required`   | 내가 처리해야 하는 결재·보완·개인 업무를 검토한다. |
| 오늘 계획    | `/work/day-plan`          | 오늘 할 일을 선택·정렬하고 실행 시간으로 연결한다. |
| 진행 중      | `/work/in-progress`       | 진행 중인 개인·원천 업무의 현재 상태를 확인한다.   |

진행 상태와 책임 주체는 독립적이다. 예를 들어 담당 부서가 처리 중인 서비스 요청은 “진행 중”이면서 “응답 대기”에 해당할 수 있다. 메뉴 이동은 오래된 상세 선택을 제거하고, 검색·정렬 등 유효한 조회 조건을 보존한다. 모바일은 하단 5개 탭과 더보기에서 6개 업무 보기 모두에 접근한다.

Calendar는 시간·일정을, Work는 업무·개인 계획을 소유한다. 공유 Home의 Flow는 요약을 통해 해당 업무로 진입시키며, AI는 선택한 업무의 근거 분석·읽기·출처·복사·대화 이어가기를 제공한다. 일정 생성·계획 추가·AI 답변 수신을 업무 완료로 취급하지 않는다.

## 마지막 전문 리뷰에서 수정한 기능 결함

- **권한 검토 버전 경합:** 확인 화면의 대상·버전·결정·사유를 고정한다. 제출 전 원천을 다시 읽고 권한을 재평가한다. 다른 버전이거나 읽기 전용이면 명령을 보내지 않는다. 회수 결정 저장과 실제 권한 반영 상태를 별도 표시한다.
- **개인 체크리스트 덮어쓰기:** 편집 시작 버전을 고정한다. 배경 갱신으로 원천 버전이 바뀌면 입력을 유지하고 저장을 차단한다. 최신 목록을 비교한 뒤 최신 사용 또는 초안 대체를 명시적으로 선택해야 하며, 재변경 시 다시 차단한다.
- **일괄 처리와 세션 변경:** 실행을 사용자·테넌트·identity plane 및 컴포넌트 수명에 묶는다. 세션 변경·화면 종료 후 남은 명령을 중단한다. 미전송 제외와 전송 후 결과 불명을 구분하며 취소된 명령을 자동 재시도하지 않는다.
- **일괄 결과 과장:** 개인 명령은 항목별, Workspace 지원 명령은 원자적 그룹으로 실행한다. 확인·충돌·권한 없음·결과 불명·지원 제외를 분리하고 확인된 항목을 다시 보내지 않는다.
- **200% 확대:** CSS zoom 이후 남아 있는 데스크톱 media query만 의존하지 않고 실제 셸 너비를 관측해 메뉴와 본문을 재배치한다.
- **오늘 계획과 Flow 갱신:** 계획 저장 이후 Flow의 개인 계획 조회를 무효화해 이동 시 변경이 반영되게 한다. 접근 불가 원천은 제목을 추정하지 않고 불투명 참조를 유지한다.
- **Flow 서비스 보완 진입:** 보완 대기 항목은 검증된 원천 URL을 통해 Services 상세로 이동한다. Work는 같은 SERVICE 참조를 중복 제거해 요약하되 Services의 보완 폼이나 명령을 재구현하지 않는다. 브라우저에서 문서 handoff와 Work발 foreign POST 0회를 확인한다.
- **시각 밀도:** 데스크톱 목록은 충분한 너비에서 식별자/제목/상태 열을 정렬한다. 모바일의 상세 필터는 접고, AI가 열리면 중복 필터를 숨긴다. 잘못된 radius 문자열을 실제 디자인 토큰 값으로 교정했다.

## 검증 결과와 증거의 성격

최종 수치와 로그는 [검증 요약](implementation-evidence/2026-09-07/validation.json)에 기록한다. 브라우저 시험은 실제 React 화면과 요청 경로·직렬화·응답 검증을 사용하되 권한·업무·AI 응답은 통제된 fixture다. 실제 운영 원천 또는 운영 AI에 대한 성공 증거로 바꿔 표현하지 않는다.

백엔드는 PostgreSQL 통합·보안·서비스 보완·개인 업무·Calendar·계약 검증 143건을 통과했고 로컬 Platform/Auth/Gateway에 변경을 반영했다. 프런트엔드에서는 화면별 브라우저 여정, 1440/1280/390/320 및 200%, 키보드·dark·forced-colors·부분 실패, 단위·타입·배포용 컴파일을 확인한다. 자동 axe의 serious/critical 0건은 모든 실제 보조기기와 OS 가상 키보드 검증을 뜻하지 않는다.

최종 정적 검사에서 누락된 `REQUESTER_RESPONDED` 공통 표시 사전의 한국어·영어 항목을 추가했다. 타입·담당 파일 ESLint·번역·표시 사전·원천 권한 계약 검사는 통과했다. 저장소 전체 디자인 시스템 게이트에는 동시 변경된 다른 앱의 기존 JSX 사용 25건 감소에 대한 baseline 갱신이 남아 있으므로 전체 저장소 릴리스 게이트 통과로 표현하지 않는다.

## 남은 외부 조건과 디자인 차이

1. **서비스 보완 API의 실제 테넌트 활성화:** 구현·로컬 배포·도메인/통합 시험은 완료되었으나 tenant 1은 기존 v3 ACTIVE이고 새 action을 포함한 v6은 DRAFT다. 독립된 provider 승인과 platform 활성화가 필요하다. 필요한 검토 범위·체크섬·정확한 endpoint·현재 401/403 근거는 [활성화 검토 자료](2026-09-07-service-response-activation.md)에 준비했다. 승인 주체나 credential을 임의로 만들거나 권한 검사를 끄지 않는다.
2. **원천 API가 제공하지 않는 증빙:** 첨부 목록/다운로드, ERP 잔액, 단말 보안 판정 등은 현재 응답 계약에 없다. 원본 증빙 열기와 제공되지 않은 상태를 표시한다. 시안의 정적 예시를 실제 확인 정보로 표시하지 않는다.
3. **Flow 전체 외형:** 10번은 전사 공통 Flow 홈에 업무·계획 기여와 이동을 구현했다. 원본 10의 Work 사이드바를 포함한 전체 전용 대시보드 외형과 같지는 않다. 10번 기능 명세는 기존 Flow의 앱 실행·조직 소식·일정·개인화 구조를 유지하고 전체 Flow 재설계를 제외하도록 정의했다. 이 역할 경계를 유지했으며 동시 진행 중인 전사 홈 변경도 보존했다. 이 차이를 시안 전체 외형과 동일하다고 판정하지 않는다.
4. **픽셀 동일성:** 공통 셸·글꼴·아이콘·토큰, 실제 원천 데이터와 추가 오류/복구 정보에 따른 차이가 있다. 동일한 데이터·치수의 픽셀 오차 0%를 검증하지 않았으므로 “18개 화면 100% 픽셀 동일” 또는 “모든 운영 연결 완료”로 판정하지 않는다.

18개 화면의 구조와 기능 연결, 정식 권한 릴리스, 원본 픽셀 동일성은 서로 다른 검증 항목이다. 이 구분을 유지해야 이전의 축소 구현을 완료로 보고한 오류를 반복하지 않는다.
