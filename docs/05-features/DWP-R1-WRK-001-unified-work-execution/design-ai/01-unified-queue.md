# 01. 통합업무함 — 앱 기본 화면

화면 ID: `WRK-Q01` · 기준일: 2026-09-04 · 상태: 디자인 목표, 구현 확인표 대조 필요

## 독립 전달용 공통 계약

이 문서 전체를 디자인 AI에 전달해 주세요. 다른 번호의 문서를 보지 않아도 아래 계약을 지켜 디자인할 수 있습니다. 00-shared-context.md가 함께 제공되면 상세 토큰·용어 정의를 추가 적용합니다.

DWP는 조직·권한 기반 디지털 워크플레이스입니다. 업무 앱은 여러 앱의 **내 처리 책임과 실제 결과**를 연결합니다. 기본 진입은 통합업무함이며 기존 ‘업무 홈’을 새로 디자인하지 않습니다. 보기·상세·대화상자를 별도 영구 메뉴로 늘리지 않습니다. Flow는 발견·앱 실행, Calendar는 시간 예약, 전자결재/서비스는 원본 처리, 알림은 읽음·전달, 메일/메신저는 대화, DWAI·ON은 분석·초안·검토형 실행을 소유합니다.

원본 상태, 기한의 긴급도, 개인이 선택한 오늘 계획, Calendar 예약, 원천 반영 결과를 구분합니다. 알림 정리·원본 열기·AI 응답·시간 경과를 업무 완료로 표시하지 않습니다. 원천 항목에는 해당 원천이 허용한 행동만, 네이티브 개인 할 일에는 DWP의 시작·완료·편집을 제공합니다. 권한/지원 계약이 확인되지 않으면 직접 처리 대신 허용된 원본 이동이나 해당 기능 없는 상태를 설계합니다.

원천 접근 상태는 서버가 현재 접근을 확인한 AVAILABLE, 개인 북마크에 참조만 저장된 REFERENCE_ONLY, 확인/사용 불가인 UNAVAILABLE을 구분합니다. REFERENCE_ONLY는 ‘원본 확인 필요’이며 원본 API에서 권한·최신 내용을 확인하기 전입니다. 연결/동기화 성공으로 표현하지 않습니다. AVAILABLE도 개별 변경 명령의 권한을 자동 허용하지 않습니다.

현재 요청은 **디자인 의뢰**입니다. 전체 화면·상태 변형·상호작용·컴포넌트/필드 명세를 만들어 주세요. 코드를 생성하거나 새 앱을 개발·배포하지 마세요. 아래 수치·사람·제목은 모두 기준 시각 2026-09-04 09:30 Asia/Seoul의 **가상 디자인 fixture**입니다. 운영 데이터·실제 연동·완료된 API라고 설명하지 마세요. ‘기존 기반 / 선행 개발 목표 / 조건부 후속’ 구분은 디자인 인계 주석에 남기고 내부 기술명은 사용자 화면에서 숨깁니다.

기존 DWP 셸과 업무 execution-flow/standard 밀도를 사용합니다. 라이트 모드 참고: accent #285C9E, secondary #0C847C, canvas #F5F7FA, selection #E5EDF7. 모서리 4/6/8px, 간격 4/8/12/16/24/32px, 한글 시스템 글꼴, Lucide 아이콘. 의미 토큰으로 다크·고대비에 대응합니다. 유동 셸 안의 안정적인 목록·상세 관계를 쓰고 큰 Hero·무관한 이미지·KPI 카드 나열·장식 차트·글로우·경쟁사 외관 복제를 피합니다.

## 사용자 과업

- 주 사용자: 여러 앱에서 처리할 일을 배정받는 구성원, 결재자, 검토자.
- 질문: “내 조치로 남은 것은 무엇이며 어느 것부터 어디서 처리할까?”
- 주 행동: 선택 업무의 정확한 다음 행동 실행 또는 원본 처리 화면 열기.
- Archetype: list-detail. 보조는 내 책임의 짧은 예외 요약입니다.
- 경로: `/work/queue`; 구 업무 홈으로 한 번 더 우회시키지 않습니다.

## 디자인할 전체 화면

작은 페이지 제목 ‘통합업무함’과 “내게 배정되거나 내가 추적한 업무”라는 범위 설명을 둡니다. 새로 조회한 시각/원천 확인 상태와 ‘개인 할 일 추가’를 배치합니다. 첫 화면의 대부분은 처리할 업무에 씁니다. 동일 수치의 KPI 네 개를 다시 만들지 마세요.

검색·보기·필터 → 목록 → 선택 상세의 일관된 구조를 만듭니다. 전체/내 조치/진행/응답 대기/완료는 원본 책임 상태 기준이고 오늘 계획은 별도 개인 상태입니다. 기한 초과·오늘 마감은 결합 가능한 시간 필터로 만듭니다. 예: ‘진행 중 + 오늘 마감’이 가능합니다. 직접 분류와 조회 가능한 데이터에 없는 팀·프로젝트·개인 생산성 분석을 추가하지 않습니다.

목록 행 정보의 우선순위:

| 우선 | 정보                         | 규칙                                                                     |
| ---- | ---------------------------- | ------------------------------------------------------------------------ |
| 1    | 해야 할 행동이 드러나는 제목 | ‘구매 승인’, ‘사유 보완’, ‘초안 정리’처럼 책임이 읽힘; 2줄까지 핵심 유지 |
| 2    | 원본 상태와 기한             | ‘검토 대기 · 오늘 11:00’; 진행 중과 지연을 별도 표식으로 병기            |
| 3    | 출처/유형·내 역할            | 전자결재/서비스/DWP 할 일; 팀 전체 상태로 오인하지 않음                  |
| 4    | 오늘 계획 여부·우선순위      | 계획 추가와 완료 체크를 혼동하지 않는 조작                               |
| 5    | 마지막 확인·처리 가능 여부   | 정상 반복은 압축, 지연/권한/원천 오류만 명료하게 노출                    |

정렬 기준을 설명할 수 있어야 합니다. ‘지연 우선, 기한, 우선순위’ 등의 실제 계약에 맞춘 정렬명과 이유를 명시하고, 가짜 AI 중요도 점수나 산식 없는 영향 점수를 넣지 않습니다. 기한 없음의 위치를 정의합니다. 사용자의 선택 항목이 갱신되어도 목록이 갑자기 이동하지 않게 처리 규칙을 명세합니다.

## 대표 fixture와 상호작용

APR-031 ‘고객 지원 장비 구매 승인’, 검토 대기, 오늘 11:00; IG-014 ‘재무 시스템 접근권한 정기 검토’, 오늘 17:00; SR-088 ‘원격접속 사용 사유 보완’, 내 응답, 9월 5일; NAT-001 ‘분기 고객 안내 초안 정리’, 기한 없음·오늘 계획; NAT-002 ‘팀 예산 검토 메모’, 진행 중·오늘 17:00·계획 미선택을 사용합니다. 다섯 건의 fixture를 제품의 실제 총건수처럼 일반화하지 않습니다.

행 선택은 상세를 열고 완료시키지 않습니다. 원천 항목은 ‘검토’, ‘원본에서 보완’과 네이티브 ‘완료’를 구분합니다. 검색·원천·기한·상태·선택은 복귀 가능한 맥락이며, 저장 보기의 범위는 실제 저장 계약에 맞춥니다. 서버 페이지가 있으면 현재 조회 범위·더 보기/페이지 이동·전체 검색 범위를 명세합니다. 첫 100개만 읽고 이를 전체 검색 결과로 표현하지 않습니다. 일괄 선택은 항목별 허용 행동의 교집합을 보여줍니다. 서로 다른 원천 20개를 한 번에 승인하는 그림을 만들지 않습니다.

## 반드시 디자인할 상태

1. 정상 업무 다섯 건과 선택 상세.
2. 정상 0건: “현재 내 조치가 없습니다.” 유입 범위 설명과 권한 기반 ‘개인 할 일 추가’. 최근 동기화 성공 근거가 없으면 전부 완료라고 말하지 않음.
3. 검색 0건: 조건을 표시하고 ‘필터 초기화’. 전체 업무가 없다는 안내와 다름.
4. 원천 연결/지원 범위 안내: 개인정보·관리자 기능 없이 내가 볼 수 있는 출처와 마지막 확인.
5. 한 원천 실패: 정상 목록 유지 + “일부 업무를 확인하지 못했습니다” + 해당 출처 재조회.
6. stale·권한 회수·선택 항목 삭제/배정 해제: 민감 상세 제거, 목록 맥락 유지, 원본 최신 상태 재확인.
7. 선택 3건 중 2건만 행동 가능: 사유 및 대상 수, 제한된 실행, 결과는 09번과 연결.

## 구현 범위와 인계

기존 기반은 큐·필터·검색·저장 보기·URL 선택·Review 상세입니다. 상태와 긴급도 분리, 네이티브 생성, 개인 계획, 원천 능력 기반 행동은 선행 개발 확인 대상입니다. 실서버에 업무가 없는 상태와 입력/연동 부재를 구분하는 UX를 포함하되 원천 설정이 일반 사용자에게 가능하다고 가정하지 마세요.

## 화면별 통과/실패

- 첫 viewport에 책임이 읽히는 실제 목록 행 또는 의미 있는 빈 상태와 다음 경로가 보이면 통과.
- 같은 항목에 ‘진행 중’과 ‘오늘 마감’을 함께 표현할 수 있어야 통과.
- 오늘 계획 미선택 업무를 오늘 마감이라는 이유만으로 계획에 넣으면 실패.
- ‘검토 대기’ 원천 항목에 일반 완료 체크를 제공하면 실패.
- 상세에서 돌아오면 필터와 선택이 복원되고, 권한 회수된 본문은 제거되어야 통과.
- 모든 행을 똑같은 큰 카드로 만들거나 기존 업무 홈을 중간에 재도입하면 실패.

## 필수 제출과 공통 통과 기준

- 업무 제목과 사용자가 이해하는 원천명·공식 업무번호를 우선합니다. 현재 호환 화면에 보이는 `PERSONAL_TASK:UUID:` 같은 기술 참조·canonical key·불투명 token을 새 디자인의 업무번호로 복제하지 않습니다. 실제 공식 번호가 없으면 번호를 임의 생성하지 않고 제목과 원천 라벨로 식별합니다. 긴 한영 제목은 상세에서 전체 확인할 수 있어야 합니다.

- 프레임 이름은 `화면ID-크기-테마-상태`로 명명합니다. 1440×900, 1280×800, 390×844, 320×568, 1280px 200% 확대를 모두 제출합니다. 주요 정상 화면은 라이트/다크, 중요 예외는 강제 고대비 변형을 포함합니다.
- 데스크톱을 축소하지 말고 모바일 목록→상세→행동→복귀를 재배치합니다. 320px에서 페이지 가로 넘침·중첩 패널·가려진 주요 행동이 없어야 합니다. 터치 대상은 최소 44px 조작 영역을 확보합니다.
- 키보드 Tab 순서, 가시적 focus, Enter/Space, Escape/뒤로, 대화상자 focus trap/복원, 상태 공지의 문구·시점을 명세합니다. 드래그는 버튼 대안을 제공하고 한글 IME 중 Enter 제출을 막는 동작을 표시합니다.
- 본문 대비 4.5:1, 큰 글자와 핵심 경계/조작 상태 3:1, 상태의 텍스트/아이콘 병기, 긴 한영 제목과 없는 값의 표현을 확인합니다. Reduced Motion에서 위치 이동·지속 애니메이션 없이 같은 의미를 전달합니다.
- 전체 로딩/오류, 정상 0건, 검색 0건, 부분 실패, stale, 권한 없음/회수, 버전 충돌, 실행 중/성공/실패 중 이 화면에 해당하는 상태를 별도 프레임 또는 명세로 제출합니다. 실패를 0이나 성공으로 바꾸면 실패입니다.
- 반복 컴포넌트 anatomy/variants/spacing/최소폭/최대폭/텍스트 처리/모바일 변화/상태/토큰 대응, 필드 의미·편집 주체·null, 행동 전제·효과·취소·실패·복귀를 표로 제출합니다.
- 그림뿐 아니라 사용자의 행동 전후를 연결한 prototype 또는 번호가 있는 흐름도를 제공합니다. 다른 앱으로 이동했다가 돌아왔을 때 필터·선택·스크롤·작성 상태 중 무엇을 유지하는지 명시합니다.
- 아래 화면별 기준과 공통 기준을 모두 통과해야 디자인 완료입니다. 단순히 메뉴가 있거나 API 이름이 보이거나 성공 화면 한 장이 있다는 이유로 통과시키지 않습니다. 기능 지원 여부가 미확정이면 구현 확인표에 남기고 성공한 것처럼 꾸미지 않습니다.

관련 구현·범위 확인은 `implementation-coverage.md`와 저장소의 최신 코드/검증 결과를 사용합니다. 이 프롬프트만으로 운영 제공을 보증하지 않습니다.
