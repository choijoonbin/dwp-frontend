2026-09-07 기준. 사용자 제공 [Stitch 프로젝트](https://stitch.withgoogle.com/projects/13391261371843159731)의 **18개 프레임(데스크톱 11개·모바일 7개)**을 기준으로 구현과 대표 여정을 다시 점검했다. Work와 Services 보완 제출의 이번 개발 범위는 마감했다. 실제 테넌트의 새 서비스 응답 권한 활성화와 저장소 전체 릴리스 승인은 완료되지 않았다.

이 문서는 재개 전의 완료 수치와 원본 대조 기록을 대체한다. 확인은 [18개 화면 대조 갤러리](implementation-evidence/2026-09-07-resume/index.html), [검증 결과와 로그](implementation-evidence/2026-09-07-resume/validation.json), [원본 확인 기록](implementation-evidence/2026-09-07-resume/original-observations.json)에서 할 수 있다.

## 이전 결과가 부족했던 원인

기존 구현은 `/work/queue` 한 곳에 상세·계획·AI를 모으는 앞선 설계 결정을 우선했다. 승인된 디자인의 6개 메뉴와 18개 화면 각각을 수용 조건으로 관리하지 않았고, 큐 렌더링·일부 API 동작 검증을 디자인 전체의 완료로 확대했다. 이 판단과 완료 표현은 잘못이었다. 원천 앱으로 이동하는 일부 URL도 현재 공식 경로와 달랐고, Services의 보완 작성·확인·제출 흐름에는 구현과 오류 복구가 더 필요했다.

이번에는 화면 매핑, 사용자 여정, 실패·권한 상태, 실제 캡처를 각각 확인했다. 개인 업무·계획 전문가, 모바일·접근성 전문가, 원천 앱 경계 검토와 최종 통합 검증을 나눠 수행했다. 중단되거나 과부하로 실패한 실행 로그는 최종 통과 로그와 분리해 보존했다.

## 사용자가 할 수 있는 일

주 사용자는 여러 앱에 처리 책임이 흩어진 임직원이다. “지금 내가 처리할 업무는 무엇이며, 어디서 실행해야 하는가?”에 답하는 목록–상세 화면을 기본으로 제공한다. 오늘 계획은 실행 순서와 수행 시간을 정하는 화면이고, 개인 할 일·서비스 보완 입력은 작성과 확인에 집중한 양식이다.

| 메뉴         | 경로                      | 제공 행동                                          |
| ------------ | ------------------------- | -------------------------------------------------- |
| 통합업무함   | `/work/queue`             | 원천별 업무 검색·필터·정렬·선택과 상세 확인        |
| 내 조치 대기 | `/work/action-required`   | 내가 검토·응답·실행해야 하는 항목 확인             |
| 오늘 계획    | `/work/day-plan`          | 계획 추가·제거·순서 저장, 업무 열기·수행 시간 연결 |
| 진행 중      | `/work/in-progress`       | 진행 중 업무 추적과 개인 상태 변경                 |
| 응답 대기    | `/work/awaiting-response` | 다른 담당자의 응답과 원천 상태 확인                |
| 완료된 업무  | `/work/completed`         | 완료가 확인된 항목 조회와 허용된 개인 업무 재개    |

모바일은 하단 탐색과 더보기에서 6개 보기에 접근한다. 개인 할 일은 생성·편집·삭제 확인, 복수 원천 연결, 체크리스트 저장과 진행률, 상태 전환을 제공한다. 오늘 계획과 Calendar의 일정 저장은 업무 완료와 별개의 동작이다. AI는 선택 업무의 맥락·질문·응답·출처·복사를 제공한다.

## 재개 후 수정한 주요 결함

- **원천 이동:** 결재 보완은 공식 요청 경로, 서비스는 `/services/my/:id` 또는 `/services/drafts/:id`로 이동한다. 실제 소유 앱 상세가 열리는 것까지 확인했다. Work에서 결재·서비스 명령을 중복 실행하지 않는다.
- **개인 업무 상태와 진행률:** 상태 버튼을 기존 명령의 중복 방지·재시도 흐름에 연결했다. 체크리스트 진행률은 서버에 저장된 결과를 기준으로 하며, 미저장 편집을 완료된 진척으로 표시하지 않는다. 버전 충돌에서는 입력을 유지한다.
- **개인 기록과 계획:** 입력 구성·여백·삭제 위치·모바일 상태 버튼을 정리했다. 한글 조합 중 Enter 오작동, 원천 연결 해제, 오늘 계획 열기·제거, 일정 연결의 늦은 응답 혼입을 점검·수정했다.
- **접근권한 검토:** 최신 모바일 M1의 접힌 근거, 유지·회수 2열 선택과 사유 입력을 반영했다. 제출 미리보기, 원천 버전·권한 재검증, 충돌 후 사유 보존을 유지한다. 결정 기록과 실제 권한 반영을 구분한다.
- **서비스 보완:** Services 안에서 작성→검토→제출→접수를 제공한다. 사용자·범위·접근 모드 전환 후 늦은 응답이 새 작성 내용에 반영되지 않게 했다. 같은 요청의 다음 보완 주기를 다시 열고, 409 충돌 뒤 503 재조회 실패에서도 작성 내용을 보존한다. 권한 거부와 없는 원본의 차단은 유지한다.
- **일괄 결과:** 확인·충돌·권한 없음·결과 불명을 구분한다. 응답을 잃은 요청은 같은 식별자와 본문으로 재시도하고, 확인된 항목은 중복 제출하지 않는다.

개인 업무 검토는 [전문가 기록](implementation-evidence/2026-09-07-resume/personal-plan-audit.md), 모바일 M1은 [검토 기록](implementation-evidence/2026-09-07-final/mobile-review-handoff.md), 서비스 보완은 [최종 검증·캡처](implementation-evidence/2026-09-07-resume/services-final/README.md)에 상세히 남겼다.

## 원본과 다른 부분 및 외부 완료 조건

원본 18개 중 모바일 M1·M2는 최신 Polished 노드로 바뀐 것을 링크에서 직접 확인했다. 갤러리에는 이전 두 이미지를 최신 원본으로 표시하지 않고 현재 미리보기 링크를 제공한다. M2는 실제 320px와 낮은 뷰포트에서 개인 기록·저장을 확인했다.

| 범위              | 반영 방식과 남는 차이                                                                                                                                                  |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 02 결재·04 서비스 | Work의 요약에서 각 소유 앱 상세로 이동한다. 원본의 입력 양식 전체를 Work 상세 안에 그대로 배치한 구성과 다르다. 서비스 보완은 소유 앱에서 실제 작성·제출까지 구현했다. |
| 07 계획·10 Flow   | 실제 개인 업무·계획 지표와 정확한 진입을 제공한다. 예시 예측 수치는 만들지 않았고, 전사 Flow 전체를 Work 전용 화면으로 바꾸지 않았다.                                  |

| 12 모바일         | M1의 검토 구조와 M2의 기록 여정을 반영했다. 실제 업무 상태·공통 셸·오류 복구가 포함돼 원본의 시연용 단계 배치·높이와 다르다.                                           |
| 공통              | 승인된 정보 계층·탐색·주요 행동을 DWP 구성요소에 반영했다. 실제 글꼴·토큰·데이터·권한 및 복구 상태 때문에 픽셀 오차 0%를 달성했다고 판정하지 않는다.                   |

서비스 보완에 필요한 권한 번들 **v6은 DRAFT**, 실제 테넌트 활성화는 **BLOCKED_EXTERNAL**이다. 독립된 provider 승인·platform 활성화와 해당 환경에서의 제출 검증 증거가 없다. 이는 화면 개발을 추가로 하면 해결되는 조건이 아니다. 중앙 통합에서 확인한 상태를 유지하며 [정식 활성화 검토 자료](2026-09-07-service-response-activation.md)에 검토 범위·endpoint·체크섬·절차를 준비했다.

개발 결과와 운영 활성화, 화면별 구현 범위와 원본 픽셀 동일성은 별개로 보고한다. 이번 자료는 6개 메뉴와 18개 프레임의 구현·기능 검증 근거이며, 위 차이까지 없다는 의미의 “100% 동일” 판정은 아니다.
