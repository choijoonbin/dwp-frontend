# Work 배정 업무 — 기존 시안에 추가할 디자인 요구

이 문서는 기존 00~12 프롬프트의 원본을 수정하지 않는 **배정 업무 유형 전용 추가 지시**입니다. API 계약은 [contract.md](contract.md)를 함께 전달합니다. 실제 Meeting adapter·승격 통합과 새 화면 구현은 아직 완료로 확인하지 않았습니다.

사용법: 아래 ‘공통 추가 프롬프트’ 전체와 필요한 01/05/09/12 추가 프롬프트를 함께 복사하여 해당 기존 시안과 전달합니다. 기존 개인 할 일은 그대로 두고, `Work 배정 업무` 유형에만 추가 규칙을 적용합니다. 새 영구 메뉴·별도 업무 홈·조직 전체 관리 대시보드를 만들지 않습니다.

## 공통 추가 프롬프트

> 당신은 DWP 제품 디자이너입니다. 기존 통합업무함 시안에 회의 출처의 **확정 배정 업무** 유형을 추가해 주세요. 결과는 화면 시안·상태 변형·상호작용·컴포넌트 명세이며 코드/새 앱/배포를 만들지 마세요.
>
> Meeting은 사람이 검토한 후보·원문·인용·확정을 소유하고, Work는 확정된 제목·설명·담당자·기한·수락·진행·완료를 소유합니다. 기존 개인 할 일은 다른 사람에게 재배정하지 않습니다. “회의 후보 확정”과 “Work 업무 생성”, “담당자 수락”, “업무 완료”를 서로 다른 결과로 표현하세요.
>
> 서버는 수락 상태(PENDING/ACCEPTED/DECLINED)와 업무 상태(OPEN/IN_PROGRESS/WAITING/COMPLETED/CANCELLED)를 별도로 줍니다. 기한의 긴급도와도 구분하세요. 요청자는 담당자의 수락·완료를 대신하지 않습니다. 취소·재배정은 최초 생성자만 가능하고 재배정 시 새 담당자의 수락이 다시 필요합니다. 행동 노출은 현재 capability에 따릅니다. 과거 담당자의 새 행동·현재 업무 조회가 허용된 것처럼 디자인하지 마세요.
>
> Meeting 출처 접근이 사라지면 회의 제목·인용뿐 아니라 source 참조·링크·버전도 모두 숨깁니다. 대신 “회의 출처를 현재 확인할 수 없습니다”처럼 표시하세요. Work가 소유한 확정 제목·설명·배정·진행은 Work 권한에 따라 유지되며 수행도 독립적입니다. 모든 버튼을 출처 실패 때문에 비활성화하지 마세요. 새 생성·재배정은 원천 권한 재확인이 필요합니다. 이 도메인에 개인 북마크의 REFERENCE_ONLY를 넣지 마세요.
>
> 출처는 AVAILABLE/UNAVAILABLE/NOT_REQUESTED 세 상태입니다. 정상 목록은 원본을 조회하지 않아 NOT_REQUESTED를 반환하며 참조·링크·버전이 null, 재배정 capability가 false입니다. “회의 출처는 상세에서 확인”처럼 중립적으로 안내하고 연결 성공·권한 거부·장애로 표현하지 마세요. 목록의 모든 행을 자동 원천 조회하게 만들지 마세요. 상세를 선택하면 현재 조회 결과에 따라 AVAILABLE/UNAVAILABLE로 바뀝니다. 과거 상세의 링크나 승인 상태를 목록에 다시 채워 넣지 마세요. 실제 Work 조회·수행 권한은 출처 미조회와 별개입니다.
>
> 검토되지 않은 AI 후보를 입력하거나, Work 생성 화면에서 후보의 담당자/기한/본문을 임의로 덮어쓰는 UI를 만들지 마세요. 최초 조건은 Meeting의 사람 검토/확정 흐름에서 결정됩니다. Work 재배정은 별도 권한과 현재 상태를 검토하는 명령입니다. WorkAssignment ID·UUID·revision·원천 코드·reasonCode를 일반 사용자용 라벨로 노출하지 마세요. 표시할 공식 번호가 없다면 제목·업무 유형으로 식별하고 가짜 번호를 만들지 마세요.
>
> 기존 DWP 공통 셸·토큰·Lucide·ActionButton/FilterBar/목록·상세·dialog의 시각 언어를 유지하세요. 화면별 1440×900, 1280×800, 390×844, 320×568, 1280px 200% 확대를 제출하세요. 라이트/다크·강제 고대비·긴 한영 문구·Reduced Motion, 최소 44px 터치 조작 영역, 키보드 Tab/Enter/Space/Escape·가시적 focus·dialog 복귀를 포함하세요. 본문 대비 4.5:1, 큰 글자/핵심 경계 3:1과 색 외 상태 단서를 확보하세요. 페이지 가로 넘침·가려진 주 행동·모바일 키보드에 가린 오류는 실패입니다.
>
> 디자인 예시는 아래 가상 fixture만 사용하세요. 운영 데이터나 연결 성공의 증거가 아닙니다. 프레임 주석에 fixture임을 표시하되 제품 본문에 개발용 배지를 넣지 마세요. 정상뿐 아니라 수락 대기·거절·수행 대기·취소·원천 불가·권한 회수·재배정 경쟁·응답 미확인·부분 실패를 제출하세요. API/adapter가 검증되지 않은 흐름은 시안의 조건부 상태로 구분하고 운영 제공으로 표현하지 마세요.

## 01 통합업무함 시안 추가 프롬프트

대상: 기존 [01 통합업무함](../design-ai/01-unified-queue.md). 위 공통 추가 프롬프트와 함께 전달합니다.

> 기존 큐에 Work 배정 업무 유형을 통합하세요. 주 사용자는 업무를 받은 담당자와 자신이 요청한 업무를 확인하는 구성원입니다. 질문은 “내 수락/수행이 필요한가, 상대의 응답을 기다리는가?”이며 주 행동은 해당 항목 선택 후 현재 역할에 맞는 다음 행동입니다. Archetype은 기존 list-detail입니다.
>
> 같은 큐의 보기/필터로 ‘내가 담당’과 ‘내가 요청’을 구분하고 별도 좌측 영구 메뉴를 추가하지 마세요. 업무 제목→현재 내 책임→수락 상태/업무 상태→기한→요청자/담당자 순으로 읽히게 하세요. 요청자와 담당자가 같은 경우 중복 항목·중복 수를 만들지 않도록 표기 기준을 명세하되 self 배정 허용을 임의로 추가하지 마세요.
>
> ‘수락 대기’를 ‘진행 중’으로, ‘거절됨’을 ‘완료’로 표시하지 마세요. 기한 초과는 수락 상태와 동시에 존재할 수 있습니다. 일반 완료 체크박스나 개인 할 일 일괄 처리에 배정 업무를 무조건 포함하지 마세요. 상세에서 role/capability에 맞는 명시적 수락·거절·수행 행동으로 이어 주세요.
>
> ‘내가 담당’ 0건과 ‘내가 요청’ 0건, 검색 0건, 통합 큐의 다른 소스 API 일부 실패, 목록 갱신 중 재배정으로 항목 접근이 사라진 상태를 각각 설계하세요. 배정 목록의 NOT_REQUESTED는 정상 조회이며 ‘회의 연결 실패 n건’이나 부분 실패 배지의 원인이 아닙니다. 목록에서는 출처 링크와 재배정 직접 실행을 제공하지 말고 상세로 이어 주세요. Work 접근이 사라진 경우 이전 제목/담당자/행동을 잔존시키지 말고 현재 확인 범위와 목록 복귀를 안내하세요. 선택·필터·스크롤은 허용되는 범위에서 복귀할 수 있어야 합니다.
>
> 제출: 기존 큐 정상 프레임의 추가 행/필터, 수락 대기와 거절의 선택 상세 연결, 부분 실패/재배정 권한 회수 변형, 행 컴포넌트의 두 상태 축·긴 문구·작은 화면 사양. 수락·진행·기한을 구분하고 실제 역할의 다음 행동이 보이면 통과입니다. 새 Work 홈·새 영구 메뉴·범용 완료를 추가하면 실패입니다.

## 05 상세 시안 추가 프롬프트

대상: 기존 [05 개인 할 일 상세](../design-ai/05-detail-native-task.md)의 상세 구성에 **별도 배정 업무 변형**을 추가합니다. 개인 할 일에 수락·재배정을 붙이지 않습니다. 위 공통 추가 프롬프트와 함께 전달합니다.

> 주 사용자는 현재 담당자 또는 최초 요청자입니다. 질문은 “누가 어떤 조건을 맡았으며 지금 내가 할 수 있는 조치는 무엇인가?”입니다. 담당자의 주 행동은 수락/거절 또는 수락한 업무의 시작·대기·완료, 요청자의 주 행동은 허용된 재배정/취소입니다. Archetype은 큐의 선택 상세이며 재배정/사유 입력은 작은 focus form/dialog입니다.
>
> 필드 순서: Work 확정 제목·설명, 요청자/현재 담당자, 수락 상태와 수행 상태, 확정 기한, 현재 역할의 주 행동, 공개 가능한 출처, 배정·수락·진행 이력. 같은 사람인 최초 요청자와 이번 배정자를 불필요하게 반복하지 말고 정확한 이력에서 구분하세요. 시간 기록이 없으면 대시 등 정의된 null 표현을 사용하고 추정 시각을 만들지 마세요.
>
> 수락 대기에는 조건 검토 후 ‘수락’과 ‘거절’을, 수락 후 활성 업무에는 실제 capability에 따른 ‘시작/대기로 변경/완료’를, 요청자에는 ‘담당자 변경/업무 취소’를 제공합니다. 요청자가 수락·완료를 대행하거나 개인 업무의 보관·재개·자유 편집을 복제하지 마세요. 거절 후 상세에는 거절 결과와 허용된 다음 행동을 남깁니다.
>
> 목록의 ‘출처 미조회’에서 상세 조회 중, 조회 후 AVAILABLE, 조회 후 UNAVAILABLE로 이어지는 변형을 만드세요. 목록 canReassign=false를 영구 권한 거부로 설명하지 말고 상세의 현재 capability로 재판정하세요. 상세 성공에서도 원문을 읽거나 회의 참석을 허용받았다는 표현은 하지 마세요. 원본 이동 시 Meeting이 권한을 다시 확인합니다. 실패 시 예전 reference/링크/버전을 유지하거나 재배정 가능 여부를 추정하지 마세요.
>
> 재배정 form은 현재→새 담당자, 확정 Work 조건, 새 담당자의 수락이 다시 필요하다는 영향, 정책이 제공하는 사유 선택, 확인/취소를 표시하세요. 임의 사용자 ID 입력이나 전체 사원 목록 공개를 요구하지 마세요. 후보 선택은 owner가 허용한 범위에 한정합니다. 거절·취소·재배정은 사유 코드가 필수입니다. 사용자용 사유 선택지·라벨은 별도 확인 대상으로 표시하고 raw reasonCode 입력창이나 아직 서버가 받지 않는 자유사유 본문을 만들지 마세요.
>
> 재배정과 구 담당자의 수락/완료가 경합하면 자동 재시도하지 말고 현재 담당자·상태가 바뀌었음을 설명하고 다시 검토하게 하세요. 확정 중에는 중복 제출을 막되 취소/닫기의 영향을 명시하세요. 권한이 없어지면 이전 민감 source와 명령을 제거하세요. 원천만 불가한 상태는 Work의 확정 조건과 수행을 유지하고 출처 reference/링크/버전을 숨기는 별도 프레임으로 만드세요.
>
> 제출: 역할별 상세, 수락 전/후·거절·대기·완료·취소, 재배정 검토/충돌, source 불가, 원본 왕복 흐름, capability별 버튼·문구·상태 전이표. 배정 상태와 수행 상태가 구별되고 재배정 후 새 수락이 필요함이 드러나면 통과입니다. 개인 task 재배정·대리 수락·원본 삭제에 따른 Work 자동 삭제가 나타나면 실패입니다.

## 09 복구·결과 시안 추가 프롬프트

대상: 기존 [09 원천·복구·일괄 결과](../design-ai/09-source-status-batch-results.md). 위 공통 추가 프롬프트와 함께 전달합니다.

> 주 사용자는 명령을 보낸 요청자/담당자입니다. 질문은 “내 요청이 실제로 적용됐고 지금 업무 상태는 무엇인가?”이며 주 행동은 결과 확인 또는 변경된 조건의 재검토입니다. Archetype은 기존 결과 패널/dialog입니다.
>
> 명령이 적용된 결과와 현재 업무 상태를 나란히 구분하세요. 예를 들어 ‘수락 요청은 적용됐지만 이후 담당자가 변경됨’을 표현할 수 있어야 합니다. 늦게 온 성공 receipt만 보고 현재 담당자·상태를 과거로 덮어쓰지 마세요. 기술 version/revision은 내부 판정에 사용하고 일반 사용자에게 수정하도록 요구하지 마세요.
>
> 필수 변형: 처리 중, 실제 반영 확인, 응답을 받지 못해 결과 미확인, 같은 요청 결과 재확인, 현재 버전/배정 변경 충돌, 현재 권한 없음, source 확인 불가로 생성/재배정 거절, Work 생성 성공·Meeting 연결/알림 확인 미완료. ‘결과 확인’과 ‘새 요청’을 구분하고 모든 오류에 동일 재시도 버튼을 붙이지 마세요.
>
> NOT_REQUESTED는 재시도할 오류가 아닙니다. Work 명령은 적용됐지만 응답의 출처 확인이 불가하면 ‘업무 변경은 반영됐습니다. 회의 출처는 현재 확인할 수 없습니다’처럼 결과를 분리하세요. 생성/재배정의 사전 권한 확인이 만료되어 적용되지 않은 경우에는 ‘조건을 다시 확인한 뒤 요청해 주세요’처럼 재검토를 안내하고 자동 명령 재전송을 하지 마세요. 서버의 제한 시간·HMAC·revision 같은 구현 용어를 사용자에게 해결하도록 요구하지 마세요.
>
> Meeting의 현재 인증된 사용자가 후보를 확정한 뒤 자신의 브라우저에서 Work를 생성합니다. 생성 timeout 뒤 ‘다시 만들기’를 기본 행동으로 만들지 말고 같은 UUID 명령의 receipt와 현재 접근 가능한 동일 후보 Work를 확인하는 경로를 설계하세요. 백그라운드 서버 worker가 사용자를 대신하여 생성 중이라는 상태를 만들지 마세요. 원본 열기·알림 읽기를 수락/완료로 표현하지 마세요. 서로 다른 assignment action을 개인 할 일 일괄 완료에 섞지 말고, 실제 지원 계약이 없다면 일괄 행동 없는 상태를 제시하세요.
>
> 제출: 상태별 정확한 문구·허용 행동·남는 객체·복귀 위치를 표로, 정상/충돌/미확인/부분 성공을 프레임으로 제시하세요. source 불가에서는 참조·링크·버전까지 비노출해야 합니다. 처리 결과와 현재 상태가 구분되고 중복 생성을 유도하지 않으면 통과입니다. 요청 접수만으로 수락·완료·알림 전달 성공을 표시하면 실패입니다.

## 12 모바일·접근성 시안 추가 프롬프트

대상: 기존 [12 모바일·접근성](../design-ai/12-mobile-accessibility-journeys.md). 위 공통 추가 프롬프트와 함께 전달합니다.

> 주 사용자는 작은 화면 또는 키보드로 업무를 검토하는 담당자/요청자입니다. 질문은 “현재 역할과 조건을 놓치지 않고 수락·수행·재배정을 끝내고 목록으로 돌아갈 수 있는가?”입니다. Archetype은 기존 목록→상세와 일시적인 전체 화면 form입니다.
>
> 390/320px에서 수락 상태·수행 상태·기한을 세로로 분리하고 주요 행동을 source preview보다 앞에 놓으세요. 재배정 form의 담당자 선택·사유·충돌 오류가 가상 키보드에 가려지지 않게 하세요. 고정 하단 행동이 마지막 필드/오류를 덮지 않아야 합니다. 작은 화면에 데스크톱 표 전체를 축소하지 마세요.
>
> 아래 여정을 터치와 키보드 양쪽으로 연결하세요: ① 내 담당 목록→조건 검토→수락→시작→목록 복귀, ② 거절→요청자 보기→담당자 변경 검토, ③ source 불가 상태→허용된 Work 수행, ④ 재배정 중 구 담당자의 명령 충돌→현재 상태 재검토, ⑤ 응답 미확인→같은 요청 결과 확인. 접근이 회수된 경우 기존 민감 상세를 유지하는 복귀를 만들지 마세요.
>
> ①과 ③에는 정상 목록의 출처 미조회→선택 상세의 출처 확인→목록 복귀를 포함하세요. 미조회는 오류 공지로 읽히지 않고, 확인 불가일 때만 해당 안내가 공지되어야 합니다. 화면이 좁거나 확대됐다는 이유로 이전 출처 링크를 캐시에서 재노출하거나 배정/수행 상태 중 하나를 생략하지 마세요.
>
> Tab 순서·focus-visible·Enter/Space·Escape·뒤로·dialog focus trap/복원, 완료 후 다음 의미 있는 focus, 상태 공지의 문구·중복 공지 억제를 명세하세요. 한글 IME 확정 Enter가 제출되지 않게 하고, 사유/이름의 긴 한영 문자열, 200% 확대, 고대비·Reduced Motion에서도 동등하게 작동해야 합니다.
>
> 제출: 320/390px 정상·충돌·source 불가·키보드 입력 프레임과 번호가 있는 왕복 흐름, focus 지도, 공통 컴포넌트 변경표. 모든 행동이 현재 역할·capability와 맞고 조건을 읽은 뒤 실행할 수 있으면 통과입니다. 가려진 오류·가로 페이지 넘침·색만으로 수락 구분·임의 자동 재시도가 있으면 실패입니다.

## 반환할 결과물과 완료 경계
