# DWP-R1-ADM-009 근거 및 비판적 검토

> 조사 원칙: 공식 제품·개발자·보안 문서에서 기능 Pattern과 한계를 함께 채택한다. 외부 제품의
> 화면, Asset, 권한 모델 또는 Runtime을 그대로 복제하지 않는다.

## 1. 현재 문제의 정확한 해석

착수 전 `HomeItemGallery`는 전체 Catalog가 아니라 `hiddenApps`와 `hiddenWidgetKeys`만 표시했다.
따라서 기본 Home에 모든 허용 항목이 이미 보이면 `앱 0 / 정보 위젯 0`이 됐다. 이는 API 실패가
아니지만 `홈에 항목 추가`라는 제목 때문에 사용자가 공급 가능한 Widget이 하나도 없다고 해석했다.
이번 Frontend Slice에서는 유형 Tab을 제거하고, 매 진입 기본 `라이브러리`가 Entitled App·Widget
전체와 `추가/복원/홈에 있음` 상태를 표시하도록 수정했다. `숨긴 항목`은 App·Widget 통합 복원
View로 분리했다.

동시에 다음 구조적 한계가 실제로 존재한다.

- Widget Definition 5개가 Frontend 정적 Registry와 닫힌 Type Union에 결합돼 있다.
- Provider Code Set에 Key를 추가해도 Renderer·Config Contract가 없어 새 Widget이 되지 않는다.
- App Catalog는 동적이지만 App이 Widget Definition을 기여하는 계약은 없다.
- `widgetKey`가 Definition과 Instance 식별자를 겸해 동일 Widget의 복수 설정 배치가 어렵다.
- 현재 `HomeTemplate`은 전체 Home Layout이고 일반 사용자 Widget Preset 공유 모델이 아니다.
- Tenant와 Provider 관리 Surface에 Widget Lifecycle Mutation 계약이 없다.

따라서 짧은 UX 수정과 장기 Widget 생태계 기반을 분리해 진행해야 한다.

## 2. 공식 사례 비교

아래 공식 문서는 2026-08-27 다시 확인했다. Microsoft는 Viva 개인 Dashboard에서 재배치·숨김을
지원하면서 Audience Targeting은 보안 수단이 아니라고 명시하고, Atlassian도 Client Display
Condition 위에 별도 Permission 검사를 요구한다. 따라서 DWP의 UI Filter는 발견성에만 사용하고
Server 권한 판정을 대신하지 않는다.

| 사례                        | 채택할 Pattern                                                         | 비판적 한계와 DWP 판단                                                                                   |
| --------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Microsoft Viva / SharePoint | App 팀 공급, Tenant Catalog 배포, 관리자 Dashboard 게시, 사용자 재배치 | Audience Targeting은 보안이 아니다. 과거 Domain-isolated Web Part는 종료됐으므로 그대로 복제하지 않는다. |
| Adaptive Cards              | 표현 Schema와 실제 데이터 분리, Host 렌더링, 버전·Fallback             | Template Service는 Alpha/Preview 성격이므로 운영 의존성으로 채택하지 않는다. 개념만 사용한다.            |
| Salesforce Lightning        | Component Metadata, App Builder 속성, Org·Profile·Form factor 활성화   | Namespace Sandbox와 CSP도 서버 권한을 대체하지 않는다. 자유 Component는 인증된 Provider에 한정한다.      |
| ServiceNow UI Builder       | Component·Data Resource·State·Event 분리, Audience Variant             | UI Audience와 원천 ACL을 별도로 유지해야 한다.                                                           |
| Jira / Forge                | Gadget Definition·Instance Configuration·Dashboard 공유 분리           | Display Condition은 보안이 아니다. iframe만으로 임의 코드가 안전해지지 않는다.                           |
| Backstage                   | Plugin Extension의 명시적 Input/Output·Attachment Point                | 일반 사용자 Template UX의 직접 모델은 아니며 Endpoint 권한 Enforcement를 각 Plugin이 빠뜨릴 수 있다.     |

## 4. 비판적 합성

가장 안전한 합성은 Viva의 공급·Tenant 배포 계층, Adaptive Cards의 표현·데이터 분리, Jira의
Definition·Instance 분리, ServiceNow의 Data Resource 계약, Salesforce의 Component Metadata와
Backstage의 확장 지점을 결합하는 것이다.

다음은 채택하지 않는다.

- 앱마다 자체 Home Builder와 임의 HTML·JavaScript를 제공하는 방식
- Audience, 표시 조건, Frontend 숨김을 권한 검사로 사용하는 방식
- 공유 객체를 모든 사용자가 직접 편집해 변경이 즉시 전파되는 방식
- Template에 조회 결과, 사용자 ID, Token 또는 Credential을 저장하는 방식
- Version, Owner, Migration, Kill Switch, Rollback이 없는 Catalog
- 지원하지 않는 Schema나 권한 오류를 빈 화면으로 축소하는 방식

## 5. 위험과 대응

| 위험                                | 대응                                                                 |
| ----------------------------------- | -------------------------------------------------------------------- |
| Builder 자유도가 보안·접근성을 훼손 | 일반 사용자는 선언형 Preset만, Code Widget은 별도 Provider 인증      |
| 여러 Widget의 N+1 조회·Polling      | Runtime Broker가 Source별 Batch·Cache·Freshness Budget 강제          |
| 공유 Preset의 데이터 유출           | 설정만 공유하고 모든 Binding·ACL을 현재 열람자 기준으로 재평가       |
| Definition 업데이트로 Home 파손     | 불변 버전, 호환 범위, Preview, Migration, Rollback                   |
| Tenant 정책과 개인 설정 충돌        | Provider 안전 정책 → Tenant 정책 → User Preference 우선순위 고정     |
| Catalog가 Card Soup으로 변질        | 각 Widget에 운영 질문, Source, Freshness, 1차 Action, 정보 예산 요구 |
