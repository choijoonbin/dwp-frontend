# DWP-R1-ADM-009 기획 및 아키텍처

## 1. 페이지·제품 계약

| 항목             | 결정                                                                                                        |
| ---------------- | ----------------------------------------------------------------------------------------------------------- |
| Primary user     | Home을 구성하는 일반 사용자, Tenant Experience 관리자, Provider App Owner                                   |
| Primary question | 현재 사용자에게 안전하고 유효한 Widget은 무엇이며 누가 어떤 범위로 공급·게시·사용할 수 있는가?              |
| Primary action   | 사용자는 Widget을 추가·설정하고, Tenant는 허용·대상을 게시하며, Provider는 Definition 버전을 검증·배포한다. |
| Page archetype   | User `Library/Studio`, Tenant `List-detail + Workflow`, Provider `Registry + Release command center`        |
| North star       | Widget 수가 아니라 권한을 지킨 첫 업무 Action과 안정적인 원본 업무 연결                                     |

## 2. 목표와 제외 범위

목표:

- 숨김 복원과 전체 Catalog 탐색을 구분한다.
- App 공급과 사용자 설정·공유를 분리한다.
- 동일 Definition의 복수 Instance와 사용자별 데이터 Binding을 지원한다.
- Provider, Tenant, User의 3개 평면과 Fail-closed 권한 교집합을 고정한다.
- Version, Deprecation, Revocation, Migration과 감사 가능한 Rollback을 제공한다.

제외:

- 사용자 임의 HTML·JavaScript·CSS·SQL·GraphQL·외부 URL Embed
- Tenant가 Provider 보안 정책이나 원천 데이터 ACL을 완화하는 기능
- 사용자 Preset의 Cross-tenant 공유
- MVP의 임의 Remote Component, Theme Marketplace, AI 자동 게시·배치
- Widget 내부 세로 Scroll, 장식 Chart와 출처 없는 합성 데이터

## 3. 도메인 용어

| 객체                      | Owner              | 내용                                                            | 데이터 포함                     |
| ------------------------- | ------------------ | --------------------------------------------------------------- | ------------------------------- |
| `WidgetDefinition`        | Provider/App Owner | Stable Key, Renderer, Data·Action·Config Contract, 크기·Surface | 실행 계약만, 사용자 데이터 없음 |
| `WidgetDefinitionVersion` | Provider Release   | 불변 SemVer, Manifest, Bundle Digest, 호환성·Fallback           | 없음                            |
| `WidgetPreset`            | User 또는 Tenant   | Definition 참조, 필드·상대 Filter·표현 Recipe                   | 설정만, 결과·Credential 없음    |
| `WidgetInstance`          | User               | Home View 내 실제 배치, Instance별 설정·버전·위치               | 개인 설정만                     |
| `HomeView`                | User               | 이름 있는 개인 Home                                             | Instance 참조                   |
| `HomeBlueprint`           | Tenant 또는 User   | 여러 Instance Recipe와 Layout의 공유 Snapshot                   | 설정만                          |
| `CatalogListing`          | Provider/Tenant    | 발견·설명·검증·호환성 Metadata                                  | 실행 데이터 없음                |
| `AudienceRule`            | Tenant             | 역할·그룹·조직·License 등 대상 Rule ID                          | 자유 Query 금지                 |

기존 `HomeTemplate` API는 Home 전체 Layout 의미를 유지한다. 호환 기간에는 UI만
`Home Blueprint`로 표현하고, 단일 Widget 공유 객체에 `HomeTemplate` 이름을 재사용하지 않는다.

## 4. 3개 관리 평면

### 4.1 Provider Control Plane

- App Registry에 Definition과 Publisher를 연결한다.
- Manifest·Renderer Kind·Config Schema·Data Capability·Permission·Egress를 검증한다.
- Security, Privacy, Accessibility, Performance, Locale과 상태 Preview를 인증한다.
- Version Channel·Ring·Deprecation·Kill Switch·Replacement를 관리한다.
- Tenant 데이터 본문을 열람하지 않고 집계 Health와 영향 범위만 본다.

역할 후보: `WIDGET_DEVELOPER`, `WIDGET_REVIEWER`, `WIDGET_RELEASE_MANAGER`, `PROVIDER_AUDITOR`.
고위험 Definition은 작성자와 게시자를 분리한다.

### 4.2 Tenant Administration Plane

- Provider Catalog 중 Tenant 허용 Definition과 Version Channel을 정한다.
- Connector·Scope·Egress·Data Class·공유 정책을 더 엄격하게 제한한다.
- Audience, 기본 배치, 필수·잠금 속성, Quota와 Rollout Ring을 게시한다.
- 사용자 Preset·Blueprint의 Tenant Library 게시를 검토한다.
- Tenant 단위 Disable, 영향 Preview, Revision·Rollback과 감사 이력을 관리한다.

역할 후보: `WIDGET_CATALOG_CURATOR`, `HOME_EXPERIENCE_EDITOR`, `WIDGET_PUBLISHER`,
`DATA_STEWARD`, `TENANT_AUDITOR`.

### 4.3 End-user Studio / Library / Sharing Plane

- 유효 Catalog를 검색·필터·Preview한다.
- App → Definition/Source → Field/Filter → 표현 → Preview 순서로 Instance를 만든다.
- 자신의 Preset을 Private, Direct, Group 범위로 공유하거나 Tenant Library 검토를 요청한다.
- 받은 Preset은 권한·호환성 Diff를 확인한 뒤 개인 사본으로 적용한다.
- 복수 Home, Revision, Device Preview와 조직 기본값 Reset을 사용한다.

공유는 권한을 만들지 않는다. 게시자 권한으로 실행하거나 게시자의 Connector Binding을 재사용하지
않는다.

## 5. 공급과 Runtime 구조

```text
App Team
  └─ signed manifest + data adapter
       → Provider Control RBAC·SoD façade
          → Platform Definition Registry / Certification / Release
          → Tenant Catalog Policy + Audience + Rollout
             → Effective Catalog
                → User Preset / Instance / Home View
                   → Widget Runtime Broker
                      → current-session authorization
                      → Domain API / source ACL
                      → central renderer + safe action
```

일반 Widget은 중앙 Renderer가 승인된 `LIST`, `STATUS_SUMMARY`, `METRIC`, `TIMELINE`,
`TREND` Recipe로 렌더링한다. `TREND`는 실제 동일 Metric 시계열·기간·기준·Text 대안이 있을 때만
허용한다.

App 전용 복잡한 설정은 Schema 기반 Configuration Adapter가 검증된 설정만 반환한다. Code Widget은
별도 Origin Sandbox, Capability RPC, CSP·SRI, Egress Allowlist, CPU·Memory·Timeout, A11y와
보안 심사를 갖춘 후 별도 Phase에서만 허용한다.

## 6. Fail-closed 권한과 Binding

```text
effective = providerPublishedAndSafe
         ∩ packageRequestedCapabilities
         ∩ tenantEntitlementAndPolicy
         ∩ audienceRule
         ∩ currentUserAppAndDomainPermission
         ∩ sourceDataAcl
         ∩ surfaceDeviceVersionCompatibility
```

- Gateway가 검증된 Session에서 Tenant·User를 재생성한다.
- Preset에는 `ASSIGNED_TO_ME`, `TODAY`, `MY_TEAM` 같은 상대 Binding만 저장한다.
- Runtime이 현재 Principal·Org Graph·대리 Context로 Binding을 해석한다.
- Browser가 Tenant/User ID, OAuth Token, 원천 Credential 또는 임의 Source URL을 보내지 않는다.
- Action 목적 Route도 현재 사용자 권한을 다시 확인한다.
- Cache Key는 Tenant, Subject, Permission Fingerprint, Definition Version, Config Hash를 포함한다.
- 개인 Data Cache를 Tenant 공용 Cache로 승격하지 않는다.

## 7. Lifecycle과 Version

Definition 상태를 하나의 진행률 Enum으로 합치지 않는다.

| 축               | 상태                                           |
| ---------------- | ---------------------------------------------- |
| Definition       | `ACTIVE`, `RETIRED`                            |
| Version workflow | `DRAFT`, `SUBMITTED`, `APPROVED`, `REJECTED`   |
| Version release  | `UNPUBLISHED`, `PUBLISHED`, `DEPRECATED`       |
| Version safety   | `CLEAR`, `QUARANTINED`, `REVOKED`              |
| Certification    | `NOT_RUN`, `PASS`, `FAIL`, `EXPIRED`, `WAIVED` |

`PUBLISHED`와 `QUARANTINED`처럼 동시에 참이어야 하는 상태를 단일 Lifecycle 값으로 표현하지 않는다.

Preset·Blueprint는 상태를 한 필드에 섞지 않는다.

- Lifecycle: `DRAFT | ACTIVE | DEPRECATED | REVOKED | ARCHIVED`
- Visibility: `PRIVATE | DIRECT | GROUP | TENANT`
- Review: `NOT_REQUIRED | PENDING | APPROVED | REJECTED`

Instance의 Runtime 상태는 `READY | DEGRADED | STALE | BLOCKED_BY_POLICY |
MISSING_ENTITLEMENT | MIGRATION_REQUIRED | DEFINITION_REVOKED`다. 차단 시 저장 참조를 삭제하지 않고
민감 데이터 없는 이유·대체·제거 Action을 제공한다.

Published Definition·Preset·Blueprint Revision은 불변이다. Patch·호환 Minor는 Canary와 Contract
Test 후 승격할 수 있지만 Major·Config Schema 변경은 Preview·Migration·Tenant 승인·Rollback이
필수다.

Revocation 의미:

- Preset Unlist/회수: 신규 적용 금지, 기존 개인 사본 유지
- Tenant Disable: 해당 Tenant Runtime만 차단
- Provider Security Revocation: 전체 Runtime 즉시 Fail Closed
- Deprecation: 유예 기한·Replacement·Migration 안내

## 8. 기존 계약 Migration

1. 현재 5개 정적 Widget을 비인증 Legacy Seed로 매핑하고 Control-plane 결과만 Shadow 비교한다.
2. 기존 Tenant에 5개 explicit allow 정책을 Backfill하되 신규 Definition Publish는 Allow나 배치를 만들지 않는다.
3. Shadow Diff 0과 Kill·Quarantine Drill 이후에만 v5 Catalog Read를 Authoritative로 전환한다.
4. Layout v5의 `widgetKey`마다 persisted `instanceId`를 부여하고 v6 Dual-write를 시작한다.
5. Layout v6부터 `definitionKey`와 `instanceId`를 분리해 같은 Definition의 복수 배치를 허용한다.
6. Runtime Broker 뒤에만 신규 Data Capability를 열고, 그 뒤에 데이터 없는 Preset을 도입한다.
7. 기존 `usr_home_preferences`, `HomeTemplate`, Classic/Flow Renderer를 즉시 삭제하지 않는다.
8. 알 수 없는 Definition, Version, Renderer와 Authoritative Registry 장애는 정적 Fallback 없이 Fail Closed한다.

현재 `HomePreferenceService`의 누락 Widget 자동 추가 로직에 Registry Publish를 연결하지 않는다. 새
Definition 게시가 기존 Home에 `visible=true` 항목을 생성하면 Tenant 정책·사용자 의사를 모두
우회하기 때문이다.
