## 1. 목표

Flow Home을 기존 개인 Layout과 업무 연속성을 잃지 않고 단계적으로 제공한다. 문제 발생 시 DB를
되돌리지 않고 Tenant Variant 또는 환경 Kill Switch만으로 Classic Home을 즉시 복원한다.

성공은 단순 화면 노출이 아니라 다음으로 판정한다.

- Home의 유일한 세로 Scroll Owner가 Document일 것
- 기존 편집·앱 Folder·Widget 순서·숨김·크기 설정이 보존될 것
- 앱 Badge가 실제 Notification Count이거나 표시되지 않을 것
- Context 96px, Dock 128px·8 visible App 목표로 첫 Viewport가 `Now` 주 Action과 앱
  실행 진입점을 제공할 것
- Desktop이 `Now 8 + 첫 personal 4`, 기본 `Work Signals 4 + Next 8`로 빈 Grid를
  남기지 않고 Mobile·실제 200% 글자 크기에서 한 열로 Reflow할 것
- 필수·Critical 공지만 Rail에 노출하고 일반 Updates는 업무 뒤에 노출할 것
- 영구 Assistant Rail·여백이 없고 Tenant Logo 실패가 Shell을 깨뜨리지 않을 것
- `FORBIDDEN`, `UNAVAILABLE`, Partial, 날짜 불일치가 정상·빈 상태로 위장되지 않을 것
- 부분 API 장애가 Home 전체 Blank로 확산되지 않을 것
- Classic↔Flow 전환에서 Preference Payload Hash가 변하지 않을 것

## 3. Feature Gate

1차는 Generic Provider Rollout을 Browser Runtime에서 직접 호출하지 않는다. 현재 Provider 평가
API는 관리자 `READ` 권한이 필요하고 `externalExecutionEnabled=false`이기 때문이다.

두 Gate를 모두 사용한다.

| Gate                                  | 위치                       | 기본값    | 목적                  |
| ------------------------------------- | -------------------------- | --------- | --------------------- |
| `DWP_HOME_FLOW_ENABLED`               | Platform Runtime 환경 설정 | `false`   | 전체 긴급 차단        |
| `compositionPolicy.experienceVariant` | Tenant Home Experience v3  | `CLASSIC` | Tenant별 승인 Rollout |

판정:

```text
if !DWP_HOME_FLOW_ENABLED              -> CLASSIC
else if tenantVariant != FLOW_V1       -> CLASSIC
else                                   -> FLOW_V1
```

Policy 누락, 알 수 없는 Version·Variant, JSON 파손 또는 조회 실패도 `CLASSIC`이다. 개인화 허용
여부는 별도 `personalCustomizationEnabled`로 계속 서버에서 강제한다.

2차에서 Provider Feature Rollout을 Runtime에 연결하려면 Service-to-service 평가 API, Platform
Tenant ID와 Provider Tenant UUID Mapping, Cache, Fail-closed, 감사 계약을 별도 승인한다.

## 4. 배포 순서

### Stage 0 · Contract 먼저

1. Platform Backend가 Composition Policy v1·v2·v3을 모두 읽도록 배포한다.
2. `experienceVariant` 누락 시 `CLASSIC`인 Contract Test를 통과한다.
3. Preference 동시 저장 Race를 `409 E1009`로 변환한다.
4. OpenAPI의 Required·Enum·Error Response를 보강하고 Client Type을 재생성한다.

Exit:

- 구 Frontend + 신 Backend 회귀 0
- Home Preference Read·Write·Reset Contract Test 100%
- Migration 전 Snapshot Hash 보관

### Stage 1 · Additive 데이터·Notification

1. Composition Policy v3 기본값을 `CLASSIC`으로 Additive Migration한다.
2. 기존 Policy 문서를 v3으로 보강하되 Preference Row는 수정하지 않는다.
3. Notification 앱별 Summary API를 배포한다.
4. Frontend Query의 30초 `staleTime`·`refetchInterval`과 `generatedAt` ±30초
   Freshness Gate를 고정한다.
5. Production-like 데이터에서 Query Plan과 p95를 검증한다.

Exit:

- Policy Row Count·JSON 검증 100%
- 앱별 Count와 Inbox 표본 대조 일치
- Notification API 장애가 기존 Notification Center에 영향 없음
- 권한 없음·최초 Load·Refetch 오류·오래된 성공 Cache에서 Badge가 즉시
  Fail-close되고 정적·Home Overview Count로 대체되지 않음

### Stage 2 · Frontend Dark Launch

1. Flow Component와 Composer Adapter를 배포하지만 Kill Switch를 `false`로 둔다.
2. Storybook·E2E·Visual Regression을 CI에서 수행한다.
3. Classic과 Flow가 동일 Preference Fixture를 읽는 Snapshot Test를 수행한다.

Exit:

- Runtime 사용자 노출 0
- Classic Bundle·Route Regression 0
- Console Error와 Critical·Serious Axe Violation 0

### Stage 3 · Internal Ring

1. Kill Switch를 켠다.
2. 내부 검증 Tenant만 `FLOW_V1`을 게시한다.
3. Member·Manager·Operator, 한국어·영어, Desktop·Mobile을 검증한다.

최소 관찰 시간은 2개 업무일이며 다음 Health Gate를 모두 만족해야 한다.

- Home Error Rate가 Classic 대비 `+0.5%p` 이하
- Preference Save 성공률 `99.5%` 이상
- Notification Badge p95 `300ms` 이하
- Home Overview p95 `1,000ms` 이하
- INP p75 `200ms` 이하, CLS p75 `0.1` 이하, LCP p75 `2.5s` 이하
- Critical·Serious Axe Violation 0건
- 내부 세로 Scroll Container 위반 0건
- Layout Hash 불일치 0건

### Stage 4 · Pilot Tenant

- 지원 가능한 소수 Tenant를 명시적으로 승인받아 `FLOW_V1` 게시
- Tenant별 최소 5개 업무일 관찰
- Help Desk 문의, Editor Conflict, Scroll Reach, App Launch 성공률 검토
- 건강한 Tenant만 다음 Ring으로 이동

### Stage 5 · 확대

Tenant 수 기준이 아니라 사전 승인 Ring으로 확대한다.

```text
Internal -> Pilot -> Early Adopter -> General Availability
```

각 Ring은 독립 승인과 최소 관찰 시간을 가진다. 자동으로 다음 Ring으로 넘어가지 않는다.

## 6. Alert와 Rollback Trigger

### 즉시 Rollback

아래 중 하나면 새 Tenant 확대를 중단하고 전체 Kill Switch를 끈다.

- 권한 밖 데이터 또는 다른 사용자의 Count·Layout 노출
- Preference 손상·유실·다른 사용자 Layout 덮어쓰기
- Home 전체 Blank·무한 Reload·편집 저장 Loop
- Classic↔Flow 전환 중 Layout Payload 변경
- Critical 보안 결함 또는 Critical·Serious 접근성 결함

### Tenant Rollback

아래 중 하나면 해당 Tenant만 `CLASSIC`으로 게시한다.

- Home Error Rate가 Classic 대비 `+1.0%p` 초과 15분 지속
- Preference Save 성공률 `99.0%` 미만 15분 지속
- Home Overview p95 `2,000ms` 초과 15분 지속
- App Badge p95 `600ms` 초과 또는 Error `2%` 초과 15분 지속
- 반복 가능한 Scroll Trap 또는 주요 업무 진입 차단
- 지원 문의가 합의한 Pilot 한도를 초과

### 관찰·수정

단일 Widget 또는 Badge 원천 장애는 Home 전체 Rollback보다 해당 기능 Degrade를 우선한다. 단,
장애가 첫 Viewport의 `Now` 또는 App Dock 실행을 막으면 Tenant Rollback 기준을 적용한다.

## 8. 데이터 Rollback 원칙

- 1차는 `usr_home_preferences` Schema v5와 `appLayout` v1을 유지한다.
- Flow Renderer는 Preference를 자동 Migration하여 저장하지 않는다.
- Composition Policy v3은 v1·v2 호환 Reader를 가진다.
- Rollback은 Variant 전환이며 Flyway Down Migration이 아니다.
- 기존 Tenant Background Asset을 삭제하지 않는다.
- Classic과 Flow가 같은 Preference를 읽으므로 사용자 설정을 Reset하지 않는다.
- Migration 오류 시 새 배포를 중단하고 수정 Forward Migration을 사용한다.

2차 전환은 `기존 Preference -> Default View Backfill -> Shadow Compare -> Dual Write -> Read Switch`
순서를 사용한다. Rollback 기간에는 기존 Store를 유지하고 Read Switch만 되돌린다.
