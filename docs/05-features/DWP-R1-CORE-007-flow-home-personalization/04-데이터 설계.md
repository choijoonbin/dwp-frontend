## 1. 결정 요약

1차 Flow Home은 기존 사용자 설정을 파괴하지 않는 **호환 우선 전환**을 사용한다.
`usr_home_preferences`의 Preference Schema v5와 `layout.appLayout` v1을 그대로 유지하고,
기존 행을 일괄 변환하거나 삭제하지 않는다. 새 화면의 정보 구조와 표현은 Runtime Renderer가
담당하며, Classic Home과 Flow Home은 동일 Preference를 읽는다.

1차에서 추가되는 영속 변경은 Tenant별 Home Variant를 결정하는
`adm_home_experiences.composition_policy` Schema v3뿐이다. 앱별 알림 Badge는 Notification의 기존
사용자 Projection을 집계하며 업무·메일·알림 본문을 Home Preference에 복제하지 않는다.

2차의 다중 개인 홈, 공유 Template, 기기별 고급 Layout, 영구 Version History는 별도 테이블로
확장한다. 1차 테이블을 즉시 교체하지 않는다.

## 3. 1차 Preference 불변조건

서버는 저장할 때 다음을 강제한다.

1. 등록된 `surfaceKey`, `widgetKey`, `presentation`, `size`, `height`만 허용한다.
2. Widget Key는 중복될 수 없으며 최소 하나의 개인 Widget은 표시 상태여야 한다.
3. 조직 정책으로 잠긴 Widget은 숨길 수 없다.
4. `appLayout.version`은 `1`이어야 한다.
5. 앱 ID는 Group 또는 Folder 한 곳에만 존재할 수 있다.
6. Folder는 자신이 선언한 `groupId`에만 배치되며 Folder ID와 App ID가 충돌할 수 없다.
7. `hiddenAppIds`는 중복될 수 없고 Group·Folder에 동시에 남을 수 없다.
8. 개인 설정은 최대 Widget 30개, Folder 50개, Group 12개, 직렬화 크기 96KB다.
9. `version` 불일치는 `409 E1009`로 거부한다.
10. 실행 코드, 픽셀 좌표, 임의 CSS, 업무 본문, 메일·알림 내용, Prompt와 Credential은 저장하지 않는다.

현재 서버 Source는 1~10 불변조건, App·Folder 상호배타 검증과 낙관적 잠금 Race의
`409` 변환을 구현했다. 최신 통합 Frontend Production Build·자동 검증은 통과했고,
Backend Canonical Contract·Migration과 운영 데이터 검증은 출시 Gate에서 별도로 확인한다.

## 4. 높이 Token의 vNext 의미

저장값은 바꾸지 않지만 `workspace-home`의 Flow Renderer에서 의미를 다음처럼 바꾼다.

| Token      | 기존 의미  | Flow Home 의미       |
| ---------- | ---------- | -------------------- |
| `short`    | 288px 고정 | 요약 콘텐츠 2행 예산 |
| `standard` | 368px 고정 | 요약 콘텐츠 3행 예산 |
| `tall`     | 448px 고정 | 요약 콘텐츠 4행 예산 |
| `expanded` | 560px 고정 | 요약 콘텐츠 6행 예산 |

Flow Home Widget은 콘텐츠 높이로 확장하고 Home 문서가 유일한 세로 Scroll Owner가 된다. 예산을
초과한 데이터는 `상위 N개 + 총 건수 + 전체보기`로 표현한다. 저장 Token 값과 Classic Renderer의
해석은 유지되므로 즉시 Rollback할 수 있다.

`WorkSignals`의 네 Metric은 서로 다른 업무 건강도 차원이므로 일반 목록 행 예산을 적용하지 않는다.
이 복합 위젯은 기본 네 Metric과 2×2 구조를 유지하고 높이에 따라 Padding, 비교 표현, Trend와
Freshness의 상세 수준을 조정한다. 사용자가 콘텐츠 표시 수를 명시적으로 저장했거나 Source가
가용하지 않은 경우에만 Metric 수가 줄어든다.

`PLATFORM.HOME_WIDGET_HEIGHT`의 기존 `blockSizePx`, `contentRows`, `phoneMode` Metadata는 Classic
호환을 위해 덮어쓰지 않는다. Forward Migration으로 아래 관리형 필드를 Additive 추가해 Consumer가
Renderer별 의미를 추론하지 않게 한다.

```json
{
  "blockSizePx": 288,
  "contentRows": 2,
  "phoneMode": "CONTENT",
  "flowBlockMode": "CONTENT",
  "flowScrollPolicy": "DOCUMENT"
}
```

`flowScrollPolicy` 허용값은 1차에서 `DOCUMENT` 하나뿐이다. Tenant나 사용자가 이를
`CONTAIN|INTERNAL`로 바꿀 수 없다.

## 5. Flow 고정 Zone과 개인 Action Queue Reconcile

Flow Home의 관리형 고정 위치는 Renderer와 Tenant Policy가 소유하지만, Action Queue는
개인 Preference가 소유하는 Widget이다.

| Flow 영역           | 위치 Source of Truth                 | v5 Preference와의 관계                                                |
| ------------------- | ------------------------------------ | --------------------------------------------------------------------- |
| `My App Dock`       | `FLOW_V1` Renderer의 상단 Slot       | `appLayout`은 Dock 내부 App·Folder만 제어하고 Page 위치는 바꾸지 않음 |
| 관리형 공지         | Composition Policy `governedZones`   | 개인 `widgets`에 합성하거나 저장하지 않음                             |
| Action Queue        | 개인 `command-rail` Widget Entry     | Flow의 `action-queue`와 1:1 매핑하고 표시·순서·크기·높이를 적용       |
| 개인화 가능 Section | Reconcile된 개인 Widget·Section 순서 | Tenant Registry가 허용한 표시·순서·정보 예산만 적용                   |

기존 `command-rail` Widget Entry는 Classic과 Flow가 공유하는 개인 저장 정본이다. Flow Adapter는
이 Entry를 `action-queue`와 1:1로 매핑하며, 사용자는 숨김·복원과 순서 이동, `large|full`
크기, `short|standard` 높이를 저장할 수 있다. Flow 저장은 이 변경을 동일한
`command-rail` Entry로 round-trip하여 Classic Rollback에서도 유지한다.

기존 Device Layout Overlay 호환을 위해 Flow 클라이언트 Adapter는 화면 별칭 `action-queue`와
저장 Key `command-rail`을 모두 해석하되 API Payload에는 하나의 `command-rail` 폭 설정만
기록한다. 기존 Overlay는 그대로 유효하며 두 Key를 별도 Widget으로 중복 저장하지 않는다.

`zoneOrder`, `fixedZones`, `managedZoneOverrides`, `now.visible`처럼 v5에 없는 필드로 고정 Zone을
변경하려는 Payload는 저장 검증에서 거부한다. 이 규칙은 개인 `command-rail` Widget 변경에는
적용하지 않는다. 관리형 공지 변경은 개인 Preference가
아닌 승인된 Home Experience Revision으로만 수행한다.

## 6. Tenant Composition Policy v3

`adm_home_experiences.composition_policy`는 다음 Additive 계약으로 승격한다.

```json
{
  "schemaVersion": 3,
  "experienceVariant": "CLASSIC",
  "personalCustomizationEnabled": true,
  "governedZones": [
    {
      "zoneKey": "announcements",
      "placement": "CANVAS",
      "visible": true,
      "size": "compact",
      "height": "short",
      "sortOrder": 20
    }
  ]
}
```

규칙은 다음과 같다.

- 허용 Variant는 `CLASSIC|FLOW_V1`이다.
- v1·v2 문서는 읽을 때 `CLASSIC`으로 승격한다.
- 알 수 없는 Version·Variant는 Fail-closed `CLASSIC`과 개인화 비활성으로 처리한다.
- 영속 기본값은 `CLASSIC`이다.
- `FLOW_V1` 게시와 복원은 기존 Home Experience Revision·Audit 계약을 재사용한다.
- Runtime의 실제 Variant는 환경 Kill Switch와 Tenant Variant를 모두 만족해야 한다.

```text
effectiveVariant =
  DWP_HOME_FLOW_ENABLED && experienceVariant == FLOW_V1
    ? FLOW_V1
    : CLASSIC
```

## 7. 앱별 알림 Badge 데이터

현재 Home App 정의의 정적 Badge는 데이터가 아니므로 제거한다. Notification Service의 기존
`ntf_user_notifications`, `ntf_notifications`, `ntf_notification_types.owner_app_key`를 사용자 범위로
집계한다.

```json
{
  "appKey": "messaging",
  "totalUnread": 6,
  "actionableUnread": 2,
  "urgentUnread": 0,
  "lastActivityAt": "2026-08-21T00:29:45Z"
}
```

불변조건은 다음과 같다.

- 집계는 로그인 사용자의 Tenant·User Projection만 사용한다.
- Home App Registry에 `notificationSourceKey`를 명시하고 이름 추론을 금지한다.
- Frontend는 현재 Entitled App과 교집합한 Count만 표시한다.
- `0`은 Badge를 표시하지 않는다. 장애·부분 장애에서 정적 숫자로 대체하지 않는다.
- REST Query의 Cache Stale·Refetch 간격은 각각 30초다. 응답 `generatedAt`은
  현재 기준 ±30초 범위에서만 Badge Source로 신뢰한다.
- Notification 권한이 없거나 Query 최초 Load·Refetch가 실패하거나 성공 Cache가
  30초를 넘기면 모든 Summary Badge와 Metadata를 제거한다. 이전 Badge·정적 Count·
  Home Overview Count로 Fallback하지 않는다.
- Fresh·Healthy Partial 응답에서만 성공 App의 Count를 유지하고 실패 Source를
  제거한다.
- 앱별 집계에 사용자 ID, 제목, 본문, Thread ID 또는 업무 Object ID를 반환하지 않는다.
- 기존 Index로 Query Plan을 검증하고 목표를 충족하지 못할 때만 앱별 Counter Projection을 추가한다.

## 8. Communications Action Snapshot

Home의 필수·Critical Rail은 일반 소식 표본에서 Action 항목을 다시 추론하지 않는다.
`GET /v1/communications`가 Tenant·User·Role·현재 활성 기간·Audience를 적용한 사용자 전체
Action Snapshot을 함께 반환한다.

| 필드              | 의미                                                                                   |
| ----------------- | -------------------------------------------------------------------------------------- |
| `required`        | 확인 필수이면서 아직 확인하지 않은 항목 수. Critical이라는 이유만으로 포함하지 않는다. |
| `criticalUnread`  | `severity=CRITICAL`이며 아직 읽지 않은 항목 수                                         |
| `actionable`      | `required ∪ criticalUnread`의 ID 중복 제거 합집합 수                                   |
| `actionableItems` | 위 합집합의 Action-first 상세 Slice                                                    |

`criticalUnread`와 `actionable`은 일반 소식의 `featured + items`, `scope`, 검색어와 콘텐츠 유형
필터에 독립적인 DB 집계다. `actionableItems`도 같은 필터와 일반 소식 표본에 독립적이며 다음 순서로
정렬한다.

1. 읽지 않은 Critical
2. 확인 기한이 가까운 항목
3. 고정 항목
4. 최근 게시 항목

일반 활성 소식 Hydration은 기존 최대 100건을 유지한다. 응답 `size`와 Action 상세 Slice는 요청당
1~48건으로 제한하고 Home은 8건을 요청한다. 따라서 `actionable`은 전체 권위 건수이고
`actionableItems`는 우선순위 상세 Slice일 수 있다. 집계와 상세 ID 조회는 동일한
`REPEATABLE_READ` Snapshot에서 수행한다.

신규 필드는 Additive 계약이다. Rolling 배포 중 구버전 서버에서는 Frontend가 기존 `required`와
현재 응답 항목으로 안전하게 Fallback하되, 신규 서버에서는 권위 집계와 `actionableItems`를 우선한다.

## 9. 손상 데이터 복구 계약

저장된 Preference가 현재 Registry와 조정 불가능하더라도 Home 전체를 `500`으로 만들지 않는다.
서버는 다음 정보를 포함한 복구 가능 기본 Layout을 반환한다.

```json
{
  "customized": true,
  "integrityStatus": "RECOVERED",
  "layout": {
    "appLayout": {
      "version": 1,
      "groups": {},
      "folders": {},
      "hiddenAppIds": []
    },
    "presentation": "balanced",
    "widgets": [
      {
        "widgetKey": "command-rail",
        "visible": true,
        "size": "large",
        "height": "short"
      }
    ]
  },
  "version": 7,
  "warnings": ["INVALID_STORED_LAYOUT"]
}
```

현재 `version`을 유지해 사용자가 저장 또는 초기화할 수 있어야 한다. 원본 Payload는 감사·장애
조사 범위에서만 취급하고 Browser로 반환하지 않는다. `VALID|RECONCILED|RECOVERED`는 Additive
응답 필드이며 구버전 Client가 무시할 수 있어야 한다.

## 10. 2차 확장 Schema

### 10.1 `usr_home_views`

| Column                                | 계약                     |
| ------------------------------------- | ------------------------ |
| `view_id`                             | UUID PK                  |
| `tenant_id`, `user_id`, `surface_key` | 소유 범위                |
| `view_key`                            | 사용자 범위 Stable Key   |
| `name`                                | 정제된 표시명, 최대 80자 |
| `is_default`                          | Surface별 활성 기본 Home |
| `schema_version`, `layout_payload`    | 검증된 Layout Snapshot   |
| `version`                             | 낙관적 잠금              |
| 감사 Column                           | 생성·수정 Actor와 시각   |

제약:

- `UNIQUE(tenant_id, user_id, surface_key, view_key)`
- `(tenant_id, user_id, surface_key) WHERE is_default` Partial Unique Index
- 사용자별 Surface당 최대 10개 View

### 10.2 `usr_home_view_revisions`

| Column                       | 계약                      |
| ---------------------------- | ------------------------- |
| `revision_id`                | UUID PK                   |
| `view_id`, `revision_number` | View별 불변 순번          |
| `schema_version`, `snapshot` | 복원 가능한 전체 Snapshot |
| `source`                     | `USER`, `TEMPLATE`, `AI`  |
| `change_summary`             | 정제된 변경 요약          |
| `created_at`, `created_by`   | 생성 증적                 |

Revision은 Append-only이며 `UNIQUE(view_id, revision_number)`를 강제한다.

### 10.3 `adm_home_templates`

Tenant 공유 Template은 `template_id`, Audience, Lifecycle, 검증된 Layout, Version, 게시 Actor를
저장한다. Template 적용은 개인 View의 새 Revision을 만들며 원본 Template과 이후 개인 변경을
분리한다.

## 11. 2차 전환 규칙

1. 신규 테이블을 Additive 생성한다.
2. 기존 `usr_home_preferences` 행을 각 Surface의 `default` View로 Backfill한다.
3. Tenant·User·Surface별 Row Count와 정규화 JSON Hash를 비교한다.
4. Dual Read와 Shadow Compare를 수행한다.
5. 안정화 후 Dual Write를 켜고 신규 Store를 Read Source로 전환한다.
6. Rollback 기간에는 기존 Preference 테이블을 삭제하거나 쓰기 금지하지 않는다.
7. 보존기간과 복구 훈련 완료 후 별도 승인 Migration에서만 Legacy 정리를 검토한다.

## 12. Privacy·Retention

| 데이터                     | 분류                        | 보존                                    |
| -------------------------- | --------------------------- | --------------------------------------- |
| Widget·App 배치, 표현 모드 | `PREFERENCE_ONLY`           | 계정·Tenant 정책에 따름                 |
| 앱 실행 횟수·최근 사용     | `CONFIDENTIAL` 행동 신호    | 기존 Workspace Preference 정책          |
| 앱별 알림 Count            | `CONFIDENTIAL` Runtime 집계 | 응답·Cache만, Home에 별도 저장하지 않음 |
| Home 행동 Telemetry        | 집계 Metric                 | 자유 Text·개인 ID 금지                  |
| 업무·메일·알림 본문        | Home 저장 금지              | 원천 Domain 정책                        |

AI 제안은 Layout Diff만 생성하고 업무 본문이나 행동 원장을 Preference에 기록하지 않는다. AI가
사용자 승인 없이 Layout을 저장·이동·삭제할 수 없다.

## 13. 출시 전 승인 항목

- [ ] Product: 1차 Source of Truth와 2차 통합 범위
- [ ] Design: 높이 Token의 콘텐츠 예산 의미와 모든 `전체보기` 목적지
- [ ] Platform: Composition Policy v3, Preference 복구 응답, Migration
- [ ] Notification: 앱별 집계 Query·SLO·부분 장애 계약
- [ ] Security·Privacy: Telemetry Dimension과 사용 신호 Retention
- [ ] QA: Classic↔Flow 전환 시 Layout Hash 보존 증거

이 문서가 기록한 Source 구현 완료는 운영 활성화를 의미하지 않는다. 위 승인, Backend
Canonical Contract Test, Migration·Rollback Drill과 운영 Owner가 연결된 뒤만
Release-ready로 전환한다.
