# 실행 관측·증적 아키텍처

기준일 2026-09-07. 이 문서는 활동 앱이 표시하는 실행 단계, 지연 시간, 원천 상태, 재시도 정보와 감사 증적의 정본·권한·상태 의미를 고정한다. 운영 배포·운영 환경 검증은 사용자 요청에 따라 제외하지만, 코드·DB 이행·API·UI·로컬 씨드·자동 검증의 로컬 완료 기준은 하나의 계약으로 관리한다.

## 설계 원칙

1. Agent 실행 상태는 `dwp_agent.ai_agent_runs`가 소유한다. Platform에 실행 복제 원장을 만들지 않는다.
2. 메일·캘린더 연결 상태는 Platform의 기존 개인별 productivity subject/stream 원장을 읽는다. 실행 상세의 원천 관측치는 Agent가 해당 run의 실제 호출에서 측정한다.
3. 감사 hash와 일별 무결성 checkpoint는 Platform 감사 원장이 소유한다. Agent의 결정적 중앙 UUID는 조회 주소일 뿐 실제 중앙 ingest나 검증의 증거가 아니다.
4. 질문, 답변, 인용 본문, 대화 제목, connector credential, provider identifier, raw error는 활동 API에 노출하지 않는다. 실행 제목은 신뢰할 수 있는 agent catalog key에서만 만든다.
5. 없는 단계, 없는 지연 시간, 추정 연결률을 만들지 않는다. 미계측과 미검증은 `NOT_AVAILABLE`, `PARTIAL`, `PENDING`, `UNAVAILABLE`로 구분한다.

## Agent 실행 계측

Agent V31은 기존 run에 audit 주소와 provenance를 추가하고 현재 attempt의 stage/source telemetry 테이블을 추가한다. run API는 다음을 제공한다.

- `activityTitle`: prompt가 아닌 서버 카탈로그 기반 안전 제목
- `attempt`: lease generation에서 계산한 1 이상의 시도 차수
- `lease`: `ACTIVE | EXPIRED | RELEASED`와 만료 시각
- `currentStage`, `stages`: 순서, 상태, 시작·종료 시각, 실측 `durationMs`
- `progressPercent`: 저장된 5개 operational stage의 완료·건너뜀 전이를 각 20%로 계산한 값
- `measurementStatus`: `MEASURING | MEASURED | PARTIAL | NOT_AVAILABLE`
- `sourceHealth`: 해당 run에서 실제 시도한 원천의 결과, latency, 최근 시도·성공 시각
- `auditEvidence`: Agent audit ID, 결정적 중앙 record 주소, 연결 상태
- `dataProvenance`: `LIVE | SAMPLE`

단계 전이는 run/attempt lease fencing을 만족한 writer만 추가할 수 있다. 종료 단계는 수정하지 않고 retry는 같은 run의 새 generation으로 분리한다. 성공한 terminal run의 미실행 operational stage는 `SKIPPED`로 닫지만, 실패 run은 실제 전이만 계산하며 자동으로 100%가 되지 않는다.

PostgreSQL 목록·상세 조회는 run과 telemetry를 `READ ONLY REPEATABLE READ` snapshot으로 읽고 최초 generation에 결속한다. 조회 중 재시도가 시작되어도 이전 attempt row와 새 telemetry를 혼합하지 않는다.

## 감사 증적 의미

Platform evidence의 `linkStatus=LINKED`는 사건이 실제 중앙 audit record를 가진다는 뜻이다. 무결성은 별도의 `integrityStatus` 값으로만 표시한다.

- `PENDING`: 중앙 audit event는 있으나 해당 일자 checkpoint가 없음
- `VERIFIED`: 기존 감사 서비스가 저장한 checkpoint 검증 결과
- `FAILED`: 기존 감사 서비스가 저장한 실패 결과
- `UNAVAILABLE`: 연결, 권한 또는 검증 결과가 없음

`recordHash`, `hashAlgorithm`, `verifiedAt`은 `ADMIN.AUDIT_VIEW:VIEW`에서만 노출한다. `integrityScope=DAILY_CHECKPOINT_REPORTED`는 감사 원장 소유자가 저장한 일별 관측이며 법적 진본성, 규정 준수, 감사 통과를 보증하지 않는다.

기존 Activity event의 `auditStatus`는 하위 호환용 link 표기이므로 checkpoint 판정으로 사용하지 않는다. UI의 무결성 상태는 evidence receipt의 `integrityStatus`를 사용한다.

Agent는 local audit ID에서 UUIDv5 중앙 record 주소를 계산해 저장하지만, 현재 publisher에는 중앙 ingestion acknowledgement가 없다. 따라서 정상 run도 `auditEvidence.status=PENDING`이며 스스로 `LINKED` 또는 `VERIFIED`를 선언하지 않는다. Platform 중앙 receipt API는 같은 tenant/actor, source service `dwp-agent-runtime`, target type `AGENT_RUN`, UUID target을 실제 조회하고, 아직 ingest되지 않았으면 404를 반환한다.

## 개인 원천 상태

Platform source API는 현재 사용자의 permitted Mail/Calendar stream만 반환한다. effective status는 다음 우선순위로 계산한다.

`connector.lifecycle → connector.policy → subject.consent → connector.health → stream.state`

따라서 policy가 `BLOCKED` 또는 `REVIEW_REQUIRED`이면 underlying stream이 `READY`여도 차단 상태를 먼저 표시한다. 응답의 `observedAt`은 Platform 저장 원장을 읽은 시각이며 `lastAttemptAt`/`lastSuccessAt`과 구분한다. 빈 목록은 연결되지 않았거나 읽을 권한이 없는 coverage이며 100% 건강 상태가 아니다.

Agent `sourceHealth`는 connector 전체 상태가 아니라 해당 run에서 실제 시도한 source call의 결과다. 둘을 하나의 성공률로 합치지 않는다.

## SAMPLE 격리

- Platform fixture는 `SAMPLE`이며 서버 기본값은 OFF다. `DWP_ACTIVITY_LOCAL_FIXTURES_ENABLED=true`, 사용자 `900018`, correlation `activity-local-joonbin`, source event prefix `activity-local:`이 모두 맞을 때만 목록·상세·native evidence에 포함한다. source fixture도 reserved connector key일 때만 local flag로 노출한다. 실행 summary는 항상 SAMPLE을 제외한다.
- Agent fixture는 `/api/agent/v1/runs` list/detail에서 provenance를 유지한 채 표시하지만 공통 `/api/agent/v1/activity/**`는 LIVE만 읽는다. 따라서 공통 피드·상세·KPI에는 SAMPLE이 없다.
- Platform cursor scope는 local fixture flag를 포함하므로 flag 전환 전 cursor를 재사용하지 못한다.

| 소유자   | 활성화·실행 조건                                                                                                                                                                  | 생성 내용                                                    |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Platform | Flyway가 아닌 `seed-local-activity-demo.sql`을 transaction에서 실행하고 `SET LOCAL dwp.activity.seed_profile='local-joonbin'`; 표시 시 `DWP_ACTIVITY_LOCAL_FIXTURES_ENABLED=true` | SAMPLE native work/event 3건, 개인 connector 2건, stream 3건 |
| Agent    | `DWP_ENVIRONMENT=local`, `DWP_AGENT_LOCAL_ACTIVITY_SEED_ENABLED=true`, `DWP_AGENT_DATABASE_URL` 설정 후 startup                                                                   | SAMPLE run 4건과 현재 attempt stage/source telemetry         |

두 seed는 `tenant_id=1`, `user_id=900018`(`joonbin@sk.com`)에만 귀속된다. Platform은 IAM user와 Calendar person public ID 결속을 먼저 확인한다. Agent는 run ID와 request ID를 잠금 상태에서 tenant/user/provenance까지 검사한다. 충돌 시 일부 데이터를 남기지 않고 transaction을 실패시킨다.

Platform connector fixture의 공개 effective status는 primary MAIL `READY`, primary CALENDAR `STALE`, attention MAIL `BLOCKED`다. 예약 connector/subject/stream ID에 기존 credential, provider binding 또는 sync cursor가 있으면 해당 레코드를 재사용하지 않고 전체 transaction을 실패시킨다. 이 데이터의 `semantics=LOCAL_FIXTURE`와 timestamp는 Microsoft Graph 또는 외부 provider의 실제 동기화 증거가 아니다.

Agent fixture 4건은 완료된 grounded run, policy handoff, source unavailable/not configured, runtime failure를 제공한다. 실제 로컬 적용 결과는 run 4건, stage 21건, source-health 4건이다. 모든 audit 상태는 `PENDING`이며 prompt·답변 본문·비밀번호·token·credential·권한 grant는 생성하지 않는다.

## 캐시·실패 처리

Platform security filter는 `/v1/workspace/activity/**`의 성공·오류 응답 모두에 `Cache-Control: private, no-store, max-age=0`를 설정한다. Agent run API도 성공 응답과 명시적 detail 404/503을 `no-store`로 보낸다. 프런트는 증적 요청이 실패했을 때 이전 receipt를 재사용하거나 `VERIFIED`로 유지하지 않는다.

부분 원천 장애에서는 성공 원천 결과를 유지하면서 실패 원천과 freshness를 명시한다. 모든 원천이 실패했거나 권한이 없으면 빈 값과 원인을 보여 주고 추정 KPI를 만들지 않는다.
