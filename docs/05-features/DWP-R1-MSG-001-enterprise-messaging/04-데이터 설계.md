# 04. 데이터 설계

## 1. 데이터 소유권

- System of Record: 신규 PostgreSQL Database `dwp_messaging`
- Message Body: R1 PostgreSQL Partitioned Store
- Attachment Binary: Object Storage
- Search Document: OpenSearch 파생 Projection
- Presence·Typing·Connection: Redis TTL Data
- Space Membership: `dwp_space`가 원장, Messaging은 접근 Projection만 소유
- Person Profile: `dwp_people`가 원장, Messaging은 안정 ID와 최소 Snapshot만 소유
- App/Admin Grant: `dwp_auth`가 원장

메시지를 Space, Platform, Notification Table에 나누어 저장하지 않는다. 한 Conversation의
메시지·Reaction·Revision은 하나의 Messaging 원장에 한 번만 저장한다.

## 2. 공통 규칙

- 모든 Tenant 데이터 Table은 `tenant_id`를 가진다.
- FK는 가능한 한 `(tenant_id, entity_id)` Composite Scope를 검증한다.
- 외부 식별자는 UUIDv7을 사용하고 연속 내부 ID를 URL에 노출하지 않는다.
- 시각은 `TIMESTAMPTZ`, 사용자 표시는 Preference의 IANA Timezone으로 변환한다.
- 변경 가능한 Aggregate는 `version BIGINT` Optimistic Lock을 사용한다.
- 상태와 유형은 Check Constraint로 허용 값을 제한한다.
- 자유 형식 HTML과 검증되지 않은 JSON을 저장하지 않는다.
- 이메일·사용자 이름을 Membership Key로 사용하지 않고 `user_id`, `person_public_id`를 사용한다.
- Runtime Role, Migration Role, Compliance Export Role을 분리한다.

Application Repository는 모든 Query에 Tenant 조건을 강제한다. 민감도가 높은 배포에서는
Transaction 시작 시 검증된 Tenant Context를 설정하는 PostgreSQL RLS를 Defense-in-depth로
추가하며, Connection Pool Context 누수 테스트를 필수로 한다.

## 3. Table 설계

### 3.1 Tenant와 정책

| Table                    | 핵심 Column                                        | 역할                           |
| ------------------------ | -------------------------------------------------- | ------------------------------ |
| `msg_tenants`            | `tenant_id`, `home_region`, `lifecycle_state`      | 메시징 Tenant Provisioning     |
| `msg_tenant_policies`    | 생성, 수정·삭제, 읽음, 파일, 외부, AI 정책         | 현재 Tenant 정책 Version       |
| `msg_retention_policies` | `scope_type`, `retention_days`, `retain_revisions` | 대화 유형·분류별 보존          |
| `msg_policy_revisions`   | 이전·이후 Payload, 행위자, 사유                    | 정책 변경 증거와 Rollback 근거 |

Retention 기본값은 Source Code나 Seed 상수로 고정하지 않는다. SKAX 개발 Tenant에는 예시
정책을 Seed할 수 있지만 실제 딜리버리에서는 법무·보안 승인을 받은 Tenant 정책을 적용한다.

### 3.2 대화와 Membership

| Table                               | 핵심 Column                                           | 역할                        |
| ----------------------------------- | ----------------------------------------------------- | --------------------------- |
| `msg_conversations`                 | 유형, 제목, 분류, 공개성, 상태, 정책 Reference        | 대화 Aggregate              |
| `msg_conversation_bindings`         | `SPACE`, `MEETING`, `WORK_ITEM` Reference             | 외부 업무 Context 연결      |
| `msg_conversation_memberships`      | Principal, Role, Source, 유효기간, 이력 시작 Sequence | Local ABAC 원장             |
| `msg_membership_projection_offsets` | Source, Aggregate, Sequence, 상태                     | Space·People 동기화 정합성  |
| `msg_conversation_sequences`        | `next_sequence`, `version`                            | Conversation 단조 증가 순서 |

`msg_conversations` 주요 규칙:

- `conversation_type`: `DIRECT`, `GROUP`, `CHANNEL`, `ANNOUNCEMENT`, `INCIDENT`, `MEETING`
- `lifecycle_state`: `ACTIVE`, `ARCHIVED`, `DELETION_PENDING`, `DELETED`
- `membership_mode`: `DIRECT`, `MIRRORED`, `SCOPED_SUBSET`
- `history_policy`: `FULL_HISTORY`, `FROM_JOIN`, `NO_HISTORY`
- `data_classification`: DWP 공통 `PUBLIC`, `INTERNAL`, `CONFIDENTIAL`, `RESTRICTED`
- 1:1 DM은 `(tenant_id, direct_participant_fingerprint)` Unique

`msg_conversation_memberships` 규칙:

- `principal_type`: `USER`, `BOT`
- `member_role`: `VIEWER`, `MEMBER`, `MODERATOR`, `OWNER`
- `membership_source`: `DIRECT`, `SPACE`, `ORG_GROUP`, `MEETING`, `INVITE`, `PROVISIONING`
- `history_start_sequence` 이전 메시지는 API와 검색 모두에서 반환하지 않음
- Source Membership이 해지되면 수동 Membership으로 자동 변환하지 않음

## 4. Message Store

| Table                    | 핵심 Column                                                       | 역할                           |
| ------------------------ | ----------------------------------------------------------------- | ------------------------------ |
| `msg_messages`           | Message ID, Conversation, Sequence, Sender, Current Content, 상태 | 사용자 조회 Current Projection |
| `msg_message_revisions`  | Message ID, Revision, Content, 변경 사유·시각                     | 수정·삭제 이력                 |
| `msg_message_mentions`   | Message, Mentioned Principal, Mention Type                        | 알림·검색·감사                 |
| `msg_reactions`          | Message, Principal, Reaction Key                                  | Reaction 원장                  |
| `msg_attachments`        | Object Reference, Hash, MIME, Size, Scan 상태                     | 첨부 Metadata                  |
| `msg_message_tombstones` | 삭제 유형, 정책, 삭제 시각, 색인 상태                             | 삭제 전파와 재처리             |

`msg_messages` 주요 Column:

- `message_id UUIDv7`
- `tenant_id BIGINT`, `conversation_id UUID`
- `sequence BIGINT`
- `thread_root_message_id UUID NULL`
- `sender_user_id BIGINT`, `sender_person_public_id UUID NULL`
- `sender_display_snapshot VARCHAR(200)`
- `content_schema_version INTEGER`, `content_payload JSONB`
- `message_type`: `USER`, `SYSTEM`, `APP`, `DECISION`, `ACTION`
- `delivery_state`: 영속 원장에서는 `COMMITTED`만 저장
- `current_revision INTEGER`
- `edited_at`, `deleted_at`, `retention_until`
- `created_at`, `version`

Unique는 `(tenant_id, conversation_id, sequence)`에 둔다. `message_id`는 Application이 생성한
UUIDv7이며 Idempotency Ledger와 함께 중복을 막는다. Conversation Sequence는 같은 Transaction
안에서 증가시키며 Gap은 허용한다.

### Revision과 삭제

- 수정은 Current Payload를 갱신하고 이전·신규 Revision을 남긴다.
- 사용자 삭제는 본문을 Tombstone으로 바꾸되 정책이 요구하는 Revision은 보존한다.
- Retention 삭제는 Search, Attachment, Cache, Projection에 Tombstone Event를 발행한다.
- Legal Hold가 있으면 사용자 화면에서 사라져도 승인된 Compliance Store에는 보존할 수 있다.
- Hold가 포함된 Partition은 통째로 Drop하지 않는다.

## 5. Partition과 Index

R1 `msg_messages`와 `msg_message_revisions`는 다음 계층을 사용한다.

1. `created_at` 월 단위 Range Partition
2. 각 월 안에서 `conversation_id` Hash Subpartition
3. 기본 16개 Hash Bucket, Capacity Test 후 조정

필수 Index:

- `(tenant_id, conversation_id, sequence DESC)`
- `(tenant_id, sender_user_id, created_at DESC)`
- `(tenant_id, thread_root_message_id, sequence ASC)` partial
- `(tenant_id, retention_until)` partial for non-held rows
- Mention은 별도 Table의 `(tenant_id, mentioned_user_id, created_at DESC)`

History Cursor는 `beforeSequence`와 `limit`을 사용한다. Offset Pagination을 사용하지 않는다.
Partition 수, Autovacuum, Bloat, Index Size, Retention Window를 운영 지표로 둔다.

## 6. 사용자 상태 데이터

| Table                               | 역할                                            |
| ----------------------------------- | ----------------------------------------------- |
| `msg_read_cursors`                  | 사용자별 마지막 읽은 Sequence, 마지막 표시 시각 |
| `msg_user_conversation_preferences` | Mute, Notification, Favorite, Sidebar Section   |
| `msg_drafts`                        | 사용자·대화별 Versioned Draft                   |
| `msg_scheduled_messages`            | 실행 시각, Timezone, Payload, 상태, Idempotency |
| `msg_saved_items`                   | Later, Reminder, 완료 상태                      |
| `msg_thread_follows`                | Follow와 Notification 수준                      |

메시지별 Read Receipt Row를 모든 대형 채널에 생성하지 않는다. 사용자·대화별 Cursor로 읽음을
계산하고, 1:1·소그룹에만 정책상 허용된 읽음 상태를 Projection한다.

Draft는 다른 사용자에게 보이지 않고 짧은 Retention을 가진다. Client Local Storage만을 원장으로
사용하지 않아 기기 전환과 Browser 종료에도 복구한다.

## 7. 업무 연결과 App

| Table                       | 역할                                                             |
| --------------------------- | ---------------------------------------------------------------- |
| `msg_action_links`          | Message와 Work·Approval·Calendar·Service 객체의 안전한 Reference |
| `msg_app_installations`     | Tenant/Space 설치, Manifest Version, Scope, 상태                 |
| `msg_bot_identities`        | Bot Principal, Publisher, App Reference, 상태                    |
| `msg_webhook_subscriptions` | 승인 Event, Target Secret Reference, 재시도 정책                 |

`msg_action_links`는 대상 객체 전체를 복사하지 않는다. `app_key`, `resource_type`,
`resource_public_id`, `route`, `last_known_state`만 저장하고 열 때 대상 앱에서 권한을 재검증한다.

## 8. 파일 데이터

`msg_attachments`는 다음 상태를 가진다.

`QUARANTINED → SCANNING → AVAILABLE | BLOCKED → DELETED | HELD`

- `object_key`, `version_id`, `sha256`, `detected_mime`, `declared_mime`, `size_bytes`
- `scan_engine`, `scan_signature_version`, `scan_result`, `scanned_at`
- `classification`, `retention_until`, `legal_hold_state`
- File Name은 화면 표시 Metadata이며 Object Key에 원문을 넣지 않는다.
- 동일 Hash라도 Tenant 간 Deduplication을 하지 않는다.

## 9. Legal Hold와 eDiscovery

| Table                       | 역할                                            |
| --------------------------- | ----------------------------------------------- |
| `msg_compliance_cases`      | Case ID, 목적, 승인자, 기간, 상태               |
| `msg_legal_hold_scopes`     | 사용자, 대화, Space, 기간 Scope                 |
| `msg_hold_capture_jobs`     | 과거 Capture와 증분 Capture Cursor              |
| `msg_compliance_exports`    | Watermark, Hash Manifest, WORM Object Reference |
| `msg_compliance_access_log` | 누가, 왜, 무엇을 조회·내보냈는지 증거           |

Hold는 Retention보다 우선한다. Case 종료 후에도 기존 Tenant Retention에 따라 삭제 가능 시점을
다시 계산한다. Export는 Object Version, Manifest Hash, 생성 Tool Version을 함께 고정한다.

## 10. 신뢰성 Table

| Table                     | 역할                                                |
| ------------------------- | --------------------------------------------------- |
| `msg_idempotency_keys`    | Actor, Operation, Key, Request Hash, 결과 Reference |
| `msg_domain_event_outbox` | Transactional Event 발행                            |
| `msg_domain_event_inbox`  | Consumer Dedupe, Ordering, Lease, Retry             |
| `msg_projection_offsets`  | Search·Realtime·Notification Consumer 진행 위치     |
| `msg_reconciliation_runs` | Space·Search·Attachment·Retention Drift 검사        |

Idempotency Key 재사용 시 Request Hash가 다르면 `409`로 거부한다. Outbox가 발행되지 않아도
메시지는 Committed 상태이며 재처리 Worker가 복구한다.

## 11. 개인정보와 퇴직자

- Message에는 회사 이메일을 반복 저장하지 않는다.
- 발신자 이름 Snapshot은 역사적 문맥을 위한 최소 정보이며 Message Retention을 따른다.
- People 계정 비활성화 즉시 새 전송과 구독을 막는다.
- Hold가 없고 법적 삭제 대상이면 Snapshot을 정책에 따라 `탈퇴한 구성원`으로 가명화한다.
- Search Index와 Cache에도 같은 가명화·삭제 Event를 적용한다.
- Presence, Typing, 검색 Query 원문을 장기 보관하거나 Analytics 원문으로 사용하지 않는다.
