# 04. 데이터 설계

## Bounded Context

| Prefix  | 소유 책임                    | 대표 Table                                                     |
| ------- | ---------------------------- | -------------------------------------------------------------- |
| `ppl_*` | Core HR Workforce Projection | Person, Worker, Assignment, Organization, Relationship         |
| `tme_*` | Time & Attendance            | Schedule Profile, Worker Schedule, Time Card, Entry, Exception |
| `abs_*` | Absence & Leave              | Leave Plan, Enrollment, Balance, Request                       |
| `bnf_*` | Benefits Experience          | Program, Plan, Enrollment Window, Enrollment                   |
| `pay_*` | Payroll Readiness·문서 참조  | Pay Cycle, Pay Statement Reference                             |
| `tal_*` | Talent·Learning·Journey      | Journey Template·Instance, Goal, Learning Assignment           |
| `svc_*` | 공통 Employee Service        | Category, Definition, Request, Timeline                        |
| `int_*` | 외부 HRIS 연계               | Source, Mapping, Connector, Receipt, Sync Run                  |
| `sys_*` | 감사·Outbox·서비스 기준      | Audit Event, Delivery Ledger, Tenant Service                   |

Core HR Person·Worker를 각 업무 Table에 복제하지 않는다. 모든 업무 Row는 `tenant_id`와
`worker_id` 복합 FK로 활성 Workforce Projection을 참조한다.

## 핵심 무결성

- Tenant가 다른 Worker·Plan·Card를 참조할 수 없도록 복합 FK를 사용한다.
- 사용자에게 노출하는 식별자는 UUID `public_id`, 내부 Join은 BIGINT PK를 사용한다.
- 쓰기 가능한 Aggregate는 `version`으로 Optimistic Concurrency를 강제한다.
- Time Card는 `(tenant_id, worker_id, period_start_date)`당 하나다.
- 활성 Time Entry는 Card·일자·유형당 하나다.
- 제출·승인 휴가는 PostgreSQL `tstzrange` Exclusion Constraint로 시간 구간 중복을 막는다.
- Leave Balance는 승인 완료 시에만 Pending·Used를 전이한다.
- 제출 휴가 철회는 Cancellation Evidence와 Version을 저장한 뒤 Pending만 원복한다. 승인 후
  취소는 Used Balance를 직접 되돌리지 않고 승인된 정책 Workflow에서 처리한다.
- 팀 부재 Query는 현재 유효한 직속 Assignment만 사용하고 향후 60일로 제한한다.
- HR 문의는 `svc_*`를 재사용하며 `hr_case`, `hr_request` 같은 중복 Aggregate를 만들지 않는다.
- 급여 문서는 금액 Payload를 저장하지 않고 암호화 저장소의 Opaque Reference와 Checksum만 보유한다.
- 업무 변경은 동일 Transaction의 Audit Outbox에 기록한다.

## JSONB 사용 원칙

JSONB는 Tenant별로 변할 수 있으나 독립 조회·제약·관계가 필요하지 않은 규칙 Payload에만
사용한다.

| 허용                                                              | 금지                                                 |
| ----------------------------------------------------------------- | ---------------------------------------------------- |
| 근무일 패턴, Plan Rule, Payroll Readiness, Journey Task Blueprint | Worker Identity, 승인 상태, 금액, 유효일, 관계, 권한 |

JSONB는 `jsonb_typeof` 제약을 가지며 계약 Version 또는 Code Catalog와 함께 진화한다.

## 데이터 출처

| `data_origin` | 의미                                    |
| ------------- | --------------------------------------- |
| `SOURCE`      | 승인된 외부 System of Record에서 동기화 |
| `MANUAL`      | 권한 있는 사용자가 DWP에서 생성         |
| `REFERENCE`   | Local/Pilot 검증용 비권위 데이터        |

Reference Seed는 Tenant Provisioning 때 멱등 실행하며 고객 운영 데이터로 승격하지 않는다.

## 확장 원칙

- 국가별 규칙은 Core Table 증식보다 Policy Version·Code Catalog·Connector Contract로 확장한다.
- Payroll 계산, Benefit Provider Transaction, LMS Content는 해당 System of Record에 남긴다.
- Compensation·Performance·Recruiting이 독립 수명주기와 권한을 가지면 별도 Prefix와
  Migration으로 추가하고 `ppl_workers`를 참조한다.
- Table Rename은 의미 개선만으로 수행하지 않는다. 데이터 소유권이 바뀔 때 ADR과 호환
  View·이행 계획을 먼저 승인한다.
