## 문제와 근거

- 대상 사용자: 일반 구성원, 프로젝트·조직 리더, Space Owner, Content Reviewer,
  Tenant Governance 관리자, App·Data·Security 담당자
- 현재 Trigger: 공통 목적을 가진 구성원이 사람, 문서, 업무 앱, 결재, 일정과 AI Context를
  한곳에서 운영하고 싶을 때
- 현재 문제: `DWP Workspace`가 정적 Label에 머물고 Tenant, 개인 업무, 협업 Context의
  의미가 분리되지 않았다. 별도 Space 수명주기·Scoped Membership·Template·게시 통제도 없다.
- 시장 근거: Teams·Slack·Notion·Confluence·SAP Work Zone은 모두 목적별 협업 단위,
  Owner 위임, 접근 수준, Template과 중앙 Governance를 제공한다.
- 핵심 위험: 모든 생성·콘텐츠를 중앙 건별 승인하면 속도와 책임이 모두 떨어진다. 반대로
  무통제 셀프서비스는 중복·고아 Space, 외부 공유, 권한·보존 Drift를 만든다.

## 범위

### In scope

- `Space` 독립 App과 Context Selector
- My Spaces, Discover, Favorites, 최근 Space, 가입·생성 요청
- Versioned Template와 Tenant 배포 정책
- Space 생성 위험 평가와 Approval Hub 연동
- Space 내부 역할, Membership, Group·HR 조직 동적 연결, Guest 기간제 접근
- Overview, Activity, Content Metadata, Task·Calendar·Approval·App·Resource Binding
- Content Type별 Draft·Review·Publish·Moderation 정책
- Space Owner Studio와 Tenant Control Center
- Lifecycle Review, Owner 재지정, Archive·Restore·Delete·Legal Hold
- Search·Agent Context와 Source ACL 필터
- i18n, 접근성, Mobile·Tablet·Desktop, Audit·Observability

### Non-goal

- Teams·Slack를 대체하는 자체 실시간 Chat·Video Engine 전체 구현
- SharePoint·Drive·Jira·SAP 원문 복제
- 별도 전자결재 Engine 구현
- HR 조직 계층을 Space 구조로 강제
- Provider가 Tenant Content를 기본 열람하는 Support 모델
- R2에서 외부 조직 간 Federation 전체 구현

### Horizontal Core와 Industry Pack 경계

- Core: Space, Membership, Policy, Template, Lifecycle, App·Resource Binding, Agent Context
- Telecom·Semiconductor Pack: Network Incident, Fab Shift, Quality Review, Customer War Room 같은
  Template·Policy·Connector 묶음
- 업종 Pack은 Core Table이나 Workflow를 Fork하지 않고 Versioned Extension으로 배포한다.

### Build·Embed·Connect 결정

- Build: Space Directory, Template, Request, Owner Studio, Content Metadata, Lifecycle
- Connect: Auth/IAG, Approval Hub, App Registry, Audit, Search, Agent Runtime
- Embed: 승인된 업무 App의 Space Context View
- External SoR: Chat, Document, Issue, ERP 원문은 Connector Reference로 연결

## 생성 정책

### 위험 신호

- 공개 범위: Private, Discoverable, Tenant-wide, External
- 데이터 분류: Public, Internal, Confidential, Restricted
- 구성원: 내부 사용자, 동적 Group, Guest, 외부 조직
- App·Connector: 사전 승인 여부, OAuth Scope, 쓰기·관리 권한

- 기간·규모: 종료일, 예상 Member·Content Volume
- 규제: Legal Hold, Export Control, 개인정보, 고객 데이터

## Journey

### Space 생성

1. 사용자는 `/spaces/new`에서 목적 또는 Template을 선택한다.
2. 이름·목적·Owner·공동 Owner·기간을 입력한다.
3. 공개 범위, 분류, 구성원 Source와 예상 규모를 정한다.
4. App, Connector, Knowledge Source와 Agent 사용을 선택한다.
5. 시스템은 예상 승인 경로, 정책 이유, Provisioning 항목을 Preview한다.
6. 제출 후 Approval Hub가 필요한 결정을 수집한다.
7. 승인 완료 시 Provisioning Saga가 Space, Membership, 기본 Content, Binding을 만든다.
8. 사용자는 Timeline과 실패·재시도 상태를 확인한다.

### 가입과 접근

1. 사용자는 Discover에서 자신에게 공개된 Space를 찾는다.
2. Open은 즉시 가입하고 By Request는 사유·기간을 제출한다.
3. Invite Only·Hidden은 초대 또는 직접 Deep Link 권한 검사로만 접근한다.
4. 기간제 Membership은 만료 전에 Owner와 사용자에게 알린다.

### Content 생성·게시

1. 사용자는 Content Type과 Template을 선택하고 Draft를 작성한다.
2. 자동 검사가 Malware, DLP, 분류, 링크 안전성과 필수 Metadata를 확인한다.
3. 일반 협업 Content는 즉시 게시하고 공식·외부·규제 Content만 Reviewer Queue로 보낸다.
4. 승인·반려·수정 요청은 Version과 Comment를 보존한다.
5. 게시 후 검색·Agent Index는 동일 ACL과 삭제 계약으로 갱신한다.

### Lifecycle

1. 종료일 또는 비활성 기준 도달 시 Owner Review Task를 만든다.
2. Owner는 연장, Owner 이관, Read-only Archive, 삭제 요청 중 하나를 선택한다.
3. 미응답·Owner 부재는 Governance Queue로 Escalation한다.
4. Archive 후 복구 기간을 거쳐 Legal Hold와 보존 계약을 확인하고 Purge한다.

## 정책과 위험

- 개인정보·기밀등급: Tenant Classification Catalog를 사용하고 Space 기본값보다 약한
  Content 분류를 금지할 수 있다.
- 보존·삭제: Space Policy와 원본 SoR 정책 중 더 강한 계약을 적용한다.
- 법무·규제: Legal Hold 중 Purge 금지, 외부 공유·Export는 별도 Evidence를 남긴다.
- AI 사용: Tenant·App·Space·Source ACL 교집합을 강제하며 재학습에 사용하지 않는다.
- Separation of Duties: Template 작성·게시, 요청·승인, Grant·Review를 가능한 한 분리한다.
