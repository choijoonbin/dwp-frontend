# DWP-R1-CORE-006 Pilot 권한 Registry Seed

## 1. 목적과 권위

이 문서는 Technical Canary, Approvals와 HCM의 순차 Authorization Bundle에 들어갈
PAGE/DATA/ACTION·Predicate Seed를 고정한다. [05-API 권한 계약](./05-API%20권한%20계약.md)의
Capability·Access Policy·Entitlement Expression Descriptor와 이 문서의 Route·Profile·Binding·
Predicate Seed를 함께 조립한 단 하나의 Backend Canonical
`contracts/product-authorization/product-surfaces-v1.yaml`이 생성 원천이다. 둘 중 하나만으로
Seed를 만들거나 제2의 수기 Registry를 두지 않는다. Generator Diff 0 승인 전에는 활성화하지 않으며,
구현자가 Route Key, Public Gateway Path, Service PEP Path나 Access Profile을 다시 정하지 않는다.

표기 규칙:

- `P:`는 Public Gateway Binding, `S:`는 Downstream Service PEP Binding이다.
- Platform은 `P /api/platform` ↔ `S /v1`, Approval은 `P /api/approvals` ↔ `S /v1`,
  People은 `P /api/people` ↔ `S /v1`을 명시적으로 저장한다. Runtime Prefix 추론은 금지한다.
- PAGE만 UI Path/Pattern을 가진다. DATA와 ACTION은 Browser Resolver에 참여하지 않는다.
- 모든 Product Route는 표의 Surface와 동일한 Product/Surface를 가진다.
- Surface Entry를 먼저 평가하고 Child Route는 표의 Profile 하나를 다시 평가한다.
- `full-work`, `full-management`, `auditor`, `provider-support`, `legacy-oversight` Profile
  우선순위는 각각 300, 300, 200, 150, 100이다.
  Client는 Profile을 선택하지 않는다.
- UI Pattern은 React Router와 같은 `:id`, API Binding은 OpenAPI와 같은 `{id}`를 사용한다.
  두 표기는 Generator가 임의 변환하지 않고 각 Catalog 원문과 대조한다. API의 `{id}`는 Runtime
  Wildcard 권한이 아니다.

### 1.1 Compact Row의 결정적 확장

아래 표는 Canonical YAML을 사람이 다시 설계하지 않도록 다음 규칙으로 완전히 확장한다.

| Section                      | Product / Surface                                 | `navigationContextId`       | 기본 Service / Owner                     |
| ---------------------------- | ------------------------------------------------- | --------------------------- | ---------------------------------------- |
| Communications Work          | `communications / communications.work`            | `communications.work`       | `platform` / Platform + Security         |
| Communications Manage        | `communications / communications.management`      | `communications.management` | `platform` / Platform + Security         |
| Services Work                | `services / services.work`                        | `services.work`             | `platform` / Platform + Security         |
| Services Manage              | `services / services.management`                  | `services.management`       | `platform` / Platform + Security         |
| Approvals Work/Manage        | `approvals / approvals.work 또는 approvals.admin` | 해당 Surface Key            | `approval` / Approvals + Security        |
| HCM Personal/Team/Ops/Manage | `hcm / hcm.*`                                     | 해당 Surface Key            | `people` / People + HR Security          |
| Named Review                 | `subject=GOVERNED_CONTEXT`, Context=`work.work`   | `work.work`                 | `auth` / Identity + Workspace + Security |

- Row의 `mappingVersion=1`, `policyVersion=1`, `lifecycleState=ACTIVE`다. Bundle은 다음 불변
  Promotion Chain으로 나누며 아직 구현·검증되지 않은 Row는 다음 Bundle에도 넣지 않는다.

| Bundle Key / Version   | 활성 Row 집합                                          | Release Gate                |
| ---------------------- | ------------------------------------------------------ | --------------------------- |
| `product-surfaces / 1` | W0 Registry + Named Review + Communications + Services | V87·V88, Canary OpenAPI/PEP |
| `product-surfaces / 2` | 승인된 Version 1 Snapshot + Approvals                  | V89, Approvals Contract/E2E |
| `product-surfaces / 3` | 승인된 Version 2 Snapshot + HCM                        | V90, HCM Contract/E2E       |

세 Bundle은 같은 `bundleKey=product-surfaces`와 서로 다른 Version·SHA-256를 가진 Immutable
Snapshot이다. 다음 Wave는 직전 승인 Snapshot을 입력으로 새 Version을 생성하고 하나뿐인 Active
Pointer를 원자적으로 바꾼다. 서로 다른 Bundle Key의 Active Pointer를 병렬 생성하지 않는다.
Rollback은 같은 Key의 직전 승인 Version으로만 수행한다. Post-Pilot 예약 Key는 행 자체가 없으며
ACTIVE/RETIRED Row로 추론하지 않는다.

- PAGE의 `uiRouteId`는 Route Contract Key에서 `route.`와 `.page`를 제거한 안정값이고 UI 열의
  Pattern을 그대로 사용한다. DATA/ACTION은 UI 필드를 갖지 않는다.
- Public/Service Binding Pair는 Route Key + 표의 위에서부터 `binding.01`, `binding.02` 순의
  Stable Key를 가진다. Service Binding은 위 표의 기본 `serviceKey`를 물리화한다. HCM의
  `/services/**`, `/catalog/code-sets/**` Binding은 행에서 `S[platform]`으로 Override하고 Owner도
  Platform을 공동 승인자로 추가한다. Canonical YAML에는 축약어가 아니라 양쪽 Method·Path·
  `serviceKey`를 모두 물리화한다.
- `PAIR[service](METHOD /path)`는 축약 표기일 뿐 Runtime Prefix 규칙이 아니다. Generator는
  `platform → /api/platform + /v1`, `approval → /api/approvals + /v1`,
  `people → /api/people + /v1`, `auth → /api/auth + /auth`의 정확한 Public/Service 두 Binding을
  즉시 물리화한다. 한 행의 Path 목록은 각 Method·Path마다 별도 Stable Binding Pair가 되며
  `/**`, “동일 Suffix” 문자열이나 Prefix 추론을 YAML에 남기면 Build를 실패시킨다.
- 표의 `fixed name=value`와 `allowlist {...}`는 양쪽 Binding의 Typed
  `pathParameterConstraints`로 물리화한다. 표시가 있는 Parameter를 자유 문자열로 남기면 Build를
  실패시킨다.
- PAGE/DATA의 각 응답 Binding은 기본적으로 `<routeKey>.<profileKey>.projection.v1`과 OpenAPI Operation의
  Versioned Response Schema Key를 갖는다. Generator가 현재 Schema의 허용 Field Path와 Hash를
  Bundle에 물리화하며, Schema 변경은 새 승인 Bundle 없이는 Default-deny다. ACTION에는 Read
  Projection을 만들지 않는다. 표가 `→ <projectionPolicyKey>`를 명시하면 그 Key가 기본 생성 규칙보다
  우선하며, 같은 Binding·Profile에 둘을 동시에 만들면 Build를 실패시킨다.
- Work PAGE/DATA의 기본 Profile은 `full-work`, Management는 `full-management`다. 표가
  `auditor`, `provider-support`, `legacy-oversight`를 명시한 경우에만 해당 Profile을 추가한다.
- Profile의 기본 `readOnly`는 `full-work=false`, `full-management=false`, `auditor=true`,
  `provider-support=true`, `legacy-oversight=true`다. Route가 Read-only를 명시하면 그 값이 우선하며,
  현재 유효한 Mutation Grant가 없는 Effective Context·Scope는 서버가 최종적으로 true로 낮춘다.
  어떤 규칙으로도 단일 boolean이 결정되지 않으면 Seed Build를 실패시킨다.
- `full-work`, `full-management`, `auditor`, `legacy-oversight`의 `activeAccessModes`는
  `[NORMAL,ELEVATED]`, `provider-support`는 `[PROVIDER_SUPPORT]`다. 다른 Mode를 합치거나 빈 배열을
  만들면 Build를 실패시킨다.
- Access 표기는 `<profileKey>: policy:<key>`, `<profileKey>: capability:<key>` 또는
  `<profileKey>: expression:ANY|ALL(<key>...)`만 허용한다. 아래 행의 축약 표기는 이 문서에서
  규정한 총함수로 먼저 정규화하고 Canonical YAML에는 실제 Typed Member와 Key만 쓴다.
  Work Access Policy는 Communications=`communications.work-access.v1`,
  Services=`services.work-access.v1`, Approvals=`approvals.work-access.v1`다.
- `target X`는 `targetBindingKinds:[X]`, `targets [X,Y]`는 정렬·중복 제거한 Non-empty 배열,
  `predicate K`는 `predicatePolicyKeys:[K]`, `predicates [K1,K2]`는 같은 순서의 AND 배열로
  물리화한다. `→ projectionKey / ResponseDto`는 해당 Binding/Profile의 명시
  `responseProjectionBindings` Override다. 이 문법에 맞지 않는 Access Cell은 Build 입력으로
  허용하지 않는다.
- Predicate 표기는 다음 Registry Key로 확장한다: `Self` → `predicate.self-person.v1`,
  `Visible Communication` → `predicate.visible-communication.v1`,
  `Communication Reader` → `predicate.communication-reader-action.v1`,
  Services `Own Request` → `predicate.platform.own-request.v1`, Approvals `Own Request` →
  `predicate.approval.own-request.v1`, `Relationship+TP` → `predicate.team-target-population.v1`,
  `Domain TP` → `predicate.hcm-domain-target-population.v1`, `Configuration Scope` →
  `predicate.hcm-configuration-scope.v1`. Object Version은 Owner Service별
  `predicate.platform.object-version.v1`, `predicate.approval.object-version.v1`,
  `predicate.people.object-version.v1`을 사용한다. `Claimable Task` →
  `predicate.approval-task-claimable.v1`,
  `Decidable Task` → `predicate.approval-task-decision.v1`, `Published Form Target` →
  `predicate.approval-published-form.v1`, Export Population →
  `predicate.hcm-export-population.v1`. Approval Task Read는
  `predicate.approval-task-readable.v1`, Organization Approval/Publish SoD는 각각
  `predicate.hcm-org-approval-sod.v1`, `predicate.hcm-org-publish-sod.v1`이다.
  이 Key와 표의 `SELF|OBJECT|RELATIONSHIP|TARGET_POPULATION|CONFIG_SCOPE` Target Binding은
  Access Profile에 저장하고 Client 입력으로 받지 않는다.

Capability Descriptor의 미표기 필드는 다음과 같이 총결정한다. `owner`는 Section 표의 Owner,
`mappingVersion=1`, `policyVersion=1`, `lifecycleState=ACTIVE`, `riskTier=LOW`,
`activationPolicy=null`, `sodPolicyId=null`, `sunsetAt=null`이다. 표의 HIGH는
`STEPUP-MGMT-HIGH-V1`, CRITICAL은 `STEPUP-MGMT-CRITICAL-V1`로 Override한다. Publish는 해당
Maker-checker SoD, Approvals Recovery는 `SOD-APR-OPS-AUDIT-V1`, Org Publish는
`SOD-HCM-ORG-PUBLISH-V1`, Org Approval은 `SOD-HCM-ORG-APPROVAL-V1`을 결속한다. Legacy
Oversight는 05 계약의 Owner·Sunset·Projection을
Override한다. `resolvedCapabilityCode`, Responsibility, Scope Resolver는 05의 Exact Matrix와 이
Seed의 Access/Predicate를 결합하며 어느 하나라도 비면 Build를 실패시킨다. 모든 Governed Access
Policy와 Entitlement Expression도 Owner=해당 Product+Security, Version 1, ACTIVE로 물리화하고
05의 Typed Tree·Mode·Resolver를 그대로 저장한다. Pilot Entitlement Expression Key는
`COMMUNICATIONS_WORK_ACCESS_V1=APP.COMMUNICATIONS:VIEW`,
`SERVICES_WORK_ACCESS_V1=APP.EMPLOYEE_SERVICES:VIEW`,
`APPROVALS_WORK_ACCESS_V1=APP.APPROVALS:VIEW`와 05에 열거한 HCM 식으로 고정한다.

### 1.2 Predicate Policy Seed

모든 행은 Version 1, ACTIVE이고 Owner는 `Owner Service + 해당 Product + Security`다.
`parameterSchemaKey`는 `<predicatePolicyKey>.parameters.v1`이며 Parameter가 없는 경우에도
`additionalProperties=false`인 빈 Object Schema를 물리화한다. Fixed/Allowlist가 있는 Route는 그
값을 해당 Schema에 결속한다. `routeContractKeys`는 아래 Route Seed에서 해당 Key를 참조하는 행을
정렬한 정확한 역참조 목록으로 생성한다. 역참조 밖 Route, 빈 Evidence Schema, 미등록 Parameter
Schema를 만들면 실패한다. Target Kind 열의 `/`는 OR가 아니라 Descriptor가 허용하는 정확한
Non-empty Set이다. Predicate가 여러 개인 Profile은 모두 AND로 실행한다. 각 Predicate의 Effective
Target Set은 `Profile Target ∩ Descriptor Target`이며 Non-empty여야 하고, 모든 Effective Target
Set의 합집합은 Profile Target Set과 정확히 같아야 한다. 한 Descriptor가 Profile Target 전체를
혼자 포함할 필요는 없으며 미포함·초과 Kind는 Build를 실패시킨다.

## 6. Seed Validation Gate

Bundle Activation 전 Generator와 Contract Test는 다음을 모두 만족해야 한다.

1. Active PAGE는 58개다. Canary 정적 Menu 12 + Approvals 15 + HCM 25 = 52개의 Menu-owning
   PAGE와 Communications 4 + Services 2 = 6개의 Dynamic non-menu PAGE가 각각 정확히 한
   Contract를 가진다.
2. 모든 PAGE/DATA/ACTION은 Non-empty Access Profile, Public Gateway Binding과 Service PEP
   Binding을 가진다. UI-only Index는 실제 첫 Child로 Resolve하고 API 없는 가짜 PAGE를 만들지
   않는다.
3. Public/Service OpenAPI Method·Path가 양방향 일치하고 미등록 Controller Method는 Pilot
   Capability로 열리지 않는다. `신규` Row는 해당 Wave의 Controller·양쪽 OpenAPI·PEP Contract가
   같은 Release Candidate에 존재한 뒤에만 Bundle을 ACTIVE로 바꾼다.
4. Surface Entry Policy와 Child Access를 모두 통과해야 하며 둘을 한 ANY 식으로 합치지 않는다.
5. HCM `{domain}`은 time/absence/benefits/pay/talent Key로 생성 확장되고 Runtime Wildcard가 없다.
6. Full/Auditor/Support/Legacy Profile의 Precedence, Projection Schema Hash, Read-only와 Sunset이
   결정적이다.
7. 신규 Team Endpoint는 OpenAPI·PEP·Audit·Fixture와 같은 Bundle/Release에 있을 때만 ACTIVE다.
   Reference Publish와 Rotate-secret Key는 Pilot Active Bundle에 존재하면 실패하며, 향후
   `bundleStatus=DRAFT`인 새 Bundle에 `lifecycleState=ACTIVE` Row로 처음 제안할 때도 별도 기능
   ADR·저장소·PEP·Audit·Fixture를 함께 요구한다.
8. Feature Flag Off여도 신규 PEP와 Route Registry는 유지하고 Compatibility Shell만 사용한다.
9. 모든 Capability·Access Policy Descriptor의 `routeContractKeys`는 Route Profile과 MODE_BRANCH
   Member에서 정렬 생성한 양방향 역참조와 Exact Match하며 고아·수기 추가가 0개다.
