## 6. Authority·SoD Test

- Responsibility와 Capability의 Product/Resource Set 불일치 거부
- `MANAGE`만으로 Approve, Publish, Execute, Export, Grant/Revoke 거부
- Access Request는 Requester ≠ Approver, Approver ≠ Fulfiller를 같은 Object/Risk Policy에서
  검사
- App Access Manager와 Approver/Reviewer의 **겹치는 Resource Set**에서만 충돌
- Approvals Publish는 Maker ≠ Publisher를, Recovery Assignment는 겹치는 Resource
  Set의 Operator ≠ Auditor를, Recovery Mutation은 정확한 Event의 Operator ≠
  Originator 및 Operator ≠ Assigned Auditor를 검사
- Approvals Task Claim은 Claimable Predicate, Decision은 Decidable Predicate·Object Version과
  Requester ≠ Actor를 각각 검사하고 다른 Action의 Predicate를 재사용하지 않음
- HCM Org Approval은 Approver ≠ Maker와 Expected Version을 검사하고 Publish Capability·Step-up으로
  대체하지 않음
- 자기 권한 승인·자기 이행 거부
- 마지막 App Owner와 Emergency Admin 보호
- Denied Attempt에 Reason Code, Actor, Target, Scope와 Correlation ID 기록
- 만료·회수 후 다음 Governed Request에서 제외
- 미지원 `ORG_UNIT/RESOURCE` JIT Activation 자체 거부, Request·Grant Row 0, Denied Audit 1
- Freshness 없는 MFA `amr`만으로 Step-up 통과 금지
- 일반 OIDC Login의 `pwd+otp`·literal `mfa`는 `OIDC_STEP_UP` Provenance가 없으므로
  Challenge 서명 대신 `CONTINUATION_REQUIRED`; 명시 Mapping을 통과한 STEP_UP
  `pwd+otp`·`hwk`는 각각 `[mfa,otp,pwd]`·`[hwk,mfa]` + `OIDC_STEP_UP`으로 Auth
  서명 후 Approval 검증 통과
- STEP_UP `pwd` Only·미지·대소문자 변형 AMR은 Session 승격·Challenge 서명 0,
  완전한 강도 조합이 없는 Provider 설정은 Production Readiness 실패
- Step-up Challenge의 Target·Object Version·Method/Path·Payload Digest·Decision Revision
  중 하나라도 바꾸면 Domain Mutation·Nonce 소비 0
- Responsibility A + Capability B + Scope C의 교차 조합 거부
- Permission-only Legacy Admin은 입증된 Scope Backfill 또는 Owner Review 전까지 자동 확대 금지
- Unknown·Retired·Cross-surface·Method-mismatched Route Contract Key는 모두
  `ROUTE_DENIED`
- Post-Pilot 예약 `hcm.reference.publish`, `hcm.integration.rotate-secret`은 Active
  Registry Row·Grant·Challenge가 0이며 Direct Evaluation은 `AUTHORITY_UNAVAILABLE`, 가상 Route는
  `ROUTE_DENIED`
- Named Reviewer는 ACTIVE Campaign·현재 Assignment·Reviewer·Object Version이 모두 맞는 자신의
  `WORK_ITEM_1` Detail·Decision만 허용하며 stale version, revoked assignment, 다른 Reviewer Item은
  Product/Admin 권한으로 우회하지 않음
- Auth·Policy·Product Relationship·Target Population·Support Revision을 각각 단독으로
  변경해도 새 Composite Revision 발급, 이전 Revision Mutation은 Domain 접근 전 409
- Legacy Oversight에 신규 Child GET 또는 금지 Field를 추가한 Fixture는 각각 403
  또는 Projection 제거를 보장

## 8.1 Direct Evaluation 성능 Gate

- Planner는 현재 PAGE, Product Base/Surface Index 또는 공식 Legacy Redirect Target으로 소유 제품을
  하나만 결정한다. Router와 같은 대소문자 비구분 의미를 사용하되 원 URL·Query·Hash는 변경하지 않는다.

## 11. Telemetry 검증

- Audit와 UX Event가 다른 Store·Schema·권한을 사용한다.

- `task.started|completed|failed|abandoned`와 `scope.switch.started|completed|failed`가 회전형
  Journey `attemptId`로만 상관됨
- Feature Flag Cohort와 Tenant 단위 Rollout Stage 기록
- Event 수집 실패가 업무·관리 Action을 막지 않음
- 권한 Denial 보안 Audit는 Analytics 실패와 무관하게 남음
- 성공률은 completed/started, 빠른 복귀는 meaningful action 없이 30초 내 returned/exposed,
  완료 시간은 completed Attempt만으로 계산됨
- 5초 인지 정확도와 SEQ는 Pilot별 최소 20명·Persona별 최소 4명의 Moderated Test로 측정됨

## 12. Rollout Gate

### 단계

1. 현행 Combined Navigation 최소 14일, Pilot App별 5 Tenant·Critical Task Start 300건 Baseline
2. 내부 Tenant: Canary → Approvals 7일 → HCM 7일, 동시 변경 금지. 모든 Fixture Journey를
   Browser 조합별 3회 이상 반복
3. Design Partner 최소 5 Tenant Opt-in, App별 최소 14일·Task Start 200건
4. Eligible Tenant 10% → 25% → 50% → 90%. 각 Stage 최소 7일, 노출 Tenant 10개,
   App별 Task Start 500건을 모두 충족할 때만 Advance
5. 10% Holdout도 Tenant 10개·Task Start 500건을 충족하고 사전 등록 KPI 비교 후 100%

모수가 부족하면 관찰 기간을 연장하며 표본 Gate를 낮춰 Advance하지 않는다. 보안·Privacy·접근성
Zero-tolerance Gate는 표본 수와 무관하다.

### 즉시 Rollback

- 권한 또는 Scope Escape 1건
- 만료 후 민감 Data 잔류 1건
- 유효 Start 50건 이상에서 Critical Task 성공률 85% 미만
- Stage 표본 충족 후 기존 Work Task Median이 Baseline 대비 10% 초과 악화
- Blocker 접근성 결함
- 예상된 Policy Denial을 제외한 Management Mutation Error/403가 60분·50건 이상 구간에서 5%를
  넘고 동시에 Baseline의 2배 이상
- 등록된 Legacy Deep Link의 Runtime 손실 1건

`U_p` Off는 업무·관리 Plane과 단일 `앱 관리` 진입점을 유지하는
Compatibility-separated Shell로만 되돌리고 Sibling Guard·Effective Context·PEP를 유지한다.
혼합 Sidebar로는 되돌아가지 않는다. 인가 회귀는 직전 승인 Capability Policy Version으로 원자
Rollback하며 Auth Assignment와 Audit Data를 삭제하지 않는다.

장애 대응과 운영 Rollback을 구분한다. Provider 평가 실패 시 Latch v2의 마지막 승인 `S/E_p`를
유지하고 `U_p=0`으로 내려 `111→110`만 허용한다. 장애를 이유로 `110→100/000`으로 자동 강등하거나
Legacy 전역 E·`MANAGE`를 사용하지 않는다. Product·Security Owner가 `E_p=false`인 더 높은 Revision을
승인·발행한 경우에만 `S=1`에서 `110→100` 운영 Rollback을 수행하며 Assignment·Audit·불변 Bundle은
보존한다.
