## 중단 회수 최종 증분

  결정도 기대 `productId`·`surfaceId`·APP resource가 모두 같은 경우에만 호환 Guard를 통과한다.

## 2026-09-07 최종 UX·권한 재감사 증분

앞선 `P0 0 / P1 0` 판정 이후 동일 URL에서 권한이 회수될 때 제거되는 제품 Shell control의

- 포커스 provenance를 제품 plane, 인증 identity, query·hash를 포함한 현재 URL에 결속했다.
  권한 갱신 중의 `null/body` blur는 보존하되 실제 외부 focus 이동, window 이탈, 다른 URL·identity
  전환에서는 즉시 폐기한다. pointer intent는 다음 task의 실제 active element를 확인하므로 Shell
  빈 영역 click만으로 유효한 provenance를 버리지 않는다.
- Surface 권한 회수로 Shell 전체가 사라지면 안정적인 page-level `<main
id="dwp-main-content">` 안 H1으로, PAGE 권한 회수로 기존 Shell이 남으면 중첩 main 없이 상태
  H2로만 포커스를 인계한다. 제거되는 control이 실제 focus를 가졌을 때만 동작하며 skip link 등

- `surface-denied` 문구를 canonical manifest의 `work`·`management` plane으로 분리했다. URL 문자열로
  추론하지 않으며 plane을 알 수 없으면 중립 문구로 fail-safe한다.
- `/admin/...` 제품 관리 legacy URL은 인증·Workspace 경계만 확인한 뒤 query·hash를 보존해

  boundary가 단일 소유한다. `/admin/spaces` 권한 기반 index도 같은 보존·replace 계약을 따른다.
- Approvals pilot의 allowed fixture가 단순히 Shell만 보고 통과하지 않도록 실제 PAGE contract,
  route kind, surface, 메뉴 exact set, direct-route content와 access-state 부재를 별도 회귀로
  검증한다. denied fixture는 메뉴 비노출과 direct-route local deny를 함께 검증한다. 기존 pilot
  파일은 maintenance 상한 1,318줄을 유지했다.

baseline의 해당 행만 1,318 → 1,266으로 낮췄다. 다른 소유자가 변경한 baseline 행은 보존했다.
Preparation 화면의 표기는 기존 `MeetingStatusChip` 재사용으로 정합했고, 공통 display locale는
변경하지 않았다. display-dictionary 독립 재검사도 통과했다. 이어서 전체 architecture와
production build를 재실행해 PASS했다. build에 포함된 OpenAPI·권한 정본·fixture·API/feature
경계·source-size·maintenance·디자인 시스템·i18n·display·ESLint·TypeScript·Vite·번들 검사도
통과했다. 이후 별도 제품 소유자가 계속하는 기능 변경·실제 서비스 배포는 이 실행의 인증 범위가 아니다.

### 초기 번들 초과의 추가 개선

전체 build에서 초기 번들 예산 초과를 실제 재현했다. 독립 전문가와 소스맵을 대조한 결과,
초기 로딩되는 Approval 내비게이션 및 공통 권한 helper가 `shared-utils` 루트 barrel을 runtime
import하면서 다른 제품의 API 모듈까지 초기 그래프에 포함하는 것이 원인이었다.

공통 `product-surface-capability-access.ts`와 `use-product-surface-request-scope.ts`의 import를
기존 auth leaf 모듈로 좁혔다. Approval 소유자는 별도로
`approval-inbox-queue-navigation.tsx`의 API import 한 줄을 기존 approval API leaf로 정합했다.
렌더링·lazy 시점·권한 판정·메뉴·query 동작은 변경하지 않았다. 두 공통 helper가 다시 runtime
루트 barrel을 가져오지 못하도록 TypeScript AST 기반 회귀 2건도 추가했다.

| 초기 번들 | 보정 전     | 보정 후     | 기존 한도   |
| --------- | ----------- | ----------- | ----------- |
| raw       | 1,175.9 KiB | 1,050.5 KiB | 1,074.2 KiB |
| gzip      | 334.3 KiB   | 306.8 KiB   | 317.4 KiB   |
| 요청 수   | 5           | 5           | 5           |

raw 125.4 KiB, gzip 27.5 KiB를 줄였고 예산·allowlist를 늘리지 않았다.
보정 뒤 전체 단위 검사, 전체 build, 앱 관리자 Chromium·mobile 회귀까지 다시 통과했다.

### 추가 고대비 모드 후보의 판정

Meeting 소유자가 전달한 dark·forced-colors 대비 후보도 전문가가 공통 소스를 읽기 전용으로
확인했다. 일반 Typography·primary/quiet Button에는 명시적인 `WebkitTextFillColor` 고정값이
없으며, 공통 theme의 해당 선언은 input autofill에만 적용된다. 제공된 mobile/WebKit 화면은
Chromium 버튼의 실제 대비를 증명하지 않으므로 공통 P1로 확정하지 않았다.

[W3C 색상 조정 규격](https://www.w3.org/TR/css-color-adjust-1/#forced-colors-properties)은
forced-colors의 computed color와 실제 used color를 구분한다.
[WHATWG text-fill 규격](https://compat.spec.whatwg.org/#the-webkit-text-fill-color-property)의
상속·초깃값도 대조했다. 계산된 대비 수치만으로 전역 테마를 변경하지 않았고, 실제 paint와
브라우저·media 상태를 분리한 제품 회귀는 Meeting 소유 작업에 인계했다. 이 후보를
앱 관리자 미해결 결함이나 전역 대비 PASS의 증거로 사용하지 않는다.

## 새로 회수한 공통 정적 차단

Work 소유 클라이언트의 `POST /internal/v1/meeting-followups/resolve`가 기존 서비스 경계
검사기의 단일 파일 path marker 및 세 가지 service-token 가정 때문에 등록되지 못했다.
공통 검사기에 별도 `signedWorkload` 프로파일을 추가하고 실제 protocol·signer 소스와 연결했다.

- 기존 token 기반 인터페이스의 경로·인증·trace 조건은 유지한다.
- protocol 상수와 실제 import·endpoint·POST bytes·서명·subject/source/action·30초 만료·nonce를 확인한다.
- 다른 서비스 소스, 경로 탈출, 잘못된 client 경로, 주석·문자열 위조 marker를 거부한다.
- 만료 산술 확장, Gateway/legacy token 재사용, 자동 retry 및 redirect 허용을 거부한다.
- 검사는 정적 계약 검사다. 암호학적 실행, receiver replay 방지, 현재 사용자 권한의 증명으로 간주하지 않는다.

backend `scripts/tests/test_service_boundaries.py`의 18개 회귀와 전체 서비스 경계 검사를 통과했다.
`./gradlew checkServiceBoundaries --no-daemon --max-workers=1`도 BUILD SUCCESSFUL이며,
독립 재감사에서 지적한 경로 검증·만료 산술·redirect 위장 회귀를 포함한다.
Work production 코드는 Work 소유 작업이 유지하며, 실제 trace 전파·민감 헤더 비전달 HTTP
검증은 해당 소유 작업의 [구현 보고서](../DWP-R1-WRK-001-unified-work-execution/meeting-assignment/implementation-report.md)에 기록한다.

## 완료와 분리해야 하는 새 연동 요구

Meeting→Work 원천 전환은 현재 **NO-GO**다. 서비스 간 서명은 호출자와 요청 본문을 증명하지만
그 사용자의 현재 Meeting 이용 권한이나 새 업무 담당자의 적격성을 대신하지 않는다.

1. Auth: Meeting 전용 인증·audience의 좁은 평가 포트가 필요하다. 기존 Gateway 전용 평가
   API나 자격 증명을 재사용하지 않는다. 현재 계정·tenant 상태, durable identity plane,
   entitlement, exact capability, scope 및 revision을 서버가 재조회해야 한다.
2. 공통 계약: 현 v4의 회의 생성 권한을 후속 업무 전환·재배정 권한으로 대체하지 않는다.
   다음 additive 후보에서 internal-only binding과 본문 action을 표현하고, 정확한 permission
   매핑·역할 부여·risk tier를 승인해야 한다. 기존 v1~v4 바이트·checksum은 유지한다.
3. People: 현재 HCM actor/scope 평가 API는 target assignee 적격성 API가 아니다.
   Auth user↔People person 결속과 최신 lifecycle을 확인하는 독립 대상 판정 계약이 필요하다.
4. Meeting: 위 권한에 현재 report/candidate ACL, 사람의 확정, retention, source version을
