# DWP-R1-CORE-006 데이터 설계

## 1. 데이터 소유권

Product Surface 자체는 업무 데이터를 소유하지 않는다. 다음 기존 Source를 조합한 Read Model을
사용한다.

| Source / Owner  | 데이터                                                  | 역할                |
| --------------- | ------------------------------------------------------- | ------------------- |
| Auth            | 역할, Permission, DENY, Auth Source Revision            | 행위 권한 원장      |
| Auth            | Resource Set, Responsibility, Assignment, Validity      | 관리 책임·범위 원장 |
| Auth            | Privileged Eligibility, Activation, Expiry, Assurance   | JIT 원장            |
| Provider        | Support Session, Tenant, Scope, Mode, Reason, Expiry    | 지원 접근 원장      |
| Product Service | Target Population, Object ACL, Field Mask, Object State | 최종 대상 인가      |
| Frontend        | Product Manifest, Route와 Navigation Projection         | UX Projection       |
| Analytics       | 비식별 Surface UX Event                                 | 사용성 측정         |
| Audit           | Capability, Scope, Actor, Target, Before/After, Outcome | 보안·규제 증적      |

## 2. 신규 논리 모델

### 2.1 Product Management Capability Descriptor

제품별 Route와 분산된 Gateway Path Mapping의 Drift를 막기 위해 Auth가 소유하는 Versioned
Descriptor를 둔다. 물리 Table 이름은 2.6의 Immutable Bundle Schema로 고정한다.

| 필드                           | Type               | 계약                                                                      |
| ------------------------------ | ------------------ | ------------------------------------------------------------------------- |
| `contract_key`                 | string PK          | Manifest·Route·Test가 참조하는 영구·불변 ID                               |
| `capability_code`              | string             | 현 Policy Version의 Exact `resource:action` Mapping                       |
| `mapping_version`              | integer            | Contract Key→Exact Action Mapping Version                                 |
| `product_key`                  | string             | Frontend Manifest와 일치                                                  |
| `surface_key`                  | string             | 서버가 허용하는 안정 Contract Key                                         |
| `route_contract_keys`          | string[]           | 해당 Action을 요구하는 Route·Method Contract                              |
| `resource_key`                 | string             | `ADMIN.*`, `DATA.*`, `ACTION.*`                                           |
| `action`                       | string             | Exact Permission Code                                                     |
| `authority_mode`               | enum               | `PERMISSION`, `PERMISSION_AND_RELATIONSHIP`, `PERMISSION_OR_RELATIONSHIP` |
| `responsibility_requirement`   | enum               | REQUIRED/NOT_REQUIRED/LEGACY_OVERSIGHT                                    |
| `scope_resolver`               | string             | Resource Set, Target Population 등 Typed Resolver                         |
| `risk_tier`                    | enum               | LOW/MEDIUM/HIGH/CRITICAL                                                  |
| `activation_policy`            | string nullable    | Step-up/JIT/Approval Policy Ref                                           |
| `sod_policy_id`                | string nullable    | Scope·Object와 검사 시점을 가진 Conflict Policy                           |
| `requires_product_entitlement` | boolean            | APP Entitlement 명시적 AND 여부                                           |
| `owner`                        | string             | 제품·Security 승인 Owner                                                  |
| `sunset_at`                    | timestamp nullable | Legacy Oversight·Compatibility 종료 시각                                  |
| `legacy_source`                | string nullable    | 기존 Role·Permission·Endpoint 증거                                        |
| `policy_version`               | integer            | Audit·Cache Invalidation                                                  |
| `lifecycle_state`              | ACTIVE/RETIRED     | 퇴역 Capability 재활성 금지                                               |

하나의 Active `contract_key`는 한 Policy Version에서 정확히 하나의 Exact
`capability_code`로만 Mapping한다. Manifest Entry와 Navigation, Route Catalog은 Raw
Permission Code가 아니라 `contract_key`를 참조하고, Gateway가 승인된 Version의 Exact
Code로 Resolve한다.

`route_contract_keys`는 Route Seed의 `requiredAccess`에서 정렬 생성한다. Direct Capability,
Capability Expression Member와 Governed Access Policy의 MODE_BRANCH Capability Member가 요구하는
모든 Active Route를 포함하며, 수기 부분집합을 허용하지 않는다. Route→Descriptor와
Descriptor→Route 역참조가 다르거나 Unknown·Retired Route가 포함되면 Bundle Build를 실패시킨다.

Capability Descriptor는 Permission 계열의 행위 계약만 소유한다. 순수 Relationship,
Entitlement와 Provider Support Session은 Capability로 만들지 않고 2.3의 Product Access
Policy Descriptor가 소유한다.

`MANAGE`는 모든 Action의 Wildcard가 아니다. Resource별 Action Implication이 필요하면 별도
Versioned Policy로 저장하고 `APPROVE`, `PUBLISH`, `EXECUTE`, `EXPORT`, `LEGAL_HOLD`,
`GRANT`, `REVOKE`, Secret Rotation을 암묵 포함하지 않는다.

### 2.2 Governed Route Authorization Contract

화면 Route ID와 Capability Contract Key를 같은 Namespace로 사용하지 않는다. Router Definition에서
생성되는 Route 계약을 Auth Registry에 등록하고 Gateway Method까지 결속한다.

| 필드                    | Type             | 계약                                                                                                                                                   |
| ----------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `route_contract_key`    | string PK        | Product `route.<product>.<surface>.<route-path>.<kind>` 또는 비제품 `route.context.<navigation-context-token>.<route-path>.<kind>` 형식의 영구·불변 ID |
| `navigation_context_id` | string           | 전체 메뉴 분류표의 안정 Governed Navigation Context                                                                                                    |
| `subject`               | union            | `PRODUCT(product_key,surface_key)` 또는 `GOVERNED_CONTEXT`; Context ID는 Top-level 필드 하나만 권위로 사용                                             |
| `route_kind`            | PAGE/DATA/ACTION | Browser Page, Read Data, Mutation Command 구분                                                                                                         |
| `side_effect_free`      | boolean nullable | POST DATA만 true 필수; Business State·Workflow Outbox 변경 금지                                                                                        |
| `ui_route_id`           | string nullable  | PAGE의 Router·Navigation 안정 ID; DATA/ACTION은 null                                                                                                   |
| `ui_route_pattern`      | string nullable  | PAGE의 Segment-safe Canonical Pattern; DATA/ACTION은 null                                                                                              |
| `access_profiles`       | Profile[]        | 서버가 선택하는 Access·Projection Profile; Non-empty                                                                                                   |
| `gateway_api_bindings`  | Binding[]        | Stable Key + Method·Path + Typed Path Parameter Constraint                                                                                             |
| `service_pep_bindings`  | ServiceBinding[] | 같은 Key·Constraint + 필수 `service_key` + Service Method·Path                                                                                         |
| `owner`                 | string           | Product·Security 승인 Owner                                                                                                                            |
| `policy_version`        | integer          | Capability·Router·PEP 대조 Version                                                                                                                     |
| `lifecycle_state`       | ACTIVE/RETIRED   | 퇴역 Route 계약 재활성화 금지                                                                                                                          |

Product Route Subject는 `product_key + surface_key`를 둘 다 가지며 비제품 Subject는 둘 다 갖지
않고 `GOVERNED_CONTEXT` Type만 가진다. `navigation_context_id`는 두 Subject 모두 Top-level
필드 하나만 권위로 사용한다. `navigation_context_id`는 `_`가 없는 lower-kebab 점 구간만
허용한다. 비제품 Key의 `navigation-context-token`은 점을 `__`로 치환한 가역 Encoding이며,
Decode 결과 불일치·비정규 Token은 Bundle Build를 실패시킨다. 별도 Token Registry는 두지 않는다.
예시 Key는 `route.approvals.admin.policies.page`,
`route.approvals.admin.operations.retry.action`,
`route.approvals.work.task-detail.data`, `route.hcm.management.org-design.page`다. Capability
Key인 `approvals.policy.read`를
Route Key로 재사용하지 않는다.

`route.context.work__work.review-detail.data`처럼 `work.work` Navigation Context에 속한 Named Reviewer
업무는 Product Surface가 아니다. 동일 Governed Route Registry를 사용하되 Product/Surface를
null로 고정하고 121 Product Menu의 Surface Registry로 투영하지 않는다.

```ts
type RouteAccessProfile = {
  profileKey: string;
  precedence: number;
  activeAccessModes: readonly [
    'NORMAL' | 'ELEVATED' | 'PROVIDER_SUPPORT',
    ...('NORMAL' | 'ELEVATED' | 'PROVIDER_SUPPORT')[],
  ];
  requiredAccess:
    | { type: 'capability'; capabilityContractKey: string }
    | {
        type: 'capability-expression';
        mode: 'ANY' | 'ALL';
        capabilityContractKeys: readonly [string, ...string[]];
      }
    | { type: 'policy'; accessPolicyKey: string };
  targetBindingKinds?: readonly [
    'SELF' | 'OBJECT' | 'RELATIONSHIP' | 'TARGET_POPULATION' | 'CONFIG_SCOPE',
    ...('SELF' | 'OBJECT' | 'RELATIONSHIP' | 'TARGET_POPULATION' | 'CONFIG_SCOPE')[],
  ];
  predicatePolicyKeys?: readonly [string, ...string[]];
  responseProjectionBindings?: readonly [
    {
      apiBindingKey: string;
      projectionPolicyKey: string;
      responseSchemaKey: string;
    },
    ...{
      apiBindingKey: string;
      projectionPolicyKey: string;
      responseSchemaKey: string;
    }[],
  ];
  readOnly: boolean;
};
```

같은 Route의 일반 관리자, Auditor, Provider Support와 Legacy Oversight는 서로 다른 Profile을
사용한다. Client는 Profile Key를 요청하지 않는다. 서버가 현재 Effective Grant로 허용되는
Profile 중 현재 `activeAccessMode`가 `activeAccessModes`에 포함되는 것만 계산한 뒤 Registry의
고유 `precedence`가 가장 높은 하나를 선택하고 응답에
선택된 Opaque `routeGrantRef`만 반환한다. 동률, 중복 Profile Key, 복수 Profile의 같은
Precedence는 Registry Error다. 빈/중복/Unknown `activeAccessModes`도 Registry Error다.
`targetBindingKinds`와 `predicatePolicyKeys`는 Assigned Object,
Self, Reporting Relation, Target Population과 Configuration Scope를 Route Profile에 결속한다.
Client가 Object·관계·Population을 선택하거나 Raw Predicate를 제출하지 않는다. Field Mask·
Response Schema는 Capability가 아니라 선택된 Route Profile과 Stable API Binding Pair에 속한다.
Predicate가 여러 개면 모두 AND로 실행한다. Predicate별 Effective Target Set은 Profile Target과
Descriptor 허용 Target의 교집합이고 각각 Non-empty여야 하며, 그 합집합이 Profile Target Set과
정확히 같아야 한다. 따라서 Relationship/Target Population Predicate와 Object Version Predicate가
서로 다른 Target Kind를 나눠 소유할 수 있지만 미포함·초과 Kind는 Build를 실패시킨다.
PAGE/DATA Profile은 응답 본문을 가진 모든 Binding Key마다
`responseProjectionBindings` 한 개를 가져야 하며 누락·중복·미등록 Projection은
Default-deny다. ACTION Profile은 `responseProjectionBindings`를 금지한다. Public과 Service Binding은
같은 Stable Binding Key로 1:1이어야 하고 Method 또는 Path가 한쪽에만 있으면 Build를 실패시킨다.
Service Binding의 `service_key`는 `auth | platform | approval | people` 등 배포·OpenAPI Audience를
가리키는 안정 Key이며 생략하거나 Public Prefix만으로 추론하면 Build를 실패시킨다.
Service Path Grammar는 해당 Service OpenAPI가 권위이며 `platform/approval/people`은 `/v1/**`,
`auth`는 `/auth/**`를 사용한다. 다른 Service의 Grammar를 섞으면 실패한다.
두 Binding의 `path_parameter_constraints`는 Parameter별 `{kind:'FIXED',value}` 또는
`{kind:'ALLOWLIST',values}`만 허용하며 같은 Stable Binding Key 양쪽에서 같아야 한다. `surfaceKey`,
HCM `domain`, Code Set, Event Type처럼 값이 권한 의미를 바꾸는 Parameter는 Constraint가 없으면
Build를 실패시킨다.

Router Definition이 Registered Product Route Catalog과 `route_contract_key` Projection을 생성한다.
Cross-repository CI는 Manifest Surface, UI Route ID·Pattern, Auth Route Contract, Public Gateway
Method·Path와 Downstream Service PEP Binding이 동일 Version으로 완전히 매칭되는지 검사한다. Client가
Route Key를 보내는 것은 Guard·상태 표시를 위한 입력일 뿐 Permission 선택권이 아니며,
모든 Product API는 등록된 Method·Path 계약을 서버에서 다시 평가한다.

PAGE만 `ui_route_id/ui_route_pattern`을 가지며 Browser URL Resolver에 참여한다. DATA와 ACTION은
UI Pattern을 금지한다. DATA는 GET/HEAD이거나 명시적으로 `side_effect_free=true`인 POST Query만
허용한다. 후자는 Business State와 Workflow Outbox를 변경하지 않고 Response Projection을
필수로 가진다. 민감 조회의 append-only Security Audit Outbox는 허용하되 응답·업무 상태에 영향을
주지 않아야 한다. ACTION은 Mutation이며 `side_effect_free`와 Response Projection을 금지한다. Kind와
금지 필드가 맞지 않으면 Registry Build를 실패시킨다.

### 2.3 Governed Access Policy Descriptor

Personal·Team·Assigned Work와 Support처럼 Permission으로 왜곡하면 안 되는 진입 정책을
Versioned Descriptor로 고정한다.

| 필드                           | 계약                                                                               |
| ------------------------------ | ---------------------------------------------------------------------------------- |
| `access_policy_key`            | Manifest·Route·Fixture가 참조하는 영구·불변 Key                                    |
| `navigation_context_id`        | 전체 메뉴·업무 Context의 안정 ID                                                   |
| `product_key`, `surface_key`   | Product Policy면 둘 다 필수, 비제품 Policy면 둘 다 null                            |
| `evaluation_type`              | SINGLE/MODE_BRANCH                                                                 |
| `authority_mode`               | SINGLE 전용; ENTITLEMENT/RELATIONSHIP/ENTITLEMENT_AND_RELATIONSHIP/SUPPORT_SESSION |
| `entitlement_expression_key`   | SINGLE 전용 Versioned App Entitlement 식; 미사용 Policy는 null                     |
| `requires_product_entitlement` | 별도 App Entitlement AND 조건                                                      |
| `relationship_resolver`        | Reporting·Delegation·Named Assignment 등의 Product Owner Resolver                  |
| `scope_resolver`               | Self·Team·Target Population·Support Scope Resolver                                 |
| `surface_entry_keys`           | Product Policy의 Surface Entry; 비제품 Policy는 빈 배열                            |
| `route_contract_keys`          | 해당 Policy를 참조하는 등록 Route 계약                                             |
| `support_scopes`               | SINGLE SUPPORT_SESSION 전용 정확 Scope; 그 외 null                                 |
| `mode_branches`                | MODE_BRANCH 전용 Active Mode별 Typed Access 계약                                   |
| `owner`, `policy_version`      | 판정 Owner와 Cache·Audit·Rollback Version                                          |
| `lifecycle_state`              | ACTIVE/RETIRED                                                                     |

Entitlement만 필요한 Approvals·Communications·Services Work Policy는
`ENTITLEMENT`, HCM Team은 `ENTITLEMENT_AND_RELATIONSHIP`, Provider Support는
`SUPPORT_SESSION`으로 명시한다. Auth는 관리 원장, Product Service는 관계·Target
Population 판단을 소유하고 Gateway Read Model이 결과만 합성한다.

`route_contract_keys`도 Route Seed의 Policy Profile과 MODE_BRANCH 역참조에서 정렬 생성하며
양방향 차이·고아 Route·수기 추가를 Bundle Build에서 거부한다.

OpenAPI·DTO와 Registry Validator는 Descriptor를 다음 Discriminated Union으로 생성한다.

```ts
type GovernedAccessPolicyBase = {
  accessPolicyKey: string;
  navigationContextId: string;
  requiresProductEntitlement: boolean;
  relationshipResolver?: string;
  scopeResolver: string;
  routeContractKeys: readonly string[];
  owner: string;
  policyVersion: number;
  lifecycleState: 'ACTIVE' | 'RETIRED';
};

type GovernedAccessPolicySubject =
  | {
      productKey: string;
      surfaceKey: string;
      surfaceEntryKeys: readonly [string, ...string[]];
    }
  | {
      productKey: null;
      surfaceKey: null;
      surfaceEntryKeys: readonly [];
    };

type GovernedAccessPolicyDescriptor = GovernedAccessPolicyBase &
  GovernedAccessPolicySubject &
  (
    | {
        evaluationType: 'SINGLE';
        authorityMode:
          'ENTITLEMENT' | 'RELATIONSHIP' | 'ENTITLEMENT_AND_RELATIONSHIP' | 'SUPPORT_SESSION';
        entitlementExpressionKey?: string;
        supportScopes?: readonly [string, ...string[]];
        modeBranches?: never;
      }
    | {
        evaluationType: 'MODE_BRANCH';
        authorityMode?: never;
        entitlementExpressionKey?: never;
        supportScopes?: never;
        modeBranches: readonly [AccessPolicyModeBranch, ...AccessPolicyModeBranch[]];
      }
  );
```

SINGLE `SUPPORT_SESSION`만 Non-empty `supportScopes`를 가지며 다른 SINGLE Mode에서는 이를
금지한다. MODE_BRANCH는 Top-level Authority·Entitlement·Support Scope를 갖지 않고 Branch만
평가한다. 금지 필드가 직렬화되거나 필수 필드가 비면 Build·Seed를 실패시킨다.

Entitlement Expression은 별도 Versioned Registry에서 Key, `ANY | ALL` Tree, Exact App
Entitlement Leaf, Owner, Version과 Lifecycle을 고정한다. Empty Tree, Unknown/Retired Leaf와
빈 Permission Payload는 Fail Closed다. Runtime Role 문자열이나 Frontend Boolean을 식에 넣지
않는다.

`MODE_BRANCH`는 다음 Discriminated Branch만 허용한다.

```ts
type AccessPolicyModeBranch =
  | {
      activeAccessMode: 'NORMAL' | 'ELEVATED';
      resultGrantKind: 'CAPABILITY';
      capabilityMode: 'ANY' | 'ALL';
      capabilityContractKeys: readonly [string, ...string[]];
      responsibilityRequirement: 'REQUIRED' | 'NOT_REQUIRED' | 'LEGACY_OVERSIGHT';
    }
  | {
      activeAccessMode: 'PROVIDER_SUPPORT';
      resultGrantKind: 'POLICY';
      authorityMode: 'SUPPORT_SESSION';
      supportScopes: readonly [string, ...string[]];
    };
```

서버가 결정한 Active Access Mode와 정확히 한 Branch만 평가하며 Branch 결과를
합집합하지 않는다. Communications Management/Content와 HCM Operations Overview는 NORMAL에서
Capability Grant, PROVIDER_SUPPORT에서 Read-only Policy Grant를 반환한다. 빈 Branch,
중복 Active Mode, Support Branch의 Capability Key는 Registry Validation Error다.

### 2.4 Predicate Policy Descriptor

Object·관계·Target Population·Field 제약을 문자열 이름만으로 남기지 않는다. 각
각 `predicatePolicyKey`는 같은 Authorization Bundle의 Versioned Descriptor를 참조한다.

| 필드                        | 계약                                                             |
| --------------------------- | ---------------------------------------------------------------- |
| `predicate_policy_key`      | 영구·불변 Key                                                    |
| `owner_service_key`         | 실제 Evidence를 판정하는 `auth/platform/approval/people` Service |
| `target_binding_kinds`      | 허용 `SELF/OBJECT/RELATIONSHIP/TARGET_POPULATION/CONFIG_SCOPE`   |
| `input_evidence_schema_key` | Object State·Version·관계·Population 입력의 Versioned Schema     |
| `parameter_schema`          | Fixed Value·Allowlist·금지 Field 등 Typed Parameter              |
| `route_contract_keys`       | 이 Predicate를 소비하는 Route Allowlist                          |
| `owner`, `policy_version`   | Product·Security Owner와 Version                                 |
| `lifecycle_state`           | ACTIVE/RETIRED                                                   |

Product Service가 Evidence 권위를 유지하고 Gateway/Auth는 Opaque Decision Ref만 합성한다. Unknown
Predicate, Owner Service 불일치, Predicate의 허용 Target Kind를 벗어난 조합, Evidence Schema Hash
Drift와 빈 Allowlist는
Fail Closed다. 복수 Predicate는 2.2의 교집합·Union-cover 규칙을 적용한다. Predicate Parameter를
Client가 선택할 수 없고 Route Profile에 고정한다.

### 2.5 EffectiveProductSurfaceContext

영속 원장이 아니라 현재 Actor, Access Mode와 Policy Revision에서 계산하는 Read Model이다. Auth의
Management Grant, 기존 Work Entitlement와 Product Service의 Relationship Eligibility를 Gateway가
표시용으로 합성한다. Product Service의 Target Population·Object 인가 권위는 이동하지 않는다.

| 필드               | 설명                                                                               |
| ------------------ | ---------------------------------------------------------------------------------- |
| `contractVersion`  | DTO Schema Version                                                                 |
| `decisionRevision` | Auth·Policy·Relationship·Target Population·Support를 포함한 Opaque Composite Token |
| `sourceRevisions`  | 운영 진단용 Auth/Policy/Product/Support Revision; Client 조합 금지                 |
| `generatedAt`      | 서버 시각 Offset·Freshness 진단용                                                  |
| `contextKey`       | Client 조합용이 아닌 Opaque Effective Context 참조                                 |
| `productKey`       | Product Manifest Key                                                               |
| `surfaceKey`       | 정확히 한 안정 Surface Key                                                         |
| `plane`            | Work 또는 Management                                                               |
| `accessMode`       | 서버 Session이 결정한 NORMAL/PROVIDER_SUPPORT/ELEVATED                             |
| `accessSource`     | ENTITLEMENT/RELATIONSHIP/MANAGEMENT/SUPPORT                                        |
| `effectiveGrants`  | Capability 또는 Policy·책임·Scope·Validity가 결속된 Grant                          |
| `scopes`           | Opaque Key, Kind, Label, `isDefault`, 파생 Read-only, Validity                     |
| `revalidateAt`     | 다음 Grant·Scope·Session 만료 또는 Policy 재평가 중 가장 이른 시각                 |

Effective Grant는 다음 Discriminated Union이다.

```ts
type EffectiveGrant =
  | {
      grantKind: 'CAPABILITY';
      capabilityContractKey: string;
      resolvedCapabilityCode: string;
      authorityMode: 'PERMISSION' | 'PERMISSION_AND_RELATIONSHIP' | 'PERMISSION_OR_RELATIONSHIP';
      predicatePolicyKeys?: string[];
      responsibilityRequirement: 'REQUIRED' | 'NOT_REQUIRED' | 'LEGACY_OVERSIGHT';
      responsibility?: { code: string; resourceSetKey: string };
      scopeKeys: string[];
      requiresProductEntitlement: boolean;
      readOnly: boolean;
      activationState: string;
      validUntil?: string;
    }
  | {
      grantKind: 'POLICY';
      accessPolicyKey: string;
      authorityMode:
        'ENTITLEMENT' | 'RELATIONSHIP' | 'ENTITLEMENT_AND_RELATIONSHIP' | 'SUPPORT_SESSION';
      policyDecisionRef: string;
      scopeKeys: string[];
      requiresProductEntitlement: boolean;
      readOnly: boolean;
      validUntil?: string;
    };
```

Entitlement·Relationship 기반 Personal·Team·Reviewer와 Support를 인공 Permission으로
변환하지 않는다.
서로 다른 Grant의 Capability·Policy·책임·Scope를 Cartesian 결합하지 않는다. 하나의
Context는 `product + surface + 서버가 결정한 activeAccessMode`를 한 번만 표현하고
Grant별 Read-only·Validity 차이는 그 안에 보존한다. Scope의 `readOnly`는 해당 Scope에서
현재 유효한 Mutation Grant가 하나도 없을 때만 `true`다.

Assignment ID, Grant ID와 상세 Evidence는 Client Payload에 과도하게 노출하지 않고 서버 Audit에서
보존한다. Client가 보내는 Context·Scope Key는 최종 권한 증거가 아니다.

### 2.6 Immutable Authorization Registry Bundle

Rollback 가능한 Versioning을 위해 논리 Key를 단일 Mutable PK로 저장하지 않는다. Auth Migration
`V87__create_product_surface_authorization_registry.sql`은 다음 물리 모델을 추가한다.

| Table                                 | PK / Unique                                 | 계약                                                                                     |
| ------------------------------------- | ------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `auth_product_authorization_bundle`   | `bundle_id`; unique `(bundle_key, version)` | DRAFT/APPROVED/ACTIVE/RETIRED, schema version, checksum, owner, approver, 승인·활성 시각 |
| `auth_product_capability_contract`    | `(bundle_id, contract_key)`                 | Exact Action·Authority·Risk·SoD·Lifecycle의 Immutable Revision                           |
| `auth_product_access_policy`          | `(bundle_id, access_policy_key)`            | SINGLE/MODE_BRANCH Descriptor와 Branch Schema 검증                                       |
| `auth_product_entitlement_expression` | `(bundle_id, expression_key)`               | Typed ANY/ALL Tree와 Exact App Entitlement Leaf                                          |
| `auth_product_predicate_policy`       | `(bundle_id, predicate_policy_key)`         | Owner Service·Target Kind·Evidence Schema·Typed Parameter                                |
| `auth_governed_route_contract`        | `(bundle_id, route_contract_key)`           | Navigation Context·Route·Access Profile·Public/Service Binding·Projection Revision       |
| `auth_product_authorization_active`   | `bundle_key`; unique active `bundle_id`     | 현재 승인 Bundle Pointer와 CAS Revision                                                  |

모든 Foreign Key는 같은 `bundle_id` 안에서만 참조하며 Cross-bundle 조합을 금지한다. ACTIVE Row를
Update하지 않고 승인된 Bundle 전체를 새 Version으로 만들고 하나의 Transaction에서 Active
Pointer를 CAS 교체한다. Rollback도 직전 APPROVED Bundle로 Pointer를 원자 교체하며 Assignment,
Audit와 과거 Bundle을 삭제하지 않는다. Checksum·Approver·Activation Event는 Audit에 남긴다.

### 2.7 Product-scoped Rollout 원장과 Durable Latch v2

Rollout bit와 권한 Bundle은 서로 다른 원장이다. Provider Feature Rollout 원장은 다음 23개
Canonical Flag의 승인 Revision을 저장하고 Gateway가 제품별 상태를 합성한다.

| 축    | Flag 수 | Key                                                           | 범위·불변식                                                     |
| ----- | ------: | ------------------------------------------------------------- | --------------------------------------------------------------- |
| `S`   |       1 | `access.product-surfaces.context-shadow.v1`                   | Tenant-global; Context Envelope의 모든 제품이 같은 bit·revision |
| `E_p` |      11 | `access.product-surfaces.capability-enforcement.<product>.v1` | Tenant+Product; `E_p ⇒ S`                                       |
| `U_p` |      11 | `ux.product-surfaces.<product>.v1`                            | Tenant+Product; `U_p ⇒ E_p`                                     |

`<product>`는 Checksummed Rollout Inventory의 11개 Key만 허용한다. 기존 전역
`access.product-surfaces.capability-enforcement.v1` Row와 Revision은 전환 증거·구버전 호환을
위해 삭제하지 않지만 신규 `(S,E_p,U_p)` 합성, Context Envelope와 PEP 선택에는 읽지 않는다.
`V37__seed_product_surface_capability_enforcement_flags.sql`은 11개 `E_p` Flag와 Decision Revision을
default-off로 추가하며 기존 Migration을 수정하지 않는다. Production의 `S/E_p/U_p` 기본값은 모두
Off다.

Gateway의 Durable Safety Latch v2는 Evaluation Cache와 분리된 Redis Hash다.

| 항목                 | 계약                                                                                                                    |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Logical key          | `dwp:gateway:product-surface:se-latch:v2:<tenantId>:<productKey>`                                                       |
| Schema               | `schema=2`, `productKey`, `shadowEnabled`, `shadowRevision`, `enforcementEnabled`, `enforcementRevision` 정확히 6 Field |
| Lifetime             | `PERSIST`; TTL이 있으면 Corrupt                                                                                         |
| Write                | Provider가 `S`와 해당 `E_p`를 모두 권위 있게 반환할 때 Lua/CAS로 원자 승인                                              |
| Load/Migration fence | v2 단일-key LOAD → MISSING이면 Legacy 단일-key probe → v2 단일-key 재조회; 다중-key Lua 금지                            |
| Revision             | 낮은 Revision은 저장 Snapshot 유지, 같은 Revision의 다른 bit는 Conflict, 더 높은 Revision만 갱신                        |
| Validation           | 11개 Product Allowlist, Exact Flag Key, Opaque Revision, Cohort·Reason, `E_p ⇒ S`를 모두 검증                           |

Provider 평가가 실패하면 `tenant+product` v2 Snapshot을 읽는다. `FOUND`는 마지막 `S/E_p`를
복원하고 `U_p`를 Off로 계산하므로 `111→110`만 가능하다. v2와 Tenant 전역 Legacy v1 Key가 모두
없는 새 Tenant·Product의 `MISSING`만 `000`으로 계산한다. v2는 없지만 Legacy v1이 있으면 제품별
귀속을 추정하지 않고 `MIGRATION_REQUIRED`, Hash/Schema/TTL/Revision이 잘못되면 `CORRUPT`, Redis
Timeout·장애는 `UNAVAILABLE`로 분류하며 세 상태 모두 503 Fail Closed다.

Redis Cluster Cross-slot을 피하기 위해 v2 Product Key와 Legacy Tenant Key를 같은 Lua Script에
전달하지 않는다. 최초 v2 `MISSING` 뒤 Legacy Key를 단독 조회하고, 그 사이 v2 Migration이 생성되는
Race를 닫기 위해 v2를 다시 조회한다. 재조회 v2가 `FOUND`, `CORRUPT` 또는 `UNAVAILABLE`이면 그
결과가 우선한다. v2가 두 번 모두 `MISSING`일 때만 Legacy `MISSING`은 신규 `000`, Legacy
`FOUND`는 `MIGRATION_REQUIRED`로 확정한다.

Local repeatable Seed는 24개 Row(`S` 1 + Legacy 전역 E 1 + `E_p` 11 + `U_p` 11)를 정확히 검증한다.
Local에서만 `S=1`; Approvals·Communications·HCM·Services의 `E_p/U_p=1`로 네 제품은 `111`,
나머지 7개 제품의 `E_p/U_p=0`으로 `100`이다. Legacy 전역 E의 Local 값은 호환 증거일 뿐 이
Truth Table에 영향을 주지 않는다.

## 3. 계산 규칙

```text
active roles and groups
+ exact allow/deny permissions
+ active app responsibilities and resource sets
+ supported JIT grant
+ active provider support session (exclusive mode)
+ product capability policy
+ product relationship eligibility
→ effective product surface contexts
```

1. 비활성·퇴역 Resource와 Capability를 제거한다.
2. `DENY`를 먼저 적용한다.
3. Assignment·Grant·Support Session의 `validFrom/validTo`를 평가한다.
4. Responsibility가 가리키는 App Resource Set과 Capability의 Product를 교차 검증한다.
5. 기본 `REQUIRED` Responsibility와 Exact Capability를 AND하고 명시적 예외만 적용한다.
6. Capability Descriptor 또는 Access Policy Descriptor의 Authority Mode와
   `requiresProductEntitlement`를 적용한다.
7. 서버 Session이 Active Access Mode를 하나로 결정한다. Active Support Session 중에는
   같은 Session의 NORMAL Context를 평가·반환하지 않고 일반 Write를 합산하지 않는다.
8. SoD와 Risk Activation 상태를 적용한다.
9. Product·Surface·Active Access Mode별 Context 하나를 만들고 다음 재평가 시각
   `revalidateAt`과 Opaque Composite `decisionRevision`을 계산한다.
10. 결과가 없는 Surface는 허용 Context에 포함하지 않는다.

Navigation Endpoint는 허용 Context만 반환한다. Direct Route의 Expired·Activation·Step-up·SoD
상태는 별도 서버 Evaluation 결과를 사용하며 Frontend가 Role 문자열로 재구성하지 않는다.

## 4. Cache와 Invalidation

| 계층             | Key                                                                          | TTL / Invalidation                                  |
| ---------------- | ---------------------------------------------------------------------------- | --------------------------------------------------- |
| Auth Read Model  | tenant + actor + activeAccessMode + composite decisionRevision               | 짧은 TTL, 모든 Source Revision 변경 즉시 무효화     |
| Gateway Context  | tenant + actor + activeAccessMode + decisionRevision                         | 매 Governed Request에서 최신 Revision·Validity 확인 |
| Frontend Context | tenant + actor + activeAccessMode + decisionRevision                         | Revision·만료·Support 종료 즉시 제거                |
| Product Query    | tenant + actor + product + surface + scope + decisionRevision + domain query | `meta.accessSensitive=true`                         |

만료 시각이 Cache TTL보다 먼저면 만료 시각을 TTL 상한으로 사용한다. Auth 또는 Scope Resolver를
확인할 수 없을 때 이전 Allow를 사용하지 않고 Fail Closed한다.

Gateway는 Governed Response의 공통 Envelope 또는 Response Metadata에 최신
`decisionRevision`을 제공한다. State-changing Request는 `expectedDecisionRevision`을
보내고 Gateway·Service는 Domain
Mutation 전에 불일치 409를 반환한다. Client Identity·Permission Header로 전달하지 않는다.

Revision mismatch, 401/403/409 Access Reason, Expiry Timer와 Support 종료의 Client 순서는 다음과
같다.

```text
cancel in-flight
→ clear rendered sensitive content
→ remove every accessSensitive query
→ clear last-route convenience state
→ broadcast tenant+actor+accessMode invalidation to other tabs
→ refetch surface contexts
```

Mutation은 자동 Retry하지 않고 Idempotent GET만 Context 갱신 후 한 번 재시도한다. 늦게 도착한
응답은 요청 시점 Decision Revision·Context Key가 최신 상태와 다르면 Commit하지 않는다. Countdown은 서버
`generatedAt`으로 계산한 Clock Offset을 사용한다. Revocation Event 전달 실패나 Shared Cache
상태에서는 Allow Cache를 사용하지 않는다.

## 7. Retention과 Privacy

- EffectiveProductSurfaceContext는 영속 보존하지 않고 필요한 Audit Evidence만 남긴다.
- UX Event Retention과 Access Role은 Privacy Owner 승인 전 Production에서 활성화하지 않는다.
- Scope Display Name에 민감 조직명이 포함될 수 있으므로 Analytics에는 `scopeKind`만 전송한다.
- Browser Storage는 Session 종료 후 남지 않는다.
- Support Context Cache는 Session 만료 즉시 삭제한다.

## 8. Migration 불변식

- `WORKSPACE_MEMBER`, Custom Role·Resource·Resource Set, Responsibility와 유효기간을 보존한다.
- UI Route 이동만으로 Permission·Assignment를 추가·회수하지 않는다.
- 변경되지 않은 Assignment에 대해 지원되는 Capability의 `EffectiveAllow_after`는
  `EffectiveAllow_before`보다 넓어지지 않는다.
- 의도적 권한 축소는 영향 사용자·Role·Route·API 목록과 별도 승인을 가진다.
- 제품별 `U_p` Rollback은 Navigation Projection만 되돌리고 신규 Guard·PEP를 유지한다.
- Legacy Mutation API가 남으면 Canonical API와 같은 Domain Service·PEP·Idempotency를 사용한다.
- 미지원 `ORG_UNIT/RESOURCE` JIT는 ACTIVE Record를 만들지 않고 요청 단계에서 거부한다.

## 9. Migration·Rollback

Auth Database Migration은 Versioned Capability Descriptor, Governed Access Policy Descriptor,
Entitlement Expression, Predicate Policy Descriptor, Governed Route Authorization Contract와
Lifecycle·Seed를 한 승인 단위로
추가한다. HCM Migration은 필요한 Granular Resource·Action만 추가한다. 기존 Role Permission을
즉시 삭제하지 않는다. Tenant-global `S → 제품별 E_p → 같은 제품 U_p` 순서로 진행하고 Shadow
Evaluation에서 기존 허용과 신규 Context 결과를 비교한다. 전역 Legacy E는 이 순서에 참여하지
않는다. `E_p=false`인 더 높은 승인 Revision을 발행하는 명시적 제품 Rollback은 `S=1`에서
`110→100`으로 전환할 수 있지만, Provider·Redis 장애가 이를 대신해서는 안 된다.

UI Rollback은 Compatibility Shell을 사용하되 신규 Sibling Guard와 PEP를 유지한다. 인가 회귀는
직전 승인된 Versioned Capability Policy로 원자적으로 되돌린다. 기존 Assignment와 Audit Evidence를
삭제하지 않으며 On/Off 모든 조합에서 Management-only 사용자를 Parent App Guard로 차단하지 않는다.
